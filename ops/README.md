# Демонстрационный стенд

Стек из четырёх сервисов: база, разовое заполнение демо-проектом, API ядра,
клиент за nginx. Одна команда поднимает всё.

```bash
docker compose up --build
# открыть http://localhost:8080
```

Порт хоста меняется переменной `ORBITA_PORT`, пароль базы — `ORBITA_DB_PASSWORD`:

```bash
ORBITA_PORT=3000 ORBITA_DB_PASSWORD=... docker compose up --build -d
```

Первая сборка идёт несколько минут: собирается ядро на Gradle и клиент на Vite,
качаются зависимости. Дальше пересборка только изменившихся слоёв.

## Что поднимается

| Сервис | Образ | Роль |
| --- | --- | --- |
| `db` | `postgres:16` | Хранилище. Данные в томе `orbita-db`, переживают пересоздание контейнеров. |
| `seed` | `ops/api.Dockerfile --target seed` | Разовое заполнение демо-проектом «Орбита-IoT». Отрабатывает и выходит. |
| `api` | `ops/api.Dockerfile --target api` | API ядра, порт 8090 внутри сети. Наружу не публикуется. |
| `web` | `ops/web.Dockerfile` | Собранный клиент + nginx: статика и проксирование `/api`. |

**Образа два, а не один.** Фикстуры демонстрационного проекта живут в тестовом
наборе исходников и в образ изделия не попадают (STEP-7-9 §7.2). Общий образ
был бы удобнее ровно до того дня, когда демонстрационные данные оказались бы
в рабочем проекте — и это заметили бы на обзоре, а не при сборке.

**API наружу не публикуется** намеренно: единственный вход — nginx. Тогда `/api`
значит одно и то же и в разработке (прокси Vite), и в контейнере, а в клиенте
нет ни адреса API, ни настройки CORS.

## Заполнение при повторном подъёме

`SeedDemoKt` отказывается работать по непустой базе — и когда там чужой проект,
и когда демо уже загружено. Для повторного `docker compose up` второй случай —
норма, поэтому `ops/seed.sh` различает их **по причине отказа**, а не по коду
возврата:

- база пуста → проект загружается, код 0;
- демо уже загружено → заполнение пропускается, код 0;
- в базе объекты рабочего проекта → отказ, код 1, стек не поднимается.

Последнее — не помеха, а защита: заполнение демо-данными базы рабочего проекта
есть ровно то, чего заполнитель обязан не допустить.

## Начать заново

```bash
docker compose down -v     # -v удаляет том с данными
docker compose up --build
```

## Что видно на стенде

Демо-проект намеренно неидеален: в нём есть требование без закрывающего
события, небазированные объекты и риск к эскалации. Мастер слева показывает
это состоянием шагов — на демо-проекте закрыты Ш3 и Ш5, остальные несут
замечания. Витрина, где всё зелёное, не показывает, как система ловит
проблемы, а это в ней главное.

## Выкат на сервер

Тот же `docker-compose.yml`. На сервере нужен Docker с плагином compose:

```bash
git clone git@github.com:dechernov-stack/orbita.git && cd orbita
printf 'ORBITA_PORT=80\nORBITA_DB_PASSWORD=<пароль>\n' > .env
docker compose up --build -d
docker compose ps
```

`.env` в репозиторий не попадает и попасть не должен — он в `.gitignore`.

Проверка после подъёма (в журнале API должна быть строка со всеми тремя
признаками):

```bash
docker compose logs api | grep 'database_ready schema_checked api_started'
```

`schema_checked` не отдельная строка, а часть этой: схема сверяется с моделями
при старте, и расхождение роняет запуск (`Migrator`, `SchemaCheck`). Если
строки нет — API не поднялся, и смотреть надо журнал, а не браузер.

## Обновление

```bash
git pull && docker compose up --build -d
```

Миграции применяются при старте API, заполнение демо-проекта повторно не идёт.
