# Структура репозитория

Один репозиторий: требования, схемы, спецификация поведения и код живут вместе.
Разделение на «репозиторий документов» и «репозиторий кода» разрывает цифровую нить —
требование перестаёт быть связанным с реализующим его кодом.


## Принципы разложения

**1. Одно имя на всех уровнях.**
Префикс идентификатора служит именем файла ТЗ и именем модуля кода:
`TZ-BAL-005` → `docs/tz/TZ-BAL.md` → `core/bal/`. Таблицы соответствия не нужны,
трассировка «требование → код» механическая.

**2. `schemas/` — нормативная часть, не вспомогательная.**
Структура данных задаётся схемами; код обязан им соответствовать (TZ-MOD-001).
Поэтому схемы лежат в корне, а не внутри модуля.

**3. `spec/` отделено от тестов модулей.**
`spec/` — эталон поведения, не зависящий от языка реализации: описывает, *что* система
делает. Тесты в `core/*/src/test/` проверяют, *как* это сделано в Kotlin.
Расхождение реализации с `spec/` — дефект реализации, а не эталона.

**4. `tools/` отделено от `spec/`.**
`tools/` проверяет сами документы (схемы валидны, трассировка цела) и в продукт не входит.

**5. `docs/model/` отделено от `docs/tz/`.**
Концепция и модельные документы отвечают на вопрос «почему так»; ТЗ — «что сделать».
Первые меняются при пересмотре замысла, второе — при уточнении работ.

## Точки, где возможны разные взгляды

| Вопрос | Принято | Альтернатива |
| --- | --- | --- |
| Один репозиторий или два | Один: требования рядом с кодом | Отдельный репозиторий документов — если у документов иной круг доступа |
| `web/` в этом же репозитории | Да: контракты общие | Отдельный репозиторий — если клиент делает другая команда |
| Модули `core/` по разделам ТЗ | Да | По слоям (domain/app/infra) — но тогда трассировка требует реестра |
| Регламенты в репозитории | Да, `docs/regulations/` | Внешняя ссылка — если регламенты версионируются отдельно |

Если по любой строке решение иное — меняется только раскладка каталогов;
схемы, ТЗ и `spec/` не затрагиваются.
