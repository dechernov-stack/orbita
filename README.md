# Орбита

Информационная система поддержки разработки космической системы IoT на ранних
фазах жизненного цикла (Pre-Phase A / Phase A по NPR 7120.5, NPR 7123.1):
от нужд стейкхолдеров до пакета для детального проектирования.

Внутри — демонстрационный проект «Орбита-IoT»: группировка малых аппаратов
для сбора телеметрии с наземных терминалов. На нём и надо смотреть.

---

## Что нужно

Только **Docker с плагином compose** (`docker compose version` должно
отвечать). Ни Java, ни Node, ни PostgreSQL ставить не нужно — всё собирается
внутри образов.

## Одна команда

```bash
docker compose up --build
```

Первый запуск идёт несколько минут: собирается ядро на Gradle и клиент на Vite.
Дальше пересобираются только изменившиеся слои.

Когда в журнале появится строка про `api_started`, открыть:

**http://localhost:8080**

Порт занят? `ORBITA_PORT=3000 docker compose up --build`.

## Что смотреть первым

Слева — мастер из семи шагов, это весь путь проекта. Экраны шага — вкладками
сверху.

1. **Ш5 «Моделирование» → вкладка «Сравнение вариантов».** Три варианта
   группировки, роза по трём осям и фронт Парето. Главный экран системы:
   решение о выборе облика принимается здесь, и видно, чем один вариант
   лучше другого и чем за это платят.
2. **Ш5 → вкладка «Баллистика».** Те же варианты на глобусе: трассы, зоны
   обслуживания, покрытие по широтам.
3. **Ш2 → вкладка «Карта спроса».** Откуда берётся нагрузка: населённые
   пункты внешнего датасета плюс шесть сценариев потребления.
4. **Ш7 «Пакет» → «Готовность к точке».** Что мешает пройти обзор SRR:
   поимённо, а не «готовность 60 %».

## Почему половина шагов светится жёлтым

Так и задумано. Демо-проект **намеренно неидеален**: есть нужда, не
породившая ни одного сервиса; класс потребителей, который присутствует
в спросе, а профиля обслуживания не имеет; требования без запланированной
верификации; риск, требующий эскалации.

Витрина, где всё зелёное, показывает, что система умеет рисовать таблицы.
Она не показывает главного — как система находит проблемы до того, как
их найдут на обзоре.

Закрытыми на демо-проекте выглядят Ш3 и Ш5. Остальные пять несут замечания,
и каждое замечание названо словами.

## Начать заново

```bash
docker compose down -v      # -v удаляет том с данными
docker compose up --build
```

Подробности стенда, выкат на сервер и разбор при отказе — [`ops/README.md`](ops/README.md).

## Без Docker: из исходников

Нужны JDK 21, Node 22 и PostgreSQL 16. Две команды в двух терминалах:

```bash
bash ci/local_db.sh                  # локальный кластер и роль
./gradlew :core:com:demoServer       # API + демо-проект,  порт 8080
```

```bash
cd web && npm ci && npm run dev      # клиент, порт 5173 (проксирует /api)
```

Открыть **http://localhost:5173** — дальше то же самое.

Этот путь — для разработки: `demoServer` очищает базу и заполняет её заново
при каждом запуске, чего изделию делать нельзя.

## Проверки

```bash
bash ci/checks.sh          # схемы, трассировка, эталоны, тесты ядра, типы клиента
cd web && npm run check:screens   # экраны в настоящем браузере (нужны оба сервера выше)
```

Ожидаемый итог — «ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ»: 484 проверки исполняемых эталонов
и 694 теста ядра.

Файлы `spec/*.py` — не примеры, а **эталоны поведения**. Расхождение
реализации с эталоном есть дефект реализации, а не эталона.

## Данные

`data/ne_50m_populated_places_simple.geojson` — Natural Earth 50m populated
places, **общественное достояние**. Это не растр плотности населения:
сельское население в нём не представлено вовсе, городское сосредоточено
в точке. Для карты спроса на терминалы приближение осмысленно — терминалы
ставят там, где есть инфраструктура, — но называть его плотностью населения
нельзя, и в самой карте записано именно то, чем он является.
