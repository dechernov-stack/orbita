# CLAUDE.md — правила работы в репозитории

Проект: информационная система поддержки разработки космической системы IoT (далее — ИС).
Назначение ИС: выработка требований к элементам КС и передача пакета в детальное проектирование (Pre-Phase A / Phase A по NPR 7120.5, NPR 7123.1).

Этот файл читается первым в каждом сеансе. Он задаёт ограничения, конвенции и способ работы с требованиями.

---

Структура репозитория и принципы разложения — `STRUCTURE.md`.
Соответствие модулей кода разделам ТЗ — `core/README.md`.

## 1. Порядок работы

1. Работа ведётся по требованиям из `docs/tz/`. Единица работы — одно требование `TZ-<МОДУЛЬ>-NNN`.
2. Перед реализацией требования: прочитать сам блок требования, его `TRACE-UP` и связанные ADR.
3. Реализация идёт от `ACCEPTANCE`: **сначала тесты по пунктам чек-листа, потом код**. Пункт `ACCEPTANCE` без теста считается невыполненным.
4. Изменение текста требования (`REQ`, `MOP`, `ACCEPTANCE`) — отдельным коммитом, не вместе с кодом. Требование со `STATUS: Baseline` не изменяется без явного указания.
5. Коммит ссылается на требование: `TZ-BAL-014: расчёт зоны обслуживания по линиям`.
6. Если требование противоречит другому требованию, ADR или физике — **остановиться и сообщить**, не разрешать противоречие самостоятельно.

## 2. Жёсткие ограничения проекта (реестр решений Р1–Р9)

Нарушение любого пункта — ошибка независимо от того, как сформулирована задача. Полные обоснования — в `docs/adr/`.

| № | Ограничение |
| --- | --- |
| Р1 | Полезная нагрузка — только **regenerative** (обработка на борту). **Bent-pipe не реализуется и не моделируется.** |
| Р2 | Платформы — только диапазон **12U … 100 кг**. Конфигурации вне диапазона помечаются недопустимыми, а не рассчитываются. |
| Р3 | Межспутниковая связь — **только РЧ**. **Оптический ISL не моделируется.** |
| Р4 | Режимы КА — **статические географические маски**. Динамический планировщик — только интерфейс-заглушка, без реализации. |
| Р5 | Терминалы всех классов **знают эфемериды**; КА ведёт широковещательный маяк альманаха. Передача «вслепую» моделируется как деградированный режим, не как штатный. |
| Р6 | Класс B' использует **эфемеридный backoff** (после N попыток — ожидание следующего КА). |
| Р7 | Подвижность — **статика + маршруты**. Роуминг регуляторных зон не реализуется. |
| Р8 | Карта спроса — трёхслойная: население (сетка ~100×100 км) → единичные объекты и маршруты → сценарная библиотека. |
| Р9 | Сервис несёт **QoS-профиль по видам потребителей** (A'/B'/C'); MOP порождаются попарно «сервис × вид потребителя». |

Дополнительно:
- **Баллистику не пишем сами** — ядро Orekit. Собственные реализации пропагаторов, моделей тени и событий видимости не создаются.
- **Модульность лёгкая**: без шин сообщений, плагинных загрузчиков и горячего переключения. Взаимодействие модулей — через контракты данных из `schemas/`. Смена протокола или модуля = пересборка.
- **GPL-код не заимствуется** (ns-3, FLoRa, ELoRa — только как источник эталонных чисел для калибровки, см. `spec/reference/`).

## 3. Конвенции

**Идентификаторы требований:** `TZ-<МОДУЛЬ>-NNN`, где модуль — `COM` (общесистемные), `MOD` (модель данных), `REQ` (требования и трассировка), `BAL` (баллистика), `KA` (аппарат), `USR` (потребители), `NET` (протокол), `FLW` (потоки), `AI` (ИИ-контур), `OUT` (отчёты и экспорт).
Номера **стабильны и не перенумеровываются**. Отменённое требование получает `STATUS: Cancelled` и остаётся в файле.

**Термины** (единообразно в коде, тестах и текстах):

| Термин | Значение | Не путать с |
| --- | --- | --- |
| Зона видимости | Геометрический footprint (угол места ≥ минимального) | Зоной обслуживания |
| Зона обслуживания | Подмножество footprint: бюджет линии замыкается + есть ёмкость | Зоной видимости |
| Карта спроса | Сетка ячеек с интенсивностями по классам потребителей | Картой покрытия |
| MOE | Показатель качества сервиса | MOP (показатель требования) |
| TPM | Отслеживаемый технический параметр с резервом и трендом | Параметром вообще |
| Популяция | Группа терминалов с общим профилем | Отдельным терминалом |
| A' / B' / C' | Классы терминалов: односторонний / с подтверждением / оперативного управления | Классами устройств LoRaWAN (A/B/C) |

**Язык:** документация и комментарии — русский; идентификаторы в коде, имена полей схем и сообщения об ошибках — английский.

**Единицы:** СИ внутри ядра. Величина без явной единицы в схеме — ошибка. Углы хранятся в радианах, отображаются в градусах.

## 4. Приёмка

Требование считается выполненным, когда: все пункты `ACCEPTANCE` покрыты тестами и тесты проходят; расчётные требования дополнительно сверены с эталонами из `spec/reference/`; `STATUS` обновлён.

**Сквозной критерий (применяется ко всему расчётному коду):** прогон Монте-Карло сценария не должен деградировать по времени относительно бюджета, заданного в `TZ-COM-004`. Изменение, ухудшающее этот показатель, не принимается, даже если функционально корректно.

## 5. Чего не делать

- Не изобретать физику: расчёты — по опубликованным моделям, со ссылкой в комментарии.
- Не расширять область: детальное проектирование, наземный сегмент как ПО эксплуатации, биллинг, эксплуатационная телеметрия — вне ИС.
- Не заменять `ACCEPTANCE` на «работает по-моему».
- Не создавать заглушки, имитирующие расчёт (возврат правдоподобных чисел вместо вычисления). Нереализованное — явная ошибка `NotImplemented`.
- Не хранить результаты моделирования как истину в модели требований: результат расчёта привязывается к сценарию и версии входных данных.
