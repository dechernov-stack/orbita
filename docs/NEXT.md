## Открытые вопросы

* **Сервер api однопоточный** (10.09). Разбор вынесен в фон заданием
  (ADR-069) — стенд отвечает; синхронными остаются печать PDF и «Написать
  связно» (секунды). Пул потоков с сериализацией доступа к базе — отдельным
  решением, когда появится вторая долгая операция.

* **Стенд: причина `exit code 2` у backend Postgres не установлена**
  (отчёт `docs/tz/v2/отчёты/СТЕНД-ПАДЕНИЯ-PG-08-09.md`). Api теперь
  переживает обрыв (пул + переподключение, тег `v2-stand-pool`), сокет на
  SIGTERM закрывается, журнал базы называет клиента. Если падение
  повторится при закрытом сокете — снимать core dump backend, а не
  трогать api.




* **Окно взятия WBS выбором элементов** (шип B, 2026-09-07). `POST
  /v2/wbs/take` берёт с полки ВСЕ 56 пакетов; на прогоне у проекта шесть
  узлов состава, и 41 пакет остаётся без пары — выход сцены 12 честно
  держит проект. Для полок Arcadia окно взятия сделано (ADR-054 ред. 2),
  для WBS — нет.

* **§10 и §11 отчёта** (допущения и открытые вопросы) наполняются полем
  знаний: факты с меткой [П] и неразрешённые темы. На прогоне волны 4
  разбора материала нет, поэтому разделы пусты законно.

* **Эталон `reference-scenes-10-12-models` не поставлен**: экраны сцен
  10–12 и раздела моделей сделаны по сложившемуся языку (плотность по
  роли, тест действия, три размера), а не по эталону.



* **Носитель нужды ND-0006 — «субъекты КИИ»** (шип A, 2026-09-07). Разбор
  назвал носителем «субъекты КИИ» (187-ФЗ), но стороной их не завёл и
  действия на это не предложил. Система говорит об этом при приёме и
  отказывает на маршруте носителя. Вопрос владельцу: заводим ли «субъекты
  КИИ» стороной проекта (роль «потребитель»/«регулируемый»), или нужда
  принадлежит уже заведённой стороне.

* **Выход сцены 3 не закрыт содержанием**: у четырёх из пяти сторон
  (Правительство РФ, АО «ГЛОНАСС», Ространснадзор, Роскосмос) нет ни одной
  нужды. Записка их нужд не даёт — это инженерная работа, а не код.

* **Предложения сцен 2–6 на прогоне пусты законно**: из 23 действий плана
  принято 22, непринятое — одно (норматив ПНСТ 996-2024, уже лежит на
  полке поставкой). Полосу с непустым составом видно на свежем разборе.



* **Стейкхолдер с несколькими ролями** (замечание живого прохода ПМИ-3,
  владелец: «не критично, надо поправить потом»). Сейчас `role` — одно
  значение из перечня, а один и тот же участник бывает разом регулятором,
  заказчиком и потребителем: ГКРЧ и Роскомнадзор регулируют и потребляют,
  Минтранс заказывает и регулирует. Правка: `role` → массив ролей с
  сохранением совместимости (одиночное значение читается как список из
  одного), матрица группирует по каждой роли, обобщение в профиль А2 берёт
  главную. Задевает схему стейкхолдера, матрицу покрытия, заведение
  носителей из нужд и профиль полки — поэтому отдельным шипом, не правкой
  на ходу.

* **Дизайн формы карточки объекта** (поставлен инженером на втором заходе,
  2026-08-25). Сделанное по ходу прогона — вкладки «Определение / Готовность /
  История», действия и препятствия сверху, поля-ссылки списками, ужатие
  таблицы при открытой карточке — снимает остроту, но карточка остаётся
  сырой формой по схеме: без группировки полей по смыслу (постановка /
  показатель / верификация), без разумной ширины колонок, подформы событий
  верификации громоздки. Нужен осознанный проход дизайном (пользователь:
  «дизайном займёмся позднее» — по всему приложению разом, эскизы
  docs/ui/reference как основа).

* **Автопростановка происхождения из документа-источника** (ADR-030,
  отложено): материал, порождённый службой из исходного документа SD-NNNN,
  пока не несёт `provenance.import.dataset = SD@версия` автоматически.
