  `POST /v2/materials/{код}/role` (`Intake.setRole`), клиент «Прочитать
  документ» ходит им, а не правкой на месте. Ответ у устава несёт карту
  пробелов.
* **Досье документа** — `GET /v2/materials/{код}/dossier`: оригинал (версия,
  знаков, блоков, заменяет/заменён), роль, ранг, резюме, режим приёма,
  прогоны, вклад по видам и по решениям, уникальных · подтверждений ·
  противоречий (по связям фактов между документами и по смыслу утверждения),
  сущности на документе с пометой «только на нём», полезность =
  сущностей + уникальных + подтверждений + противоречий (слагаемые рядом) и
  оценка человека одной строкой (`POST …/usefulness`, истина
  `material.usefulness.note`). Второй взгляд — `GET /v2/entities/{код}/basis`:
  сущность → основания с якорями, цитатами, ролями и рангами документов,
  снятые основания помечены.
* **Откат вклада** — `POST /v2/materials/{код}/rollback` с причиной: факты
  документа сняты (`cancelled` + помета), сущности только на них — сняты,
  с другими основаниями — остались с пометой «основание снято» (нить к
  снятому факту снята — доля знаний его не считает), прогоны `rolled_back`
  с учёткой, план разбора снят, конфликты величин пересчитаны. Мера
  «откат Приморья — постановка из записки цела» — `DocumentDossierTest`.
* **Приём режимом** — `POST /v2/materials/{код}/accept` (истина
  `material.accept_mode`): весь документ · по разделам (якоря разделов
  канона) · выборочно (номера действий) — исполняют план разбора; «только
  в контекст» — фактам `noted`, сущностей нет; «отклонить» — `rejected` с
  причиной, решённые человеком факты пакет не переписывает. Прочитанное
  документом (контур чтения) по-прежнему принимается на вкладке постановки —
  режим приёма говорит об этом словами.
* **Партия каталога** — `POST /v2/materials/batch`: каждому файлу своя
  карточка и роль (правится до запуска), загрузка тем же маршрутом, что и
  форма, разбор — очередью фоновых заданий (ADR-069, одна очередь на роутер
  и маршруты знаний); `GET /v2/materials/batch?codes=` — сводка: документов ·
  фактов · противоречий · дублей источников (одинаковый отпечаток канона) ·
  состояние заданий. Мера «каталог из 6 файлов — одна сводка» —
  `DossierRoutesTest`.
* **Библиотека проекта** — `POST /v2/materials/take` (`Intake.takeMaterial`):
  документ другого проекта (кроме устава) берётся с фактами, связями между
  фактами и темами (по метке), решения прежнего проекта не переезжают,
  прогон помечен «взято из библиотеки … вызова модели не было»; повтор
  ничего не удваивает. Мера «норматив взят в новый проект, вызовов 0».
* **Карта пробелов устава** — `GET /v2/materials/{код}/gaps` и ответом
  загрузки при роли «устав»: двенадцать пунктов `ТРЕБОВАНИЯ-К-ЗАПИСКЕ-МИССИИ`
  узнаются по словам канона (якорь первого совпадения, число блоков), ворота
  сцен по решению (2 — без 1, 2, 3; 4 — без 6; 6 — без 5; 5 — без 8). Это
  узнавание по разметке, а не суждение: меру полноты считает человек; на
  записке владельца находятся ≥ 10 пунктов из 12.
* **Клиент** (`dossier.tsx`): в строке документа — «Досье» (резюме,
  прогоны, вклад, сущности → «на чём стоит», приём режимом, оценка, откат с
  причиной своим окном), у устава — «Карта пробелов»; в форме загрузки —
  партия каталога со сводкой и строка карты пробелов после загрузки устава;
  под таблицей — «взять документ из проекта…» (библиотека другого проекта,
  показывается и на пустом проекте). `facts()` порта больше не отдаёт снятые
  факты.

**Не делалось / вопросы владельцу.**

* Роль документа «предлагается по содержимому» (РЕШЕНИЕ §6) — живой вызов,
  в §3 не входит; в партии роль называет человек до запуска.
* Приём «выборочно» на экране — через план разбора (галочки действий)

## Шип 4 · §4 — документы живьём (25.09)

По `ЗАДАНИЕ-ШИП-4-ДОЛГИЙ` §4 и ADR-058 §Незакрытое. Живые вызовы — только
днём живой модели, на локальной копии стенда владельца (`PJ-ПМИ7`); отчёт —
`docs/tz/v2/отчёты/ДЕНЬ-ЖИВОЙ-МОДЕЛИ-ШИП-4.md`.

**Сделано.**

* **Рендер тем же портом, что stub.** `Documents.write` разложен на
  `prepareWrite` (промпт из элементов — чтение базы, поток запросов) и
  `applyWrite` (сторож чисел и оборотов, запись принятого): живая модель,
  подстановка теста и фоновое задание идут одной дорогой.
* **Связный текст и печать — фоновыми заданиями** (`DocumentJobs`, по
  образцу ADR-069): `POST /v2/documents/{код}/write {background:true}` →
  202 с заданием `DJ-NNNN`, ответ из журнала применяется сразу (201);
  `GET …/jobs/{id}`; печать — `POST …/print/jobs {engine}` → задание,

  потоке запросов. Клиент считает секунды вслух и опрашивает раз в две
  секунды; «собрать PDF» у заголовка документа даёт ссылку с движком.
* **Рецензия патчами** (`rendering.style_patches`, `reviewer`,
  `accepted_at`, статус draft · reviewed · accepted): `POST
  …/review {section, text, author}` кладёт правку изложения патчем (общий
  префикс/суффикс сняты: что стояло → что стало, кто, когда) поверх текста

  отказ 422; «принять как есть» — `POST …/renderings/accept`. Новый текст
  модели — новый черновик, прежние правки к нему не относятся. На экране:
  «править изложение · сохранить правку · принять как есть», состояние и
  число правок у текста.
* **Печать Typst.** Двоичный файл — в образе изделия из официального
  образа `ghcr.io/typst/typst:v0.13.1` (`COPY --from`, без apt: политика
  образа не менялась, ADR-058 §Незакрытое закрыт по заданию владельца);
  `Documents.printWith(engine)`: `typst` — строгий режим (нет файла — отказ
  словами), `pdfbox` — прежняя печать, `auto` — Typst, когда он есть;
  движок называется в ответе и в манифесте пакета точки
  (`GET /v2/points/{точка}/package.zip?engine=typst`, строка «печать: typst»).
  Исходник Typst — из тех же строк, что на экране: титул с авторами из
  элементов и базовой линией, таблицы из строк stub-рендера с шапкой,
  принятая проза абзацами, колонтитул. Для локальных тестов двоичный файл
  кладётся в `build/tools/typst` (`docker create ghcr.io/typst/typst:v0.13.1`
  + `docker cp`); без него компиляция в тесте пропускается вслух.
* **Верификация против поля кнопкой у документа** стояла с знаний v2
  (`Проверить против поля →` в карточке документа) — оставлена как есть.
* **Обороты вместо голых квалификаторов** (находка дня живой модели):
  квалификатор берётся с двумя следующими словами («не их замещение»), он

  шаблона отклоняло честный текст «без замещения существующих систем».

**Меры.** §1 ConOps связным текстом живой модели — принят с первого раза
(9 с); число без опоры — отказ (`DocumentsTest`, живой текст лишних чисел
не дал); PDF пакета MCR через Typst — четыре PDF в архиве, манифест
называет движок. MCReport §3 — первый прогон отклонён за голое «не» (ложное срабатывание, починено оборотами), второй принят с первого раза (19 с), обороты дословно.

**Не делалось / вопросы.**

событие · контракт, дата или диапазон, флот, `source` (факт-основание), `feeds`.

«понятие → вид» называет ОНТОЛОГИЯ (`target_kind`), карты в Kotlin нет.
Основание веха получает от системы — тот кандидат-факт, из которого выведена;
заполняются только поля-`ref fact` истины схем, так что составной источник
требования это не задевает. Род вехи онтология не называет и взять его неоткуда:
без него запись не отвечала бы своей схеме — сверка отказывает и называет поле,
а в поле знаний у вехи появился выбор рода.

**Генератор схем научился союзу типов** (`A | B` → `anyOf`) и форме `tbr{…}`.
Побочно исправлены поля, у которых союз прежде сворачивался в одну ветвь и
вторая отвергалась схемой: `fact.value`, `fact.source`, `requirement.measure`,
`parameter.measure` и ещё пять. Видов стало 94.

**Обязательное поле правкой больше не снимается.** `PATCH /v2/entities/{код}`
отказывает на пустое значение обязательного поля, а карандаш в клиенте шлёт
только ТРОНУТЫЕ поля. До этого правка формулировки нужды молча уносила класс
вместе с ответственным за TBR — поймано состязательным обзором правки.

Прогон стенда `walk_scenes.py` назначает класс покрытым нуждам на сцене 6;
сторож `check_tor_mode.py` ждёт у вехи действие `create_entity milestone`,
а не точку.

Подробности — ADR-070 (решения 9–10), поставка в
`docs/tz/v2/поставка-09-12/ЗНАНИЯ-V2-ПРИНЯТЫ.md`.

## Остановка ПМИ-6 (14.09): постановку собрал НЕ синтез, а приём плана разбора

Владелец остановил прогон: «Постановка» набралась мусором — нужды из текста РОЛИ
стороны, сторонами стали «Президент РФ» и «Правительство РФ», покрытие «0 из 9».
Диагноз владельца — `docs/tz/v2/поставка-09-14/ОСТАНОВКА-ПМИ6-ДИАГНОЗ.md`.

**Разбор поправил диагноз в двух местах, и это важнее самих правок.**

1. **Сущности создал не синтез.** Все девять нужд, две цели и тринадцать сервисов
   заведены каналом `service` через приём ПЛАНА РАЗБОРА (`EntityIntake.accept`), а не
   акцептом предложений синтеза. Тот путь не спрашивал онтологию, не проверял
   обязательных связей и не смотрел на ранг материала. Синтез (SR-0001) как раз
   предлагал разумное: первое предложение — сторона «Минтранс России» из двух
   обязательных фактов записки.
2. **«Покрытие 0 из 9» не значит «цели и сервисы не образованы».** Они образованы:
   целей две, сервисов тринадцать. Покрытие считает нужды, у которых есть связь
   `covers` и от цели, и от сервиса. Таких связей в проекте ноль, потому что план
   заводил цель без поля `needs`, а сервис — без `needs` и без класса.
3. **Правило «интерес стороны — ЭТО НУЖДА» было наше.** Оно появилось в промпте
   разбора 12.09 по просьбе владельца «сторона без нужды не проходит» и прямо
   породило ND-0002…ND-0009. Онтология всё это время говорила обратное: нужда — из
   `framing` с предикатами «нуждается в · требует · не хватает» либо из `assessment`
   о стороне с меткой [П]. Правило снято.

**Что сделано.**

- `orbita.knowledge.api.FormationRules` — правило образования из онтологии стало
  воротами на нашей стороне: понятие образуется только из фактов, которые называет
  `from_facts` (вид, предикаты, субъект, метка, признак). Одно правило на три
  контура: приём плана, синтез, промпт.
- Приём плана (`EntityIntake.accept`) получил ворота: правило образования,
  обязательные связи понятия и ранг. Материал ранга «сомнительный» пакетом не
  принимается вовсе; отказ называет причину поимённо.
- Вид факта стал обязательным. Молчаливый `framing` по умолчанию ставил фактам ровно
  тот вид, из которого образуется нужда. Перечень восьми видов берётся из
  сгенерированного `KindSpec.enums` — генератор схем теперь выносит перечни полей.
- Синтез: правило образования ушло в промпт и им же проверяется ответ модели.
- Подтверждение источников поднимает ранг не только карточки материала, но и его
  фактов. Без этого запрет на сомнительное закрыл бы обе дороги, и исследование
  стало бы бесполезным.
- Промпт исследования переложен под формат владельца, плюс правило, которого у него
  нет: субъект — ИМЯ предмета, а не класс строки. В его же файле §2–§5 несут в
  субъекте «акт», «программа/стратегия», «объекты применения» — все нормы схлопнулись
  бы в одну карточку.
- Экран поля знаний показывает ранг материала и гасит пакетный приём сомнительного,
  объясняя, что делать. Непринятое больше не проглатывается.
- Сторож `check_stakeholder_needs.py` различает помету и отказ: «сторона без нужды» —
  помета онтологии, а не отказ.

Мера — `FormationGateTest` (9 тестов, ни одного вызова модели): строка роли нуждой не
становится, автор акта стороной не становится, сомнительный материал пакетом не идёт,
цель без нужд не принимается, факт без вида отклоняется.

**Сцена 8 встала на «целей без требования: 8» — связать было нечем (19.09).**
Условие из шаблона фазы («каждая цель покрыта требованием») смотрит на

закрыть условие было физически нечем. Теперь источники правятся в карточке:
добавить цель · нужду · ограничение · материал, снять лишнее — и условие
закрывается содержанием, а не обходом. Счётчик выходов заговорил словами
(журнал З-08): «требования к системе: 12 из 3 — есть» вместо «12/3». Помехи
базирования сведены по сути — «нет критерия приёмки — 12: карточка требования,
поле „Критерий приёмки"» вместо сорока одной отдельной строки, и сказано, что
они закрываются в карточке.

**«Базировать нажимал — всё осталось черновиком» (19.09).** Снимок заводился

черновиками: код фиксировал версии и не трогал ступень. Истина схем даёт

означало «решать нельзя» там, где вход включён; послабление годится только для
сборки без входа. Заодно экран точки обязан говорить, КТО решает, и предлагать
переключить роль, а не показывать кнопку, которая отвечает отказом.

внутрь его поля. На стенде полки перезалиты загрузчиком (версия 2 шаблонов).

Одно расхождение сторож НЕ правит, а называет долгом: истина описывает вид
«process_catalog» как ОДИН процесс, а полка кладёт весь каталог одной записью
со списками `processes` (17) и `tools` (6) — печать SEMP §6/§10 разворачивает
эти списки и права, семнадцать строк стоят там с шипа G. Освобождение
поимённое (`ДОЛГ` в стороже) и с самопроверкой: закроется — сторож потребует
его снять. Чем является каталог — вопрос владельцу ниже.

**Обратный случай: код пишет поля, которых у вида нет.** Тот же разбор нашёл
вторую половину беды — документ проекта на стенде несёт `lead`, `standard`,
`phase`, `phase_template`, а у вида «проект» по истине поля зовутся `manager`
и `phase_current`, а `standard` и `phase_template` не названы вовсе. Где
истина уже говорит — код переучен (`manager`, `phase_current`; чтение
переживает старые документы). Где не говорит — вопрос владельцу ниже.

**Латиница в печати — тот же брак, что прочерк.** Получив наконец поле,
§3 FAD напечатал «technical»: словарь подписей у шаблона плоский (одно слово
на все виды), а истина знает, что у ограничения это «техническое», а у риска
«техническая» — восемь таких расхождений на 117 кодов. Печать теперь берёт
метку ПО ВИДУ И ПОЛЮ (`GeneratedKinds.enumLabels["constraint.type"]`), словарь
шаблона остался запасным, значение вне перечня идёт как есть. Где истина
меток не назвала (состояние записи, решение точки, метод оценки, ключи точек)
— слова добавлены в словарь полки: в нём лежали `BOTTOM_UP` заглавными, а
данные несут `bottom_up`, и метод печатался латиницей. На стенде все четыре
документа проекта (FAD, FA, MCReport, ConOps) печатаются без латиницы.

**Пустые колонки, оставшиеся после правки, — это уже не имена, а данные:**
* MCReport §6 «Реестр рисков»: вероятность, влияние, стратегия и владелец
  пусты во всех 12 строках — заполнять их нечем (см. доделки по рискам выше).
* FA §1 «Класс миссии»: у проекта ПМИ-7 поле пустое с заведения.

**План работ фазы задан по факту прохода (21.09, просьба владельца «поставь
любые реалистичные даты — тут править слишком долго»).** Точки: Внутренний
обзор 19.09, MCR 20.09 (дата её решения — раньше неё внутренний обзор стоять
не может), KDP-A 02.10. Окна двенадцати сцен — по дням, когда их содержание
заводилось на самом деле (17–21.09, `born_in` записей). Экран плана не даёт
ни одного замечания, критерии всех трёх точек выполнены: KDP-A ждёт только
решения владельца.

**«Явного перехода нет, а экспертиза выглядит непонятно» (21.09).** Кнопка
решения стояла в самом низу карточки точки — за матрицей зрелости на девять
строк и списком замечаний: владелец базировал последний документ и решения не
нашёл. Решение поднято СРАЗУ ЗА ГОТОВНОСТЬЮ, и перед ним строкой сказано, что
точку держит («Держит 1: «Д2 · Отчёт о концепции миссии». Сервер откажет, пока
это не закрыто»).

Экспертиза врала галочкой: «☑» значило лишь «по вопросу нет замечания», а не
«ответили да» — ответов система не хранит вовсе. Теперь вопрос без замечания
стоит точкой, кнопка зовётся «ответить «нет» → замечание», и под заголовком
сказано прямо: записывается только «нет». **Вопрос владельцу:** нужно ли
хранить «да» (кто и когда ответил) — это запись экспертизы, а не помета
экрана, и без неё чек-лист ПМИ остаётся устным.

**«А если их просто нет?» (22.09).** §11 «Открытые вопросы» требовал строку
перечня, и завершить раздел честным «их нет» было нельзя — только выдумав
вопрос. Между тем правильное содержание документа именно такое: «Открытые
вопросы: нет», сказанное словами, с именем и датой. Шаблон раздела теперь
может объявить `empty_ok_with_statement`, и тогда пустой перечень закрывается
ТЕЗИСОМ человека; у пустого перечня на экране стоит «их нет — закрыть раздел
тезисом», а элемент получает помету «перечень пуст и закрыт тезисом: «нет» —
это ответ, а не пропуск». Правило объявляет шаблон, не код: где пустой список
означает незавершённую работу (варианты, риски, стоимость), всё как было.
Флаг поставлен только §11 — остальным разделам той же природы (§9 отказы от
объёма, отклонённые варианты) его ставить владельцу.

**Карточки проекта нет — заведённое не правится.** Имя руководителя, класс
миссии и название проекта задаются ОДИН раз, в окне заведения сцены 1: вид
«проект» служебный и на месте не правится (`правимые` в SceneRoutes), экрана
у него тоже нет. На ПМИ-7 это видно в документах: §2 FAD печатает
руководителем «инженер» (умолчание автора), §1 FA — пустой класс миссии, и
поправить это в продукте нечем. Доделка: карточка проекта с правкой этих
полей — рядом с доделками по рискам, тем же входом «правка строки на месте».

**KDP-A: ворота держали то, чего в интерфейсе не было (21.09).** Владелец:
«Д1 · FAD … не базирован: нет ни одной линии базирования … при этом как
базировать FAD — непонятно, в интерфейсе нет кнопок» и «Д2 · MCReport … полны
8 из 11 разделов». Разбор нашёл три входа, которых не существовало ни на одном
экране, при живых маршрутах:

* **Базирование документа.** `POST /v2/documents/{код}/baseline` стоит с шипа
  C, вызова в клиенте не было вовсе. Теперь на экране документа — «Базировать»:
  имя линии подсказывается ближайшей непройденной точкой, занятое имя не даёт
  нажать (линия неизменяема — перебазирование заводит новое имя), рядом список
  прежних линий с отметкой.
* **Отказы от объёма (§9 MCReport).** Форма сцены 7 слала `descopes: []`
  жёстко, а ответ маршрута их и не нёс — раздел «Что вынесено за границы первой
  очереди» наполнить было нечем. Теперь `GET /v2/concept` отдаёт отказы, вид
  «baseline_concept» правится на месте, и отказы с отклонёнными вариантами
  дописываются к принятому решению по ходу, а не называются разом в миг выбора.
* **Варианты построения (§2 MCReport).** `POST /v2/variants` стоит с волны 4,
  экран вариантов только читал. Хуже: маршрут требовал показатель всегда, а §2
  печатает имя и подгруппы — вариант, описанный строем, завести было нельзя.
  Теперь форма сцены 7 заводит вариант строем (Walker-Delta · Walker-Star ·
  ССО, высота, наклонение или ЛВУ, плоскости, в плоскости), показатель —
  необязателен; пустой вариант отказывается словами.

**Запертая кнопка молчит, а число без ступени не значит ничего (21.09).**
Владелец нажал «Базировать» и «вернулся всё так же»: поле «кто базирует» было
пустым, кнопка — заперта, а причина жила в подсказке под курсором, которой на
нажатии не видно. Теперь имя автора берётся ИЗ УЧЁТКИ (`useАвтор`:
`/api/auth/whoami`), а помеха пишется строкой «Нажать нельзя: …» — то же
исправлено у «Проверить против поля», где кнопка запиралась так же.

И вторая половина той же жалобы — «3 из 5 непонятно»: полнота считалась к
MCR, к обзору, который уже позади, и ступень нигде не называлась. Документ
теперь считается к БЛИЖАЙШЕЙ НЕПРОЙДЕННОЙ точке (`Documents.gateAhead`),
шапка говорит «полнота 4 из 6 к KDP-A», а под ней строкой — каких разделов не
хватает и чего каждый ждёт; разделы, которых ступень ещё не ждёт, названы
отдельно и в счёт не идут.

**«Где мы находимся — вообще непонятно» (21.09).** Экран документов показывал
полноту каждого документа по отдельности, а КОМПЛЕКТ — то, чего точка ждёт от
документов вместе, — жил матрицей зрелости на экране точек, куда из документов
дороги не было; базированный документ в списке ничем не отличался от
небазированного. Теперь: строка списка говорит «базирован «KDP-A» · 21.09» или
«не базирован» и к какой ступени считана полнота; над списком — комплект точки
её же словами («Ехать дальше нельзя: 3 из 5 не готовы», с причиной у каждой и
кнопкой «открыть»); на экране документа — строка матрицы про ЭТОТ документ
(«KDP-A ждёт зрелость F — не базирован. Пока так — точка не пустит»).

**«Ждёт сцен 7» — это адрес, а не жалоба (21.09).** Раздел документа называл
сцену, которой наполняется, и на этом заканчивал: перехода не было, и человек
читал адрес, не зная, куда идти. Теперь у незакрытого раздела стоит «к месту:
сцена N» — та же дорога, что у условий точки. Сцены берутся из шаблона
раздела; если их больше трёх (§11 «наполняется по ходу фазы» называет десять),
дорога не предлагается — десять кнопок это не адрес, а шум.

**«Просто бред — куда и что писать непонятно» (21.09).** Пришёл по своей же
дороге «к месту: сцена 7» и увидел, что высадил человека в чистое поле:
экран сцены 7 — это 2700 пикселей, первый из них занимает состав системы на
49 узлов, а карточек «Варианты построения» было ДВЕ — старая (только чтение,
из раздела моделей) и моя новая с формой. Плюс в «Базовом варианте» разом
жили форма выбора варианта и списки решения, и поле «Отклонённый вариант»
было на экране дважды.

Починено: карточка вариантов ОДНА — форма переехала внутрь той, где варианты
сравниваются (правило «одно место на понятие»); форма выбора базового
варианта прячется, когда вариант уже назван; обе формы говорят, какой раздел
какого документа ими закрывается; переход «к месту» несёт ПРИЧИНУ — экран
работы первой строкой пишет «Сюда вас послал документ: §2 Анализ альтернатив
— «Варианты построения и их метрики»: 0 из 1» и подводит к той карточке, чьё
имя названо в причине (сверяются два имени из данных, таблицы в коде нет).

И вдогонку, по тому же замечанию: экран сцены 7 читался плохо сам по себе.
Состав системы на 49 узлов занимал весь первый экран (1450 пикселей) — теперь
свёрнут до двенадцати со строкой «…и ещё 37» и ссылкой «показать все» в шапке;
карточка вариантов встала ПЕРЕД выбором базового (выбирают из них, а не
наоборот), и «Базовый вариант» перестал повторять списками то, что уже сказал
сводкой. Высота экрана с 2747 пикселей до 1646.

§11 «Открытые вопросы» тоже получил дорогу (21.09). Тема — не выход сцены:
она может появиться на любой, поэтому шаблон называет для §11 десять сцен и ни
одного адреса. Элемент раздела теперь несёт ВИД, который читает его запрос
(`select`), и экран называет место по нему: «к месту: поле знаний → «Завести
тему»», причём поле знаний открывается СРАЗУ ручным вводом — дорога обязана
приводить к форме, а не к экрану, где форму ещё искать.

**Истина о варианте построения расходится с кодом и схемой.** У вида
`constellation_variant` истина знает `name`, `subgroups`, `working`; сравнение
вариантов и Парето читают `metrics`, которых у вида нет, а порог берут у вида
`criterion`, который в истине описывает совсем другое (ворота, проверку, сцену
и признак «держит»). Схема при этом сгенерирована с артефактами разбора:
поле подгруппы зовётся `usage*→component_usage(КА)`, а «наклонение ЛИБО ЛВУ»
стало одним именем `inclination|ltan`. Запись в хранилище схему не проверяет,
поэтому всё это годами не всплывало. Вопрос владельцу ниже.

## Открытые вопросы

* **Что такое вариант построения: строй или показатели?** (21.09). Истина
  описывает `constellation_variant` строем (`subgroups`), код сравнения —
  показателями (`metrics`), а вид `criterion` в истине — про ворота, не про
  пороги показателей. Назвать истиной: показатели и пороги у варианта либо
  отдельным видом. Заодно генератор схем не разбирает две записи истины:
  `usage*→component_usage(КА)` и `inclination|ltan` уходят в схему именами
  полей как есть.

* **Каталог процессов: запись на процесс или каталог со списком?** (21.09).
  Истина схем называет вид «process_catalog» одним процессом; полка
  ПОЛКА-ПРОЦЕССЫ-СИ — каталогом со списками `processes` и `tools` внутри
  одной записи. Печать SEMP §6/§10 живёт по полке. Назвать истиной один из
  двух видов: либо `processes[]`/`tools[]` у каталога, либо 17 записей вида.

* **`project.standard` и `project.phase_template` — поля кода, которых нет у
  вида** (21.09). Код пишет в документ проекта стандарт («NASA-7120») и код
  шаблона фазы; истина схем у вида «проект» их не называет, так что печать про
  них спросить не может, а сторож запроса их отвергает. Оба — настоящие
  свойства проекта, а не выдумка экрана: стандарт показывает карточка портфеля,
  шаблон фазы держит переход после KDP-A. Вопрос владельцу: назвать их истиной
  (`standard: ref standard`, `phase_template: ref phase_template`) или увести
  стандарт в шаблон фазы, где он уже есть, и читать оттуда.

* **Сервер api однопоточный** (10.09). Разбор вынесен в фон заданием
  (ADR-069) — стенд отвечает; синхронными остаются печать PDF и «Написать
  связно» (секунды). Пул потоков с сериализацией доступа к базе — отдельным
  решением, когда появится вторая долгая операция.

* **Стенд: причина `exit code 2` у backend Postgres не установлена**
  (отчёт `docs/tz/v2/отчёты/СТЕНД-ПАДЕНИЯ-PG-08-09.md`). Api теперь
  переживает обрыв (пул + переподключение, тег `v2-stand-pool`), сокет на
  SIGTERM закрывается, журнал базы называет клиента. Если падение
  повторится при закрытом сокете — снимать core dump backend, а не
  трогать api.




* **Окно взятия WBS выбором элементов** (шип B, 2026-09-07). `POST
  /v2/wbs/take` берёт с полки ВСЕ 56 пакетов; на прогоне у проекта шесть
  узлов состава, и 41 пакет остаётся без пары — выход сцены 12 честно
  держит проект. Для полок Arcadia окно взятия сделано (ADR-054 ред. 2),
  для WBS — нет.

* **§10 и §11 отчёта** (допущения и открытые вопросы) наполняются полем
  знаний: факты с меткой [П] и неразрешённые темы. На прогоне волны 4
  разбора материала нет, поэтому разделы пусты законно.

* **Эталон `reference-scenes-10-12-models` не поставлен**: экраны сцен
  10–12 и раздела моделей сделаны по сложившемуся языку (плотность по
  роли, тест действия, три размера), а не по эталону.



* **Носитель нужды ND-0006 — «субъекты КИИ»** (шип A, 2026-09-07). Разбор
  назвал носителем «субъекты КИИ» (187-ФЗ), но стороной их не завёл и
  действия на это не предложил. Система говорит об этом при приёме и
  отказывает на маршруте носителя. Вопрос владельцу: заводим ли «субъекты
  КИИ» стороной проекта (роль «потребитель»/«регулируемый»), или нужда
  принадлежит уже заведённой стороне.

* **Выход сцены 3 не закрыт содержанием**: у четырёх из пяти сторон
  (Правительство РФ, АО «ГЛОНАСС», Ространснадзор, Роскосмос) нет ни одной
  нужды. Записка их нужд не даёт — это инженерная работа, а не код.

* **Предложения сцен 2–6 на прогоне пусты законно**: из 23 действий плана
  принято 22, непринятое — одно (норматив ПНСТ 996-2024, уже лежит на
  полке поставкой). Полосу с непустым составом видно на свежем разборе.



* **Стейкхолдер с несколькими ролями** (замечание живого прохода ПМИ-3,
  владелец: «не критично, надо поправить потом»). Сейчас `role` — одно
  значение из перечня, а один и тот же участник бывает разом регулятором,
  заказчиком и потребителем: ГКРЧ и Роскомнадзор регулируют и потребляют,
  Минтранс заказывает и регулирует. Правка: `role` → массив ролей с
  сохранением совместимости (одиночное значение читается как список из
  одного), матрица группирует по каждой роли, обобщение в профиль А2 берёт
  главную. Задевает схему стейкхолдера, матрицу покрытия, заведение
  носителей из нужд и профиль полки — поэтому отдельным шипом, не правкой
  на ходу.

* **Дизайн формы карточки объекта** (поставлен инженером на втором заходе,
  2026-08-25). Сделанное по ходу прогона — вкладки «Определение / Готовность /
