Это **исходные документы заказчика**, а не проектная документация: правятся
только вместе с самим регламентом.

## Приложения — нормативная структура документов

Приложения 2–4 `BP-PhaseA.md` задают структуру разделов документов, которые
генерирует ИС (TZ-OUT-001):

| Приложение | Документ | Генератор |
| --- | --- | --- |
| 2 | Спецификация требований | `DocumentTemplate.RequirementSpecification` |
| 3 | ConOps (заготовка) | `DocumentTemplate.ConOps` |
| 4 | Описание архитектуры системы | `DocumentTemplate.ArchitectureDescription` |

Таблица разделов в генераторе — вторая копия таблицы отсюда, и разойтись молча
она не может: `RegulationSectionsTest` разбирает эти файлы и сверяет номера,
заголовки и содержание разделов посимвольно. Правка регламента без правки
генератора роняет сборку.

## Почему `.md`, а не `.docx`

Файлы пришли с расширением `.docx`, но содержимым являются обычным текстом
UTF-8 с таблицами Markdown — Word их не открывает. Расширение приведено
к содержимому.

Заодно имена приведены к латинице. Причина техническая: `sun.jnu.encoding`
берётся JVM из локали при старте и ключом `-D` не переопределяется; в локали
POSIX она равна ASCII, и путь с кириллицей становится недостижим —
`InvalidPathException` возникает раньше, чем файл будет прочитан. Требовать
от каждой машины сборки правильной локали ради двух имён файлов дороже, чем
назвать файлы латиницей: русские заголовки остались внутри документов.

Исходные имена: `Регламент_БП_PreA.docx`, `Регламент_БП_PhaseA.docx`.
