# 10. Модель данных и контракты

Статус: Draft. Источник: Концепция ИС v0.3, разд. 4; модельные документы.
Схемы: `schemas/` — нормативная часть. Текст ниже задаёт требования к их применению; при расхождении текста и схемы приоритет у схемы.

---

## 1. Состав схем

**Общие (`schemas/common/`)**

| Схема | Назначение |
| --- | --- |
| `quantity` | Величина: значение + обязательная единица + происхождение + допуск/резерв |
| `provenance` | Происхождение значения: ручной ввод / расчёт / предложение ИИ / импорт |
| `status` | Статусная модель Draft → Preliminary → Approved → Baseline |

**Ядро модели (`schemas/core/`)** — цифровая нить

| Схема | ID | Место в нити |
| --- | --- | --- |
| `need` | `ND-NNNN` | Стейкхолдер → Нужда |
| `service` | `SV-NNNN` | Сервис + QoS-профили по видам потребителей |
| `requirement` | `RQ-NNNN` | Требование + MOP + верификация |
| `component` | `CM-NNNN` | Дерево «Система — Компоненты» + параметры + TPM |
| `scenario` | `SC-NNNN` | Расчётный случай + воспроизводимость |

**Контракты между модулями (`schemas/contracts/`)**

| Схема | Контракт |
| --- | --- |
| `terminal-profile` | Профиль терминала A'/B'/C' |
| `demand-map` | Потребители → баллистика, потоки |
| `spacecraft` | Модель КА (платформа + ПН) |
| `radio-link` | Радиолиния с бюджетом |
| `service-zone` | КА → баллистика: зона обслуживания по линии |
| `visibility` | Баллистика → потоки: предрасчитанные события |
| `protocol-adapter` | Сменный протокол |
| `flow-result` | Потоки → KPI: результат Монте-Карло |
| `kpi-vector` | Баллистика → визуализация: вектор KPI варианта |

## 2. Решения, закодированные в схемах

Ограничения Р1–Р9 выражены типами, а не проверками в коде — нарушение отклоняется валидацией на границе модуля:

| Решение | Место в схеме | Механизм |
| --- | --- | --- |
| Р1 regenerative | `spacecraft.payload.architecture` | `const: "regenerative"` |
| Р2 12U–100 кг | `spacecraft.platform.dry_mass_kg` | `minimum: 12, maximum: 100` |
| Р3 РЧ ISL | `radio-link.medium` | `const: "rf"` |
| Р4 статические маски | `spacecraft.modes[].geo_mask_ref`, `scheduler_hook` | заглушка отдельным полем |
| Р5 эфемериды | `terminal-profile.ephemeris.knows_ephemeris` | `const: true` |
| Р6 эфемеридный backoff | `terminal-profile.reliability_policy.backoff` | значение `ephemeris_wait` |
| Р7 подвижность | `terminal-profile.mobility.model` | `enum: [static, route]` |
| Р8 карта спроса | `demand-map.layers` | три слоя, `population` обязателен |
| Р9 QoS-профили | `service.qos_profiles[].consumer_class` | массив профилей, `minItems: 1` |

## 3. Требования

### TZ-MOD-001. Схемы как нормативный источник структуры

```
REQ:        Структура данных ИС определяется JSON-схемами в schemas/.
            Изменение структуры выполняется изменением схемы; код,
            расходящийся со схемой, считается дефектным.
RATIONALE:  Единый источник истины распространяется и на структуру данных.
TRACE-UP:   TZ-COM-001; TZ-COM-007
TRACE-DOWN: —
VERIFY:     TEST
ACCEPTANCE:
  - [ ] все схемы валидны по JSON Schema 2020-12
  - [ ] все $ref разрешаются внутри schemas/
  - [ ] валидация схем выполняется в CI
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-MOD-002. Валидация на границе модуля

```
REQ:        Данные, передаваемые между модулями, валидируются по
            соответствующей схеме на границе принимающего модуля.
            Невалидные данные отклоняются с указанием поля и правила.
RATIONALE:  При лёгкой модульности контракт данных — единственный барьер
            от расползания связей.
TRACE-UP:   TZ-COM-002; TZ-COM-007
TRACE-DOWN: TZ-AI-002; TZ-BAL-001; TZ-FLW-001; TZ-KA-001; TZ-USR-001
VERIFY:     TEST
ACCEPTANCE:
  - [ ] каждый межмодульный вызов валидирует вход по схеме
  - [ ] сообщение об ошибке содержит путь до поля и нарушенное правило
  - [ ] негативные наборы из tests/reference/example-violations.json отклоняются
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-MOD-003. Ограничения Р1–Р9 выражены типами

```
REQ:        Решения Р1–Р9 выражаются ограничениями схем (const, enum,
            minimum/maximum), а не проверками в прикладном коде.
            Сообщение об отклонении ссылается на соответствующий ADR.
RATIONALE:  Ограничение, выраженное типом, невозможно обойти по невнимательности;
            ограничение в коде — можно.
TRACE-UP:   ADR-001…ADR-009; TZ-COM-008
TRACE-DOWN: TZ-KA-001; TZ-USR-002
VERIFY:     TEST
ACCEPTANCE:
  - [ ] bent-pipe ПН отклоняется схемой spacecraft
  - [ ] масса вне 12–100 кг отклоняется схемой spacecraft
  - [ ] оптический ISL отклоняется схемой radio-link
  - [ ] терминал без эфемерид отклоняется схемой terminal-profile
  - [ ] роуминг регуляторных зон отклоняется схемой terminal-profile
  - [ ] текст ошибки содержит идентификатор ADR
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-MOD-004. Величина без единицы и происхождения недопустима

```
REQ:        Любое числовое значение модели хранится как quantity:
            значение + единица + происхождение. Значения без единицы
            или без происхождения не сохраняются.
RATIONALE:  TZ-COM-005; ошибки единиц — классическая причина потери миссий.
TRACE-UP:   TZ-COM-005
TRACE-DOWN: TZ-BAL-004; TZ-KA-003
MOP:        доля значений модели с полным quantity = 100%
VERIFY:     TEST
ACCEPTANCE:
  - [ ] попытка сохранить число без единицы отклоняется
  - [ ] попытка сохранить значение без provenance отклоняется
  - [ ] углы хранятся в rad, отображаются в градусах
  - [ ] предложение ИИ с accepted=false не участвует в расчётах и отчётах
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-MOD-005. Граф зависимостей параметров и пересчёт

```
REQ:        Параметр может задаваться формулой от других параметров.
            ИС строит граф зависимостей, пересчитывает зависимые значения
            при изменении источника и помечает затронутые результаты
            моделирования устаревшими (stale).
RATIONALE:  Параметрическая модель (логика Valispace); TZ-COM-006.
TRACE-UP:   КОНЦ-2; КОНЦ-4; TZ-COM-007
TRACE-DOWN: TZ-KA-004; TZ-OUT-002
VERIFY:     TEST
ACCEPTANCE:
  - [ ] изменение параметра пересчитывает зависимые за один проход
  - [ ] циклическая зависимость выявляется и отклоняется при вводе формулы
  - [ ] сценарии, использовавшие изменённый параметр, получают stale=true
  - [ ] отчёт «устаревшие результаты» доступен
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-MOD-006. Зона обслуживания отделена от зоны видимости

```
REQ:        Модель различает зону видимости (геометрия) и зону обслуживания
            (замыкание бюджета линии + ёмкость). В расчёт качества сервиса
            передаётся зона обслуживания, раздельно по каждой линии и
            профилю терминала.
RATIONALE:  Зона приёма A' шире зоны двустороннего контура C'; смешение
            понятий завышает оценку покрытия.
TRACE-UP:   КА-3.3; КОНЦ-5.2-А
TRACE-DOWN: TZ-BAL-005; TZ-KA-005
VERIFY:     TEST
ACCEPTANCE:
  - [ ] service-zone содержит limiting_factor для каждой границы
  - [ ] service_elevation_deg ≥ min_elevation_deg во всех случаях
  - [ ] зоны для профилей A' и C' на одной конфигурации различаются
STATUS:     Draft
OWNER:      ведущий системный инженер
```
