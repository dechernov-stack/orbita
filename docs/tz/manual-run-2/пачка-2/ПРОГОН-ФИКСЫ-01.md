# Фиксы прогона — пачка 1

## Ф-01 · Порядок дат не держит границу фаз

**Условие приёмки (после шипа 1):** отчёт показал сквозное правило и
тест, но не назвал створку исходного наблюдения владельца. Закрытие
требует: (1) воспроизвести точный сценарий и назвать, где прошло /
что именно наблюдалось; (2) подтвердить или доделать **опору календаря
через границу фаз** (первая веха фазы открывается от последней вехи
предыдущей) — второй пункт Ф-01, в отчёте не упомянут.

Phase A может начинаться раньше конца Pre-A — правило круга 2 было
сформулировано «внутри фазы» (моя формулировка, признаю́), граница фаз
выпала.

**Нужно:** правило порядка — по **сквозной ленте жизненного цикла**:
вся последовательность вех проекта монотонна (…вехи Pre-A < KDP-A ≤
вехи Phase A < KDP-B…). То же одно правило на сервере, тот же текст
отказа с именами точек («SRR не может быть раньше KDP-A»); опора
календаря первой вехи фазы — последняя веха предыдущей. Тест на границу.

## Ф-02 · Коды ограничений: что задумано, что нет

Задумано: **коды стабильны** — на них ссылаются промпты службы («запрет
Р1») и трассировки; дыры в нумерации законны (убранное не переиспользует
код — как у требований). На код — подсказка: «код стабилен, на него
ссылаются промпт и трассировка».

Не задумано — **два префикса**. Появившиеся П1/П2 рядом с Р1…Р7 — зоопарк:
семантика групп (техническое / программное / пусковое) — это **категория
полем**, не буква идентификатора. Привести: один префикс Р- для всех
ограничений проекта; П1/П2 мигрируют в следующие свободные Р-коды с
ре-линком ссылок (их пока мало — дешевле сейчас); категория «пусковое» —
полем.

И проверить «убрать»: ограничения обязаны **отменяться с историей**
(механика Б-02), не удаляться жёстко; отклонение затравочного ограничения —
это след решения, он ценен для точки.

*Попутно по существу: П1/П2 (только российские РН, старт с Восточного) —
ограничения с зубами: Восточный режет достижимые наклонения, и метрика
пусковых партий (Б7) обязана их учитывать при сравнении построений —
проверю связку при разборе итога.*

## Ф-03 · Типы документов — смысловые подсказки из глоссария

При складывании своего файла тип обязан объяснять себя наведением: что
это, что система из него извлечёт, что важно в карточке. Показ — тултипом
на чипе типа + строкой под выбранным (механика подсказок уже общая).

**Источник — глоссарий**, не хардкод клиента: тип документа = запись
глоссария с брифом (один источник, как словарь единиц). Заодно закрыть
«глоссарий недоступен пользователю»: пункт «Справочники» в панели
Библиотеки — глоссарий и единицы просмотром.

Черновики брифов (владельцу на правку):
- **Записка миссии** — постановочный документ заказчика: цели, сроки,
  нормативные ссылки. Служба извлечёт цели и нужды, профили
  стейкхолдеров (полка А2), типовые риски (Б3).
- **Норматив** — стандарт/ГОСТ с обозначением и **редакцией**: пункты
  станут основаниями требований; смена редакции подсветит зависимые.
- **Даташит** — характеристики компонента: выжимка свойств для модели
  аппарата и типовых требований.
- **Справка** — контекстный материал: участвует в промпте службы,
  извлечений не порождает.
- **Прочее** — лежит материалом проекта; служба его не читает, пока не
  переопределён тип.

## Ф-05 · Промпт постановки — из данных, не из общих слов

Найдено владельцем на новом заходе: промпт О2 не подтягивает ничего из
библиотеки — без записки генерация холостая, предупреждение это лишь
признаёт.

1. **Замысел миссии — обязательная мини-форма** (Ш1 дорастает): для
   кого · что делает · где · горизонт — четыре поля или один связный
   абзац. Без замысла кнопка генерации постановки **заблокирована с
   причиной** («нет замысла — генерация даст общие места»), не
   предупреждение мелким шрифтом.
2. **Сборка из библиотеки по классу миссии**: класс «НОО · связь и IoT»
   тянет в промпт типовые сервисы класса, профили стейкхолдеров (А2),
   типовые риски (Б3), автоприменённые нормативы (Б1), термины глоссария
   класса.
3. **Взятые наборы Ш2 — рамкой**: «в проекте 34 типовых требования —
   опираться, не дублировать».
4. **Акцептованный урожай разбора (Д2) — контекстом** «уже принято»:
   цели/нужды/стейкхолдеры из документов, если есть.
5. **Предпросмотр — состав по источникам со счётчиками**: замысел ·
   библиотека класса (N позиций) · материалы (M блоков) · принято (K) ·
   запреты (Р…). Пустой источник — видимая строка «— пусто», общие слова
   вместо данных невозможны по построению.

Мера: на проекте с классом и взятой библиотекой промпт О2 несёт
конкретику полок (позиции считаются в предпросмотре); без замысла —
блокировка с причиной; пакетный канал ПМИ не затронут.

## Ф-06 · Библиотека запрашивает данные, а не ждёт молча

Владелец: инженер «стоит и смотрит на неведомые идеи» — система должна
сама говорить, какие данные ей нужны и в каком формате.

1. **Анкеты характеристик по ролям носителей** — библиотечные шаблоны
   форм (по классу миссии): платформа · полезная нагрузка · терминал ·
   наземная станция. Поле = имя · единица из справочника · обязательность
   · подсказка из глоссария (механика Ф-03).

   Пример «Платформа» (класс НОО-IoT): формат · масса, кг · масса под ПН,
   кг · мощность для ПН (средняя/пик), Вт · энергоёмкость АКБ, А·ч ·
   точность ориентации, ° · срок активного существования, год · Δv, м/с ·
   диапазон рабочих температур, °C.

   Пример «Полезная нагрузка IoT»: масса, кг · потребление
   (дежурное/пик), Вт · диапазон частот, МГц · чувствительность, дБм ·
   каналов одновременного приёма, шт · скорость канала, бит/с · объём
   буфера, МБ.

2. **Три пути заполнения**, все явные на форме: рукой · взять типовой с
   полки (шаблоны компонентов уже есть) · **приложить даташит — разбор
   Д1/Д2 предзаполняет поля** с координатами блоков; инженер сверяет и
   акцептует, происхождение у каждого значения.

3. **«Чего не хватает» — вычисляется**: модель аппарата и моделирование
   объявляют потребные поля; незаполненное обязательное — разрыв
   «данные не заданы» со ссылкой «заполнить форму» (в готовность и в
   задания — механика процесса).

4. Анкеты — данными на полке (правится без кода), связь с Д2: класс
   сущности `property` в урожае метится именем поля анкеты.

5. **Зрелость по точкам — не перестараться (правка владельца).** У поля
   анкеты — атрибут «требуется к ‹точке›» (дух матрицы зрелости,
   NPR 7120.5 прил. I). В Pre-A анкеты — **приглашение, не требование**:
   разрыв «данные не заданы» считается только по полям, чья точка —
   ближайшая; остальное — тихая законная пустота. Заполнить раньше
   срока — законно (платформа уже выбрана — вносите); TBD живёт до своей
   точки (ADR-031). Приоритет Pre-A — «что и зачем строим»: замысел,
   цели, нужды, сервисы; характеристики железа по умолчанию зреют к
   SRR/SDR, кроме концептуально необходимых раньше (диапазон частот —
   к MCR, без него нет концепции связи).

Мера: в пустом Pre-A проекте «Модель аппарата» показывает запросы с
формами и тремя путями, **не горя разрывами железа**; приложенный даташит
LR1121 предзаполняет поля с якорями; к SDR незаполненная масса платформы —
разрыв в готовности; к MCR — только концептуальные поля.

## Ф-07 · Замысел миссии — генерируется из документов

Владелец: табличка из четырёх полей рядом с разобранной запиской —
убожество; постановка уже приложена и разобрана.

1. **Три пути заполнения замысла** (паттерн Ф-06): рукой (форма остаётся
   запасным путём) · **собрать из документов** — генерация по урожаю Д2 и
   блокам канона · уточнить правкой в любой момент.
2. **Вид пакета `mission_intent_from_docs`**: вход — акцептованный урожай
   + канон; выход — четыре поля связным текстом, **каждое с якорями
   происхождения** (для кого — из стейкхолдеров; что делает — из
   сервисов/нужд; где — из географии; горизонт — из целей). Канал тот же:
   пакетом в ПМИ, живым вызовом в бою; акцепт правкой инженера.
3. Блокировка Ф-05 дорастает: «нет замысла — [заполнить рукой] или
   [собрать из документов →]» (вторая кнопка активна при наличии
   разбора).
4. Промпт О2 подтягивает **и блоки канона** выбранных документов, не
   только урожай, — если Ф-05 этого не дотянул, дотянуть здесь.
5. Заготовка ПМИ: `ПАКЕТ-ЗАМЫСЕЛ-ЗАПИСКИ.json` — приложен к пачке,
   шаг мастера проходит вставкой без токенов.

Мера: проект с запиской → «собрать из документов» → четыре поля с
якорями, инженер правит и акцептует, генерация О2 разблокирована;
проект без документов — форма рукой, как в Ф-05.

## Ф-08 · Путь документа к ИИ не ведёт за руку

Владелец собрал записку по шаблону — «для ИИ ничего не изменилось»:
блоки в промпт не выбраны (без выбора уходит одно оглавление), замысел
пуст, урожая нет. Три починки:

1. **Умолчание «В промпт» — по типу документа**: постановочные (записка
   миссии) — все разделы включены при загрузке; справка — выключена;
   снятие — осознанное исключение (симметрия правилу чекбоксов Ш2).
2. **Полоса-проводник на карточке постановочного документа**: после
   загрузки — приглашения цепочкой «разобрать → акцептовать урожай →
   собрать замысел → в промпт», каждое ведёт к месту; сделанное гаснет.
   Мёртвых состояний «загрузил и смотри» не остаётся.
3. **Метки источников [И]/[В]/[П] — в разбор**: правило промпта Д2
   дополняется — метка утверждения переносится в поле `source_mark`
   урожая ([П]-цели не путать с внешними фактами); шаблон записки
   узаконивает метки разделом «Обозначения источников».

Мера: загрузка записки по шаблону → разделы в промпте по умолчанию,
полоса ведёт до замысла; [П]-метка цели «1 млн терминалов» видна в
урожае и в карточке цели после акцепта.

*Режим фиксов: копим пачкой, передача — по команде владельца.*

## Ф-04 · Разбор документов при загрузке — выжимка-спутник

Решение владельца, оформлено отдельно: `РЕШЕНИЕ-РАЗБОР-ДОКУМЕНТОВ.md` —
двухслойное хранение (файл + машиночитаемый разбор с координатами),
детерминированный пайплайн с канонизацией единиц и термами глоссария,
LLM только поверх выжимки. Этапность Д1–Д3 в решении; в пачку.
