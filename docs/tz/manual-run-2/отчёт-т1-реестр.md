# Отчёт Т-1 (О-12): реестр требований по эталону круга 4

Вёрстка — по замороженному `reference-req-registry.html` (круг 4); сервер —
три куска по заданию. Снимки четырёх состояний на живом стенде (212
требований) — `снимки-т1/`.

## Сервер

- **Реестр одним запросом** — расширен существующий `/views/requirement-tree`
  (нового API нет — ловушка 5): строка несёт вид (`kind`: numeric при mop —
  поле, которое Г5 сделает хранимым), родителя RQ→RQ, носителя **с именем**,
  обоснование, версию, владельца, происхождение и **флаги помет**.
- **Пометы считает сервер** по истории версий одним SQL
  (`ObjectStore.historyByType`): «изменено после утверждения» — версия ушла
  от первой утверждённой (правка всегда даёт новую версию, переход статуса —
  нет); «показатель пересчитан после базирования» — mop текущей версии ≠ mop
  первой Baseline-версии. На живом реестре: 144 и 140 — волны правили массово,
  пометы честно это показывают.
- **`saved_view` (VW, схема 45-я, миграция V028)** — серверный объект, не
  localStorage: `GET/POST /views/req-views`; личные виды фильтрует сервер по
  учётке, `owner_login` проставляет сервер из сессии (документ клиента его
  не задаёт). Мера — ReqRegistryTest: личный вид не виден второй учётке,
  проектный виден, вид переживает перезаход; флаги помет — тем же тестом.

## Клиент (Requirements.tsx — переверстан целиком)

- Тулбар тремя строками: раздел+вкладки+«Добавить требование»+«⋯» (выгрузки
  ReqIF/CSV/JSON и загрузка пачкой ушли в меню) · Дерево/Плоско +
  «Группировка: ‹критерий› ▾» + чипы видов + поиск + «⚙ Вид» · счётчики
  разрывов (клик — фильтр).
- Группировка со схлопыванием — клиентская по данным одного запроса;
  «Не распределено» первой; дерево внутри группы: ребёнок с отступом «└»
  строго после родителя, без дублирования строки (кейс круга 3 закрыт
  тестом); родитель в другой группе → строка корнем своей группы.
- Раскрытие строки: три колонки сути (показатель+обоснование · трассировка
  ↑↓+пометы · носитель+верификация), Esc сворачивает, ↑↓ ходят по строкам
  (раскрытие следует), Enter раскрывает — проверено на живом стенде.
- Карточка — вся рабочая область: крошка, статус·версия, чипы помет,
  `N из M` и пред./след. **по текущей выборке** (снимок: «1 из 23» при
  схлопнутых сиротах); секции двумя колонками: показатель, трассировка
  («в матрицу →», «детей нет — декомпозировать»), обоснование, распределение
  («к носителю →»), верификация, история с откатом (`/edit/{id}/history` +
  undo), полоса «Предложения ИИ» (порождённые службой Draft-дети этого
  требования; Принять — promote, Отклонить — cancel).
- Конфигуратор «⚙ Вид»: состав чекбоксами, порядок перетаскиванием,
  сортировка кликом по заголовку; **один источник состояния** — таблица и
  конфигуратор читают один массив колонок (тест).
- Массовые действия: чекбоксы + полоса «Выбрано: N · Базировать N
  требований?» с подтверждением числом; отказы поимённо.
- **Боковой инспектор требований удалён** (решение круга 2 исполнено);
  intent-переходы «к объекту» с других экранов открывают карточку.
- Тесты клиента — первые vitest в репо (`requirementsView.test.ts`, 17):
  дубль ID невозможен (8 сочетаний разрезов + кейс круга 3), конфигуратор =
  факту, счётчики разрывов сходятся, пред./след. по выборке; прогон включён
  в `ci/checks.sh`.

## Вопросы владельцу

1. Плотность (выше): 27 строк — потолок при 26px строке и трёх тулбарах.
2. В эталоне конфигуратора порядок строк (Показатель раньше Вида) расходится
   с порядком колонок таблицы (Вид раньше Показателя). Взят порядок таблицы —
   конфигуратор обязан совпадать с фактом.
3. «Декомпозировать» из карточки открывает создание требования БЕЗ
   автоподстановки родителя (derives_from заполняется в форме рукой):
   заготовить автоподстановку — отдельная правка формы, скажите если нужна.
