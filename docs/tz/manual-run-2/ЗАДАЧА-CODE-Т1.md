# Задача Code: Т-1 «Реестр требований» (позиция О-12 очереди)

Эталон заморожен кругом 4: `reference-req-registry.html` → `docs/ui/reference2/`
(поставка владельца, придёт его коммитом). Четыре состояния стенда — один
экран в вёрстке. Решение круга 2 действует: **бокового инспектора для
требований больше нет** — прежняя панель удаляется, её маршруты/якоря ведут
в карточку.

## Вёрстка — по эталону, ничего сверх

1. **Тулбар тремя строками, у каждой одна работа**: раздел + вкладки +
   «Добавить требование» + меню «⋯» (выгрузка, загрузка пачкой);
   форма данных — Дерево/Плоско · «Группировка: ‹критерий› ▾» · чипы
   сохранённых видов · поиск · «⚙ Вид»; строка счётчиков-фильтров разрывов.
2. **Группировка со схлопыванием** — клиентская: носитель / уровень /
   статус / владелец; заголовок группы с шевроном и счётчиком; «Не
   распределено» — первая группа, в строках приглашение «распределить».
3. **Дерево**: связи требование→требование с отступом и шевроном ветки.
4. **Раскрытие строки** (клик/Enter): три колонки сути по эталону;
   Esc сворачивает, ↑↓ ходят по строкам.
5. **Карточка требования** — вся рабочая область: крошка «← Реестр»,
   `N из M` и пред./след. **по текущей выборке** (фильтры и группировка
   учитываются), секции двумя колонками, полоса «Предложения ИИ» с
   Принять/Отклонить по месту.
6. **Конфигуратор вида**: состав колонок чекбоксами, порядок
   перетаскиванием, сортировка кликом по заголовку; **конфигуратор всегда
   равен факту таблицы** — рассинхрон невозможен по построению (один
   источник состояния).
7. **Массовые действия**: полоса выделения с подтверждением числом
   («Базировать 12 требований?»).
8. Пометы-квадратики у статуса (пересчитан / изменено после утверждения) с
   расшифровкой в раскрытии и карточке; тексты и типографика — дословно из
   эталона.

## Сервер — три куска под экран

1. **Вид `saved_view`**: колонки · порядок · сортировка · фильтры ·
   группировка · форма (дерево/плоско); область — личный (учётка В3) или
   проектный; чипы читают его, «+ сохранить» пишет. **Не localStorage** —
   учётки уже есть, вид должен переживать перезаход и машину.
2. **Реестр одним запросом**: строки приходят со всем для отрисовки —
   носитель, родитель-требование (RQ→RQ, где нет — пусто), агрегат
   верификации, **флаги помет с сервера** (клиент семантику «пересчитан» /
   «изменено после утверждения» не вычисляет). Догрузка по одному
   требованию — только для раскрытия и карточки.
3. **Этапность колонки «Вид»**: до Г5 значение вычисляемое
   (числовое при `mop`, иначе текстовое) — сервером, тем же полем, которое
   Г5 потом сделает хранимым.

## Приёмка

- [ ] снимки четырёх состояний рядом с эталоном **на живом стенде** с
      реестром миссии (212), расхождения поимённо или их нет;
- [ ] ≥30 строк на 1440×900; длинная формулировка не обрезана при
      свободном месте; дубль ID невозможен (тест);
- [ ] Esc/↑↓ работают; пред./след. в карточке ходит по текущей выборке;
- [ ] сохранённый вид переживает перезаход; проектный вид виден второй
      учётке, личный — нет;
- [ ] конфигуратор равен факту (тест на одном источнике состояния);
- [ ] боковой панели требований в коде нет; прежние ссылки ведут в
      карточку; `ci/unwired.txt` не пополнился;
- [ ] счётчики разрывов сходятся с данными; «распределить» ведёт в
      распределение, не в пустоту.

## Ловушки

1. Оставить панель «на всякий случай» — решение круга 2 окончательное.
2. Сохранённые виды в localStorage — умирают со сменой машины; только
   серверный `saved_view`.
3. Пометы вычислять в клиенте — семантика уедет от сервера при первом же
   изменении правил; флаги приходят готовыми.
4. Пред./след. по всей базе вместо текущей выборки — инженер листает то,
   что отфильтровал, а не всё подряд.
5. Группировку тащить на сервер новым API — она клиентская по данным
   одного запроса; сервер добавляет только то, чего в строках не было
   (родитель, флаги).
6. Новые тексты, которых нет в эталоне, — вопрос владельцу, не
   самодеятельность.
