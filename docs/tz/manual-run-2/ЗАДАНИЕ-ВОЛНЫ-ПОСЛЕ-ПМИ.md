# Задание для Code: волны после ПМИ

Мерило — `ПЛАН-ПОСЛЕ-ПМИ.md` (v2); при расхождении он старше. Источник В4 —
`ЗАДАНИЕ-ГРАФ-И-ИИ.md` с поправкой §В4 ниже. Порядок волн строгий:
**В1 → [сессия] → В2 → В3 → В4**, нитка Б — параллельно с В1.

Отчёт после волны отвечает мерой волны (дословно из плана), не состоянием CI.
Веха «независимая сессия» — внешняя: Code её готовит, не проводит.

## В1. Документы

### 1.1. Сверка остатка ПМИ
Выборочная перепроверка починенного по журналу (не «по памяти»); реестр
несистемного остатка (З-У, дизайн) — в `docs/tz/manual-run/остаток.md`;
он же чек-лист выхода волны.

### 1.2. Модель документа: текст + вставки
- Раздел документа: **авторский текст** (хранимый, версионируемый, правится
  в системе) + **именованные вставки** (запросы к модели, пересобираются при
  выпуске). Схема `document_issue` расширяется; выпуск фиксирует снимок
  текста и данных вставок.
- Помета **«текст устарел»**: текст при сохранении запоминает отпечаток
  состояния своих вставок; расхождение отпечатка при выпуске — помета в
  `gaps`-механику (второй вид пробела). Помета, не блокировка и не
  перезапись. Точный механизм отпечатка — на усмотрение Code, поведение —
  как описано.
- Акцептованный ИИ-текст становится авторским; повторная генерация **никогда
  не перезаписывает** сохранённый текст — только предлагает рядом.

### 1.3. Профиль «редактор раздела»
Профиль службы: вход — шаблон раздела + состояние модели; выход — связный
текст раздела; схема «предложение → акцепт», происхождение и журнал — как
заведено. Первый документ — ConOps (Прил. 3), затем MCReport, FAD.

### 1.4. Печатная форма
Выпуск рендерится документом: титул (проект, обозначение, версия, статус,
подписи), номера и имена разделов по приложениям регламентов, таблицы,
колонтитулы. Экспорт **docx и PDF** с сервера — пакет точки уходит людям без
Орбиты. Вёрстка — по эталону Design.

**Мера В1** — из плана: пакет Д1–Д9 читает посторонний; ConOps печатается;
остаток журнала закрыт построчно.

## Нитка Б. Библиотека шаблонов (параллельно В1)

1. Вид «шаблон документа» в **библиотечной области**: разделы (имя,
   подсказка, вставки, требуемость), источник, редакция, версия. Шестнадцать
   шаблонов переезжают из enum `Documents.kt` в библиотеку; enum удаляется.
   Выпуск работает по библиотечному шаблону.
2. Профиль «извлечь структуру из документа»: вход — документ (PDF/текст),
   выход — предложение шаблона; акцепт; источник и редакция фиксируются.
3. Наполнение NASA (общественное достояние, оригиналы): приложения
   NPR 7120.5 (FAD, FA, Project Plan); приложения SP-2016-6105 (ConOps,
   SEMP, план верификации); NPR 7123.1 прил. G — чек-листы обзорных ролей;
   NASA-STD-8719.14 — ODA. **ГОСТ**: только реквизиты и собственные
   формулировки со ссылкой на пункт — полный текст в библиотеку не кладётся.
4. Свои — профилями через акцепт: типовые требования классов, шаблоны
   компонентов, профили операций, пресеты группировок.

**Мера Б** — из плана.

## Подготовка сессии (после В1)

## В2. Рабочее место узла

### 2.1. Определение и вхождение
- `component` становится **определением** (тип; версия — часть идентичности;
  связь «развитие» v1 → v2).
- Новый вид **вхождение** (`component_usage`, префикс проверить на
  уникальность): `определение × количество × роль в родителе`; свой id,
  в пачках и выгрузке.
- **Миграция**: существующие узлы — определения; каждая текущая связь
  `parent` порождает вхождение ×1. Требования (`allocated_to`) продолжают
  указывать на определения — носитель требования в Формулировании
  определение; требование к вхождению допустимо, но не выпячивается.
- Свёртка бюджетов — по вхождениям с кратностью.

### 2.2. Состав — граф над деревом
- Композиция вхождений — строго дерево: один владелец, ацикличность;
  разделяемое — связи «использует» / «размещено на» (ПО ↔ железо), не второй
  родитель.
- Интерфейсы — рёбра поверх дерева, поперёк ветвей и сегментов; видны
  вкладкой узла и матрицей N×N.
- **WBS — своя структура**: дерево работ (изготовление, интеграция,
  испытания, наземный комплекс, управление, эксплуатация); связь
  состав ↔ WBS многие-ко-многим (поле `wbs` узла мигрирует в связи);
  `cost_estimate` привязывается к элементу WBS; стоимость и сроки
  сворачиваются по дереву работ.

### 2.3. Дерево — главная навигация раздела «Система»
Строится и правится по месту: добавить ребёнка (с нуля / из шаблона
компонента нитки Б), перенести узел, вставить уровень — без потери связей и
истории. По эталону Design.

### 2.4. Узел — рабочее место
Вкладки: требования · интерфейсы · бюджеты · верификация · риски · частное
ТЗ (документ узла механикой В1, выборка `specificationOf`). Владелец узла —
поле (учёткой станет в В3). Действие узла **«Сохранить как шаблон»**:
поддерево со свойствами, портами, внутренними интерфейсами и привязанными
требованиями уходит в библиотеку по механике канала сбора
(`СТРУКТУРА-БИБЛИОТЕКИ.md`): замыкание фрагмента, поимённое предупреждение
о резке внешних связей, обезличивание в предпросмотре, происхождение.
Та же кнопка — на дереве работ, интерфейсе, выборке требований и профиле.

### 2.5. Требования — режим «по носителю»
Рядом с общим реестром; общий остаётся сквозным разрезом, перестаёт быть
единственным входом.

**Мера В2** — из плана: сценарий «ответственный за БЦВМ» без общих реестров;
две версии аппарата — две строки; интерфейс поперёк ветвей виден с двух
сторон и в матрице; стоимость — по WBS.

## В3. Многопользовательность

1. Локальные учётки, пароль, сессии; автор — из учётки везде (provenance,
   журналы). SSO — конфигурация развёртывания, не сейчас.
2. Роли на проект: руководитель · ведущий СИ · специалист · SMA ·
   DA/обзор · читатель. **Проверка прав — на сервере**, по маршрутам:
   точку фиксирует DA; базирование и изменение с основанием — ведущий СИ;
   специалист — владелец своих узлов, инженерный контур в их рамках
   свободен; замечания — обзорная роль; акцепт ИИ — по профилю.
3. Конфликт одновременной правки: существующий `base_version` — из кода 409
   в экран «кто, что, какие поля; взять их / наложить своё / открыть обе»;
   потери правок нет ни в одном исходе.

**Мера В3** — из плана.

## В4. Семантика графа + контракт

Исполняется `ЗАДАНИЕ-ГРАФ-И-ИИ.md` **с поправкой**: Г-структурная часть
(определение/вхождение, дерево, рабочее место) закрыта волной В2 — В4 берёт
остальное: виды связей и эмерджентность, замыкание, свёртка верификации и
несворачиваемая валидация, SatisfactionClaim, порты и соединения (ложатся во
вкладку «интерфейсы» без её перестройки), нормативы и применение с tailoring
(на наполнении Б), показатель в графе параметров, профили И1–И5. Плюс
онтологический контракт: проекция экспорта в RDF и SHACL-проверка в CI по
поставленному контракту.

**Мера В4** — из плана.

## Ловушки

1. **Перезапись акцептованного текста генерацией.** Никогда; только
   предложение рядом. «Текст устарел» — помета, не блокировка.
2. **Печатная форма или рабочее место без эталона.** Угадывание по описанию
   уже давало интерфейс, который переделывали.
3. **Миграция вхождений с фантазией.** Только ×1 по существующим `parent`;
   требования на определениях; массовый перенос требований на вхождения —
   запрещён.
4. **WBS копией дерева состава.** Автосоздание WBS зеркалом узлов —
   возвращение того, от чего уходим; дерево работ строится своё, связи —
   руками и шаблоном.
5. **Права в клиенте.** Кнопку спрятать можно, маршрут обязан отказать сам.
6. **Сессия силами Code.** Подготовка — да, проведение — нет.
7. **Полный текст ГОСТа в библиотеке.** Реквизиты и свои формулировки.
8. **Отчёт волны без её меры.** «CI зелёный» и «экраны открываются» — не
   ответ; мера волны — дословно из плана.
