# Фиксы прогона — пачка 1

## Ф-01 · Порядок дат не держит границу фаз

**Условие приёмки (после шипа 1):** отчёт показал сквозное правило и
тест, но не назвал створку исходного наблюдения владельца. Закрытие
требует: (1) воспроизвести точный сценарий и назвать, где прошло /
что именно наблюдалось; (2) подтвердить или доделать **опору календаря
через границу фаз** (первая веха фазы открывается от последней вехи
предыдущей) — второй пункт Ф-01, в отчёте не упомянут.

Phase A может начинаться раньше конца Pre-A — правило круга 2 было
сформулировано «внутри фазы» (моя формулировка, признаю́), граница фаз
выпала.

**Нужно:** правило порядка — по **сквозной ленте жизненного цикла**:
вся последовательность вех проекта монотонна (…вехи Pre-A < KDP-A ≤
вехи Phase A < KDP-B…). То же одно правило на сервере, тот же текст
отказа с именами точек («SRR не может быть раньше KDP-A»); опора
календаря первой вехи фазы — последняя веха предыдущей. Тест на границу.

## Ф-02 · Коды ограничений: что задумано, что нет

Задумано: **коды стабильны** — на них ссылаются промпты службы («запрет
Р1») и трассировки; дыры в нумерации законны (убранное не переиспользует
код — как у требований). На код — подсказка: «код стабилен, на него
ссылаются промпт и трассировка».

Не задумано — **два префикса**. Появившиеся П1/П2 рядом с Р1…Р7 — зоопарк:
семантика групп (техническое / программное / пусковое) — это **категория
полем**, не буква идентификатора. Привести: один префикс Р- для всех
ограничений проекта; П1/П2 мигрируют в следующие свободные Р-коды с
ре-линком ссылок (их пока мало — дешевле сейчас); категория «пусковое» —
полем.

И проверить «убрать»: ограничения обязаны **отменяться с историей**
(механика Б-02), не удаляться жёстко; отклонение затравочного ограничения —
это след решения, он ценен для точки.

*Попутно по существу: П1/П2 (только российские РН, старт с Восточного) —
ограничения с зубами: Восточный режет достижимые наклонения, и метрика
пусковых партий (Б7) обязана их учитывать при сравнении построений —
проверю связку при разборе итога.*

## Ф-03 · Типы документов — смысловые подсказки из глоссария

При складывании своего файла тип обязан объяснять себя наведением: что
это, что система из него извлечёт, что важно в карточке. Показ — тултипом
на чипе типа + строкой под выбранным (механика подсказок уже общая).

**Источник — глоссарий**, не хардкод клиента: тип документа = запись
глоссария с брифом (один источник, как словарь единиц). Заодно закрыть
«глоссарий недоступен пользователю»: пункт «Справочники» в панели
Библиотеки — глоссарий и единицы просмотром.

Черновики брифов (владельцу на правку):
- **Записка миссии** — постановочный документ заказчика: цели, сроки,
  нормативные ссылки. Служба извлечёт цели и нужды, профили
  стейкхолдеров (полка А2), типовые риски (Б3).
- **Норматив** — стандарт/ГОСТ с обозначением и **редакцией**: пункты
  станут основаниями требований; смена редакции подсветит зависимые.
- **Даташит** — характеристики компонента: выжимка свойств для модели
  аппарата и типовых требований.
- **Справка** — контекстный материал: участвует в промпте службы,
  извлечений не порождает.
- **Прочее** — лежит материалом проекта; служба его не читает, пока не
  переопределён тип.

## Ф-05 · Промпт постановки — из данных, не из общих слов

Найдено владельцем на новом заходе: промпт О2 не подтягивает ничего из
библиотеки — без записки генерация холостая, предупреждение это лишь
признаёт.

1. **Замысел миссии — обязательная мини-форма** (Ш1 дорастает): для
   кого · что делает · где · горизонт — четыре поля или один связный
   абзац. Без замысла кнопка генерации постановки **заблокирована с
   причиной** («нет замысла — генерация даст общие места»), не
   предупреждение мелким шрифтом.
2. **Сборка из библиотеки по классу миссии**: класс «НОО · связь и IoT»
   тянет в промпт типовые сервисы класса, профили стейкхолдеров (А2),
   типовые риски (Б3), автоприменённые нормативы (Б1), термины глоссария
   класса.
3. **Взятые наборы Ш2 — рамкой**: «в проекте 34 типовых требования —
   опираться, не дублировать».
4. **Акцептованный урожай разбора (Д2) — контекстом** «уже принято»:
   цели/нужды/стейкхолдеры из документов, если есть.
5. **Предпросмотр — состав по источникам со счётчиками**: замысел ·
   библиотека класса (N позиций) · материалы (M блоков) · принято (K) ·
   запреты (Р…). Пустой источник — видимая строка «— пусто», общие слова
   вместо данных невозможны по построению.

Мера: на проекте с классом и взятой библиотекой промпт О2 несёт
конкретику полок (позиции считаются в предпросмотре); без замысла —
блокировка с причиной; пакетный канал ПМИ не затронут.

## Ф-08 · Путь документа к ИИ не ведёт за руку

Владелец собрал записку по шаблону — «для ИИ ничего не изменилось»:
блоки в промпт не выбраны (без выбора уходит одно оглавление), замысел
пуст, урожая нет. Три починки:

1. **Умолчание «В промпт» — по типу документа**: постановочные (записка
   миссии) — все разделы включены при загрузке; справка — выключена;
   снятие — осознанное исключение (симметрия правилу чекбоксов Ш2).
2. **Полоса-проводник на карточке постановочного документа**: после
   загрузки — приглашения цепочкой «разобрать → акцептовать урожай →
   собрать замысел → в промпт», каждое ведёт к месту; сделанное гаснет.
   Мёртвых состояний «загрузил и смотри» не остаётся.
3. **Метки источников [И]/[В]/[П] — в разбор**: правило промпта Д2
   дополняется — метка утверждения переносится в поле `source_mark`
   урожая ([П]-цели не путать с внешними фактами); шаблон записки
   узаконивает метки разделом «Обозначения источников».

Мера: загрузка записки по шаблону → разделы в промпте по умолчанию,
полоса ведёт до замысла; [П]-метка цели «1 млн терминалов» видна в
урожае и в карточке цели после акцепта.

## Ф-09 · Библиотека в контуре ИИ: факты и кандидаты, не имена

Владелец: библиотека — хранилище старых знаний, а в генерации новых не
участвует: документы полок плохо разобраны, не в фактологии, не
порождают ограничений и требований. Ф-05 дал промпту имена позиций —
не знание из них.

1. **Разбор Д1–Д3 — и для библиотечной области**: документы полок
   получают канон + карту + урожай тем же конвейером (отпечатки,
   версии); карточка полки показывает «что система знает из этого
   документа» с приглашением доразобрать.
2. **Источник промпта «библиотека класса» отдаёт факты**: выбранные
   блоки канонов — нормы с числами и пунктами («ПП №2216: геопозиция
   не реже 1/30 с», SOLAS V/19 — состав обязанных судов), а не
   перечень кодов. Бюджет токенов — выбором блоков, как у материалов
   (колонка «В промпт» и умолчания по типу работают и на полке).
3. **Норматив порождает кандидатов**: из урожая библиотечного НПА
   система предлагает типовые требования («система должна…»,
   основание — пункт с якорем в канон) и ограничения-кандидаты;
   акцепт — на полку (типовые, LIB) или в проект по классу миссии.
4. **Граница**: полный механизм `normative_document` с редакциями,
   tailoring-применимостью и подсветкой расхождений — пакет
   «Требования как граф» после прогона (принято ранее, не трогаем
   семантику ядра сейчас). Здесь — лёгкий контур: разбор, факты в
   промпт, кандидаты через штатный акцепт.

Мера: промпт О4 несёт пункты ПП №2216 текстом с числами; предложение
требования «геопозиция ОГ ≥ 1/30 с» приходит с основанием-якорем в
канон НПА; для морского сервиса — ограничение-кандидат из SOLAS;
карточка полки НПА показывает урожай, а не только файл.

## Ф-10 · Выгрузка знаний: библиотека работает во внешнем контуре

Владелец: библиотеке нужен выход в внешний ИИ (Claude-проект) — знания

Это канал 1 TZ-AI-001, доведённый до удобства.

1. **«Собрать пакет знаний»** — механизм выгрузки в Орбите: выбранные
   артефакты → набор MD-файлов: 00-инструкция (роль + правила + схемы
   видов пакетов из реестра), 01-замысел, 02-ограничения (Р-коды с
   формулировками), 03-цели·нужды·сервисы, 04-стейкхолдеры,
   05-каноны нормативов, 06-справочник единиц, 07-глоссарий,
   08-каноны материалов. Состав — чекбоксами, каноны уже MD — выгрузка
   почти бесплатна.
2. **Отпечаток знаний**: каждый файл несёт в шапке хеш выгрузки; схема
   ответа обязует вернуть `knowledge_fingerprint`; вставка пакета
   сверяет и предупреждает «знания устарели: выгрузка от …, стенд
   изменился» — защита от рассинхрона контуров.
3. **Инструкция — генерируется из реестра**: правила промптов (11+12)
   и JSON-схемы видов — тем же источником, что у внутреннего контура;
   двух редакций правил не существует.
4. Роли контуров: внутренний [Ж] — автоматика по кнопке; внешний
   Claude-проект — интерактивная работа инженера (серии генераций,
   уточнения диалогом — дёшево). Второй канал, не замена.

Мера: выгрузка проекта «Орбита-IoT» → Claude-проект отвечает пакетом
требований с основаниями-якорями в каноны; вставка принимает пакет и
сверяет отпечаток; правка ограничения на стенде → следующая вставка
старой выгрузки предупреждена.

## Ф-12 · Проводник постановки: система ведёт по цепочке

Владелец: цели и нужды есть, а дальше маршрут не строится — «с пустыми
сервисами надо знать, что идти в Инструменты». Неочевидное знание пути —
дефект, а не свойство инженера.

1. **Полоса-проводник постановки** (паттерн Ф-08.2): замысел → цели →
   нужды → сервисы → требования; сделанное гаснет счётчиком, следующее —
   приглашение с переходом к месту действия: «сервисов нет — собрать из
   нужд →» открывает предложения с преднастроенным видом.
2. **«Следующий шаг» в шапке знает постановку**: пока цепочка не
   пройдена, он ведёт по ней, а не только по операциям фазы.
3. Правило-класс (в общие механики, третьим к мёртвой ссылке и
   самообеспечению): **пустой раздел цепочки — приглашение с переходом**,
   не голый ноль.

Мера: после акцепта нужд экран Постановки и шапка предлагают «сервисы
из нужд →» одним кликом до преднастроенного промпта; нигде на пути
постановки нет состояния «пусто и тихо».

## Ф-13 · Стейкхолдер — сущность проекта

Владелец: нужды неявно связаны со стейкхолдерами, а их в системе нет как
объектов; круг шире потребителей — регуляторы, операторы, учреждаемые
организации.

1. **Вид `stakeholder` в проекте**: имя · роль (заказчик / регулятор /
   оператор / потребитель / партнёр / учреждаемый) · интерес или
   обязанность · масштаб (шт) · происхождение (якоря) · признак
   `establishes`.
2. **Раздел «Стейкхолдеры» в Постановке** — реестр строками, раскрытие
   по паттерну П-А (в очередь переделки).
3. **Связи по регламенту**: нужда → стейкхолдер-носитель (Прил. 4:
   «источник — стейкхолдер или документ-основание»); сервис →
   стейкхолдер-оператор поверх классов A′/B′/C′. Нужда без носителя —
   мягкий разрыв со зрелостью к MCR (критерий 7.1а «согласовано со
   стейкхолдерами» придёт позже на эту же связь).
4. **Маршрут акцепта исправляется**: стейкхолдеры урожая ложатся
   **в проект** объектами; «обобщить в профиль на полку А2» — отдельное
   осознанное действие (библиотека — шаблоны, проект — факты).

**Дополнение владельца (30.08):** роли обязаны покрывать и сторону
поставки — **разработчики и поставщики компонентов** — стейкхолдеры
(связь: поставщик ↔ элемент состава, который он разрабатывает; анкета
Ф-06 этого элемента адресуется ему — стык с заданиями). И главный вид:

5. **Матрица «стейкхолдер × нужды» с покрытием** — экран в Постановке:
   строки — стейкхолдеры группами ролей (заказчики · регуляторы ·
   операторы · потребители · **поставщики** · учреждаемые); по строке —
   его нужды с тройным состоянием: заявлена / покрыта требованием
   (счётчик) / закрыта верификацией. Итог строки — «покрыто M из N»;
   нужда без носителя и носитель без нужд — видимые края матрицы, не
   потери. Колонка «согласовано» (MCR 7.1а) — заготовкой, заполняется
   позже.

Мера: после акцепта урожая — «Стейкхолдеры · 9» с матрицей; перевозчики
ОГ: «покрыто 3 из 4»; поставщик платформы связан с узлом состава и его
анкетой; учреждаемый центр помечен `establishes`.

## Ф-14 · Полки видны и наполняются (библиотека не витрина Ш2)

Владелец: в Библиотеке виден только новый файл; взятое из прошлых
проектов и сами полки — нет; наполнения нет.

1. **Экран полок**: раздел Библиотеки листает области LIB — полка →
   состав (типовые требования, профили А2, риски Б3, шаблоны
   компонентов, нормативы) строками с раскрытием; у документов полки —
   карточка «что система знает» (Ф-09 уже дал для документов —
   распространить на объектные полки).
2. **Канал «обобщить в библиотеку»**: у проектного объекта (стейкхолдер,
   требование, риск, компонент) — действие «обобщить на полку …» с
   очисткой проектной специфики и происхождением «обобщено из PJ-…»;
   права — ведущий СИ; это второй конец контура, Ш2 — первый.
3. Взятое в проект показывает нитку: «взято с полки → N объектов»
   в обе стороны (полка знает, кто её брал; объект знает исток).

Мера: полка типовых требований листается и показывает 34 позиции;
стейкхолдер «Оператор ЭРА-ГЛОНАСС» обобщается в профиль А2 одним
действием со следом; на полке видно «брали: PJ-0001, PJ-0002».

## Ф-15 · Справочники ведутся, не только читаются

Владелец: «не внести не вынести» — а решение справочника единиц прямо
обещало «нужна новая единица — открываем справочник, вставляем».

1. **Правка из UI**: глоссарий и единицы — добавление и правка записей
   на экране «Справочники» (формы по схеме вида; для единиц — размерность,
   канон/ввод/коэффициент, особый тип конверсии); удаление — мягкая
   отмена с историей, как всюду.
2. **Права**: ведение справочников — роль (владелец системы / ведущий
   СИ), реестр прав; правка единицы поднимет отпечатки разборов —
   предупреждение об объёме пересчёта до сохранения.
3. **Вынести**: справочники входят в выгрузку знаний (Ф-10) — уже; плюс
   экспорт полки файлом (MD/JSON) с экрана.

Мера: новая единица «Вт/кг» вводится с экрана и немедленно принимается
границей пакетов; термин глоссария правится, подсказка типа документа
обновляется; попытка правки без роли — отказ с именем права.

*Режим фиксов: копим пачкой, передача — по команде владельца.*
