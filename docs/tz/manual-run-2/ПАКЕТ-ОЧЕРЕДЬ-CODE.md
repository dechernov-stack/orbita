# Пакет-очередь для Code

Одна очередь вместо пяти документов. Каждая позиция ссылается на своё
задание — там подробности; здесь порядок, зависимости и меры. Работа идёт
сверху вниз внутри потока; потоки 1–2 параллельны; поток 3 — по мере
заморозки эталонов (эталоны собирает Claude, владелец даёт снимки и правки
кругов; простоя из-за них быть не должно — потоки 1–2 всегда дают работу).

**Общие правила пакета** (действуют на всё): живой стенд — база не
сбрасывается, выкатка накатом, версия тегом; замечания владельца — два
сорта, две судьбы (`ЗАДАЧА-CODE-КОНВЕЙЕР`); эталоны — `docs/ui/reference2/`,
«по эталону» = «и не сверх эталона»; отчёт позиции — её мерой, не CI.

---

## Поток 1 — стартовый путь проекта (разблокирует живой проход по ПМИ)

**О-1. «Создать проект» — переделка.** По `reference-create-project.html`
(4 состояния, рейка 68 px с подписями — общесистемно).
Источник: `ЗАДАЧА-CODE-КОНВЕЙЕР` §Задача №1. Мера: четыре снимка рядом с
эталоном, поведение — восемь пунктов руками.

**О-2. Библиотека: формы хранения и канал сбора.** Инвентаризация полок →
`INDEX.md`; три формы (объект / фрагмент-пачка / документ-файл); виды
`mission_class`, `stakeholder_profile`, `typical_risk`, `library_fragment`;
`/library/fragments/preview` + запись с происхождением.
Источник: `ЗАДАЧА-CODE-БИБЛИОТЕКА` §0–3. Мера: фрагмент с узла применяется
в другой проект и даёт работающий состав со связями «применяет».

**О-3. Мастер-путь «Начало проекта» целиком.** Сервер (состояние пути,
классы из Б4, применение наборов, сборка профиля из Ш1+Г1) + вёрстка по
`reference-project-start.html` (3 шага + свёрнутые строки).
Источник: `ЗАДАЧА-CODE-БИБЛИОТЕКА` §4, бриф мастер-пути. Зависимость: О-2.
Мера: новый проект проходит Ш1→Ш2→Ш3 до запуска генерации без выхода из
интерфейса; брошенный путь продолжается с середины.

**О-4. «Профили службы» — вёрстка.** По `reference-ai-profiles.html`
(3 состояния; вкладка «Промпт» с атрибуцией источников — серверная сборка
уже есть). Мера: запрет из профиля виден строкой в предпросмотре промпта.

**О-5. Наполнение Pre-A.** Code-часть манифеста (класс, каркасы PBS/WBS,
4 интерфейса, заготовки профилей, глоссарий, чек-листы через извлечение) +
генерация службой А2/Б3 — **всё на акцепт владельцу**, даташиты и аналоги —
ждут его материалов. Источник: `ЗАДАЧА-CODE-БИБЛИОТЕКА` §5. Мера: Ш2
показывает живые полки с фактическими счётчиками.

## Поток 2 — серверные волны, параллельно (вёрстки не требуют)

**О-6. Модель документа** (В1.2–1.3): раздел = авторский текст + вставки;
«текст устарел» пометой; профиль «редактор раздела»; повторная генерация
никогда не перезаписывает акцептованное.
Источник: `ЗАДАНИЕ-ВОЛНЫ-ПОСЛЕ-ПМИ` В1.

**О-7. Структура состава** (В2.1–2.2): определение/вхождение с миграцией
×1; композиция-дерево + рёбра; WBS своей структурой, `cost_estimate` на
WBS; «Сохранить как шаблон» — серверная часть уже в О-2, здесь привязка к
поддереву. Источник: там же, В2. Ловушки миграции — без фантазии.

**О-8. Печать серверно**: выпуск → docx и PDF (титул, разделы, колонтитулы
данными; оформление подтянется вёрсткой О-14 по эталону печатной формы).

## Поток 3 — конвейер экранов (по заморозке эталонов; их собирает Claude, владелец — снимки и правки)

**О-9. Портфель + первая установка** → **О-10. Жизненный цикл** →
**О-11. Готовность к точке** → **О-12. Реестр требований + инспектор** →
**О-13. Рабочее место узла + дерево** (встык с О-7; здесь же кнопка
«Сохранить как шаблон» в интерфейсе) → **О-14. Документ: просмотр +
печатная форма** (встык с О-6/О-8) → **О-15. Предложения ИИ + загрузка
пачкой**. Мера каждого: снимки состояний рядом с эталоном; экран виден на
стенде.

## Поток 4 — после

**О-16. Многопользовательность** (В3: учётки, роли из регламентов, права на
сервере, конфликт-экран). **О-17. Семантика графа + онтологический
контракт** (В4 по `ЗАДАНИЕ-ГРАФ-И-ИИ` с поправкой; ждёт контракта от
Claude).

---

## Сводная мера пакета

1. Владелец проходит по ПМИ переделанный стартовый путь — создание →
   мастер-путь → генерация → акцепт — **без выхода из интерфейса** и без
   встречи со старым дизайном (поток 1).
2. К моменту, когда конвейер дойдёт до О-13 и О-14, серверные О-6–О-8
   готовы — экраны садятся на живую механику, не на заглушки.
3. Отчёт по каждой позиции — её мерой; «сделано» без меры не принимается.
