# Проектная сессия (§6.1) — сценарий и бланк

Повторяет прогон миссии до KDP B **живым инженером**, не участвовавшим в
разработке. Репетиция (`docs/tz/mission-run.md`) показала, что путь проходим
и где он спотыкается; сессия проверяет, проходим ли он **без автора системы
рядом**.

**Кто проводит:** ведущий системный инженер (или системный аналитик), не
участвовавший в разработке ИС. **Где:** стенд `http://localhost:8080`,
**пустая система** (`docker compose down -v && docker compose up -d`).
**Сколько:** 2–4 часа. Подсказок нет; вопрос инженера — находка.

Материал для канала О2–О4 берётся из службы ИИ: профиль AP-0001 уже несёт
запреты Р1–Р9 и глоссарий, промпт собирает служба. Транспорт — тот, что
настроен на стенде (прямой либо закрытый контур).

## Что сделать (по шагам)

1. **Создать проект** на портфеле: имя миссии, фаза Pre-Phase A, шесть точек
   с датами. Проверить: проект создан пустым, без образцов.
2. **Завести профиль службы** (раздел «Инструменты» → «Профили службы») либо
   загрузить готовый пачкой. Убедиться, что в промпте видны запреты проекта.
3. **Постановка → цели и нужды** через службу: вход операции — записка
   миссии; принять пачкой. Посмотреть отчёт фильтра: что снято и по какому
   правилу, в том числе **правилом основания**.
4. **Нужды → сервисы → требования**: довести до **не менее 200 требований**
   через акцепт (не импортом!). Проверить журнал: предложено / снято /
   акцептовано / сколько стоило.
5. **Материал Pre-Phase A**: состав системы, WBS, альтернативы, оценка
   стоимости, ODA, риски, технологии, ConOps — руками либо пачкой.
6. **Комплект Д1–Д9** выпустить на экране «Документы».
7. **Пройти internal_review** с экрана «Готовность к точке».
8. **Замечание MCR**: завести критическое RFA, убедиться, что оно
   **блокирует** точку; закрыть с ответом; довести зрелость; пройти MCR.
9. **KDP-A**: довести зрелость комплекта, пройти; проверить, что проект
   перешёл в Phase A и сменились операции.
10. **Phase A**: входы моделирования, базирование требований пачкой,
    комплект Д1–Д10, **SRR** → **SDR/MDR** → **KDP-B**.

## Бланк (§6.1) — заполняется по ходу

| Что | Целевое | Факт |
| --- | --- | --- |
| Пройденных контрольных точек | 6 из 6 |  |
| Выходов из интерфейса (консоль, правка базы, ручной файл) | 0 |  |
| Случаев, когда система не смогла назвать, что мешает пройти точку | 0 |  |
| Требований в проекте к SRR | не менее 200 |  |
| Обрезанных колонок, кодов перечислений, перекрытий на снимках | 0 |  |
| Мест, где инженер обратился за помощью к разработчику | 0 |  |

## Снимки

По снимку на каждое прохождение точки (6 штук) плюс снимок отчёта фильтра
службы и снимок журнала вызовов — в `docs/tz/sessions/shots/`.

## Что считается провалом сессии

- инженер не дошёл до KDP B без помощи разработчика;
- система отказала, не назвав причину;
- потребовался выход из интерфейса (консоль, база, файл руками);
- к SRR набралось менее 200 требований через акцепт.
