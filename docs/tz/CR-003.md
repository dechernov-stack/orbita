# CR-003. Деревья требований и компонентов, события верификации, валидация

Изменение к контуру требований. Применять вместе с CR-001 и CR-002.
Основание: ADR-019; NASA SP-2016-6105 Rev 2 (разд. 2.4, 5.3, 5.4; прил. D, E).

Изменение вызвано разбором вопроса: как связаны дерево компонентов и дерево
требований, как заполнять V&V и куда прикладывать документ, если сначала он
предварительный расчётный по модели, а потом будет физическое испытание.
Ответ на последний вопрос потребовал пересмотра трёх сущностей сразу.

## Что было упущено

| Упущение | Следствие |
| --- | --- |
| Один блок верификации на требование | Нельзя записать «сначала расчёт по модели, потом испытание» |
| Свидетельство — строка | Нельзя выразить замещение расчёта протоколом и привязку к конфигурации |
| Валидации нет как понятия | Отсутствует вторая матрица; проверка против ConOps негде |
| Деревья не связаны | Потомок требования мог попасть на элемент из чужой ветви |
| Интерфейсные требования на одном элементе | У интерфейса две стороны; ответственность не выражается |
| Свёртка по всем потомкам | Производные требования ошибочно попадают в бюджет родителя |

## Что сделать

1. **События верификации.** Заменить блок `verification` массивом
   `verification_events[]`: метод, фаза, **уровень структуры изделия**,
   вид (`preliminary` / `qualification` / `acceptance` / `certification`),
   подход, средство, условия, критерий, статус, признак `closes`.
2. **Закрытие верификации.** Требование верифицировано только когда успешно
   завершены все закрывающие события. Предварительное событие даёт состояние
   «предварительно подтверждено». Предварительное событие закрывающим быть не может
   (ограничение и в схеме, и в БД).
3. **Квалификация и приёмка.** Квалификация — один раз на версию конструкции,
   приёмка — на экземпляр. Повторная квалификация неизменной конструкции и приёмка
   без указания экземпляра выявляются.
4. **Свидетельство — объект** `EV-NNNN` по новой схеме: вид, зрелость, источник
   (сценарий ИС либо внешний документ), конфигурация, дата, замещение.
   Свидетельство на другой конфигурации помечается неприменимым.
5. **Валидация — объект** `VA-NNNN` по новой схеме: привязка к нужде или сервису
   (не к требованию), ссылка на ConOps, вид продукта (модель / макет / прототип /
   изделие), среда. Строится вторая матрица — валидации.
6. **Согласованность деревьев.** Требование-потомок распределяется на тот же элемент
   либо его потомка; нарушение выявляется отчётом. Спецификация элемента = множество
   распределённых на него требований (представление, не отдельная сущность).
7. **Интерфейсы.** Тип объекта `IF-NNNN` с двумя сторонами; интерфейсное требование
   распределяется на интерфейс.
8. **Вид декомпозиции.** Связь `derive` несёт `derivation_kind`:
   `allocated` — участвует в свёртке бюджета, `derived` — не участвует.
9. Применить миграцию `db/migrations/V005__vv.sql`.

Эталон: `spec/traceability_semantics.py`, 34 проверки.

## Определение готовности

- [ ] все 34 проверки `spec/traceability_semantics.py` воспроизведены в тестах Kotlin
- [ ] требование с предварительным расчётом и запланированным испытанием имеет
      состояние «предварительно подтверждено», а не «верифицировано»
- [ ] протокол испытания замещает предварительный расчёт, цепочка сохраняется
- [ ] свидетельство, полученное на прежней конфигурации, помечается неприменимым
- [ ] требование-потомок на элементе из чужой ветви выявляется отчётом
- [ ] интерфейсное требование на одном элементе отклоняется
- [ ] производное требование не входит в свёртку бюджета родителя
- [ ] валидация с привязкой к требованию отклоняется
- [ ] матрица валидации формируется отдельно от матрицы верификации
- [ ] спецификация элемента собирается запросом, без отдельной сущности

## Ловушки

1. **Верификация ≠ валидация.** Первая — соответствие требованиям, вторая —
   пригодность для задачи пользователя в предполагаемой среде. Разные объекты
   привязки и разные матрицы. Слияние их в одну сущность выглядит экономией,
   но лишает проект ответа на вопрос «то ли мы построили».
2. **Предварительный расчёт не закрывает требование.** Соблазн пометить требование
   верифицированным по результату модели велик именно на ранних фазах, когда
   испытаний ещё нет. Состояние «предварительно подтверждено» существует ровно
   для этого случая.
3. **Свидетельство привязано к конфигурации.** После изменения конструкции протокол
   остаётся достоверным документом, но перестаёт быть свидетельством: он относится
   к другому изделию.
4. **Производное требование — не доля бюджета.** Оно возникает из проектного решения
   и не является частью родительской величины. Включение его в свёртку даёт
   бессмысленное превышение.
5. **Интерфейс — не элемент.** Требование к стыку имеет две стороны ответственности;
   распределение его на один элемент оставляет вторую сторону вне обязательств.
