Рабочее задание для Claude Code. Основание: архитектура разд. 9, пп. 6–7.
Область: `TZ-FLW` (8), замыкание `TZ-BAL-005/006/007` данными моделирования,
`TZ-NET-003/004` (модель коллизий и калибровка) — 13 требований.
Вне области: ИИ-контур (`TZ-AI`), клиент `web/`.

**Смысл шага.** Появляются числа, ради которых строилась система: вероятность
доставки по классам, распределение времени реакции C', узкие места, полный
вектор KPI. После него trade study даёт ответ, а не заготовку.

## 0. Долг перед шагом 4

CR-001…003 применены, решение по `geometry` подтверждено, дефект с `sys.exit`
и NULL-семантика V003 исправлены. Осталось четыре пункта.

### 0.1. Физичные фикстуры Eb/N0
Ваше наблюдение верно: при пороге SNR −20 дБ, полосе 125 кГц и скорости 250 бит/с
Eb/N0 для SF12 равно +7 дБ, а условное `−6,0` в эталоне было нефизичным и могло быть
скопировано в работу. Эталон аппарата в комплекте обновлён: Eb/N0 +6,3 дБ, скорость
250 бит/с, уровни ЭИИМ пересчитаны, добавлена проверка наличия `geometry` в схеме
(34 → 35 проверок). Число по-прежнему приходит из адаптера — в эталоне оно
лишь воспроизведено. Перенести обновлённые значения в тесты Kotlin.

### 0.2. Третий случай NULL-семантики — в V001
Аудит остальных ограничений тем же способом дал ещё одно попадание, в самой старой
миграции:

```sql
CONSTRAINT ai_needs_accept CHECK (
    provenance->>'source' <> 'ai_proposed'
    OR provenance->'ai' ? 'accepted'
)
```

При `source = 'ai_proposed'` и отсутствующем блоке `ai` левый операнд оператора `?`
равен NULL, оператор возвращает NULL, и `FALSE OR NULL` даёт NULL — запись проходит.
То есть **предложение ИИ без признака акцепта сохраняется и попадает в расчётные
выборки**, что прямо нарушает TZ-COM-005 и TZ-AI-004.

Проверено моделированием NULL-распространения, не по догадке. Остальные ограничения
V001 чисты: сравнения там идут по колонкам `NOT NULL` либо через `IS NULL`,
где NULL не возникает.

Исправить отдельной миграцией с `COALESCE(..., false)`; добавить тест на случай
«источник ai_proposed, блока ai нет».

### 0.3. ADR-020 на смену пропагатора
Переход с кеплеровского на аналитический Эйнштейна–Хехлера с EIGEN5C — архитектурное
решение: оно определяет воспроизводимость и точность всей геометрии. Оформить ADR
с основанием (кеплеровский не воспроизводит прецессию ВДУ, ради которой считается
наклонение ССО), следствиями (рост времени предрасчёта; фиксация модели поля
в `input_versions`) и **ограничением**: секунды координации заданы программной
таблицей Bulletin C, GTOD без поправок EOP; указать оценку влияния на геометрию
покрытия и условие пересмотра.

### 0.4. Поправка к числу проверок
В README пакета CR-003 указано 224 — верное число **223**: обновлённый
`spacecraft_semantics` (35 проверок) идёт с этим комплектом, а не с тем.
После применения шага 4 суммарно должно быть **262**.

## 1. Ядро Монте-Карло (`core/flw`)

### 1.1. Гибридная схема — `TZ-FLW-001`
Детерминированная аналитика на ячейку и пролёт (предложенная нагрузка, вероятность
коллизии и ёмкость из адаптера, замыкание бюджета линии), затем розыгрыш только
существенно случайных измерений. Вместо перебора всех терминалов — **выборка
представителей с весами по численности популяции** (ADR-014).
Оценка по представителям обязана быть взвешенной по численности, а не по числу
представителей (эталон: `weighted_estimate`).

### 1.2. Воспроизводимость при параллельности — `TZ-FLW-002`
Счётчиковый ГПСЧ: поток адресуется ключом «зерно × индекс реализации × индекс
сущности», а не последовательным состоянием. Результат не зависит от порядка
выполнения потоков и от числа ядер. Проверяется тестом на разном порядке обхода.

### 1.3. Генерация потоков — `TZ-FLW-003`
Пуассоновские потоки по популяциям; суперпозиция по ячейке; событийный трафик —
модулированный пуассоновский с корреляцией внутри ячейки и региона.
Суточные и сезонные профили применяются к интенсивности (готовы с шага 2).

### 1.4. Повторы и обратная связь нагрузки — `TZ-FLW-004`
Различать предложенную и обслуженную нагрузку; повторы генерируются моделью
и входят в предложенную. Отчёт содержит `offered_msgs`, `carried_msgs`,
`retransmission_ratio`.

**Ключевое свойство, которое обязано воспроизводиться.** До некоторого порога
повторы компенсируют деградацию канала: доставка не меняется, растут только повторы —
качество кажется прежним. За порогом происходит обвал: доставка падает в разы,
а число повторов на доставленное сообщение растёт кратно. Модель, показывающая
плавную деградацию, неверна.

### 1.5. Эфемеридный backoff — `TZ-FLW-005`
После исчерпания попыток на текущем аппарате — ожидание следующего по расписанию.
Обмен «надёжность за хвост задержки»: доставка растёт, хвост удлиняется на интервал
до следующего пролёта. Сокращение интервала (больше КА в плоскости) укорачивает хвост.

### 1.6. Бюджет времени реакции C' — `TZ-FLW-006`
Распределение времени реакции с разложением на семь участков; время решения внешней
системы берётся из профиля и не моделируется. Результат — `P(T ≤ T_треб)`.
Неполный бюджет отклоняется. Сравнение трёх режимов доставки на одном сценарии
обязано давать разные значения: при store-and-forward контур не закрывается.

### 1.7. Карта потоков и узкие места — `TZ-FLW-007`
Загрузка участков «потребители → КА → (ISL) → НС»; узкое место с коэффициентом
загрузки; потери переполнения буфера отдельно от канальных.

### 1.8. Деградированный режим — `TZ-FLW-008`
Доля терминалов с устаревшим альманахом растёт с редкостью пролётов и с редкостью
маяка; потери слепой передачи учитываются отдельной статьёй.

## 2. Замыкание KPI (`core/bal`)

### 2.1. Заполнение вектора — `TZ-BAL-005`, `TZ-BAL-006`
Поля, оставленные пустыми на шаге 3 (метрики классов, revisit, разрывы покрытия),
заполняются результатами моделирования. Спрос-взвешенное качество считается
по зонам обслуживания раздельно по классам.
Контрольный случай сохраняется: при населённой карте спроса построение
с преимуществом только у полюсов не выигрывает у наклонного.

### 2.2. Парето и роза — `TZ-BAL-006`, `TZ-BAL-007`
Фронт «экономика × качество» на полных векторах; данные для розы KPI, широтного
профиля и тепловых карт на трёх горизонтах усреднения.

## 3. Протокол (`core/net`)

### 3.1. Модель коллизий — `TZ-NET-003`
Аналитическая: ALOHA с эффектом захвата и квазиортогональностью режимов.
Максимум чистой ALOHA 0,184 при нагрузке 0,5 — проверяется тестом.
Пошаговая симуляция событий не используется.

### 3.2. Калибровка — `TZ-NET-004`
Эталонные наборы в `spec/reference/` с указанием источника; код GPL-симуляторов
не заимствуется. При отсутствии измерений зафиксировать аналитические свойства
модели как временный источник.

## Ловушки

1. **Плавная деградация — признак неверной модели.** Реальный канал держит качество
   до порога за счёт повторов, а затем обваливается. Модель без обратной связи
   нагрузки покажет плавное снижение и завысит ёмкость.
2. **Выборка по представителям смещает хвосты.** Оценка среднего сходится быстро,
   а P99 задержки — нет. Для показателей класса C' контролировать сходимость
   по числу представителей отдельно.
3. **Обычный ГПСЧ ломает воспроизводимость при параллельности** незаметно:
   тесты на одном ядре проходят, на восьми результат плывёт.
4. **Взвешивание по числу представителей вместо численности** даёт систематическую
   ошибку в пользу малых популяций.
5. **Время решения внешней системы не моделируется.** Это параметр контура заказчика;
   попытка его «уточнить» подменяет исходные данные допущениями.
