# 00. Общие сведения и общесистемные требования

Статус документа: Draft. Источник: Концепция ИС v0.3, разд. 1–4, 7.
Связанные: `TZ-MOD.md`, все модульные разделы.

---

## 1. Назначение и границы

ИС поддерживает фазы Pre-Phase A и Phase A жизненного цикла космической системы (регламенты БП-PPA, БП-PA) с фокусом на выработку требований к элементам КС.

**Вход:** нужды стейкхолдеров, программные цели и ограничения.
**Выход:** базированные требования уровня проекта и системы, спецификации сервисов, архитектурная модель с распределением требований (flow down), матрица верификации, результаты моделирования как обоснование — пакет, эквивалентный содержанию SRR/SDR.
**Вне границ:** детальное проектирование (Phase B+), эксплуатационное ПО наземного сегмента, биллинг, приём реальной телеметрии.

## 2. Пользователи

| Роль | Основные операции |
| --- | --- |
| Ведущий системный инженер | Требования, трассировка, архитектура, базирование |
| Проектант-баллистик | Сценарии группировок, trade studies, критерии оценки |
| Проектант КА | Параметры платформы и ПН, бюджеты, TPM |
| Аналитик сервисов | Популяции потребителей, карта спроса, QoS-профили |
| Руководитель проекта | Статусы, полнота пакета к контрольной точке, отчёты |

## 3. Основной сценарий (мастер)

Ш1 Нужды → Ш2 Сервисы (MOE, QoS-профили) → Ш3 Требования (MOP) → Ш4 Конфигурация и flow down (TPM) → Ш5 Моделирование → Ш6 V&V → Ш7 Пакет передачи.
Шаги допускают возврат и итерации; последовательность фиксирована.

## 4. Требования

### TZ-COM-001. Единая модель как источник истины

```
REQ:        Все сущности ИС (нужды, сервисы, требования, элементы, параметры,
            сценарии, результаты) хранятся в единой связанной модели.
            Документы формируются как представления модели; обратная загрузка
            содержания из документов в модель не допускается.
RATIONALE:  Authoritative source of truth (NASA-HDBK-1004). Исключает расхождение
            документов и модели.
TRACE-UP:   КОНЦ-2
TRACE-DOWN: TZ-MOD-001; TZ-OUT-001
VERIFY:     INSPECTION + тест
ACCEPTANCE:
  - [ ] генерация документа не изменяет модель
  - [ ] повторная генерация из неизменённой модели даёт идентичный результат
  - [ ] отсутствует API-метод импорта содержания документа в модель
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-COM-002. Сквозная двунаправленная трассировка

```
REQ:        ИС должна поддерживать связи по цепочке
            Стейкхолдер → Нужда → Сервис → Требование → Элемент архитектуры →
            Метод V&V → Результат моделирования,
            с навигацией в обе стороны по каждой связи.
RATIONALE:  Цифровая нить; матрицы трассировки Прил. 2 БП-PA.
TRACE-UP:   КОНЦ-2; БП-PA Прил. 2
TRACE-DOWN: TZ-MOD-002; TZ-REQ-003
VERIFY:     TEST
ACCEPTANCE:
  - [ ] для любого объекта цепочки доступны предки и потомки за один запрос
  - [ ] разрыв цепочки (объект без родителя выше Нужды) выявляется отчётом
  - [ ] удаление объекта с потомками блокируется с указанием потомков
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-COM-003. Статусная модель и базирование

```
REQ:        Каждый управляемый объект имеет статус
            Draft → Preliminary → Approved → Baseline.
            Переход в Baseline фиксирует версию; изменение объекта в статусе
            Baseline возможно только через процедуру изменения с созданием
            новой версии и сохранением предыдущей.
RATIONALE:  Регламенты БП-PPA/БП-PA, п. 6; матрица зрелости NPR 7120.5 прил. I.
TRACE-UP:   БП-PA п. 6.1
TRACE-DOWN: TZ-MOD-007; TZ-OUT-003; TZ-REQ-006
VERIFY:     TEST
ACCEPTANCE:
  - [ ] прямое изменение Baseline-объекта отклоняется с ошибкой
  - [ ] процедура изменения создаёт новую версию, предыдущая доступна для чтения
  - [ ] история переходов статусов сохраняется с автором и датой
  - [ ] отчёт «зрелость пакета к контрольной точке» показывает объекты, не достигшие требуемого статуса
STATUS:     Draft
OWNER:      руководитель проекта
```

### TZ-COM-004. Производительность Монте-Карло (сквозной критерий)

```
REQ:        Прогон эталонного сценария (группировка ≤ 60 КА, карта спроса
            ≤ 20 000 активных ячеек, горизонт 24 ч, 1000 реализаций
            Монте-Карло) выполняется не дольше 5 минут на эталонной
            конфигурации оборудования, определённой в tests/reference/.
RATIONALE:  Trade studies требуют перебора вариантов; медленный расчёт
            обесценивает многопараметрическую оценку (Концепция, разд. 7 п. 4).
TRACE-UP:   КОНЦ-5.7; КОНЦ-7.4; ADR-013; ADR-014
TRACE-DOWN: TZ-BAL-002; TZ-FLW-001; TZ-NET-003
VERIFY:     TEST (регрессия производительности в CI)
ACCEPTANCE:
  - [ ] эталонный сценарий и конфигурация зафиксированы в tests/reference/
  - [ ] замер времени выполняется автоматически при каждой сборке
  - [ ] превышение бюджета времени останавливает сборку
  - [ ] события видимости берутся из предрасчитанной баллистики, не пересчитываются в цикле Монте-Карло
STATUS:     Draft
OWNER:      ведущий системный инженер
```

OWNER:      ведущий системный инженер

  - [ ] повторный прогон даёт побитово идентичный результат
  - [ ] изменение входного параметра помечает зависимые результаты устаревшими

### TZ-COM-007. Контракты между модулями

```
REQ:        Обмен данными между модулями выполняется только через структуры,

            внутренним структурам другого модуля не допускается.

TRACE-DOWN: TZ-MOD-001; TZ-MOD-002; TZ-MOD-005; TZ-NET-001
VERIFY:     INSPECTION + TEST
ACCEPTANCE:
  - [ ] каждый межмодульный обмен имеет схему в schemas/
  - [ ] данные валидируются по схеме на границе модуля
  - [ ] нарушение схемы даёт явную ошибку с указанием поля
STATUS:     Draft
OWNER:      ведущий системный инженер
```
