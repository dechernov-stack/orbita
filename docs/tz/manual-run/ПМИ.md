# ПМИ ручного прогона «Орбиты» до KDP B

Программа и методика испытаний **проектной сессии** (§6.1 задания «прогон до
KDP B»): инженер, не участвовавший в разработке, проводит миссию от создания
проекта до решения KDP B целиком через интерфейс.

Репетиция агентом (`docs/tz/mission-run.md`) показала проходимость пути и
поймала пять дефектов. Заданием она не является: до заполнения таблиц §4
живой сессией задание не закрыто.

## 1. Назначение и условия

**Что проверяется:** проходит ли инженер шесть контрольных точек без автора
системы рядом и без выхода из интерфейса.

**Кто проводит:** ведущий системный инженер (или системный аналитик), не
участвовавший в разработке ИС. Ведущий испытаний не подсказывает; вопрос
инженера — находка, она записывается в журнал.

**Где:** стенд `http://localhost:8080`, поднятый штатным workflow
оркестратора `deploy_orbita_local` (сборка из `origin/main`), **пустая
система** — без демо-профиля и без затравки `data/pilot`.

**Сколько:** 2–4 часа. Прерывать можно: состояние живёт в базе стенда.

**Материал:** пакеты из `packets/` (см. §2) — их даёт ведущий испытаний по
ходу шагов. Инженер не сочиняет 200 требований руками и не пишет промпты:
промпт собирает служба, материал вносится каналом ИИ и загрузкой пачкой.

## 2. Подготовка (делает Code до сессии)

* Пустой стенд штатным workflow, без демо и затравки; тег версии в журнал.
* Пакеты материала отдельными файлами в `docs/tz/manual-run/packets/`:
  `01-цели.json`, `02-нужды.json`, `03-сервисы.json`, `04-требования.json`
  (формат канала ИИ), `05-входы-моделирования.json` (формат импорта).
* Эта ПМИ — в `docs/tz/manual-run/ПМИ.md`.

Отчёт о подготовке — `подготовка.md` рядом: версия стенда, чем собраны
пакеты, счёт объектов в каждом.

## 3. Ход испытаний

Шаги идут подряд; после каждого инженер заполняет строку журнала (§5).

| № | Шаг | Где | Что должно получиться |
| --- | --- | --- | --- |
| 1 | Представиться и создать проект: имя миссии, фаза Pre-Phase A, шесть точек с датами | Портфель → «Создать проект» | проект создан **пустым**, в шапке — ближайшая точка с числом незакрытого |
| 2 | Завести профиль службы ИИ: «Загрузить пачкой» → файл `00-профили-службы.json` (либо создать формой) | Инструменты → «Профили службы» | профиль виден в реестре; в промпте службы появляются запреты проекта |
| 3 | Цели миссии: собрать промпт службой, внести `01-цели.json`, принять пачкой | Инструменты → «Служба ИИ» | отчёт фильтра показывает предложено/показано/снято; принятое легло в реестр |
| 4 | Нужды: `02-нужды.json` тем же путём | там же | нужды в реестре «Цели и нужды» |
| 5 | Сервисы: `03-сервисы.json` | там же | сервисы с QoS-профилями |
| 6 | Требования: `04-требования.json` (несколько пачек) | там же | **не менее 200 требований** в реестре |
| 7 | Материал Pre-Phase A: файл `06-материал-pre-phase-a.json` | любой реестр → «Загрузить пачкой», либо Инструменты → «Загрузка пачкой» | объекты в своих реестрах |
| 8 | Выпустить комплект Д1–Д9 | Контроль → «Документы» | девять выпусков, слепки зафиксированы |
| 9 | Пройти **внутренний обзор** | Контроль → «Готовность к точке» | точка пройдена, зафиксировано решение |
| 10 | Завести критическое замечание обзора MCR (файл `07-замечания-обзора.json` кнопкой «Загрузить пачкой» либо формой) и убедиться, что оно **блокирует** точку; закрыть с ответом | Контроль → «Замечания обзора» | до закрытия точка не проходится, причина названа поимённо |
| 11 | Довести зрелость к MCR и пройти **MCR**. Один объект — кнопкой инспектора («Утвердить предварительно» → «Утвердить» → «Базировать»); все видимые — шапкой реестра: выбрать статус и нажать «Перевести все видимые» | реестры + «Готовность к точке» | точка пройдена; непереведённые названы поимённо с причиной |
| 12 | Довести зрелость и пройти **KDP-A** | там же | проект перешёл в **Phase A**, сменились операции и комплект |
| 13 | Внести `05-входы-моделирования.json` | Модели → «Входы моделирования» → «Загрузить пачкой» | сценарий и входы в реестре |
| 14 | Базировать требования пачкой | Требования → «Базировать все» | отказов 0; несбазированные названы поимённо |
| 15 | Выпустить комплект Д1–Д10 и пройти **SRR** | Документы + Готовность | точка пройдена |
| 16 | Довести архитектуру и пройти **SDR/MDR** | реестры + Готовность | точка пройдена |
| 17 | Довести комплект и пройти **KDP-B** | там же | точка пройдена, вехи исчерпаны |

На каждом прохождении точки — снимок экрана в `shots/` (`1-internal_review.png`
… `6-KDP-B.png`), плюс снимок отчёта фильтра службы и снимок журнала вызовов.

## 4. Меры (заполняется по ходу)

| Что | Целевое | Факт |
| --- | --- | --- |
| Пройденных контрольных точек | 6 из 6 |  |
| Выходов из интерфейса (консоль, правка базы, ручной файл) | 0 |  |
| Случаев, когда система не смогла назвать, что мешает пройти точку | 0 |  |
| Требований в проекте к SRR | не менее 200 |  |
| Обрезанных колонок, кодов перечислений, перекрытий на снимках | 0 |  |
| Обращений к разработчику за помощью | 0 |  |

Журнал службы ИИ (Инструменты → «Служба ИИ», нижняя таблица) — переписать
в отчёт: вызовов, предложено, снято (в том числе правилом основания),
акцептовано, токенов.

## 5. Форма журнала сессии

| Шаг | Ожидал | Получил | Выход из интерфейса |
| --- | --- | --- | --- |
|  |  |  |  |

Строка заполняется и тогда, когда всё прошло гладко: «получил ожидаемое» —
такой же результат испытаний, как и находка.

## 6. Критерии

**Испытание пройдено**, когда пройдены все шесть точек, обе таблицы §4
заполнены и в них нет выходов из интерфейса, немых отказов и обращений к
разработчику, а требований к SRR не менее двухсот.

**Испытание не пройдено**, если выполнено хотя бы одно:

* инженер не дошёл до KDP B без помощи разработчика;
* система отказала, не назвав причину;
* потребовался выход из интерфейса;
* к SRR набралось менее 200 требований;
* на снимках видны обрезанные колонки, коды перечислений вместо подписей
  или перекрытия панелей.

## 7. Отчётность

Заполненная ПМИ (копия этого файла с заполненными таблицами) — рядом, под
именем `прогон-<дата>.md`; снимки — в `shots/`. Отчёт подписывается
инженером, проводившим испытание, и ведущим испытаний.
