# Шаг 17. Блок C: отсутствующая часть модели

Блок C из разбора состояния (STEP-16 §7): ConOps, технологии и TRL, анализ
альтернатив, документы со статусной моделью, проект как объект. Это работа
над **моделью**, а не над отображением: в `CoreType` не было ни одного из
этих видов, хотя модель уже ссылалась на них в пустоту — `conops_ref`
валидации был строкой в никуда, документ «Концепция применения» — заготовкой
с вечно пустыми разделами, реестр ворот жил конфигурацией без проекта.

Принимается по тому же правилу, что Шаг 16: **путь данных** — хранимый
объект → маршрут → экран, на пустой базе через интерфейс. Проверки
`ci/wiring.py` и `ci/literals.py` остаются блокирующими.

---

## C1. ConOps: сценарии применения

Вид `conops` (`CO-NNNN`, схема `core/conops`): операционный сценарий с видом
(номинальный / нештатный / аварийный / завершение), фазой миссии,
действующими лицами, потоком шагов и критерием успеха; `traces_up` — нужды,
которые сценарий разворачивает (связь trace по ADR-027).

Связность, ради которой вид заводится:

- `conops_ref` валидации перестаёт быть строкой в никуда: при приёме
  валидации ссылка резолвится, валидация против несуществующего сценария —
  отказ с причиной;
- раздел 4 «Операционные сценарии» документа «Концепция применения»
  наполняется из хранимых объектов; раздел 7 «Валидационные положения» — из
  валидаций, привязанных к сценариям. Пустой раздел остаётся с разрывом;
- экран — вкладка «ConOps» на Ш1: сценарии рядом с нуждами, из которых они
  растут.

## C2. Технологии и TRL

Вид `technology` (`TL-NNNN`, схема `core/technology`): технология с текущим
и требуемым TRL, контрольной точкой, к которой требуемый уровень должен быть
достигнут, планом дозревания (шаги с датами) и привязкой к компонентам.

- Отчёт зрелости (`/reports/maturity`) получает раздел «технологии ниже
  требуемого TRL к точке» — и это блокирующая причина наравне со статусами;
- экран — вкладка «Технологии» на Ш4 (конфигурация): технология — свойство
  выбранной конфигурации, не отчёта.

## C3. Анализ альтернатив: решения

Вид `decision` (`DN-NNNN`, схема `core/decision`): запись trade study —
вопрос, альтернативы, критерии, выбранная альтернатива с обоснованием,
статус open → decided. Решение со статусом decided без выбранной
альтернативы или без обоснования не принимается: запись «решили, но не
скажем что» хуже отсутствия записи.

Экран — вкладка «Решения» на Ш5 рядом со сравнением вариантов: сравнение
даёт числа, решение фиксирует выбор.

## C4. Проект как объект

Вид `project` (`PJ-NNNN`, схема `core/project`): имя, фаза жизненного цикла
(Pre-Phase A / Phase A), контрольные точки с плановыми датами и состоянием.
Реестр ворот остаётся источником планок статусов; проект говорит, **какие**
точки и **когда** — готовность к точке читает перечень точек из проекта, а
не из зашитого списка в клиенте.

## C5. Статусная модель документов

Вид `document_issue` (`DI-NNNN`, схема `core/document-issue`): выпуск
документа — код шаблона, слепок содержимого (digest), дата выпуска
аргументом (воспроизводимость), статус draft → issued → approved.

- Выпуск фиксирует digest: расхождение текущей генерации с выпущенной
  видно сравнением слепков — «документ устарел» становится фактом, а не
  ощущением;
- approve без issued — отказ; повторный выпуск — новый объект, история
  остаётся;
- экран «Документы» (Ш7) получает кнопку «Выпустить» и список выпусков
  со статусами и признаком расхождения.

## Порядок и приёмка

Порции C1 → C2 → C5 → C3 → C4, каждая: миграция/схема → эталон →
ядро+тесты → маршрут → экран → прогон на стенде. Идентификаторы новых видов
входят в общий шаблон `id_pattern` (миграция V009) и в регулярку
`ci/literals.py`.

Приёмка — на пустой базе через интерфейс: завести сценарий ConOps от нужды,
валидацию против него; технологию с TRL ниже требуемого — увидеть её
блокером зрелости; выпустить документ и увидеть расхождение после правки
модели; зафиксировать решение по сравнению; завести проект и увидеть его
точки на экране готовности.
