### TZ-FLW-001. Ядро Монте-Карло и бюджет времени

```
REQ:        Модуль выполняет прогон сценария методом Монте-Карло на
            собственном аналитико-имитационном ядре, используя
            предрасчитанные события видимости и параметры канала из адаптера
            протокола. Бюджет времени по TZ-COM-004 соблюдается.
RATIONALE:  Trade studies требуют перебора вариантов; полная
            дискретно-событийная симуляция несовместима с этим бюджетом.
TRACE-UP:   TZ-BAL-002; TZ-COM-004; TZ-MOD-002; TZ-NET-003
TRACE-DOWN: TZ-FLW-002
MOP:        эталонный прогон ≤ 5 мин (TZ-COM-004)
VERIFY:     TEST
ACCEPTANCE:
  - [ ] прогон эталонного сценария укладывается в бюджет времени
  - [ ] геометрия не пересчитывается внутри цикла реализаций
  - [ ] замер времени выполняется в CI и останавливает сборку при превышении
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-002. Воспроизводимость прогона

```

TRACE-DOWN: TZ-REQ-007
VERIFY:     TEST
ACCEPTANCE:
  - [ ] два прогона с одним зерном дают идентичные результаты
  - [ ] параллельное исполнение не нарушает воспроизводимость
  - [ ] результат несёт ссылки на версии входов и модулей
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-003. Генерация потоков

```
REQ:        Трафик генерируется по профилям популяций: пуассоновские потоки
            для регулярной активности, модулированный пуассоновский поток
            для событийного трафика. Поддерживается корреляция событий
            в пределах ячейки и региона.
RATIONALE:  Коррелированные события (шторм, авария сети) — худший случай
            для ёмкости и для контура управления C'; независимые потоки
            этот случай скрывают.

TRACE-DOWN: TZ-FLW-004; TZ-FLW-006
VERIFY:     TEST
ACCEPTANCE:
  - [ ] суперпозиция потоков терминалов ячейки даёт пуассоновский поток ячейки
  - [ ] всплеск событий воспроизводится с заданными множителем и длительностью
  - [ ] суточные и сезонные профили применяются к интенсивности
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-004. Повторы и обратная связь нагрузки

```
REQ:        Модель различает предложенную (offered) и обслуженную (carried)
            нагрузку. Повторы классов B'/A' генерируются моделью и входят
            в предложенную нагрузку; результат содержит долю повторов.
RATIONALE:  При деградации канала повторы растут лавинообразно — типовой
            механизм коллапса ёмкости; без обратной связи оценки ёмкости
            завышены.
TRACE-UP:   Потребители-2.2; TZ-FLW-003; TZ-NET-003; TZ-NET-005
TRACE-DOWN: TZ-FLW-005
VERIFY:     TEST
ACCEPTANCE:
  - [ ] повторы не входят в исходную интенсивность популяции
  - [ ] отчёт содержит offered_msgs, carried_msgs и retransmission_ratio
  - [ ] контрольный случай: при снижении ёмкости канала доля повторов растёт нелинейно
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-005. Эфемеридный backoff класса B'

```
REQ:        После исчерпания попыток на текущем аппарате терминал класса B'
            прекращает передачи и ожидает следующего аппарата по расписанию
            пролётов. Ожидание учитывается в распределении задержки.
RATIONALE:  Р6/ADR-006: обмен «надёжность за задержку»; связывает качество
            сервиса B' с числом аппаратов в плоскости.
TRACE-UP:   ADR-006; TZ-FLW-004
TRACE-DOWN: TZ-FLW-007
VERIFY:     TEST
ACCEPTANCE:
  - [ ] после N попыток передачи на текущем пролёте прекращаются
  - [ ] хвост распределения задержки удлиняется на интервал до следующего пролёта
  - [ ] контрольный случай: увеличение числа КА в плоскости сокращает хвост задержки B'
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-006. Бюджет времени реакции класса C'

```
REQ:        Для класса C' вычисляется распределение времени реакции
            с разложением на компоненты: обнаружение, ожидание восходящего
            канала, транзит вверх, решение внешней системы, ожидание
            нисходящего канала, транзит вниз, доставка команды, исполнение.
            Результат — вероятность уложиться в требуемое время.
RATIONALE:  Показатель решает вопрос необходимости ISL: при
            store-and-forward ожидание может составлять десятки минут.
TRACE-UP:   Потребители-2.3; TZ-FLW-003; TZ-REQ-007
TRACE-DOWN: TZ-REQ-007
MOP:        P(T ≤ T_треб) по классу C'
VERIFY:     TEST
ACCEPTANCE:
  - [ ] результат содержит все компоненты бюджета раздельно
  - [ ] время решения внешней системы берётся из профиля и не моделируется
  - [ ] сравнение трёх режимов доставки на одном сценарии даёт разные P(T ≤ T_треб)
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-007. Карта потоков и узкие места

```
REQ:        Модуль строит карту потоков «потребители → КА → (ISL) → НС →
            потребитель данных» с загрузкой участков и указанием узких мест:
            абонентская линия, бортовой буфер, ISL, фидерная линия,
            наземная станция.
RATIONALE:  Узкое место определяет, какое требование к системе является
            определяющим; без карты этот вывод делается на глаз.
TRACE-UP:   КОНЦ-5.7; TZ-FLW-005; TZ-KA-008
TRACE-DOWN: TZ-OUT-002
VERIFY:     TEST
ACCEPTANCE:
  - [ ] загрузка каждого участка рассчитывается и сравнивается с ёмкостью
  - [ ] потери от переполнения буфера учитываются отдельно от канальных
  - [ ] узкие места перечисляются с коэффициентом загрузки
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-FLW-008. Деградированный режим терминалов

```
REQ:        Терминалы с устаревшим альманахом переходят в деградированный
            режим (слепая передача с пониженной интенсивностью). Потери
            в этом режиме учитываются отдельно; доля терминалов в
            деградированном режиме выводится в результате.
RATIONALE:  Р5/ADR-005: возраст альманаха связывает качество сервиса
            с частотой пролётов — в редко посещаемой ячейке риск деградации
            выше, и это второй штрафной механизм разрывов покрытия.
TRACE-UP:   ADR-005; TZ-USR-002
TRACE-DOWN: TZ-BAL-005
VERIFY:     TEST
ACCEPTANCE:
  - [ ] период приёма маяка сопоставляется с расписанием пролётов ячейки
  - [ ] потери слепой передачи учитываются отдельной статьёй
  - [ ] контрольный случай: снижение частоты маяка увеличивает долю деградированных терминалов
STATUS:     Draft
OWNER:      ведущий системный инженер
```
