# ТЗ: DocPilot — прототип механики документов (StrictDoc + git + ИИ-рендеринг + Typst)

Версия 1.0 · 06.09.2026 · для исполнения Codex · один репозиторий, один запуск

## 1. Цель и рамки

Проверить вживую, что документ проекта можно вести **как структуру**
(разделы + элементы с авторством), считать его **полноту** по шаблону,
**базировать** версией в git с дифом по узлам, порождать **читаемый
текст ИИ только из элементов**, рецензировать его правками изложения и
**печатать** PDF/docx — и как это выглядит для инженера. Демо-предмет —
**ConOps насосной станции** (тот же пример, что в ReqPilot/FlowPilot).

**В рамках (P0):** один документ (ConOps, 4 раздела) по шаблону с
ожиданиями полноты; шесть видов элементов; генерация `.sdoc` по
пользовательской грамматике; git-репозиторий документов с базированием
тегом и дифом по узлам; ИИ-рендеринг (или честный stub без ключа) с
привязкой каждого числа к элементу; рецензия патчами изложения; печать
`html2pdf` и Typst; экспорт `.sdoc` проходит `strictdoc check`.

**Вне рамок:** редактор прозы, авторизация, наш код «Орбиты», реестр
требований (только минимальные сущности для примера), Flowable.

## 2. Пользователи и роли

| Логин | Роль | Что делает |
|---|---|---|
| `si` | ведущий СИ | наполняет структуру, базирует |
| `eng` | инженер | добавляет элементы, тезисы |
| `rev` | рецензент | правит изложение, принимает рендеринг |

Переключение — селектором в шапке, без пароля.

## 3. Стек

- Python 3.12, **FastAPI**; **StrictDoc** (Apache-2.0, `pip install
  strictdoc`) как библиотека и CLI; **GitPython** (BSD) поверх git;
  **Typst** CLI (Apache-2.0) в образе; **diff-match-patch** (Apache-2.0);
  `python-docx` (MIT) для docx (P1); SQLite (файл) для домена.
- ИИ: провайдер через переменные окружения (`ANTHROPIC_API_KEY` или
  `OPENAI_API_KEY`); **без ключа — детерминированный stub-рендерер**,
  который собирает текст из тезисов и фактов шаблонными фразами и
  помечает вывод «STUB» в метаданных; тесты идут на stub.
- UI: React 18 + TypeScript + Vite, панели и таблицы в стиле ReqPilot.
- Лицензии зависимостей: Apache/MIT/BSD; GPL — нет (Pandoc не нужен).
- Запуск: `docker compose up` → `http://localhost:8080`.

## 4. Модель домена (SQLite; истина — база, `.sdoc` — выход)

| Сущность | Поля | Правила |
|---|---|---|
| `project` | id, name, git_path | репозиторий документов создаётся при создании проекта |
| `fact` | id, subject, predicate, value_num?, value_unit?, value_text?, source_doc, source_anchor, mark (`И`/`В`/`П`), disposition (`noted`/`adopted`/`assumed`), author, at | без источника — 400; число без единицы — 400 |
| `entity` | id, kind (`stakeholder`/`scenario`/`mode`/`requirement`), code, title, fields(json), version | версия растёт при изменении fields |
| `document` | id, project_id, template_code, code, title, owner, status (`Draft`/`Baseline`) | — |
| `section` | id, document_id, no, title, order | из шаблона |
| **`element`** | id, section_id, kind (`fact_ref`/`entity_ref`/`statement`/`query`/`figure`/`table`), ref_id?, ref_version?, text?, supports(json)?, query(json)?, author, at, order, version | `statement` с числом в тексте без `supports` — 400 |
| `baseline` | id, document_id, name, git_tag, items(json: [{element_id, version}, {fact/entity id, version}]), by, at | неизменяем |
| `rendering` | id, document_id, baseline_id?, sections(json: [{no, text, element_links}]), engine (`llm`/`stub`), model?, prompt_fingerprint, patches(json), reviewer?, accepted_at? | текст, содержащий число вне элементов, — 422 |
| `release` | id, rendering_id, files(json: pdf_html2pdf, pdf_typst, docx?), authors(json), released_by, at | авторы — из элементов baseline + рецензент |

## 5. Шаблон и грамматика

### 5.1 Шаблон `conops-pump.template.json`

Разделы: §1 Назначение и контекст · §2 Режимы и состояния · §3
Операционные сценарии · §4 Среда и ограничения. Для каждого —
`expects` по ступеням `MCR` и `SRR`, например:

```
"§3": {"MCR": [{"kind":"entity_ref","entity_kind":"scenario","min":1}],
        "SRR": [{"kind":"entity_ref","entity_kind":"scenario","min":3},
                {"kind":"statement","min":1}]}
```

и `style`: указания рендерингу («деловая проза, без маркетинга, каждое
число со ссылкой на элемент»).

### 5.2 Грамматика `orbita.sgra` (StrictDoc `[GRAMMAR]`)

Типы узлов — наши элементы; поля с `REQUIRED: True` там, где модель
требует:

```
- TAG: FACT_REF     FIELDS: MID · REF · REF_VERSION · DISPOSITION · AUTHOR · AT
- TAG: ENTITY_REF   FIELDS: MID · REF · KIND · REF_VERSION · AUTHOR · AT
- TAG: STATEMENT    FIELDS: MID · STATEMENT · SUPPORTS(multi) · AUTHOR · AT
- TAG: QUERY        FIELDS: MID · KIND · FILTER · COLUMNS · AUTHOR
- TAG: FIGURE       FIELDS: MID · REF · CAPTION · AUTHOR
- TAG: TABLE        FIELDS: MID · QUERY · COLUMNS · AUTHOR
```

Рендеринг — отдельный документ `rendered/ConOps.sdoc` с грамматикой:
`- TAG: TEXT FIELDS: MID · STATEMENT · SOURCE_ELEMENTS(multi) · ENGINE ·
FINGERPRINT`. `ENABLE_MID: True` в обоих.

### 5.3 Раскладка репозитория документов проекта (git)

```
docs/ConOps.sdoc            # структура — порождается из базы
docs/rendered/ConOps.sdoc   # рендеринг — порождается ИИ/stub, патчи рецензента
docs/typst/conops.typ       # шаблон печати (данными: титул, подписи)
```

## 6. Функциональные требования

**FR-01** Документ создаётся из шаблона: разделы, ожидания, стиль.
**FR-02** Элементы добавляются формами по виду; `fact_ref`/`entity_ref`
выбираются пикером из базы (не вводом id); `statement` — текст 1–3
предложения + пикер опор.
**FR-03** **Полнота** раздела и документа считается по `expects`
текущей ступени (переключатель MCR/SRR в шапке); невыполненное —
строкой «нужно: ещё 2 сценария → добавить».
**FR-04** Экспорт структуры в `docs/ConOps.sdoc` по грамматике при
каждом изменении (или по кнопке); `strictdoc check` — зелёный; ручная
правка файла запрещена (сторож сравнивает с базой).
**FR-05** **Базирование**: имя (`MCR`, `SRR`…) → запись `baseline` +
коммит + тег `BL-<имя>-<n>` в git; неизменяемо; список базирований.
**FR-06** **Диф** между двумя базированиями — по узлам (MID):
добавлено · изменено (поле в поле) · удалено, с авторами из git;
используется `strictdoc export --generate-diff-git` или собственный
diff по MID, если штатный неудобен (записать в README, что выбрано).
**FR-07** **Рендеринг**: по базированию (или предпросмотр) — для
каждого раздела ИИ/stub получает **только** элементы раздела и стиль
шаблона; ответ — текст с маркерами `[MID]` у утверждений; система
проверяет: каждое число в тексте присутствует в данных указанных
элементов, иначе 422 с перечнем нарушений.
**FR-08** Рендеринг сохраняется в `docs/rendered/ConOps.sdoc`
(узлы TEXT с SOURCE_ELEMENTS) и коммитится; повторный рендеринг того
же базирования — новая версия с дифом текстов.
**FR-09** **Рецензия**: `rev` правит текст раздела; система считает
патч (diff-match-patch) и **отклоняет правку сути**: изменённые числа,
добавленные числа без элемента, удалённые ссылки на элементы → 422 с
причиной; правки изложения сохраняются патчами с автором; «Принять
рендеринг» — статус accepted.
**FR-10** **Печать**: `strictdoc export --formats=html2pdf` → PDF;
**Typst** по `conops.typ` (титул: проект, документ, базирование,
авторы из элементов, блок подписей) → PDF; docx (P1) через
python-docx; все файлы — в `release`.
**FR-11** Авторы выпуска вычисляются из элементов базирования +
рецензент + выпустивший; на титуле — они.
**FR-12** Изменение факта/сущности после базирования → у документа
помета «опора изменилась» с перечнем элементов; следующий рендеринг
показывает диф текста рядом с дифом элементов.
**FR-13** Ошибки — JSON `{code, message, reasons[]}`; в UI нет
`undefined`.
**FR-14** (P1) Экспорт ReqIF из `entity(kind=requirement)` через
StrictDoc — чтобы показать «требования и документ из одного
инструмента».

## 7. Экраны (5)

1. **Документ** — разделы слева (полнота у каждого: «3/4 к MCR»),
   элементы раздела списком с автором и датой, кнопки добавить по виду;
   переключатель ступени.
2. **Элемент** — формы: факт (пикер), сущность (пикер), тезис (текст +
   опоры), запрос (вид + фильтр), фигура/таблица.
3. **Базирования** — список тегов; выбрать два → диф по узлам; кнопка
   «Базировать» с именем.
4. **Рендеринг** — текст по разделам с подсветкой источников при
   наведении (`[MID]` → элемент); «Сгенерировать» (LLM/stub —
   индикатор движка); режим рецензии; «Принять».
5. **Печать** — html2pdf / Typst / docx; список выпусков с авторами.

## 8. API (минимум)

`POST /api/projects` · `POST /api/documents` · `GET /api/documents/{id}`
(структура + полнота) · CRUD `elements` · `GET /api/documents/{id}/sdoc`
· `POST …/baseline` · `GET …/baselines` · `GET …/diff?from=&to=` ·
`POST …/render?baseline=` · `PUT …/renderings/{id}/section/{no}`
(рецензия) · `POST …/renderings/{id}/accept` · `POST …/release` ·
CRUD `facts`, `entities`.

## 9. Нефункциональные

**NFR-01** Один запуск; README с туром на 10 минут и явным указанием,
работает ли LLM или stub.
**NFR-02** `.sdoc`-файлы — только выход; сторож: расхождение файла с
базой → ошибка при следующем экспорте.
**NFR-03** Цвет не единственный носитель состояния.
**NFR-04** Тесты: pytest на FR-03/05/06/07/09/11 (на stub); один
Playwright-сценарий.
**NFR-05** Логи: базирование (тег, хеш), рендеринг (движок, отпечаток),
отказы 422 с причинами.

## 10. Демо-данные (`seed`)

Проект «Насосная станция · концепция»; факты (8): «три станции
района» [И]; «поток 120 м³/ч» [В, паспорт насоса]; «давление 6 бар» [В];
«время реакции на аварию ≤ 120 с» [П]; «диспетчерская — одна смена
из двух операторов» [И]; …; сущности: 3 стейкхолдера, 3 режима
(штатный · авария по давлению · обслуживание), 2 сценария (штатный
пуск · авария), 3 требования; элементы: §1 — 3 (замысел тезисом,
2 стейкхолдера), §2 — 3 режима, §3 — 2 сценария + тезис, §4 — 2 факта +
запрос требований. Полнота к MCR — 4/4; к SRR — §3 неполон (нужен
третий сценарий) — нарочно.

## 12. Что мы хотим узнать (ответы в README)

1. Насколько естественно грамматика StrictDoc выразила наши элементы;
   где пришлось изворачиваться (multi-ссылки, версии опор).
2. Пригоден ли штатный diff-git StrictDoc или нужен свой по MID.
3. Практичен ли сторож «число без элемента» на реальном тексте —
   ложные срабатывания (даты, номера разделов).
4. Сколько стоил Typst-шаблон против html2pdf; что лучше для пакета
   точки.
5. Где UI пришлось дописывать поверх формата; сколько строк своего
   кода против конфигурации.

## 14. Чего не делать

Свободный редактор текста структуры; правка `.sdoc` руками; хранение
истины в файлах; «зелёная» полнота без ожиданий; рендеринг из чего-либо
кроме элементов; молчаливые отказы; GPL-зависимости.
