# Решение: что берём из reqpilot-workbench — StrictDoc-канал, impact, связи с обоснованием

Правило владельца из постановки workbench, принимаем как своё:
*«Человечество уже написало достаточно универсальных платформ, которые
умеют всё, кроме работы»* — Орбита не повторяет RMS, а делает работу
поверх зрелых инструментов.

## Общая идея — верная; где граница переноса

Workbench: требования канонически в `.sdoc` (StrictDoc), архитектура —
в Capella read-only, межсистемные связи — явным `trace-links.yaml`
с обоснованием; собственный ReqIF запрещён; ценность — граф, матрицы,
impact, навигация.

**Что не переносим буквально**: файлы как единственный источник
истины. У Орбиты источник — битемпоральная БД: история, статусы с
основанием, изоляция проектов, акцепт-контур ИИ, живые матрицы и
готовность, многопользовательность. Заменять это файлами — потерять
половину системы.

**Что переносим**: StrictDoc как **канал обмена и публикации**, а не
хранилище. Это заменяет прежний план «контейнер `reqif` на библиотеке
reqif» более сильным: StrictDoc (Apache-2.0, 0.29.0) даёт ReqIF, HTML,
PDF, XLSX, JSON и валидацию грамматики штатно — **своего конвертера
не пишем вовсе**.

## 1. Контейнер `strictdoc` вместо `reqif`

- **Экспорт**: реестр проекта → `.sdoc` по **нашей грамматике** (`.sgra`):
  поля регламента (Прил. 2/4: ID, формулировка, категория, источник,
  обоснование, метод верификации, статус, версия, владелец) **плюс
  показатель** — `MOP_OP`, `MOP_VALUE`, `MOP_UNIT` (у workbench этого
  нет — тот же пробел, что у пилота). Связи — как RELATIONS грамматики
  с ролями из наших видов (Refines/Derives + `ConflictsWith`).
- Затем `strictdoc export` — ReqIF/HTML/PDF/XLSX штатно; **автономный
  HTML-отчёт** из прошлого решения тоже закрывается этим.
- **Импорт**: `.sdoc` или ReqIF (через StrictDoc) → кандидаты в акцепт
  с происхождением; чужие поля — в `foreign_attributes`.
- **Снимок базирования = `.sdoc`-файл** в репозитории проекта: диф
  между двумя базированиями — `git diff`, читаемый человеком. Это
  дешёвая и честная история для внешних ревью.
- Идентификаторы: наши коды → UID, внутренние id → MID (устойчивость
  при переименовании — паттерн workbench).

## 2. Impact-анализ — вид графа

По образцу `services/impact.py`: фокус на требовании → соседи
**группами по природе** (родители · дети · зависимые · верифицирующие
события · носители-узлы · интерфейсы · документы, где вставлено ·
**битые ссылки**), глубина 1–4, кратчайшие пути, защита от циклов.
Рисуется тем же `@xyflow/react`, что трассировка и схема потока.
Это прямой ответ на вопрос записки «Требования как граф»: *кого заденет
изменение* — ответ до изменения, а не помета после.

## 3. Связи требований — с обоснованием

`trace-links.yaml` у workbench несёт `relation` + `rationale` +
даты. У нас у `derives_from` есть вид, но нет обоснования; у связей
задач фазы `note` уже обязателен. Уравнять: **обоснование у связи
требований** — поле, мягко обязательное при базировании (разрыв
«связь без обоснования» к SRR).

## 4. Четыре матрицы workbench против наших

требования×тесты · требования×функции · требования×компоненты ·
функции×компоненты. У нас: верификация (методы шире тестов),
трассировка, покрытие нужд, зрелость. Не хватает **требования ×
узлы состава** как отдельного экрана (сейчас — группировка реестра
«по носителю») и **функции × компоненты** — появится с логической
декомпозицией (записка «граф», §6). Записать горизонтом.

## 5. Capella — горизонт с готовым паттерном

Не сейчас. Но паттерн связи с внешней моделью брать: **идентичность по
UUID, имя — снимком только для показа, обновление явное**, backend в
чужую модель не пишет. Пригодится для любого внешнего MBSE-инструмента,
не только Capella.

## 6. Дисциплина честности — подтверждена извне

«REAL CAPELLA TEST: NOT EXECUTED», fixture-режим помечен явно, кэши и
индексы объявлены производными — та же культура, что наши «витрины
запрещены» и «прокси помечен». Приятно видеть её в чужой постановке.

# Правка шипа 4 задачи «Три пакета» (после итога, по команде)

1. Контейнер **`strictdoc`** (Apache-2.0): наша грамматика с MOP;
   экспорт `.sdoc` → штатные ReqIF/HTML/PDF/XLSX; импорт → кандидаты;
   снимок базирования `.sdoc` в репозитории проекта. Меры: экспорт
   валиден `strictdoc check`; ReqIF парсится `xml.etree`; повторный
   экспорт неизменённого — тот же файл; round-trip экспорт→импорт→
   экспорт совпадает; чужие поля не теряются.
2. **Impact-вид** на `@xyflow/react` + `@dagrejs/dagre`: группы по
   природе, глубина 1–4, битые ссылки отдельной группой. Мера: для
   базированного требования impact называет узел состава, событие
   верификации и документ со вставкой; изменение показателя без
   импакта — невозможно (кнопка «что заденет» рядом с правкой).
3. **`conflicts_with`** + обоснование у связей требований + разрыв
   «связь без обоснования» к SRR.
4. Сторожа: своей графики поверх библиотек нет; собственного
   ReqIF-конвертера нет (грепом по репозиторию «REQ-IF» в нашем коде — 0).
