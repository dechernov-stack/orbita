# Разбор FlowPilot (dechernov-stack/flowpilot) — 06.09.2026

## Что есть

Spring Boot + Flowable 7: `pre-a.cmmn.xml` (8 plan items, 30 ссылок
sentry, S1–S6, M1/M2, автозавершение stage), `review.bpmn20.xml`,
`mcr-readiness.dmn` с **горячей перезагрузкой через API** (порог ворот
меняется без пересборки — AC-07 выполнен по существу). Ворота —
`GateEvaluator` (читает домен, возвращает критерии с причинами) +
`StageGateTaskListener`, который **на `complete` бросает исключение с
перечнем причин** — движок отказывает, не UI. 15 тестов, покрыты AC-01…05,
08, 09, 10; e2e есть. Объём: ~4,4 тыс. строк приложения против ~600
строк моделей.

## Что доказано для Орбиты

1. **CMMN выражает нашу фазу**: сцены = stages, точки = milestones,
   ворота = sentry, параллель S5/S6, повторное открытие сцены по
   замечанию (repetition rule) — работает, не костыль в сути.
2. **Граница движка подтверждена практикой**: исполнитель сам пришёл к
   тому, что доменные условия нельзя держать в переменных процесса —
   нужен внешний оценщик, явная переоценка после транзакции домена и
   непробиваемая проверка на завершении. Это ровно границы 1 и 3
   `РЕШЕНИЕ-ДВИЖОК-ПРОЦЕССА`: «оценщик критериев» = наша готовность.
3. **Ворота — данные**: DMN редеплоится без пересборки; матрица
   зрелости к точкам может жить таблицей.
4. **Что движок даёт и чего нет** — сформулировано честно: жизненный
   цикл, история, задачи, назначения, сроки, транзакционное завершение,
   сохранение — бесплатно; объяснения ворот, покрытие доменных связей,
   «что делать дальше», единая лента — **наши**. Движок сокращает
   самописный конечный автомат и даёт durability, но не сокращает UI.

## Что не доказано / слабые места

1. **AC-06 (перезапуск без потери состояния) не автоматизирован** —
   это главное обещание движка; добавить тест с рестартом контейнера.
2. **AC-07 не в тестах** — редеплой DMN проверен туром, не автоматом.
3. **Повторное открытие сцены из дочернего BPMN — через технические
   флаги** (`reopenS5Requested` + сброс). Работает, но это запах: в
   продуктовой модели сигнал «замечание → сцена» должен идти **CMMN
   event listener'ом** (user/generic event), не флагами в переменных.
4. **S2–S4 в UI — витрина seed-данных**, интерактив только S5/S6/обзор/
   MCR; полный CRUD есть в REST. Для оценки usability первых сцен этого
   мало — а именно первые четыре сцены мы хотели прожить.
5. **P1 не сделан**: генератор `phase-template.json → CMMN` — а это
   единственный кусок, который связывает наши шаблоны фаз (полка) с
   движком. Без него «процесс — данные» остаётся лозунгом.
6. **Лицензии**: исполнитель нашёл противоречие в моём ТЗ — H2 под
   MPL/EPL, а профиль H2 был обязательным. Правильно поймано.
   Решение: H2 — только тестовый профиль с явным waiver, в продукт не
   идёт; или Testcontainers-Postgres.
7. **Гигиена репозитория**: в корне остались артефакты первой
   итерации (Next.js-макет: `app/`, `drizzle/`, `next.config.ts`) рядом
   с настоящим прототипом. Разнести или удалить.

## Решения

- **Flowable принят** как движок процесса Орбиты v2 — с границами из
  решения и с уроком про event listener'ы вместо флагов.
- **Пилот 2 (короткий)**: AC-06/AC-07 автоматом; генератор
  `TemplateToCmmn` из `phase-template.json` (наш формат шаблона фазы —
  сцены, условия, назначения, порядок, связи FS/SS/FF/INPUT);
  замечание → сцена через event listener; S2–S4 интерактивно.
  Мера: смена порядка сцен в JSON меняет поведение без правки XML;
  рестарт — состояние то же.
- В Орбите: `GateEvaluator` = существующие проверки готовности за одной
  точкой входа; `phase_template` полки → CMMN генератором; статусы сцен
  — из движка (`PhaseWork` умирает как счётчик).

## Что оставить как есть

Архитектурный паттерн «оценщик + переоценка + listener на complete» —
переносим дословно. DMN для критериев точек — переносим. UI-проекция
«CMMN + домен» вместо сырого engine REST — переносим как принцип.
