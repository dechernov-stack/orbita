# ТЗ: FlowPilot — прототип ведения фазы на Flowable (CMMN + BPMN + DMN)

Версия 1.0 · 05.09.2026 · для исполнения Codex · один репозиторий, один запуск

## 1. Цель и рамки

Проверить вживую, что движок Flowable может **вести** фазу инженерного
проекта: открывать сцены по условиям на данных, держать ворота, адресовать
шаги людям, отмечать точки — и как это выглядит для пользователя.
Прототип, не продукт: минимум экранов, никакого дизайна сверх читаемости,
демо-предмет — концептуальное исследование **насосной станции** (тот же
пример, что в ReqPilot).

**В рамках (P0):** один Case (фаза) с 6 сценами, 2 точками, воротами по
данным, человеческими шагами для трёх пользователей, цепочкой обзора на
BPMN, критериями точки на DMN; веб-интерфейс на 5 экранов; сохранение
состояния между перезапусками.

**Вне рамок:** авторизация с паролями, LLM, Гант, дизайн-система, наш код
«Орбиты», редактор моделей (P1 — только генератор из JSON).

## 2. Пользователи и роли

| Логин | Роль | Что делает |
|---|---|---|
| `rp` | руководитель проекта · DA | принимает замысел, фиксирует точки |
| `si` | ведущий системный инженер | стейкхолдеры, цели, ConOps, требования |
| `eng` | инженер | исполняет шаги, назначенные ему |

Переключение пользователя — селектором в шапке, без пароля (режим стенда).
Все действия в движке и в домене записываются от имени текущего пользователя.

## 3. Стек

- Java 17, **Spring Boot 3**, **Flowable 7.x** (`flowable-spring-boot-starter`,
  CMMN + BPMN + DMN engines, Apache-2.0); Postgres в `docker compose`
  (профиль по умолчанию) или H2-файл (`--spring.profiles.active=h2`).
- REST API (Spring Web), OpenAPI (springdoc).
- UI: React 18 + TypeScript + Vite, без UI-библиотек (обычные панели и
  таблицы, как в ReqPilot); один `styles.css`.
- Лицензии всех зависимостей — Apache-2.0 / MIT / BSD; GPL/EPL запрещены.
- Один запуск: `docker compose up` → `http://localhost:8080`.

## 4. Модель домена (таблицы приложения, **не** движка)

Домен хранится в таблицах приложения; движок хранит только состояние
процесса; case file items — ссылки на объекты домена по id.

| Сущность | Поля | Правила |
|---|---|---|
| `project` | id, name, phase (`PRE_A`), case_instance_id | одна фаза = один case |
| `intent` | project_id, for_whom, what, where, horizon, status (`draft`/`accepted`), accepted_by, accepted_at | принять может только `rp` |
| `stakeholder` | id, project_id, name, role, interest | — |
| `need` | id, project_id, stakeholder_id (**обязательно**), statement, qos_class (`A`/`B`/`C`) | нужда без стейкхолдера не создаётся (400) |
| `goal` | id, project_id, statement, measure_value, measure_unit, year | без показателя и года — 400 |
| `goal_need` | goal_id, need_id | цель покрывает нужды |
| `conops` | project_id, status (`none`/`draft`), text | — |
| `scenario` | id, project_id, name, steps (text) | сценарии ConOps |
| `requirement` | id, project_id, code, title, statement, measure_value, measure_unit, carrier (`SYSTEM`/`PUMP_SEGMENT`/`CONTROL_SEGMENT`), verification (`test`/`analysis`/`demo`/`inspection`), status (`draft`) | носитель обязателен (400) |
| `requirement_goal` | requirement_id, goal_id | требование покрывает цели |
| `review_finding` | id, project_id, text, returns_to_stage, status (`open`/`closed`) | замечания обзора |
| `audit` | who, when, what, object | журнал домена |

## 5. Модель процесса (CMMN + BPMN + DMN)

### 5.1 Case «Pre-A · насосная станция» (CMMN) — файл `pre-a.cmmn.xml`

| Элемент | Имя | Вход (entry sentry) | Выход (exit sentry / условие завершения) |
|---|---|---|---|
| Stage S1 | Открыть проект | старт case | project создан (автоматически) |
| Stage S2 | Замысел | S1 завершён | `intent.status == accepted` |
| Stage S3 | Стейкхолдеры и нужды | S2 завершён | `stakeholders ≥ 3 ∧ каждый имеет ≥ 1 нужду` |
| Stage S4 | Цели и показатели | S3 завершён | `каждая нужда покрыта ≥ 1 целью` |
| Milestone M1 | Внутренний обзор | S2, S3, S4 завершены | — |
| Stage S5 | Draft ConOps | M1 достигнут | `conops.status == draft ∧ scenarios ≥ 1` |
| Stage S6 | Требования уровня проекта | M1 достигнут (**параллельно S5**) | `каждая цель покрыта ≥ 1 требованием ∧ у всех требований есть carrier` |
| Process Task P1 | Обзор и MCR (BPMN, п. 5.2) | S5 и S6 завершены | процесс завершён решением |
| Milestone M2 | MCR пройден | P1 завершён с решением `approve` | — |

Внутри каждого stage — **Human Task** с назначением: S2 → `rp`;
S3, S4, S5, S6 → `si` (с возможностью переназначить на `eng`); срок задачи =
плановая дата ближайшей точки (поле проекта, редактируется `rp`).

Условия sentry вычисляются **Java-делегатом «оценщик критериев»**
(`GateEvaluator`), который читает домен и возвращает список
`{criterion, satisfied, reason}`; sentry использует `satisfied`, UI —
`reason`. Переоценка — вызовом `evaluateCriteria` после каждой записи в
домен (P0) и по таймеру раз в минуту (страховка).

### 5.2 Процесс «Обзор и MCR» (BPMN) — файл `review.bpmn20.xml`

`старт → [User Task «Внутренний обзор» · si] → шлюз «есть замечания?»
→ да: [User Task «Устранить замечания» · si] → назад к обзору
→ нет: [Business Rule Task «Готовность MCR» · DMN] → шлюз «готов?»
→ нет: [User Task «Закрыть блокирующее» · si] → назад к правилу
→ да: [User Task «Решение DA» · rp: approve / return] → конец`.

### 5.3 Решение «Готовность MCR» (DMN) — файл `mcr-readiness.dmn`

Таблица с входами (считает `GateEvaluator`): `intentAccepted`,
`stakeholdersWithNeeds`, `needsCovered`, `conopsDraft`, `scenarios`,
`goalsCovered`, `requirementsWithoutCarrier`, `openFindings` — выход:
`ready` (bool) и `blockers` (строки-причины). Таблица редактируется в
XML без перекомпиляции; изменение порогов меняет поведение ворот (AC-07).

### 5.4 P1 — модель фазы из данных

`phase-template.json` (сцены, условия, назначения, порядок) →
генератор `TemplateToCmmn` → `pre-a.cmmn.xml`. Приёмка: сгенерированный
XML эквивалентен ручному по поведению (тот же прогон AC-01…AC-08).

## 6. Функциональные требования

**FR-01** Создание проекта запускает case; экран «Фаза» показывает 6
сцен и 2 точки с состояниями из движка (`available` / `active` /
`completed` / `disabled`).
**FR-02** Сцена недоступна, пока не выполнены её условия входа —
**отказ даёт движок**, а не UI; UI лишь показывает причины.
**FR-03** У каждой сцены — панель «условия выхода»: список критериев
✓/☐ с причинами (из `GateEvaluator`), обновляется после каждой записи.
**FR-04** Каждый stage создаёт human task назначенному пользователю;
экран «Мои задачи» показывает задачи текущего пользователя с
дедлайном, просроченные помечены; задачу можно переназначить (`si` → `eng`).
**FR-05** Завершение задачи/стейджа — только когда условия выхода
выполнены; иначе кнопка недоступна с причиной (и сервер отказывает).
**FR-06** S5 и S6 активны одновременно после M1 (параллельность).
**FR-07** Процесс обзора (BPMN) запускается движком после S5+S6;
замечание с `returns_to_stage` переоткрывает соответствующий stage
(повторная активация в CMMN) и после закрытия замечания stage
завершается снова.
**FR-08** Фиксация MCR (`approve`) доступна только `rp` и только при
`ready == true` от DMN; попытка иначе — отказ сервера с перечнем
`blockers`.
**FR-09** Плановые даты точек редактирует `rp`; изменение даты
пересчитывает дедлайны открытых задач (timer/due date).
**FR-10** Экран «История»: журнал движка (кто, когда, что: stage/task/
milestone) и журнал домена — одной лентой по времени.
**FR-11** Экран «Модель»: отрисовка CMMN-диаграммы текущего состояния
(P1, `cmmn-js` от bpmn.io, MIT) с подсветкой активных stages.
**FR-12** Перезапуск приложения не теряет состояние case, задач и
таймеров (AC-06).
**FR-13** Экран «Требования» в стиле ReqPilot: таблица из 6 колонок
(код · заголовок · формулировка · показатель · носитель · статус),
карточка раскрывается **вниз** под строкой.
**FR-14** Все отказы сервера — JSON `{code, message, reasons[]}` с
человеческим текстом; в UI нет `undefined`/`null`.
**FR-15** (P1) `phase-template.json` → генератор → CMMN; смена порядка
сцен в JSON меняет поведение без правки XML.

## 7. Экраны (5)

1. **Фаза** — лента сцен S1–S6 и точек M1/M2 сверху (состояния цветом
   *и* текстом), ниже — карточка выбранной сцены: «зачем», условия
   входа/выхода с причинами, задача и исполнитель, кнопка «открыть сцену».
2. **Сцена** — форма артефакта сцены (замысел / стейкхолдеры+нужды / цели /
   ConOps+сценарии / требования) + панель условий выхода справа + кнопка
   «Завершить сцену» (активна только при ✓ всех).
3. **Мои задачи** — список задач текущего пользователя: сцена, срок,
   просрочка, переназначить, открыть.
4. **Обзор и MCR** — состояние BPMN-процесса, замечания (добавить,
   закрыть), результат DMN с блокерами, «Зафиксировать MCR» (только `rp`,
   только при `ready`).
5. **История** (+ P1 «Модель» с диаграммой).

Шапка: проект · текущая сцена · ближайшая точка с датой · пользователь.

## 8. API (минимум)

`POST /api/projects` · `GET /api/projects/{id}/phase` (сцены, точки,
условия) · `PUT /api/projects/{id}/intent` · `POST …/intent/accept` ·
CRUD `stakeholders`, `needs`, `goals`, `scenarios`, `requirements`,
`findings` · `POST …/stages/{key}/complete` · `GET /api/tasks?user=` ·
`POST /api/tasks/{id}/complete|reassign` · `POST …/mcr/decide` ·
`GET …/history` · `GET …/gates` (результат `GateEvaluator` и DMN).

## 9. Нефункциональные

**NFR-01** Один запуск `docker compose up`; README с туром на 10 минут.
**NFR-02** Домен и движок — раздельные таблицы; в таблицах Flowable нет
полей домена (проверяется тестом).
**NFR-03** Модели процесса — файлы в `src/main/resources/processes/`,
автодеплой при старте.
**NFR-04** Цвет не единственный носитель состояния (текст рядом).
**NFR-05** Логи движка на INFO: активация/завершение stage, задачи,
переоценка sentry с результатом.
**NFR-06** Тесты: Flowable test harness (`CmmnRule`/Spring test) для
AC-01…AC-08; Playwright — один сквозной сценарий.

## 10. Демо-данные (`seed.sql` / `/api/demo/seed`)

Проект «Насосная станция · концепция»; замысел: «для водоканала ·
автоматизированный контроль и управление насосной группой · три
станции района · 2028»; стейкхолдеры: водоканал (заказчик), диспетчер
(оператор), эксплуатационная служба, регулятор безопасности;
6 нужд (по классам A/B/C); 5 целей с показателями (например,
«время реакции на аварию ≤ 120 с к 2028»); ConOps: 2 сценария
(«штатный пуск», «авария по давлению»); 7 требований, у одного
намеренно нет носителя, одна цель намеренно не покрыта — чтобы ворота
S6 были видны сработавшими.

## 11. Приёмочные сценарии

| AC | Сценарий | Ожидание |
|---|---|---|
| AC-01 | Создать проект; открыть S3 при непринятом замысле | S3 `disabled`, причина «замысел не принят» — от движка |
| AC-02 | `rp` принимает замысел | S2 завершён, S3 `active`, задача у `si` |
| AC-03 | В S3 два стейкхолдера, у одного нет нужд; «Завершить» | отказ с двумя причинами; добавить третьего и нужды → завершено |
| AC-04 | После S4 — M1 достигнут, S5 и S6 `active` одновременно | параллельность |
| AC-05 | В S6 требование без носителя; завершить | отказ «требование без носителя: RQ-…»; исправить → завершено |
| AC-06 | Перезапустить контейнер api | состояние, задачи, сроки те же |
| AC-07 | Изменить в DMN порог `stakeholdersWithNeeds ≥ 3` на `≥ 5` | готовность MCR — `blocked` с причиной без перекомпиляции |
| AC-08 | `eng` пытается зафиксировать MCR; затем `rp` при открытом блокере; затем `rp` при `ready` | отказ по роли; отказ с блокерами; успех, M2 достигнут |
| AC-09 | Замечание обзора с возвратом в S5; закрыть | S5 переоткрыт и завершён снова, обзор продолжился |
| AC-10 | Сдвинуть дату M1 на неделю | дедлайны задач S2–S4 сдвинулись |
| AC-11 (P1) | Сгенерировать CMMN из JSON, поменять порядок S5/S6 | поведение соответствует JSON |

## 12. Что мы хотим узнать (в README после сборки — ответы исполнителя)

1. Насколько естественно CMMN выражает «сцена открывается по условию на
   данных»; что пришлось обходить.
2. Как выглядит переоценка sentry при частых записях — задержки, лишние
   активации.
3. Повторная активация stage по замечанию — штатно или костыль.
4. Что движок даёт бесплатно: история, таймеры, назначение, дедлайны — и
   чего нет (например, «кто ждёт кого»).
5. Читаемость для пользователя: видит ли он, почему сцена закрыта и что
   сделать; где UI пришлось дописывать поверх движка.
6. Размер: строк кода приложения против конфигурации моделей.

## 14. Чего не делать

Свой движок состояний поверх Flowable; хранение домена в переменных
процесса; авторизацию; стилизацию сверх читаемости; «зелёные» ворота
без реальной проверки данных; молчаливые отказы.
