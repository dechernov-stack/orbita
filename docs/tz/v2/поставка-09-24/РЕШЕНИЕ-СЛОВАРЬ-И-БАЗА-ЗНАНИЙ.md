# Словарь — ядро. Локальная база знаний вместо промпта

## Почему промпт не держит

Промпт — это подстановка: всё, что модель должна знать, кладётся в
контекст каждого вызова. С ростом дельты (система · взаимодействие ·
ЖЦ · словарь) это сотни строк, которые модель читает по диагонали, а
мы правим в десяти местах. «Разлетимся» — точное слово. Знание должно
**лежать в базе и извлекаться по запросу**, а промпт — оставаться
коротким: задача, срез, ссылки.

## 1. Словарь — сущность первого порядка

Каждый термин — запись, а не строка в глоссарии:

| Поле | Смысл |
|---|---|
| каноническое имя | одно; всё остальное — синонимы |
| синонимы и варианты | кириллица/латиница, аббревиатуры, склонения, «как пишут в документах» («Минтранс», «Минтранс России», «Министерство транспорта РФ») |
| класс | понятие СИ · сторона · узел системы · стык · функция · документ · процесс/сцена · метка · единица |
| определение наше | одна-три строки |
| отличие от общепринятого | если есть — в чём; если нет — пусто (модель знает общее) |
| источник | стандарт (NPR 7123.1, ГОСТ ISO 15288, ECSS) · регламент · устав · полка · решение владельца |
| где используется | виды, сцены, документы |
| статус | принят · кандидат · устарел |
| связи | шире/уже (род–вид), часть–целое, «см. также» |

Словарь **связывает все истины**: код узла `OBC-SW` и «ПО управления
КА», роль `customer` и «заказчик», сцена 3 и «стейкхолдеры и нужды» —
одна запись, разные написания. Это и есть то, чего у модели нет.

## 2. Как словарь формируется — три источника, один порядок

1. **Сид** — из того, что уже есть: глоссарий СИ (41), кросс-терминология
   (27), типы документов, коды узлов и стыков из полок, роли, сцены,
   метки, единицы. Собирается генератором из истин, определения
   правятся рукой один раз.
2. **Привязка при чтении** (linking): всё, что модель извлекла из
   документа, система **обязана привязать к словарю** — сторону к
   термину-стороне, узел к коду, роль к роли. Не привязалось — термин
   становится **кандидатом** в словарь с цитатой; человек принимает
   (это и есть «аккуратно формировать»).
3. **Решения владельца**: принятое отличающееся значение — запись со
   статусом «принят» и источником «решение».

Дедупликация сторон, узлов, документов идёт **через словарь**, а не
через порог семантической близости: «Ространснадзор» и «Федеральная
служба по надзору в сфере транспорта» — одна запись.

## 3. База знаний — что в ней и как ищется

| Хранилище | Что | Как ищется |
|---|---|---|
| **реестр (Postgres)** | сущности, связи, полки, сцены, зрелости — вся структура | точно: по коду, по связям, по сцене (это уже есть) |
| **словарь** | термины с синонимами | точно по синониму + по смыслу (вектор) |
| **текстовый индекс** | блоки канонов документов, пункты нормативов, факты-цитаты, уроки наследия, результаты исследований, определения | **гибридно**: полнотекст + вектор, с фильтрами по проекту, роли документа, рангу, сцене |

Техника — без нового сервиса: **pgvector** в той же базе, эмбеддинги
блоков и терминов, гибридная выборка (BM25 + вектор) с фильтрами. На
наших объёмах (тысячи блоков на проект) этого достаточно; отдельная
векторная БД — лишний контур.

Чего **не** индексируем векторно: структуру системы и связи — они
ищутся точно, вектор их только размоет.

## 4. Как модель этим пользуется — инструменты, не подстановка

Модель получает короткий промпт (задача, сцена, призма, ссылки на
принятое) и **инструменты**:

- `term(name)` — каноническое имя, определение, синонимы, класс;
- `node(code)` / `interface(code)` — узел или стык с параметрами и
  связями;
- `facts(topic | subject, filters)` — факты по теме с цитатами и рангами;
- `clauses(norm, topic)` — пункты норматива по теме;
- `scene(key)` — что ожидается на сцене, условия выхода, зрелость;
- `similar(text, class)` — ближайшие термины/факты/сущности (вектор).

Срезы дельты по сценам (из прошлого решения) остаются, но становятся
**правилами выборки**, а не текстом в промпте: сцена 8 разрешает
`node`/`interface` как носители и подаёт реестр связей; сцена 3 —
сегменты и сервисы. Модель тянет то, что ей нужно, и цитирует, откуда
взяла.

## 5. Что даёт

- одно именование во всех контурах: чтение, синтез, сверка, документы,
  требования — через словарь;
- промпт короткий и стабильный, правка знания — в базе;
- «не разлетимся»: новый термин не проходит мимо — кандидат в словарь;
- перенос между проектами — словарь класса миссии и его база едут
  вместе с полками;
- честность — каждое утверждение модели трассируется к блоку индекса.

## 6. Порядок (без спешки)

1. **Словарь как сущность и сид** — схема, генератор из истин, экран
   словаря с кандидатами. Первым, потому что всё остальное на нём.
2. **Привязка при чтении** — извлечённое линкуется к словарю,
   несвязанное — кандидатами; дедупликация через словарь.
3. **Индекс**: pgvector, блоки канонов + термины + пункты нормативов +
   факты; гибридный поиск с фильтрами.
4. **Инструменты для модели** и переход контуров чтения/синтеза с
   подстановки на выборку.
5. Только потом — нить и ПМИ.

## 7. Что решить владельцу

- Эмбеддинги: локальная модель на стенде или API провайдера (у нас
  ключ уже есть; локальная — без внешних вызовов, но нужен ресурс).
- Словарь класса миссии — общий для всех проектов НОО-IoT или свой у
  каждого проекта с наследованием (я бы: класс — общий, проект —
  дельта поверх).
- Кто хозяин словаря в проекте — ведущий СИ (принимает кандидатов) или
  владелец системы.
