# План развития «Орбиты» — ТЗ продукта, этапы, контрольные точки

17.09.2026. Баллистическое моделирование — внешняя подсистема
владельца, подключается через API (§8); в план не входит.

## 1. Назначение и границы

**Что.** Рабочая среда системного инженера, которая **ведёт** команду
через Формулирование космической миссии (Pre-A → Phase A → вход в
Phase B): постановка из документов, состав и поведение системы,
требования с трассировкой, подтверждение расчётами, программа,
документы-снимки, точки с экспертизами, обмен с MBSE-инструментами.

**Для кого.** Ведущий (генконструктор, РП, DA) — решает и поручает;
специалист — делает своё мероприятие; внешний контур — исследует и
рецензирует.

**Чего нет.** Собственной баллистики (API), Phase B+ кроме полки
шаблонов, изготовления и эксплуатации, свободного текстового
редактора документов, самописных графики и движка процесса.

## 2. Картина продукта — что он держит

Девять областей картины мира (`КАРТИНА-МИРА-ПРОЕКТА`) и восемь
сквозных цепочек — это и есть ТЗ содержания. Механизмы, которые их
держат:

| Механизм | Что делает | Истина |
|---|---|---|
| **Движок процесса** (Flowable) | сцены, мероприятия, точки, критерии, зрелости, решения — фаза ведёт, ворота держат на сервере | шаблон фазы, регламент, Романов |
| **Знания** | документ (роль · ранг) → факты с цитатами → предложения → сущности с основаниями; словарь; база знаний; сверка; исследование; применимость | картина мира, словарь |
| **Постановка и система** | стороны · нужды · цели · сервисы · ограничения; PBS с параметрами и лестницей зрелости; стыки; функции · обмены · цепочки · режимы | полки, схемы |
| **Требования** | уровни, носители, EARS, связи с обоснованием и `suspect`, базовые линии по классам, TRL-шлюз, верификация | модель требований |
| **Подтверждение** | модели с верификацией, прогоны с версиями, свёртки с резервами против рамок, ODA; баллистика — API | шаблон моделей |
| **Программа** | WBS с парами, оценки диапазоном, пакеты созревания, риски со сроком-точкой, план | полка WBS |
| **Документы** | структура из элементов, полнота к ступени, базирование тегом, рендер только из элементов, рецензия патчами, печать | шаблоны документов |
| **Обмен** | `.sdoc`/ReqIF через StrictDoc, Capella на чтение по UUID, PVMT, выгрузка картины внешнему контуру, пакет точки | контракт Capella |
| **Интерфейс** | два входа (Мостик · Моя работа), поверхность процесса, плотность по роли, массовый приём, реестр требований, карточки | дизайн-направление |

## 3. Состояние на 17.09

**Есть и работает** (14 модулей v2, CI зелёный, 216): движок с
точками и Phase A; полки и окно взятия; требования и архитектура с
параметрами-сущностями; модели с резервами; WBS и созревание;
документы-минимум с базированием; обмен через StrictDoc; знания:
чтение документа в постановку (109 предложений, риски и замысел на
мере), массовый приём-минимум, роли документов, ворота на цитате.

**Не прожито целиком ни разу.** Ни один проект не прошёл от записки
до KDP-A руками владельца. Это главный риск и первая точка.

**Открыто**: онтология и схемы — три истины, слить в одну; словарь и
база знаний — не начаты; два входа и дизайн — эталоны есть, кода нет;
чтение — 30/43 нужд, требования на сцене 8 не проверены; Capella —
только fixture.

## 5. Контрольные точки — как принимаются

Каждая КТ — **проход владельца** по сценарию с артефактами, не отчёт
исполнителя. Критерий записан до старта этапа; отчёт — таблицей
«критерий · факт · тег»; первая строка — состояние CI. Между КТ —
короткие проверки в 10 минут после каждого шипа, только на 216.

## 6. Правила выполнения (действуют на всех этапах)

Красный CI — стоп · любая правка промпта — фикстурой до выката ·
критерий готовности только читает и имеет тест на отказ · пороги
полями, не парсингом · одна истина, правки диффом к HEAD · ИИ никогда
не на критическом пути — руками проходится всё · живые вызовы только
там, где проверяется живой контур · библиотеки версией, без GPL/EPL ·
демо только спутниковый IoT · чинятся блокеры, остальное пачкой ·
отчёт без пересказа процесса.

## 8. Внешние зависимости и API

**Баллистика (владелец).** Подключается как реализация порта
`ModelEngine`: `run(model_code, inputs{param_code: {value, unit}},
options) → {outputs{code: {value, unit}}, engine, version, run_id,
diagnostics}`; идемпотентность по отпечатку входов; единицы —
справочника Орбиты; асинхронно с опросом; результат ложится в
`model_run` с провенансом движка; М1 (построение, покрытие, P95, gaps)
и М10 (ODA) — первые модели через API. Контракт фиксируется на Э0,
интеграция — Э4; до того М1 считает встроенный движок v1.

**Capella** — модель владельца, чтение через `capellambse` по
таблице соответствий. **StrictDoc** — контейнер. **216** — Telegram-
вход, роли, ключ модели. **Провайдер модели** — структурированный
вывод обязателен.

## 9. Что не входит

Phase B+ кроме полки шаблонов документов; изготовление, интеграция,
эксплуатация; собственная баллистика; текстовый редактор; мобильный
клиент; интеграции с CAD/PLM.
