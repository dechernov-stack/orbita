# Глубина компонента по шагам проектирования — лестница зрелости

Компонент не описывается сразу: на концепции нужны масса и объём, к
обзору требований — стыки и функции, к архитектуре — режимы, элементы
обмена и бюджеты, к PDR — версии изделия и допуски. **То, что было
необязательным на прошлой ступени, на следующей становится
обязательным** — и это данные шаблона, не память инженера.

## 1. Четыре ступени (ворота Формулирования + вход в Phase B)

| Ступень | Точка | Что должен знать компонент |
|---|---|---|
| **1 · Концепт** | MCR | идентичность, `nature`, масса/объём/мощность оценкой (±30 %), TRL критических технологий, вклад в М6 и М4, типовые риски |
| **2 · Определение** | SRR | стыки названы, функции распределены, требования уровня системы распределены, параметры анкеты ±20 %, стандарты применимости, поставщик/ответственный |
| **3 · Архитектура** | SDR/MDR | элементы обмена на стыках данных, режимы (где есть поведение), развёртывание behaviour → node, бюджеты (масса · энергия · compute · data) со вкладом, параметры ±10 %, методы верификации у требований, CI заведён |
| **4 · Проект** | PDR (Phase B) | параметры ±5 % (измерено/поставщик), план версий изделия, план испытаний, ICD подписаны, WCET/ресурсы подтверждены |

Правило монотонности: грань, обязательная на ступени N, обязательна на
всех N+k; значение может уточняться, но не пропадать. Ворота считают
незакрытые грани текущей ступени разрывами; следующей ступени —
приглашениями.

## 2. Классы зрелости параметров и резервы (данными `method_catalog`)

| Класс значения | Смысл | Резерв по умолчанию |
|---|---|---|
| `estimated` | оценка команды, новая разработка | 20 % |
| `modified` | заимствованное с доработкой | 10 % |
| `off_the_shelf` | серийное, по каталогу | 5 % |
| `measured` | измерено на образце | 2 % |

Плюс системный резерв на уровне КА: 20 % к MCR → 15 % к SRR → 10 % к
SDR → 5 % к PDR. Свёртки (М6, М4, бюджет compute) применяют резерв по
классу каждого параметра и системный по ступени — и печатают оба.
У параметра: `measure` · `maturity_class` · `uncertainty` (±%) ·
`origin` · `required_to`.

## 3. Как это устроено в данных

- **Шаблон компонента** (`typical_component`) несёт **лестницу**:
  для каждой ступени — обязательные грани и параметры с единицами и
  классом зрелости по умолчанию.
- Экземпляр в проекте показывает карточку по ступеням: закрытое —
  зелёным, текущее — списком «нужно к ‹точке›», будущее — серым.
- Анкета узла — это срез лестницы на текущую ступень.
- Готовность к точке: по каждому узлу — «ступень N закрыта / не
  закрыта: чего нет».

## 4. Пример — три узла на четырёх ступенях

| Узел | Концепт (MCR) | Определение (SRR) | Архитектура (SDR) | Проект (PDR) |
|---|---|---|---|---|
| **СЭП** | масса ±30 %, мощность СБ BOL, ёмкость АКБ | напряжение шины, стыки питания, функция F-14, стандарты | DoD, циклы, EOL-мощность, вклад в М4 худший β, каналы PDU | КПД трактов, измеренные массы, версии блоков |
| **ПО управления** | перечень функций, категория критичности, TRL FDIR | развёртывание на БЦВМ, стыки данных, CPU/RAM ±30 %, ECSS-E-40 | режимы, элементы обмена TC/TM, бюджет compute ±15 %, SIL/HIL | план версий, WCET, ICD |
| **Терминал датчиковый** | класс, EIRP, батарея, целевая цена | стык датчиков, протокол, автономность ±30 % | энергия сеанса (М13), сертификация | BOM, цена партии, измеренный энергобаланс |

## 5. Полный набор шаблонов

`ПОЛКА-ШАБЛОНЫ-КОМПОНЕНТОВ.json` — 31 шаблон по узлам каркаса: для
каждого — `nature`, лестница по четырём ступеням (грани · параметры с
единицами · класс зрелости), типовые функции, стыки, модели,
стандарты, методы верификации, типовые риски. Экземпляр создаётся с
`template_ref`; узлы без своего шаблона наследуют шаблон рода
(`node`/`behaviour` по умолчанию).

## 6. Глубина — по решению конструктора (tailoring лестницы)

Лестница шаблона — умолчание. У узла в проекте — `maturity_tailoring[]`:
`{facet|param, action: add|remove|shift, to_gate?, rationale*, by*}`;
право — ведущий СИ. Записи tailoring уходят в SEMP §9 и FA §6 как
отклонения от нормы — со следом, не молча. Грани, обязательные
регламентом (масса и мощность в MEL к MCR, ODA к MCR, ConOps к MCR),
помечены `hard: true` и не снимаются; остальное — на усмотрение
конструктора в обе стороны: раньше — можно, позже — с обоснованием.

## 7. TRL как шлюз базирования и программатика созревания

Регламент (БП-PA, Прил. 5): критические технологии — TRL 6 к PDR,
план созревания с вехами, резервные решения и критерии перехода на них.
Модель это исполняет:

1. **Связь `depends_on_technology`**: параметр или требование →
   технология, с полем `revision_expected` («после ОКР значение
   пересматривается») и `sensitivity` (что именно).
2. **Условное базирование**: пока `trl_current < trl_required`,
   зависимые элементы входят в baseline как `firmness: conditional`
   с `conditional_on: технология` — отдельным списком в дифе; твёрдое
   базирование для них невозможно (сторож). Правила по точкам: SRR —
   условное допустимо; SDR — только при наличии плана созревания и
   ресурсов; **PDR — условного нет**: TRL ≥ 6 либо переход на
   резервное решение по критериям Прил. 5.
3. **Программатика**: технология с разрывом TRL автоматически
   предлагает пакет WBS `04.xx · созревание ‹технология›` с вехой
   «TRL n достигнут» (`gate.kind = technology`) — до производственных
   фаз; оценка стоимости, не содержащая пакетов созревания при открытых
   разрывах TRL, — разрыв к KDP-B; лента показывает вехи технологий
   рядом с точками фазы.
4. **После ОКР**: TRL поднят → impact по `depends_on_technology`
   называет параметры к пересмотру → инженер правит → элементы
   переходят в `firm` следующим базированием. Резервное решение
   (`fallback`) — узел-альтернатива в составе с признаком «резерв»,
   переключение — решением с основанием.
5. Риск «технология не дотянет» — типовой, создаётся с технологией,
   владелец — ведущий СИ, срок — веха TRL.
