## 1. Цель

Заменить монолит (`HttpApi.kt` 3,3 тыс. строк, `PhaseWork` как самописный
автомат, данные «куда угодно») на **модульный backend с осью
исполнения**: процесс ведёт (Flowable), сущности знают сцену рождения,
ворота держат на сервере, связи — реестром, схемы — из YAML. Каждый
модуль собирается и тестируется отдельно, зависимости только вниз.

## 2. Принципы (нарушение — брак)

1. **Модуль = Gradle-подпроект** с явным `api` (интерфейсы, DTO,
   события) и `internal` (реализация, таблицы). Другие модули видят
   только `api`.
2. **Своя схема БД у каждого модуля** (`orbita_kernel`, `orbita_process`,
   …); чужие таблицы не читаются — только через `api` или события;
   внешние ключи — только на `kernel.entity.id`.
3. **Зависимости — только вниз по слоям** (§3), проверяются
   архитектурным тестом (**Konsist**, Apache-2.0) в CI.
4. **Ядро одно**: id · code · kind · area · born_in · status · version ·
   provenance · history — в `kernel`; модули не переопределяют.
5. **Домен не в движке**: Flowable хранит состояние процесса; условия
   — внешний оценщик; переоценка после транзакции; отказ на complete.
6. **Схемы видов — из `СХЕМЫ-ПОЛЕЙ-V2.yaml`** генерацией; вид вне YAML
   не существует; поле вне схемы — отказ.
7. **Всё вычисляется**: статусы сцен из движка, покрытие/готовность/
   прогресс — read-model'ы; ручных статусов нет.
8. **Strangler**: новое рядом со старым за флагами; UI работает через
   фасад совместимости до отдельного ТЗ на интерфейсы.

## 3а. Стандарты и соответствия — процесс не привязан к одной номенклатуре

Схема Романова показывает то, что NASA-регламент прячет: у заказчика
в РФ стадии называются **предпроект · НИР · аванпроект · эскизный
проект · РД/изготовление/испытания · госиспытания · эксплуатация ·
утилизация** (РК-11КТ; стадии 0–1 в нём отсутствуют), а контрольные
точки — **экспертизы** (замысла, требований, облика миссии, облика
системы, аванпроекта, эскизного проекта, готовности к производству…).
Поэтому:

1. **`phase_template` многостандартен**: поле `standard` (NASA-7120 ·
   РК-11КТ · ISO-15288) и **карта соответствий** стадий и точек между
   стандартами — данными полки: Pre-A ↔ стадия 1 (НИР), Phase A ↔
   стадия 2 (аванпроект), Phase B ↔ 3 (эскизный проект), C/D ↔ 4–5,
   E ↔ 6, F ↔ 7; MCR ↔ экспертиза замысла/облика миссии, SRR ↔
   экспертиза требований, SDR/MDR ↔ экспертиза облика системы, PDR ↔
   экспертиза аванпроекта. Точка несёт `aliases[]`; лестница зрелости
   и ворота ключуются по id точки, имена — по стандарту проекта.
2. **Экспертиза как ворота с содержанием**: у точки — `expertise{цель,
   входные данные, контрольные вопросы[], выходы}` (строка «Экспертизы
   и контрольные точки» схемы); контрольные вопросы — чек обзора и
   критерии DMN.
3. **«Готовность системы» по стадиям** (строка схемы: концепция
   осуществимости → анализ требований → архитектура верхнего уровня →
   функциональные исходные данные → исходные данные на проектирование →
   на производство → на интеграцию → на развёртывание): у каждой стадии
   в шаблоне — **`stage_output_dataset`** — состав исходных данных для
   следующей стадии (глубина дерева состава, уровни требований, стыки,
   модели, документы); лестница зрелости компонентов (`ГЛУБИНА…`)
   привязывается к этим наборам, а пакет передачи (`РЕЕСТР… §выгрузка`)
   — их печать.
4. **Роли по стадиям** (строка «Задействованный персонал и
   менеджмент»): `phase_template.roles[]` — кто вовлечён на стадии;
   ответственные сцен выбираются из них.
5. **Каталог процессов — двухстандартный**: `process_catalog` (L0) —
   17 процессов NPR 7123.1 ↔ процессы ГОСТ ISO 15288-2023 (технические,
   управления, соглашений, организационные) ↔ механизмы Орбиты; SEMP §6,
   готовность и tailoring читают каталог, не код. MBSE-процессы — по
   ГОСТ ISO 24641-2023 пометкой.
6. **Три дорожки процесса** (схема Романова, `РОМАНОВ-СТАДИИ-0-2`):
   сцены шаблона фазы принадлежат дорожкам `design · modeling ·
   management` и связаны потоками выходов; **сцена может объявлять
   `instantiate_per: segment | element`** — экземпляр на каждый узел
   состава уровня (аванпроект элемента A, B, C); мероприятия и их
   выходы — транскрипция `ПОЛКА-ПРОЦЕССЫ-РОМАНОВ.json` (73 мероприятия
   стадий 0–2) — шаги сцен полки РК-11КТ; `system_model` получает
   `verification_status` и критерии оценки модели — модель без
   верификации не даёт выхода в базирование.
7. **Базовые линии по классам CM**: `baseline.kind` — functional
   (функциональная, к SRR) · allocated (исходные данные на
   проектирование, к SDR/PDR) · product (к производству) — как в
   строке «готовность системы»; диф и права правки — по классу.

## 4. Ось исполнения — сквозной контракт

```
создать проект (formulation/api)
→ process: экземпляр фазы = case Flowable из phase_template (library)
→ сцена N активна ⇒ Visibility открывает виды сцены
→ запись домена (любой модуль) ⇒ DomainEvent(EntityChanged)
→ process: evaluateCriteria(case) ⇒ readiness.GateEvaluator(проект, сцена/точка)
→ sentry: сцена закрыта/открыта; task listener на complete — отказ с причинами
→ точка: DMN(критерии из readiness) ⇒ decision (DA) ⇒ переход фазы (только здесь)
→ история: kernel.history + Flowable history — одной лентой в read-model
```

Инварианты оси (тест `SpineTest`): сцена не открывается раньше входа;
сущность не создаётся раньше своей сцены (born_in = текущая сцена,
отказ иначе); фиксация точки с блокирующим критерием — отказ движка;
переход фазы — только решением; перезапуск api не теряет состояние;
переоценка после каждой транзакции домена, без флагов в переменных
процесса (сигналы — event listener'ы, урок FlowPilot).

## 5. Данные

- Схемы Postgres по модулям; миграции по модулям (Flyway-нумерация с
  префиксом модуля); `-- legacy:` у переносов.
- **`born_in` у всех проектных сущностей** — миграция вычисляет из
  истории (дата ↔ фаза/сцена); где невычислимо — `pre_scenario`
  явно, не null.
- Связи — в `kernel.link` с типом из реестра и обоснованием; старые
  разрозненные ссылки (`derives_from`, `allocated_to`, `arch_link`)
  переносятся с `-- legacy:`.
- Параметры узлов — в `architecture.parameter` (сущность), из полей
  `component.params`.
- Генератор схем: YAML → JSON Schema (валидация) + Kotlin-модели
  (типы) — в `kernel`, запуск в сборке; правка YAML без перегенерации
  — отказ сборки (сторож).

## 7. Приёмка

- [ ] каждый модуль: `gradle :module:test` зелёный отдельно; Konsist —
      ни одной запрещённой зависимости;
- [ ] `SpineTest` Pre-A и Phase A; рестарт без потерь;
- [ ] `born_in` у 100 % проектных сущностей; `pre_scenario` — только с
      обоснованием в миграции;
- [ ] реестр связей: связь вне реестра — отказ; обоснование там, где
      обязательно;
- [ ] проект с `standard = РК-11КТ` показывает стадии и экспертизы
      своими именами при тех же id точек; `baseline.kind` различает
      функциональную и allocated; SEMP §6 (порт) читает `process_catalog`
      по двум стандартам;
- [ ] YAML ↔ код: сторож перегенерации;
- [ ] старый UI работает через фасад; `HttpApi.kt` — 0 строк;
- [ ] журнал ИИ, выгрузка знаний, ReqIF — как до перестройки или лучше
      (сверка мер прежних задач);
- [ ] отчёт: карта модулей с размерами, что перенесено, что снесено,
      что за флагом.

## 8. Ловушки
