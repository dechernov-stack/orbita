# Модель данных: требования и компоненты системы — раз и навсегда, вровень с Capella

Две сущности, вокруг которых всё остальное: **требование** (Орбита —
источник истины) и **компонент** (узел состава = PA Capella). Здесь —
их полная модель: поля, шаблоны, версионность, связи, выравнивание с
Capella и ReqIF. Остальные виды ссылаются на эту модель, не расширяют её.

## 1. Принципы, от которых не отступаем

1. **Требование управляется в Орбите**, Capella только читает его через
   ReqIF и объясняет реализацию. Компонент существует в обоих мирах и
   связан идентичностью по UUID — имя, тип, слой снимками.
2. **Версия — у всего**: требование, компонент, параметр, связь. Ничего
   не перезаписывается — только новая версия с автором и основанием.
3. **Базирование — именованный снимок набора**, а не флаг на записи:
   «Baseline SRR» = список (объект, версия) + `.sdoc` + дата + кем.
4. **Шаблон — библиотечная сущность; экземпляр в проекте помнит, из
   какого шаблона и с каким отклонением** (tailoring).
5. **Связь — объект с версией и обоснованием**; изменение любого конца
   после базирования делает связь «подозрительной» (suspect), пока
   человек не подтвердит.

## 2. Требование

### 2.1 Поля (проектная область; ядро — по `СХЕМЫ-ПОЛЕЙ-V2`)

| Поле | Тип | Обяз. | Смысл / выравнивание |
|---|---|---|---|
| `level` | enum project · scenario · system · subsystem · interface | ✓ | уровень иерархии; ReqIF `ORBITA.Level` |
| `code` | `RQ-P-01`, `RQ-S-13a` | ✓ | ReqIF `ReqIF.ForeignID`; StrictDoc UID |
| `title` | str | ✓ | ReqIF `ReqIF.Name`; StrictDoc TITLE |
| `statement` | text по шаблону формулировки (§2.2) | ✓ | ReqIF `ReqIF.Text`; StrictDoc STATEMENT |
| `category` | functional · performance · interface · operational · constraint · safety · environment | ✓ | определяет тип носителя и вид покрытия |
| `priority` | high · medium · low (справочник) | ✓ | |
| `measure` | `{op, value|min,max, unit}` либо `tbr{owner, gate, action}` | для performance ✓ | StrictDoc `MOP_OP/MOP_VALUE/MOP_UNIT`; ReqIF атрибуты |
| `carrier` | ref component (project/system/subsystem) · ref interface (interface) · ref scenario (scenario) | к базированию ✓ | «без носителя — не требование» |
| `verification_method` | test · analysis · demonstration · inspection · TBD | ✓ (TBD до SRR) | ReqIF `ORBITA.Verification` |
| `acceptance_criteria` | text | к базированию ✓ | наблюдаемый результат |
| `source[]` | `{kind: goal|need|constraint|requirement|material, ref, anchor?}` ≥1 | ✓ | трассировка вверх; ReqIF `ORBITA.Source` |
| `rationale` | text | ✓ | допущения — здесь |
| `normative_basis` | `{normative_document, clause}` | — | соответствие пункту нормы |
| `template_ref` | ref typical_requirement | — | если экземпляр типового (§2.3) |
| `applicability` | applied · applied_with_deviation · not_applicable + `deviation_rationale` | если `template_ref` ✓ | tailoring по FA §6 |
| `status` | Draft → Baseline (через именованный baseline) | ✓ | |
| `after_baseline_changed` | вычисляется: версия > версии в последнем baseline | — | помета «изменено после утверждения» |

### 2.2 Шаблоны формулировок — EARS (единый словарь для людей и линта)

| Шаблон | Форма | Пример |
|---|---|---|
| Всегда | ‹Носитель› должен ‹действие› ‹объект› [‹показатель›]. | КА должен хранить принятые сообщения не менее 24 ч. |
| По событию | Когда ‹событие›, ‹носитель› должен ‹действие› [в течение ‹T›]. | Когда терминал передал сообщение класса A′, ПН должна отправить подтверждение в том же сеансе. |
| В состоянии | Пока ‹состояние›, ‹носитель› должен ‹действие›. | Пока КА в аварийном режиме, КТРЛ должна работать через всенаправленные антенны. |
| Нежелательное | Если ‹условие›, то ‹носитель› должен ‹парирование›. | Если буфер заполнен, ПН должна отбрасывать сообщения класса C′ первыми. |
| Опциональное | Где предусмотрен ‹элемент›, ‹носитель› должен …. | Где предусмотрена МБРК, КА должен ретранслировать пакеты класса A′. |

Правила П13–П20 (активный залог, одна мысль, запрещённые слова,
модальность) — линтом на всех пяти шаблонах. Шаблон выбирается в
карточке, поля формы подставляются в формулировку.

### 2.3 Типовое требование → экземпляр (библиотека → проект)

`typical_requirement` (L0): код · шаблон EARS · формулировка с
плейсхолдерами `{носитель}`, `{значение}` · категория · метод ·
критерий приёмки · применимость по классу · нормативное основание.
Взятие в проект создаёт экземпляр с `template_ref` и `applicability =
applied`; правка формулировки → `applied_with_deviation` с обоснованием;
отклонение → `not_applicable` с обоснованием. Новая редакция типового
на полке подсвечивает экземпляры «шаблон обновлён» — не меняет молча.

### 2.4 Связи требования (объекты `link`, версия у каждой)

`derives_from` (вид: decomposition · derivation · refinement) ·
`allocated_to` (носитель) · `satisfied_by` (функция) · `realized_by`
(цепочка) · `verifies` (событие) · `conflicts_with` · `illustrated_by`
(диаграмма) · `applies` (типовое). **`suspect`** — вычисляемый флаг:
версия любого конца выше версии, зафиксированной в последнем baseline
→ связь подозрительна, пока не подтверждена (`confirmed_by`, `at`);
подозрительные связи — разрыв к следующей точке.

## 3. Компонент (узел состава = Physical Component)

### 3.1 Три сущности

| Сущность | Смысл | Ключевые поля |
|---|---|---|
| `component` (определение) | что это за элемент | код · имя · уровень · вид · родитель · `params[]` · `template_ref` · `applicability` · `external_identity` |
| `component_usage` (вхождение) | сколько и где | определение · родитель-вхождение · количество · роль · орбита (для КА в подгруппе) |
| `parameter` (значение параметра узла) | величина с историей | узел · ключ анкеты · `measure` · `origin` (manual · datasheet · shelf · computed · example) · `source{material, anchor}` · `required_to` · версия |

Параметр — **сущность, не поле**: у каждой величины своя версия,
происхождение и якорь; свёртки и модели читают версию параметра и
помнят её в `model_run.inputs_snapshot`.

### 3.2 Шаблоны компонентов

| Шаблон | Что даёт | Экземпляр помнит |
|---|---|---|
| каркас PBS (`pbs_template`) | дерево узлов класса миссии | `template_ref` на узел каркаса |
| **типовой компонент** (`typical_component`, L0) | узел с параметрами по умолчанию из класса изделий («платформа 12U типовая»: масса, мощность, АКБ…) с происхождением `shelf` | `template_ref` + `applicability`; отклонение параметра — origin `manual` с основанием |
| анкета (`questionnaire`) | какие параметры обязаны быть и к какой точке | `data_request` на узле |
| типовой стык (`interface_template`) | ребро с параметрами | `template_ref` |

### 3.3 Связи компонента

`part_of` (дерево, через `parent`/вхождение) · `pairs_with` (WBS) ·
`allocation` (функция → узел) · `deployed_to` (LC → узел) ·
`allocated_to` (требование → узел) · `external_identity` (узел →
элемент Capella по UUID, с обоснованием) · `feeds` (параметр узла →
модель).

## 4. Версионность — правила, одни на всё

| Событие | Что происходит |
|---|---|
| правка поля | новая версия объекта; автор; `valid_from`; старая версия остаётся |
| правка после базирования | только с `basis` (текст); помета «изменено после утверждения»; связи объекта — `suspect` |
| правка параметра узла | новая версия параметра; модели, читавшие старую, помечаются «вход изменился» |
| базирование набора | объект **`baseline`**: имя (SRR · SDR · KDP-B…), точка, `items[{ref, version}]` для требований, узлов, параметров, связей; `.sdoc` снимок; кем и когда; неизменяем |
| перебазирование | новый `baseline`; пометы «изменено» и `suspect` гаснут для вошедших версий |
| отмена | статус Cancelled с историей; из baseline не исчезает |
| диф | между двумя baseline — по объектам и версиям: добавлено · изменено (поле в поле) · удалено; печатается |

Битемпоральность: `valid_from/valid_to` (когда правда) + `recorded_at`
(когда узнали) — есть в движке, применяется ко всем трём сущностям.


### 4.1 Единица версии — атомарная сущность, классы полей, диф на версии

- **Не по полю**: журнал событий на каждое поле превращает состояние в
  вычисление, ломает ограничения БД и ведёт в EAV. Основа остаётся:
  версия = целая запись-снимок с `valid_from/valid_to/recorded_at`,
  ветвлений нет (альтернативы — отдельные сущности).
- **Атомарность по смыслу**: требование · связь · параметр узла ·
  компонент · вставка · проза версионируются раздельно — поэтому
  параметр и проза не поля, а сущности.
- **Три класса полей** (в схеме вида; умолчание — содержательное):
  *содержательное* — новая версия, после baseline нужен `basis`, связи
  → `suspect`; *служебное* (`notes`, `tags`, `comment`, `name_snapshot`,
  оформление) — история пишется, версия не растёт, подозрений нет;
  *вычисляемое* — не хранится.
- **Диф на версии**: при записи считается список изменившихся
  содержательных полей `changed_fields[]` и хранится у версии вместе с
  `basis`; «что изменилось» и «изменено после утверждения» читаются из
  него, диф между baseline — свёртка этих списков.
- Конкуренция — оптимистическая блокировка по версии; baseline
  ссылается на (объект, версия) — точность обеспечена атомарностью.

## 5. Выравнивание с Capella — контракт

### 5.1 Метамодель

| Орбита | Capella | Кто владеет |
|---|---|---|
| `requirement` | Requirements Viewpoint → Requirement (`ReqIFIdentifier`, `ReqIFLongName`, `ReqIFText`, `ReqIFChapterName`, атрибуты) | **Орбита**; в Capella — импорт ReqIF, только чтение |
| `link` требование↔требование | Requirements VP `InternalRelation` (тип = наш вид связи) | Орбита (в ReqIF SPEC-RELATION) |
| `link` требование → элемент (`allocated_to`, `satisfied_by`) | `CapellaOutgoingRelation` / `CapellaIncomingRelation` с `RelationType` = вид связи | Орбита создаёт; Capella показывает; обратная синхронизация — кандидатами |
| `component` (L2–L5) | PA `PhysicalComponent` (node/behaviour), иерархия — `ownedPhysicalComponents` | **Capella** — истина структуры при наличии модели; Орбита — зеркало по UUID; без модели — Орбита |
| `component_usage` ×N | Capella не ведёт количество — **PVMT** property `quantity` на компоненте | Орбита; в Capella — свойство |
| `parameter` | **PVMT** property values (группа `ORBITA`: mass, power…, единицы по справочнику) | Орбита пишет в ReqIF/JSON; в Capella вносится через PVMT-импорт (P1) |
| `interface` | PA `PhysicalLink` (+ `ComponentPort` на концах); RF-стык — PhysicalLink с категорией | Capella при наличии модели; Орбита зеркалит |
| `function` SA/LA | `SystemFunction` / `LogicalFunction`; `allocation` → `ComponentFunctionalAllocation` | Capella |
| `functional_chain` | `FunctionalChain` | Capella |
| `capability` | `OperationalCapability` / `Capability` | Capella (OA/SA) |
| `model_element` | любой элемент по UUID (`id` Capella) | ссылка |

### 5.2 ReqIF — атрибуты (наш профиль `ORBITA`)

`ReqIF.ForeignID` ← `code` · `ReqIF.Name` ← `title` · `ReqIF.Text` ←
`statement` · `ReqIF.ChapterName` ← раздел документа/уровень ·
`ORBITA.Level` · `ORBITA.Category` · `ORBITA.Priority` ·
`ORBITA.MOP.Op` · `ORBITA.MOP.Value` · `ORBITA.MOP.Unit` ·
`ORBITA.Verification` · `ORBITA.Acceptance` · `ORBITA.Rationale` ·
`ORBITA.Source` · `ORBITA.Status` · `ORBITA.Version` ·
`ORBITA.Baseline` · `ORBITA.Carrier` (код узла/стыка + UUID, если есть) ·
`ORBITA.Template` · `ORBITA.Applicability`. SPEC-RELATION ← `link` с
`type` и `rationale`. Идентификаторы стабильны (детерминированы из `id`).

### 5.3 Правила синхронизации

1. Направление: требования → Capella (ReqIF); архитектура → Орбита
   (чтение через `capellambse`). Обратных записей нет.
2. Идентичность — UUID; имя, тип, слой — снимок с датой; расхождение
   имени — подсказка, не ошибка.
3. Узел, зеркалящий Capella, параметры хранит у нас (PVMT — экспорт);
   структура (родитель, дети) при наличии модели — из Capella, правка у
   нас запрещена (сторож: «узел внешний — структура читается»).
4. Связь требование→элемент, созданная в Capella, приходит кандидатом
   в акцепт, не записывается сама.
5. Без модели Capella всё то же самое живёт у нас; появление модели =
   сопоставление узлов по кодам → UUID с подтверждением.

## 6. Инварианты (сторожа)

1. Требование без носителя, источника, метода — не базируется.
2. Интерфейсное — только на стык; сценарное — только на цепочку;
   характеристика без показателя — не базируется.
3. Параметр без единицы справочника и без происхождения — не
   принимается; `computed` без `model_run` — не принимается.
4. Экземпляр типового без `applicability` — не существует; отклонение
   без обоснования — отказ.
5. Baseline неизменяем; правка после него — только с основанием;
   подозрительная связь — разрыв к следующей точке.
6. Внешний узел: структуру не править; UUID не менять; снимок имени
   обновляется только явным «обновить из модели».
7. Формулировка вне пяти шаблонов EARS или с запрещёнными словами —
   помета; к базированию — разрыв.

## 7. Дополнения к `СХЕМЫ-ПОЛЕЙ-V2.yaml`

Новые/изменённые виды: `parameter` (сущность), `baseline` (именованный
снимок набора), `typical_component` (L0), поля `template_ref` ·
`applicability` · `deviation_rationale` у `requirement` и `component`,
`suspect` · `confirmed_by` у `link`, атрибутный профиль ReqIF `ORBITA` в
`export`. Патч приложен отдельным файлом.
