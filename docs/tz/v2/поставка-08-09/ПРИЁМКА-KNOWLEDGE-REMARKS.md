# `v2-knowledge-remarks` — принят; два правила; стенд — первым делом

## Принято

Три правила из прошлого ответа стали сторожами и сразу заплатили за
себя: `validate_gate_checks.py` требует отрицательный тест у каждого из
31 критерия и **нашёл критерий, который сам закрывал разрыв, который
проверял** (`maturation_planned` звал генератор созревания) — отказать
он не мог никогда. Пороги — полями, умолчаний нет; дата вехи — от плана
пакета, ручной `POST` при плане отказывает словами «правьте план, а не
веху». Замечания поля знаний — все три живьём: согласие одним кликом,
отклонение без причины — 400, загрузка во вкладке текстом/файлом/
ссылкой, ручные темы и факты с отдельной цифрой. Старый экран загрузки
снят.

## Два правила из находок

1. **Критерий готовности только читает.** Проверка не имеет права
   ничего создавать, менять или запускать — она наблюдает состояние и
   называет причину. Сторож: в коде критериев нет вызовов записи и
   генераторов (архитектурный тест по импортам `readiness` → только
   `api` чтения других модулей).
2. **Один сериализатор на вид.** Список фактов и ответ на заведение
   писались разным кодом — `manual` был в одном и не был в другом; тот
   же класс, что два построителя `Fact` раньше. DTO вида — из схемы
   YAML генерацией, рукописных построителей JSON для видов нет
   (сторож: рукописный `JSONObject`/`buildJsonObject` для вида реестра
   — отказ ревью).

## Стенд — это сейчас важнее шипа D

Семь падений Postgres за день во время прохода владельца — проход
невозможен. Две вещи, в этом порядке:

1. **Немедленно, независимо от причины**: у api — **пул соединений с
   проверкой и переподключением** (HikariCP: `connectionTestQuery`,
   `maxLifetime`, `validationTimeout`; повтор запроса при
   `connection has been closed`). Одно JDBC-соединение без переподключения
   — дефект api, который превращает любой чих базы в мёртвый стенд до
   `docker restart`. Это час работы и первый пункт.
2. **Диагностика падений** — не гадать, снять факты: строки лога PG
   вокруг падения (`server process (PID …) was terminated by signal …`
   или `exited with exit code 2` — это разные причины: сигнал 9 — OOM
   ВМ Docker, `docker inspect … State.OOMKilled`, `docker stats`
   память контейнера; exit 2 — ошибка процесса, смотреть предыдущие
   FATAL/PANIC), `checkpoint`-строки перед падением, кто был клиентом
   в момент «Broken pipe» (`application_name` в `pg_stat_activity` —
   если это скрипты прохода с 45-секундным лимитом, обрыв клиента сам
   по себе backend не валит, но подскажет нагрузку). Отчёт — факты,
   потом решение: лимит памяти контейнеру и `shared_buffers`, вынос
   `testdb` и gradle-прогонов с хоста стенда во время прохода
   владельца (тесты ядра шли 1 ч 42 м, деля процессор с api).

До починки пула — проход владельца не назначать. После — шип D.
