# Промпт формирования постановки — разбор (15.09)

## Главная причина

**Правила говорят о полях фактов, которых в промпте нет.** Правило:
«образуется только из фактов вида relation, субъект „организация"»,
«statement ← предикат + объект», «scale ← quantity о subject». А факт в
срезе выдан строкой: `F-0007 [framing] ранг · метка · якорь · тема` и
предложение прозой. Ни `subject`, ни `predicate`, ни `value/unit` модели
не показаны — она заново вытаскивает их из текста, и вся атомизация,
за которую заплачено при разборе, теряется. Формирование идёт по прозе
с правилами о структуре, которой не видно. Отсюда «что попало».

## Семь дефектов

1. **Факты без структуры** (выше). Каждый факт должен идти записью:
   `код · вид · субъект · предикат · объект/значение с единицей · метка ·
   ранг · якорь · тема`.
2. **Предикаты из онтологии потеряны при рендере.** В онтологии у
   нужды `predicate_in: [нуждается в, требует, не хватает]`, у
   ограничения — `[только, не рассматривается, исключается, не более,
   не менее]`, у стороны — роли. В промпте осталось «вид [framing] ЛИБО
   вид [assessment]» — и любой `framing`-факт становится кандидатом в
   ограничение, любая оценка — в нужду. Предикаты — единственный
   дискриминатор, их нельзя терять.
3. **Правила в машинном жаргоне и с чужими примечаниями.** «сторона
   без нужды — помета к воротам, не отказ», «§2.1 подсказка» — это
   правила для системы и для разбора, не для синтеза; они отвлекают и
   ничего не задают. Модели нужны правила на языке, с примером на
   каждое понятие и с анти-примером.
4. **Ни одного полного примера.** Один JSON-скелет с «имя стороны» и
   «связь в Арктике» — и всё. Для структурированного образования
   понятий один настоящий пример на понятие («из фактов F-a, F-b →
   предложение с полями») даёт больше, чем страница правил.
5. **Нужда ссылается на сторону именем.** «stakeholder: имя стороны» —
   ни кода принятой сущности, ни ссылки на предложение из того же
   ответа. Сторона, которой ещё нет, не может быть названа — нужды
   висят без владельца. Нужны **ссылки внутри ответа** (`ref: "p1"`) и
   коды принятых (`SK-0001`), а имена — только в `payload.name`.
6. **Принятое дано без полей, о которых выносится вердикт.** Для
   `augment/contradict` модель должна видеть у принятой цели её
   `measure` и `year`, у нужды — `statement`; дана одна строка с ролью.
   Вердикт «чем отличается» без данных — гадание, а правило 2 его
   бракует — модель выбирает `new`, и получаются дубли.
7. **Задача не ограничена сценой и объёмом.** Всё поле, все восемь
   понятий, «для каждого понятия, которое следует» — без порядка и
   потолка. Синтез для сцены 3 должен образовывать стороны и нужды;
   вехи и нормативы — не его дело в этот момент. Порядок нужен и
   внутри: сначала стороны, потом нужды со ссылками на них, потом
   цели/сервисы со ссылками на нужды.

## Что оставить как есть

Вердикты `new/augment/contradict/confirm`, обязательный `basis` из
кодов среза, «оба значения при противоречии», «принятое не меняешь»,
«ранги и метки ставит система». Это верно и остаётся.

## Переписанный промпт — `ПРОМПТ-ФОРМИРОВАНИЕ-V2.md`

Собирается системой из тех же данных, но: понятия — по сцене; факты —
записями с полями; правила — таблицей на понятие с предикатами,
примером и анти-примером; ссылки внутри ответа; принятое — с полями
вердикта; потолки и порядок; самопроверка перед выводом. Тест — тот
же `FormationGateTest` плюс две фикстуры: записка → 14/43, Приморье →
8 сторон и 0 нужд из ролей.
