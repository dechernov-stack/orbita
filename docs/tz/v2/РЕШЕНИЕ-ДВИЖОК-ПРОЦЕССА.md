# Решение: чем двигать процесс — Flowable (CMMN + BPMN), встроенный

Задача: не рисовать Гант, а **вести** фазу — сцены открываются по
условиям, ворота держат, шаги адресуются людям, сроки тикают, история
процесса хранится. Самописный `PhaseWork` довёл нас до «записок
сумасшедшего»; движок процесса — готовый класс ПО, берём с гита.

## Критерии выбора

1. Процесс — данные: модель фазы порождается из наших шаблонов, не
   пишется кодом.
2. Люди: человеческие шаги с назначением, сроками, ролями.
3. Ворота: условия входа/выхода по данным домена; блокировка на движке.
4. Итеративно-параллельные операции (О2–О12) **и** строгие цепочки
   (О12–О15) — обе природы регламента.
5. JVM/Postgres, встраивается в Ktor, без отдельного кластера.
6. Лицензия Apache/MIT, живой проект.

## Почему CMMN — точное попадание в регламент

| Регламент / наш сценарий | CMMN |
|---|---|
| фаза проекта | **Case** (экземпляр на проект) |
| сцена / операция О-N | **Stage** |
| шаг сцены | **Human Task** (назначение, срок, роль) |
| точка MCR / KDP-A | **Milestone** |
| ворота: «нельзя, пока нет ConOps» | **Sentry** с условием по данным Орбиты (entry/exit criteria) |
| артефакт сцены | **Case File Item** — ссылка на объект Орбиты (не копия) |
| «итеративно-параллельны» О2–О12 | stages без порядка, активируются по sentry |
| строгая цепочка О12→О15 | **BPMN process task** внутри case |
| эксперт-режим, необязательные шаги | **Discretionary items** |
| матрица зрелости к точкам (прил. I) | **DMN-таблица** — критерии ворот данными |
| «артефакт появился/изменился» | событие → переоценка sentry |

## Границы — чтобы движок не стал вторым доменом

1. **Домен — в Орбите.** В движке — только состояние процесса: какие
   stages активны, чьи задачи, когда сроки, какие milestones пройдены.
   Case file items — ссылки на наши объекты. Сторож: «в таблицах
   Flowable нет полей домена».
2. **Модель фазы порождается** из шаблона фазы (полка) генератором в
   CMMN/BPMN XML; XML руками не правится (сторож — как у пакетов).
3. **Sentry читают Орбиту** через одну точку — «оценщик критериев»
   (готовность): ворота остаются нашими правилами, движок их
   исполняет.
4. **Статусы сцен — из движка**, `PhaseWork` умирает как счётчик и
   остаётся проекцией; Гант, схема и рамка читают движок.
5. **Фиксация точки** = завершение milestone через движок; при
   блокирующем sentry движок отказывает — не UI.
6. Встраивание: движок в процессе api, таблицы `ACT_CMMN_*`/`ACT_RU_*`
   в той же базе отдельной схемой; отдельного сервиса нет.

## Пилот (день раздумий → неделя кода)

CMMN-case «Pre-A, сцены 1–4»: четыре stage, sentry «замысел принят»,
«≥3 стейкхолдера с нуждами», «каждая нужда ведёт к цели»; human tasks
на учётки стенда; milestone «внутренний обзор» с DMN-критериями.
Мера: сцена 3 недоступна до принятия замысла — движком; попытка
завершить milestone при открытом sentry — отказ движка с именем
критерия; «Работа» показывает активные stages и задачи из движка;
перезапуск api не теряет состояние.

## Риски

XML-модели — только генерацией; кривая обучения CMMN — у Code день;
двойная правда состояния — запрещена границей 4; производительность —
не вопрос при десятках проектов.
