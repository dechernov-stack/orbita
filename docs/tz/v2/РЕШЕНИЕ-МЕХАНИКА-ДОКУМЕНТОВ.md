# Решение: на чём делать механику документов

Нужно: структура «разделы + элементы» с грамматикой; полнота по
шаблону; версии и базирование с дифом; порождение прозы ИИ; печать
docx/pdf/html; рецензия с правками изложения. Всё это есть в open
source — сложить из четырёх кусков, не писать своё.

## Выбор

| Задача | Берём | Лицензия | Почему |
|---|---|---|---|
| **Формат структурированного документа** | **StrictDoc** (`.sdoc` с пользовательской грамматикой) | Apache-2.0 | грамматика документа объявляет **свои типы узлов с полями и обязательностью** (`[GRAMMAR] ELEMENTS: - TAG: …`) — наши элементы `FACT_REF · ENTITY_REF · STATEMENT · QUERY · FIGURE · TABLE` становятся типами узлов; композитные документы из частей; MID — стабильные машинные id узлов; экспорт HTML/PDF (html2pdf)/RST/ReqIF/Excel штатно; **`--generate-diff-git` с тегами** — диф документа между релизами из коробки; уже выбран каналом требований — один инструмент на требования и документы |
| **Версии и базирование** | **git** (встроенный **JGit**, EDL/BSD-3) — репозиторий документов на проект | BSD | базирование = коммит + тег; диф = git diff по `.sdoc` (узлами, не строками — StrictDoc сам понимает узлы); история авторов; внешний ревьюер читает в любом git-клиенте; ничего своего для версий документов не пишем |
| **Печать пакета точки** | **Typst** (компилятор, CLI) | Apache-2.0 | шаблоны титулов, подписей, оглавлений как код; PDF мгновенно и одинаково; docx — как сейчас (POI) для тех, кому нужен Word |
| **Диф текстов и патчи изложения** | **diff-match-patch** (Java) | Apache-2.0 | правка изложения хранится патчем поверх рендеринга; диф двух рендерингов рядом с дифом элементов |
| **Схемы элементов и шаблонов** | JSON Schema + `networknt/json-schema-validator` (Java) | Apache-2.0 | ожидания полноты и типы элементов проверяются схемой, не кодом |

Отвергнуто: **sphinx-needs** (MIT; сильный, но дублирует StrictDoc и
тянет Sphinx/Python-стек), **Pandoc** (GPL — только как внешний CLI,
уже так), сайты-генераторы (MkDocs/Docusaurus — не документы),
собственный «редактор документов» (это и есть путь к записям
сумасшедшего).

## Как это складывается

1. **Истина — база** (элементы, факты, сущности с версиями). Документ
   проекта **порождается** в `.sdoc` по грамматике Орбиты: раздел →
   `[SECTION]`, элемент → узел своего типа с полями (`REF`, `REF_VERSION`,
   `AUTHOR`, `SUPPORTS`, `QUERY`), тезис → `STATEMENT`. Файл — не
   редактируется руками; он выход, как канон.
2. **Полнота** проверяется дважды: у нас по `expects` шаблона и
   грамматикой StrictDoc (`REQUIRED: True` у полей) — `strictdoc
   check` в CI.
3. **Базирование документа** = запись `baseline` у нас **и** коммит с
   тегом в git-репозитории проекта (`docs/ConOps.sdoc`, `docs/…`);
   `strictdoc export --generate-diff-git` даёт диф между тегами по
   узлам — это и есть «добавлено · изменено · удалено» с авторами из
   git blame.
4. **Рендеринг прозы**: ИИ (наш канал, вид `document_render`) получает
   узлы раздела и возвращает текст; результат кладётся **рядом** —
   `docs/rendered/ConOps.sdoc` с узлами `TEXT` (по одному на раздел,
   `SOURCE_ELEMENTS: [MID…]`) — тоже под git, тоже дифуется; сторож:
   число в TEXT без MID элемента — отказ.
5. **Рецензия**: правки изложения → патч (diff-match-patch) с автором в
   `rendered` (коммит рецензента); правки сути — только через элементы
   (сторож грамматики: TEXT не может вводить поля данных).
6. **Печать**: `strictdoc export --formats=html2pdf` — рабочие PDF;
   **Typst** — пакет точки с титулами, подписями, оглавлением; docx —
   POI; **все три из одного `rendered.sdoc`**.
7. **Обмен**: тот же репозиторий отдаёт `.sdoc`/ReqIF наружу; смежник
   получает документ и требования одним git-архивом с историей.

## Границы

- StrictDoc — формат, экспорт, диф, проверка грамматики; **не
  хранилище истины** (истина — база) и не редактор для людей.
- Git — версии и диф файлов-выходов; **не версии сущностей** (они
  битемпоральны у нас); соответствие: baseline у нас ↔ тег в git,
  сторож сверяет хеш.
- Typst — только печать; шаблоны Typst — в полке шаблонов документов
  (стиль как данные).
- Свой код: генератор `.sdoc` из базы по грамматике, обратный чтец
  (для дифов и импортов), оркестрация рендеринга, сторожа.

## Пилот (после Flowable)

ConOps Pre-A: три раздела, десять элементов, грамматика Орбиты,
базирование тегом, рендеринг ИИ в `rendered.sdoc`, диф двух
базирований по узлам, PDF через html2pdf и Typst. Мера: правка тезиса
→ новый тег → диф показывает один узел; число в тексте без элемента —
отказ; PDF из Typst с титулом и подписями.
