# Компонент как узел MBSE: грани описания и пример «ПО управления КА»

Компонент — не строка состава с массой, а **узел, к которому цепляется
всё, чем живёт MBSE**: функции, стыки и обмены, режимы, параметры,
модели, бюджеты, требования, верификация, конфигурация изделия,
поставщик, документы. Ниже — грани, общие для любого компонента, и
пример поведенческого компонента, который проверяет модель жёстче
железа: **бортовое ПО управления КА**.

## 1. Два рода компонентов (как в Capella PA)

| `nature` | Что это | Пример | Capella |
|---|---|---|---|
| **node** | физический носитель: масса, габарит, тепло, крепление | БЦВМ, СЭП, антенна | PhysicalComponent (Node) |
| **behaviour** | поведенческий: функции, режимы, ресурсы вычисления | ПО управления КА, ПО ПН, ПО станции | PhysicalComponent (Behaviour), **развёрнут** на node |

Правило: behaviour обязан быть развёрнут хотя бы на одном node
(`deployed_on`); node без behaviour законен (конструкция, бак).

## 2. Грани компонента — одна карточка, много вкладок

| Грань | Что хранится | Сущности / связи | Capella |
|---|---|---|---|
| **Идентичность** | код · имя · уровень · вид · `nature` · родитель · шаблон и применимость · внешняя идентичность | `component`, `external_identity` | PhysicalComponent, UUID |
| **Функции** | какие функции исполняет | `function` → `allocation` | ComponentFunctionalAllocation |
| **Развёртывание** | behaviour → node / node ← behaviour | `link.deployed_on` | deployment |
| **Порты и стыки** | входы/выходы, физические связи, обмены через них | `interface` (стороны), `exchange.flows_over`, `port` (вычисляется из обменов) | ComponentPort, ComponentExchange, PhysicalLink |
| **Элементы обмена** | *что именно* идёт по обмену: команда, ТМ-параметр, сообщение — структура и единицы | **`exchange_item`** + **`data_type`** | ExchangeItem, ExchangeItemElement, Class/DataType |
| **Режимы и состояния** | режимы компонента, переходы, что активно в режиме | **`state_machine`** (states · transitions · triggers · guards · функции по режимам) | State Machine, Mode/State, «available in mode» |
| **Параметры** | по анкете вида (для ПО — не масса) | `parameter` × `questionnaire` | PVMT |
| **Модели** | какие модели читают/дают его параметры | `system_model.inputs/outputs` → узел | — (наше) |
| **Бюджеты** | вклад в свёртки: масса · энергия · **ресурсы вычисления** · **шина/данные** | `budget` kind mass/power/energy/link/dv/**compute**/**data** | PVMT-свёртка |
| **Требования** | носитель требований своего уровня; интерфейсные — на его стыках | `requirement.allocated_to` | Requirements VP relations |
| **Верификация** | события по методам; для ПО — SIL/HIL/ревью/WCET-анализ | `verification_event` | — |
| **Технологии** | критические технологии узла с TRL | `technology` | — |
| **Риски** | риски узла | `risk.refs` | — |
| **Конфигурация изделия** | CI и **версии изделия** (ПО v2.1 build 17) — отдельно от версий записей | **`configuration_item`**, **`product_version`** | — (CM) |
| **Нормативы** | стандарты разработки/квалификации узла | `normative_basis` требований; `standards[]` узла | — |
| **Поставщик и ответственный** | кто разрабатывает, кто отвечает в проекте | `stakeholder` (supplier) → узел; `responsible` | — |
| **Документы** | спецификация узла, ICD его стыков, план верификации | `document` со `snapshot_of` узла | — |

Вкладки карточки — грани; пустая грань показывает, что здесь ожидается
и к какой точке (зрелость), а не пустоту.

## 3. Пример: `OBC-SW` · ПО управления КА (behaviour)

| Грань | Содержание |
|---|---|
| Идентичность | `OBC-SW` · «ПО управления КА» · уровень 4 (агрегат) · `nature = behaviour` · родитель `OBC` (БКУ) · шаблон: типовой компонент «бортовое ПО управления» · применимость: с отклонением (FDIR расширен под S&F-буфер) |
| Развёртывание | `deployed_on` → `OBC-CPU` (БЦВМ, node); резервирование — холодный резерв БЦВМ-Б (второе вхождение node) |
| Функции | F-09 принять и исполнить команду · F-10 сформировать ТМ · F-16 FDIR · F-11 поддерживать ориентацию (алгоритмы СОС) · F-12 поддерживать орбиту (планирование манёвров) · F-08 транслировать альманах терминалам (через ПН) |
| Стыки | `IF-DATA-BUS` (CAN/SpaceWire к подсистемам) · `IF-TTC-OBC` (кадры TM/TC) · `IF-PL-DATA` (команды и буфер к ПН) · внутренний: `IF-AOCS-PROP` (команды ДУ) |
| Обмены и элементы обмена | `EX-TC` команда: `exchange_item` **TC-frame** {apid, seq, cmd_id, args[]} · `EX-TM` телеметрия: **TM-packet** {apid, время, параметры[] — каждый с `data_type` и единицей справочника} · `EX-EPH` альманах: **Almanac** {эпоха, элементы орбиты по КА} · внутренний `EX-AOCS-CMD` {момент ×3, Н·м} |
| Режимы (`state_machine`) | Инициализация → Демпфирование → Солнечный (safe) → Целевой (nominal) → Манёвр → Безопасный (по FDIR); переходы: `TC MODE_SET` (guard: питание ≥ порога) · `FDIR level ≥ 2` → Безопасный · таймаут связи 72 ч → Безопасный; в режиме «Безопасный» активны F-10, F-16, F-11 (солнечная ориентация); F-08 и F-12 — только в «Целевой» |
| Параметры (анкета «бортовое ПО») | загрузка CPU средняя 45 % · пиковая 80 % (к SDR) · RAM 64 МБ · ROM 128 МБ · цикл управления 100 мс · число режимов 6 · критичность **категория B** (ECSS-Q-ST-80) · RTOS «RTEMS» · язык C · объём 120 тыс. строк (оценка) · автономность без НКУ 7 сут · происхождение: типовой + оценка команды (origin shelf/manual) |
| Модели | М7 ориентация — потребитель алгоритмов (входы: моменты инерции узла КА, датчики) · М3г — генератор ТМ-потока (объём ТМ/сут из TM-packet × частота) · М14 — автономность и нагрузка операторов · **бюджет ресурсов** (compute: CPU/RAM/ROM по всем behaviour на `OBC-CPU`; data: нагрузка шины из обменов) |
| Бюджеты | вклад: compute — 45 %/80 % CPU, 64/128 МБ; data — 12 кбит/с ТМ, 0,5 кбит/с TC; масса — 0 (behaviour), энергия — через node |
| Требования (носитель) | `RQ-S-08` защита команд (криптография) · `RQ-S-05` хранение сообщений (через `IF-PL-DATA`, совместно с ПН) · функциональные по режимам: «Когда FDIR уровня ≥ 2, ПО должно перевести КА в безопасный режим в течение 10 с» (EARS: по событию) · производительность: «цикл управления ≤ 100 мс» · безопасность: «ПО должно исключать выполнение команды без аутентификации» |
| Верификация | инспекция (ревью кода, категория B) · анализ (WCET, покрытие) · испытание SIL на модели борта · HIL с БЦВМ · демонстрация режимов на ЛИ |
| Технологии | FDIR-алгоритмы: TRL 5 → 6 к PDR · планировщик манёвров ЭРД: TRL 4 → 6 · RTOS: наследие (TRL 9) |
| Риски | «SEU в памяти без ECC → зависание» (ср., выс.; ECC + watchdog) · «недооценка CPU в целевом режиме» (М-бюджет к SDR) |
| Конфигурация изделия | CI `CI-OBC-SW` · версии изделия: 0.1 (SIL-макет) → 1.0 (ЛИ) → 1.x (эксплуатация); загрузка обновлений по `IF-TTC` (F-09) — отдельное требование |
| Нормативы | ECSS-E-ST-40C (разработка ПО), ECSS-Q-ST-80C (обеспечение), ГОСТ Р 51904 — в `normative_basis` требований и `standards[]` узла |
| Поставщик | стейкхолдер-поставщик «Разработчик МКА / бортового ПО»; ответственный в проекте — ведущий СИ |
| Документы | спецификация ПО (SRS — шаблон полки), ICD `IF-DATA-BUS` и `IF-TTC-OBC`, план верификации ПО |

Что этот пример показывает: у behaviour-компонента **нет массы, но есть
ресурсы**, есть **режимы**, есть **элементы обмена с типами** — и без этих
трёх граней описать ПО нельзя, а Capella без них не соберётся.

## 4. Новые сущности и связи (дополнение к реестру)

| Вид | Поля (обязательные) | Capella |
|---|---|---|
| `component.nature` | enum node · behaviour (поле) | PhysicalComponent nature |
| `link.deployed_on` | behaviour → node; обоснование | deployment |
| **`exchange_item`** | код · имя · тип (flow · operation · event · shared_data) · элементы[{имя, `data_type`}] · обмены, где используется | ExchangeItem / ExchangeItemElement |
| **`data_type`** | код · имя · базовый тип · единица справочника · диапазон · перечисление | DataType / Class (Information) |
| **`state_machine`** | владелец-компонент · состояния[{код, имя, активные функции[]}] · переходы[{из, в, триггер (обмен/событие/таймер), guard, действие}] · начальное | State Machine / Mode / Transition |
| **`configuration_item`** | код · узел · тип (HW · SW · FW · документ) · ответственный | — |
| **`product_version`** | CI · версия изделия · дата · состав (ссылки на версии записей, baseline) · статус (макет · ЛИ · эксплуатация) | — |
| `budget.kind` | + `compute` (CPU % · RAM · ROM) · `data` (бит/с по стыкам) | PVMT |
| `questionnaire` «бортовое ПО» | загрузка CPU · RAM · ROM · цикл · режимы · критичность · RTOS · язык · объём · автономность | PVMT-группа ORBITA.SW |
| `component.standards[]` | ref normative_document | — |

Единицы для справочника: `%` (доля — есть), МБ (есть), мс (есть),
**тыс. строк** (счётная), **Н·м** (момент — добавить), категория
критичности — шкала в `method_catalog`.

## 5. Инварианты граней

1. behaviour без `deployed_on` — разрыв к SDR; node без параметров
   массы к SDR — разрыв.
2. Обмен без элемента обмена к SDR — разрыв (ICD не соберётся).
3. Компонент с режимами: каждая функция узла принадлежит хотя бы
   одному режиму; режим без активных функций — помета.
4. Параметр ресурса без бюджета — помета; бюджет `compute` считается по
   всем behaviour, развёрнутым на node.
5. Версия изделия (`product_version`) и версия записи — разные вещи;
   версия изделия ссылается на baseline записей, не наоборот.
