# Стенд: падения Postgres 08.09 — факты, решение

Заказ: ПРИЁМКА-KNOWLEDGE-REMARKS §«Стенд», пункт 2 — «не гадать, снять
факты». Снято с живого стенда 08.09 (`docker logs orbita-db-1`,
`docker inspect`, `docker stats`, `pg_settings`, `pg_stat_activity`).
Время в журнале базы — UTC; проход владельца шёл по МСК (UTC+3).

## 1. Что падало и когда

Строки постмастера за всё время жизни контейнера (журнал с 24.08):

| UTC | МСК | Строка постмастера |
| --- | --- | --- |
| 01.09 12:39:26 | 15:39 | `server process (PID …) exited with exit code 2` |
| 01.09 12:41:39 | 15:41 | `exited with exit code 2` |
| 04.09 13:47:51 | 16:47 | `exited with exit code 2` |
| 08.09 10:30:58 | 13:30 | `exited with exit code 2` |
| 08.09 10:40:00 | 13:40 | `was terminated by signal 13: Broken pipe` |
| 08.09 14:00:15 | 17:00 | `exited with exit code 2` |
| 08.09 14:05:12 | 17:05 | `exited with exit code 2` |
| 08.09 15:30:34 | 18:30 | `exited with exit code 2` |
| 08.09 17:00:05 | 20:00 | `exited with exit code 2` |
| 08.09 17:02:42 | 20:02 | `exited with exit code 2` |

Каждая строка ведёт к `terminating any other active server processes` →
`database system was not properly shut down; automatic recovery in
progress` → 30–70 с недоступности («the database system is in recovery
mode»), из них до 20 с — `syncing data directory (fsync)`.

Две строки `exited with exit code 1` (24.08, 03.09) — это штатное
завершение `logical replication launcher` при `fast shutdown request`,
не падения.

## 2. Сигнал против кода выхода — это не OOM

- Из десяти падений девять — **`exit code 2`**, одно — **сигнал 13
  (SIGPIPE)**. Сигнала 9 нет ни разу.
- `docker inspect orbita-db-1`: `OOMKilled=false`, `HostConfig.Memory=0`
  (лимита не было), `RestartCount=0`.
- Память: ВМ Docker 7,7 ГБ; `orbita-db-1` держит 42 МБ; база 40 МБ;
  `shared_buffers=128MB` (умолчание образа), `work_mem=4MB`,
  `max_connections=100`.
- Контрольные точки штатные: 3–107 буферов, до 16 с при
  `checkpoint_timeout=300s`; `max_wal_size=1024MB`; перед падениями
  ничего необычного.
- `PANIC`/`FATAL` **перед** падением нет — при `log_min_messages=warning`.

## 3. Что стоит рядом с каждым падением

Полный контекст падения 15:30 UTC:

```
15:30:34.419 [136593] LOG:  could not send data to client: Broken pipe
15:30:34.662 [136593] FATAL:  connection to client lost
15:30:34.752 [1]      LOG:  server process (PID 136592) exited with exit code 2
15:30:34.752 [1]      LOG:  terminating any other active server processes
15:30:39.155 [1]      LOG:  issuing SIGKILL to recalcitrant children
15:30:52.871 [1]      LOG:  all server processes terminated; reinitializing
15:31:09.336 [136602] LOG:  database system was interrupted; last known up at 15:16:29
```

Та же картина у 10:30, 14:00, 14:05: в ту же секунду соседний backend
(соседний PID) пишет `could not send data to client: Broken pipe`.

Пять падений 08.09 до 19:00 МСК по секунде совпадают с **остановкой
контейнера api**: 13:30 и 13:40 МСК — выкаты, 17:00 — `docker restart
orbita-api-1`, 17:05 — выкат, 18:30 — выкат. Но два падения 20:00 и 20:02
МСК пришлись на выкат, у которого **сборка не удалась** (три попытки
`DeadlineExceeded` на метаданных образа) — контейнер api не
пересоздавался и не останавливался. Значит, общий знаменатель не SIGTERM
api, а **работа выката/перезапуска на хосте Docker** (buildx, сеть
сборщика, создание и снос контейнеров).

Умершие backend — **свежие процессы**, не долгоживущее соединение api:
у api backend был PID 139037 (`idle` в `pg_stat_activity` за полчаса до
падения), умерли 142598 и, через два падения, 142702; их соседи
(142599, 142703) в ту же секунду пишут `could not send data to client:
Broken pipe`. Пара соседних PID — два подключения подряд, и это не api
(он одно соединение держал и новых не открывал). Кто — журнал сказать не
мог: `log_line_prefix` без `%a`, `log_connections=off`. Скрипты прохода
(walk_scenes, 45-секундный лимит) в базу не ходят — они ходят в api.

Что видно, а что нет:

- **Видно.** Каждое падение — в секунду выката или перезапуска на хосте;
  умирает свежий backend с кодом 2, сосед теряет клиента; соединение api
  гибнет следом («terminating any other active server processes»), и
  без переподключения api мёртв до рестарта.
- **Не видно.** Кто открывает пару подключений в момент выката и какой
  путь в backend заканчивается `exit(2)`: с `log_min_messages=warning` и
  без `log_connections` backend не оставляет ни строки. Утверждать
  механизм — гадать; заказ был не гадать.

## 4. Последствие для стенда — дефект api, не базы

Api держал **одно** JDBC-соединение без переподключения. После recovery
базы процесс жив, healthcheck красный, вход отвечает `This connection has
been closed` — до `docker restart orbita-api-1`. Любой чих базы = мёртвый
стенд.

## 5. Решение

Сделано в этом шипе (`v2-stand-pool`):

1. **Пул с проверкой и переподключением** — HikariCP в `core/mod`
   (`ReconnectingSource`): `connectionTestQuery=SELECT 1`,
   `validationTimeout=3 с`, `maxLifetime=30 мин`, `keepaliveTime=5 мин`,
   `maximumPoolSize=2`. Ядро по-прежнему видит один `Connection`
   (ADR-011), но это прокси: вне транзакции мёртвое соединение
   выбрасывается и берётся свежее; внутри транзакции — честное
   исключение, транзакция откатывается. Тест
   `ReconnectingSourceTest`: backend убивается `pg_terminate_backend`,
   следующий запрос проходит.
2. **Повтор запроса** при `connection has been closed` / SQLState 08xxx
   — `HttpApi.сПовтором`: GET повторяется один раз; запрос с телом
   повторять нельзя (тело прочитано) — он получает 503 с полем
   `retry: true` и словами «повторите запрос», а не 500.
3. **Api закрывает соединение на SIGTERM** (shutdown hook) и получает
   `stop_grace_period: 20s`: сокет закрывается, а не рвётся.
4. **Журнал базы называет клиента**: `log_line_prefix=%m [%p] %a@%h`,
   `log_connections=on`, `log_disconnections=on`; у api
   `ApplicationName=orbita-api`. Следующий обрыв читается, а не гадается.
5. **Явные числа памяти**: `shared_buffers=256MB`, `mem_limit: 1g` у
   контейнера базы. OOM исключён фактами; это гигиена — память базы не
   зависит от размера ВМ, — а не лечение.
6. **Проход владельца — хост стенда свободен**: `ops/walkthrough.sh on`
   ставит метку, при которой `ops/test-local.sh` и `ops/deploy-local.sh`
   отказывают (тесты ядра 08.09 шли 1 ч 42 м, деля процессор с api;
   каждое пересоздание api совпало с падением). `off` — снять.

## 6. Проверено живьём (08.09, 20:32 МСК)

`docker restart orbita-db-1` под работающим api нового выката: база
healthy через 7 с; первый же запрос после — `POST /api/auth/stand-login`
→ 200, `GET /api/v2/projects` → 200, повторный вход → 200; api остался
`healthy`, **без рестарта**. В журнале api: HikariCP «Connection … marked
as broken because of SQLSTATE(08003)» — мёртвое соединение выброшено,
взято свежее. В журнале базы после пересоздания каждая строка называет
клиента: `orbita-api@172.19.0.2`, `pg_isready@[local]`.

Попутно: три выката подряд не собирались — buildx-сборщик `orbita-mtu`
отдавал `DeadlineExceeded` на метаданных базового образа при исправной
сети (из контейнера сборщика реестр и `auth.docker.io` отвечают);
перезапуск сборщика не помог. Выкат прошёл сборщиком хоста
(`BUILDER=default ops/deploy-local.sh api web`, базовые образы локальные)
— путь, предусмотренный скриптом. Во время этих трёх неудачных выкатов
база не падала ни разу.

Не сделано, и почему: причина `exit(2)` в backend не установлена — по
п. 4 следующее падение придёт с именем клиента и подключениями в журнале
(проверено после пересоздания базы: `pg_isready@[local]` виден в каждой
строке). Если оно повторится с известным клиентом и закрытым (а не
оборванным) сокетом — это вопрос к самому Postgres 16.15 в этой ВМ, и
тогда снимать core dump (`ulimit -c`, `restart_after_crash`), а не менять
api. До тех пор правило простое: выкат и перезапуск на хосте стенда — не
во время прохода (п. 6), а api после любого падения базы встаёт сам (п. 1).
