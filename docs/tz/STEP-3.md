# Шаг 3. Расчётный контур: геометрия, аппарат, канал

Рабочее задание для Claude Code. Основание: архитектура разд. 9, пп. 4–5.
Область: `TZ-BAL` (9), `TZ-KA` (10), `TZ-NET` (6) — 25 требований.
Вне области: ядро Монте-Карло (`TZ-FLW`), ИИ-контур (`TZ-AI`), клиент `web/`.

**Смысл шага.** Появляется физика. После него система считает геометрию группировки,
энергетику витка, бюджеты радиолиний и зоны обслуживания — то есть всё, что нужно
модулю потоков на шаге 4. Впервые подключается внешнее расчётное ядро (Orekit).

| `spec/spacecraft_semantics.py` | 34 | Массовый бюджет, бюджет линии, зоны обслуживания, маяк эфемерид, буфер с приоритетами, регуляторный duty cycle |

**Особенность этого шага.** Эталон баллистики написан в замкнутых формулах и от Orekit

сходиться с независимым расчётом в пределах допусков. Геометрия дополнительно
привязана к реальности — радиус зоны на 550 км при угле места 25° сверяется
с известным значением работающей группировки (≈940 км).

## 1. Баллистика (`core/bal`)

### 1.1. Подключение Orekit — `TZ-BAL-001`
Пропагация, события видимости, тени, манёвры — средствами Orekit. Собственных
интеграторов, моделей тени и геометрии видимости не создавать.
Версия Orekit и модель гравитационного поля фиксируются в сценарии и входят
в `input_versions` (механика шага 1).
Данные Orekit (`orekit-data`) подключаются воспроизводимо: версия зафиксирована,
загрузка не зависит от сети во время прогона тестов.

### 1.2. Конфигуратор группировок — `TZ-BAL-003`
Walker Delta `i:T/P/F` разворачивается в перечень орбит; произвольный перечень тоже
принимается. ССО без LTAN отклоняется. Пакетный расчёт набора вариантов.
Эталон: `walker_delta`, `launch_campaigns`.

### 1.3. Предрасчёт геометрии — `TZ-BAL-002`, ADR-013
Двухуровневая сетка: видимость на грубой сетке (~800 км), затем уточнение до ячеек
спроса по границе зоны обслуживания. Результат — документ по схеме `visibility`.
**Пересчёт геометрии внутри цикла Монте-Карло недопустим** — это архитектурное
условие бюджета TZ-COM-004; на шаге 4 оно будет проверяться профилированием.
Кэш по ключу «конфигурация + эпоха + версии входов и Orekit».

**Проверить применимость сетки, а не принять на веру.** Эталон показывает: при
400 км и угле места 45° диаметр зоны падает до ~730 км, и грубая ячейка 800 км
начинает терять пролёты. Реализация обязана выявлять это условие и либо измельчать
сетку, либо отказывать с внятным сообщением. Граница лежит между 40° и 45°.

### 1.4. Энергетика витка — `TZ-BAL-004`
Энергия за виток и доля тени для худшего и лучшего сезона (северное полушарие).
Допустимая скважность ПН — величина вычисляемая, помечается `computed`.
Для ССО учитывать LTAN: терминаторная орбита даёт почти бестеневой режим.
Отрицательный баланс худшего витка помечает конфигурацию несостоятельной.

### 1.5. Спрос-взвешенное качество — `TZ-BAL-005`
Интеграл по ячейкам карты спроса (готова с шага 2) **по зонам обслуживания**,
не по геометрическому footprint, раздельно по классам A'/B'/C'.
Контрольный случай сохраняется с шага 2: при населённой карте построение
с преимуществом только у полюсов не выигрывает у наклонного.

### 1.6. Вектор KPI и Парето — `TZ-BAL-006`
Заполнение схемы `kpi-vector`: качество, экономика (число кампаний и срок
развёртывания), надёжность (кривая деградации), энергетика, среда.
Недоминируемые варианты в пространстве «экономика × качество» вычисляются;
свёртка в единый индекс, если применяется, требует явных весов и **не заменяет фронт**.

*Замечание.* Часть показателей (задержки по классам) появится только на шаге 4.
До тех пор соответствующие поля остаются незаполненными явно, а не подставляются
правдоподобными числами — заглушки, имитирующие расчёт, запрещены (CLAUDE.md §5).

### 1.7. Визуализация: данные, не картинки — `TZ-BAL-007`
На этом шаге — только выдача данных для отображения: серии для розы KPI, широтный
профиль качества с весом спроса, сетка тепловой карты доступности на трёх горизонтах
усреднения, CZML-поток для 3D. Сами экраны — в `web/`, позже.

### 1.8. Валидация против эталонов — `TZ-BAL-008`
Сверка метрик покрытия и revisit с эталонными наборами в `spec/reference/`.
Пороги: покрытие ≤ 2%, revisit ≤ 5%. Расхождение останавливает сборку.
Если эталонных наборов TAT-C нет — сформировать их из замкнутых формул
`ballistics_semantics.py` и пометить источник в файле набора.

### 1.9. Время существования и увод — `TZ-BAL-009`
Оценка времени баллистического существования с учётом массы и площади;
проверка соответствия нормам увода; потребный ΔV увода передаётся в бюджет аппарата.

## 2. Аппарат (`core/ka`)

### 2.1. Ввод модели и ограничения — `TZ-KA-001`, `TZ-KA-002`
Модель по схеме `spacecraft`; нарушения Р1/Р2/Р3 отклоняются со ссылкой на ADR
(механика шага 1). Библиотека пресетов 12U / 16U / 25–50 кг / 50–100 кг —
редактируемая конфигурация, не код.

### 2.2. Массовый бюджет — `TZ-KA-003`
Резервы по зрелости (новый 25%, модифицированный 15%, существующий 5%) плюс системный.
Сухая и заправленная масса вычисляются, помечаются `computed`.
Превышение верхней границы Р2 с учётом резервов отклоняет конфигурацию.
ΔV увода из 1.9 учитывается в заправленной массе.

### 2.3. Энергетическая модель — `TZ-KA-004`
СБ (площадь, КПД, деградация, схема установки), АБ (ёмкость, допустимая глубина
разряда), циклограмма режимов. Стыкуется с 1.4. **Потребление маяка эфемерид
входит в циклограмму** — это не опция.

### 2.4. Бюджет радиолинии — `TZ-KA-007`
Полный бюджет по каждой линии. Требуемое Eb/N0 и оверхед берутся **только из адаптера
протокола**, вручную не задаются. Бюджеты участков «терминал→КА» и «КА→НС» считаются
раздельно — сквозной бюджет не вычисляется вовсе (следствие regenerative, ADR-001).
Доплеровский сдвиг и скорость его изменения сравниваются с полосой захвата приёмника.

### 2.5. Зоны обслуживания — `TZ-KA-005`
Для каждой линии и каждого профиля терминала: угол места, при котором запас равен
требуемому, плюс **обязательный ограничивающий фактор**.
Эталон показывает физически содержательный случай: зона A' ограничена геометрией
(бюджет с запасом), зона C' — бюджетом слабой нисходящей линии до малого терминала.
Незамыкающаяся линия зоны не даёт вовсе.

### 2.6. Маяк эфемерид — `TZ-KA-006`
Расчёт занятости нисходящей линии и энергопотребления. Бюджет линии маяка считается
по худшему терминалу на краю зоны. Период маяка согласуется с допустимым возрастом
альманаха профилей терминалов; несогласованность выявляется отчётом.
Формат выбирается из трёх: расписание пролётов / полный альманах / модель орбиты.

### 2.7. Буфер store-and-forward — `TZ-KA-008`
Объём, приоритеты C' > B' > A', политика вытеснения, политика сброса.
Потери от переполнения учитываются отдельно от канальных.
Требуемый объём сопоставляется с худшим интервалом до сброса.

### 2.8. Реестр TPM — `TZ-KA-010`
Масса, энергобаланс худшего витка, запас худшей линии, ёмкость абонентской линии,
объём буфера, ΔV. Обновляются автоматически при изменении модели, тренд сохраняется
с привязкой к обзорам, выход за резерв помечается.

## 3. Адаптер протокола (`core/net`)

### 3.1. Интерфейс — `TZ-NET-001`, `TZ-NET-006`
Единственный источник параметров канала: режимы (скорость, требуемое Eb/N0, время
эфира), MAC (доступ, оверхед, ACK, нисходящий канал), модель коллизий, ёмкость.
**Ни один модуль не должен содержать констант, специфичных для LoRaWAN.**
Замена протокола — новая реализация плюс пересборка; динамической загрузки нет.

### 3.2. Реализация LoRaWAN / LR-FHSS — `TZ-NET-002`
Набор режимов SF со скоростями и порогами; LR-FHSS как вариант спутникового канала.
Адаптер без поддержки нисходящего канала отклоняется как несовместимый с Р5/Р6.

### 3.3. Коллизии и ёмкость — `TZ-NET-003`
Быстрая аналитическая модель: ALOHA с эффектом захвата и квазиортогональностью
режимов. Пошаговая симуляция событий не используется.
Ёмкость линии передаётся наружу параметром.

### 3.4. Калибровка — `TZ-NET-004`
Эталонные наборы в `spec/reference/` с указанием источника. Код GPL-симуляторов
не заимствуется. Расхождение сверх порога останавливает сборку.
Если наборов нет — зафиксировать аналитические свойства модели (максимум
пропускной способности чистой ALOHA при нагрузке 0,5; монотонность; предельные случаи)
и пометить как временный источник до появления измерений.

### 3.5. Регуляторные ограничения — `TZ-NET-005`
Предел мощности, duty cycle, частотный план по региону. Применяются и к терминалам,
и к нисходящим передачам КА. Превышение duty cycle популяцией выявляется при сборке
сценария. Регион терминала неизменен на протяжении трека (ADR-007).

## Известные ловушки

1. **Проверять применимость сетки, а не верить ADR.** Решение ADR-013 верно при
   углах места до ~40°. Условие «грубая ячейка меньше диаметра зоны» должно
   вычисляться для конкретной конфигурации, а не считаться выполненным всегда.
2. **Зона обслуживания зависит от профиля терминала.** Одна и та же линия даёт разные
   зоны для A' и C'. Расчёт «зоны спутника» без указания профиля бессмыслен.
3. **Eb/N0 — не константа аппарата.** Это свойство протокола. Появление числа
   вроде `-6.0` вне `core/net` означает, что абстракция адаптера уже нарушена.
4. **Скважность ПН вычисляется, а не задаётся.** Если она пришла как входной параметр —
   энергетический баланс потерял смысл.
5. **Маяк грузит линию везде, где есть датчики,** включая ячейки без спроса на данные.
   Забыть его в энергобалансе — занизить потребление на заметную величину.
6. **Данные Orekit — часть воспроизводимости.** Их версия фиксируется наравне
   с версией библиотеки; загрузка из сети во время прогона делает результат
   невоспроизводимым.
7. **Пустое поле честнее правдоподобного.** Показатели, зависящие от шага 4,
   остаются незаполненными явно.
