# Логика связей «Орбита ↔ Capella» + задача Code на живые шаблоны

## Принцип (владельца)

**Capella не управляет требованиями. Capella объясняет, как система
собирается их выполнить.** Истина требования — статус, версия,
базирование, показатель — в Орбите. Архитектура читается из Capella
(или из нашего внутреннего слоя функций/узлов) только на чтение.
Связи живут в Орбите (`arch_link`) с обязательным обоснованием.

## Пять связей и их смысл

| Связь | Отношение | Что говорит | Куда в Capella | Куда у нас без Capella | Считается покрытием? |
|---|---|---|---|---|---|
| Требование ↔ **функция** | `satisfied_by` | «функция реализует требование» — функциональные требования | SystemFunction / LogicalFunction (SA/LA) | вид `function` | **да** — функциональное требование без функции → разрыв к SDR |
| Требование ↔ **компонент** | `allocated_to` | «носитель отвечает» — характеристики, интерфейсные, физические | LogicalComponent / PhysicalComponent (LA/PA) | узел PBS | **да** — «Без носителя» → разрыв (есть) |
| Требование ↔ **функциональная цепочка** | `realized_by` | «сценарий выполняется этой цепочкой» — операционные/сценарные требования из ConOps | FunctionalChain | цепочка = упорядоченный набор функций (вид `function_chain`) | **да** для сценарных требований; для прочих — справочно |
| **Функция ↔ компонент** | `allocation` | «кто выполняет функцию» — функциональная → физическая архитектура | Function → Component allocation | матрица «функции × узлы» (есть) | да — функция без узла → разрыв к SDR |
| Требование ↔ **архитектурная диаграмма** | `illustrated_by` | «где это показано» — контекст для обзоров | Diagram (LAB/PAB/SAB, [FCD]) | снимок диаграммы как документ-вложение | **нет** — иллюстрация, не доказательство |

Слои Capella ↔ Орбита: OA (OperationalCapability/Activity) ↔ нужды и
сервисы (только `traced_to`, покрытия не даёт) · SA/LA ↔ функции ·
PA ↔ **узлы PBS** (идентичность узел ↔ PhysicalComponent по UUID: наш
PBS-шаблон — это и есть эталон PA).

## Правила

1. Направление: ссылки создаются в Орбите; в Capella ничего не пишется
   (сторож есть). Обратный путь требований в Capella — ReqIF через
   StrictDoc, вручную, для чтения в Requirements Viewpoint.
2. Одно требование может иметь несколько связей разных отношений;
   покрытие считается по отношению, соответствующему категории
   требования (функциональное — `satisfied_by`, характеристика —
   `allocated_to`, сценарное — `realized_by`).
3. Внешний элемент — снимок имени с датой; UUID — истина; расхождение
   имени после обновления — подсказка, не ошибка.
4. Диаграмма — вложение к обзору: SRR/SDR-пакет собирает
   `illustrated_by` автоматически как приложение.
5. Impact и граф не различают внутренние и внешние элементы.

# Задача Code: три живых шаблона

## 1. Полка «Каркас PBS» ред. 2 — по `ШАБЛОН-PBS.md`
Узлы L0–L3 обязательные, L4 по классу; коды стабильные; анкеты
сопоставлены узлам L3/L4; внешние узлы (РН, космодром) с признаком;
пары WBS. Взятие в новый проект разворачивает дерево; в существующий —
сопоставление с имеющимися узлами (диалог, не дубли). Мера: новый
проект НОО-IoT после взятия — 6 сегментов, КА с платформой и ПН
до L4, анкета платформы на узле СЭП/СОС/ДУ.

## 2. Полка «Модели системы» — по `ШАБЛОН-МОДЕЛИ-СИСТЕМЫ.md`
Вид `system_model` (проектная запись модели): статус «не построена /
прокси / расчёт», входы — ссылки на параметры узлов, выходы — с датой
и версией; связи «кормит»; готовность к точке: «модель М2 не дала
ответа к SRR» — разрыв, ведёт к экрану модели; «вход не задан» — к
анкете. Существующие расчёты (М1, М3а, М6, М12) — регистрируются записями с
выходами. **Линки М2а–г и потоки М3а–е привязаны к интерфейсам PBS**
(ребро между узлами): модель хранит `interface_ref`, интерфейсные
требования распределяются на интерфейс, сквозная латентность М3е
считается суммой плеч. **М2 радиолинии — построить четырьмя линками раздельно**: абонентская
(ПН ↔ терминал), фидерная (ПН ↔ РСС), командно-телеметрическая
(платформа ↔ НСКУ, штатный и аварийный режимы), межспутниковая (если
ISL); один расчётный движок (Фриис, запас, доплер), входы — из узлов
своих подсистем (БРТК/АФУ — ПН; КТРЛ — платформа; МБРК). Единственная
новая физика в задаче. Мера: на демо-проекте 14 записей моделей (с линками и потоками —
по интерфейсам), четыре «расчёт», остальные честно «не построена»/
«прокси»; М13 терминал и М14 наземная ИС — записи с входами из узлов
пользовательского сегмента и НКУ/НСК.

## 3. Связи Capella — по таблице выше
`arch_link.relation` ∈ {satisfied_by, allocated_to, realized_by,
allocation, illustrated_by, traced_to}; вид `function_chain`;
`model_element.type` + FunctionalChain, Diagram; покрытие по категории
требования в готовности; матрицы «требования × функции», «требования ×
цепочки» (вкладки); SRR/SDR-пакет прикладывает `illustrated_by`.
Мера: сценарное требование без цепочки — разрыв к SDR; диаграмма-fixture
привязана `illustrated_by`, покрытия не даёт, в пакет SDR попадает
приложением.

## Ловушки
1. Capella не источник требований — импорт требований из Capella
запрещён. 2. Диаграмма ≠ покрытие. 3. Модель без выхода — не модель
(«файл есть» не считается). 4. Прокси без пометки — витрина.
