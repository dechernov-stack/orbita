# Решение: структура требования, дерево, структуры Capella, читаемость

Источник — reqpilot-workbench (грамматика `.sgra`, `trace-links.yaml`,
страница требований). Берём структуру и принципы; код и дизайн не
копируем.

## 1. Структура требования — расширяем до полной

Сегодня у нас: код, формулировка, категория, родитель, обоснование,
показатель, метод верификации, статус, версия, владелец, происхождение.
Добавляем (жирным — новое):

| Поле | Смысл | Правило |
|---|---|---|
| id · code | внутренний стабильный (MID) · человеческий (UID) | есть; переименование кода не рвёт связей |
| **title** | краткое имя (для дерева, графа, попапов) | обязательно |
| statement | формулировка «‹носитель› должен…» | П13–П20 |
| category | проектное / системное / интерфейсное / … | есть |
| **priority** | высокий / средний / низкий | данными справочника; не путать с «должен/желательно» |
| status · version | статусная модель, история | есть |
| verification_method | испытание / анализ / демонстрация / инспекция | есть |
| **acceptance_criteria** | наблюдаемый результат, при котором требование считается выполненным | мягко обязательно к базированию (помета) |
| mop {op, value, unit} | показатель парой по справочнику | есть; у workbench нет — наше преимущество |
| owner | владелец | есть |
| **source** | документ-основание + якорь блока канона (Д1) | первоклассное поле, не только «происхождение пакета» |
| **normative_basis** | норматив + пункт | лёгкая форма: ссылка на объект нормы + пункт текстом; полный механизм — пакет «граф» |
| rationale | обоснование, допущения | есть |
| **tags** | свободные метки | данными; фильтр реестра и графа |
| **comment** | рабочая заметка | не печатается |
| relations | refines · derives · verifies · depends_on · **conflicts_with** | **у каждой — обоснование** (как `note` у связей задач) |

Печать и выгрузка (StrictDoc-грамматика) — по этой же структуре, поле
в поле; `.sgra` Орбиты = эта таблица.

## 2. Дерево — режим реестра требований

Два дерева, переключателем, оба с раскрытием и счётчиками на узлах:
1. **По иерархии**: проект → системные → подсистемные (derives/refines);
   узел показывает «N требований · M без показателя · K TBD».
2. **По документам-основаниям**: документ → раздел (якорь канона) →
   требование — то, что у workbench панель «Документы».

**Карточка раскрывается вниз, под строкой** (решение владельца; паттерн
П-А), во всю ширину списка — не боковой панелью. Раскладка страницы:
дерево слева (≈200 px) · список справа · карточка под строкой.

## 3. Capella — структуры данных сейчас, адаптер потом

Причина прежней отсрочки — честная: реальной модели нет, интеграция
без модели стала бы витриной. Но **структуры без модели — законны**,
если fixture помечен явно (workbench так и делает: «REAL CAPELLA TEST:
NOT EXECUTED»). Делаем:

- вид **`model_element`** (внешний элемент модели): `source_tool`
  (capella), `model_id`, `uuid` (идентичность), `type`
  (OperationalCapability · SystemFunction · LogicalFunction ·
  LogicalComponent · PhysicalComponent · FunctionalExchange ·
  FunctionalChain · Diagram), `layer` (OA/SA/LA/PA), `name_snapshot`,
  `refreshed_at`. Имя — снимок только для показа; истина — UUID.
- вид связи **`arch_link`**: требование → `model_element`, `relation`
  (satisfied_by · allocated_to · realized_by · traced_to), **rationale
  обязательно**, автор, даты.
- **носитель требования может быть внешним элементом**: в дереве
  носителей — узел-ссылка серым, «снимок от ‹даты›»; распределение,
  матрицы и impact считают его наравне с внутренними узлами.
- **адаптер `capellambse` read-only** (Apache-2.0, 0.8.0) — включается
  флагом при наличии модели; до того — fixture с баннером «модель:
  fixture, не доказательство интеграции». Backend в `.capella`/`.aird`
  не пишет никогда — сторож.
- обратный путь требований в Capella: StrictDoc → ReqIF → Requirements
  Viewpoint (ручной импорт) — описан, не автоматизируется.

## 4. Читаемость — принципы, не копия

Что делает workbench читаемым и что переносим правилами:
- **панели с заголовком и счётчиком** вместо голых блоков; плотность
  14 px, одна гарнитура, статусы бейджем с текстом (не цветом);
- **три сущности на экране** — навигация · список · карточка — и ни
  одной больше; у нас карточка вниз, значит две колонки + раскрытие;
- пустое состояние всегда с текстом («Связей пока нет.») — совпадает с
  нашим «— пусто» с причиной;
- «Открыть в штатном инструменте» — наш паттерн «к месту»;
- видимое фокус-кольцо — доступность, у нас нет — добавить в токены.

Эталон реестра в этой композиции (дерево + список + карточка вниз) —
следующая поставка, по слову владельца.

# Задача Code (в очередь после итога, кроме п. 1 — он нужен прогону)

1. **Поля требования** — миграция схемы: `title`, `priority`,
   `acceptance_criteria`, `source{doc, anchor}`, `normative_basis`,
   `tags`, `comment`; карточка и печать показывают; помета «нет критерия
   приёмки» к базированию; обоснование у связей требований.
   Пакеты Р04/Р08 ПМИ-4 несут новые поля.
2. **Дерево-режим реестра** (два дерева, счётчики, карточка вниз).
3. **Виды `model_element` и `arch_link`** + fixture с баннером; внешний
   носитель в дереве; сторож «в модель не пишем»; `capellambse` за
   флагом.
4. Токены: фокус-кольцо; статусы текстом — линт.

Меры: карточка требования показывает источник с якорем и критерий
приёмки; дерево по документам ведёт от раздела записки к требованиям;
fixture-элемент Capella назначен носителем — матрица и impact его видят,
баннер fixture на экране; грепом: записи в `.capella` — 0.
