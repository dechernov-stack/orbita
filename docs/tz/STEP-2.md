# Шаг 2. Предрасчётный контур: требования, трассировка, карта спроса

Рабочее задание для Claude Code. Основание: архитектура разд. 9, пп. 2–3.
Область: `TZ-REQ` (8), `TZ-USR` (7), `TZ-OUT-003`, `TZ-OUT-004` — 17 требований.
Вне области: баллистика, КА, протокол, Монте-Карло, ИИ-контур, клиент.

**Смысл шага.** После него система полезна без единого расчёта: инженер проходит
путь «нужда → сервис → требование → элемент → метод верификации → отчёт о зрелости»
и отдельно собирает карту спроса. Ничто здесь не требует Orekit.

## 1. Контур требований (`core/req`)

### 1.1. Нужды и стейкхолдеры — `TZ-REQ-001`
Реестр нужд по схеме `core/need`. Нужда без стейкхолдера не сохраняется.
Отчёт «нужды без сервисов-потомков».

### 1.2. Каталог сервисов и QoS-профили — `TZ-REQ-002`
Профиль отдельно по каждому виду потребителей; единый показатель на сервис
не допускается. Отчёт «класс присутствует в карте спроса, но профиля нет»
(эталон: `uncovered_consumer_classes`).

### 1.3. Требования и трассировка — `TZ-REQ-003`
Ссылка требования на сервис обязана нести `consumer_class` (Р9) — без него отклонять.
Матрица трассировки формируется из связей, не заполняется вручную.
Разрывы: требование без источника (эталон: `trace_gaps`).

### 1.4. Контроль качества формулировок — `TZ-REQ-004`
Правила: модальное «должна»; отсутствие конъюнкций в нормативной части; отсутствие
неизмеримых определений; обязательный MOP для категорий `performance` и `reliability`;
непустая формулировка. Перечень правил конфигурируем без изменения кода.
Нарушения не блокируют `Draft`, но блокируют переход в `Baseline`.

### 1.5. Flow down — `TZ-REQ-005`
Распределение требований на элементы; отчёты в обе стороны: нераспределённые системные
требования и элементы без требований (эталон: `allocation_coverage`).
Распределение на несуществующий элемент отклоняется.

### 1.6. Базирование — `TZ-REQ-006`
Условия перехода в `Baseline` (эталон: `can_baseline`): пройден контроль качества,
нет незакрытых TBD/TBR, назначен метод верификации.
Механика версий уже реализована на шаге 1 — переиспользовать, не дублировать.

### 1.7. Верификация — `TZ-REQ-007`
Метод и этап для каждого требования; связь со свидетельством по MOP; статус
«не проверено / выполнено / не выполнено». **Устаревшее (stale) свидетельство
не засчитывается** (эталон: `verification_status`).

### 1.8. Готовность к контрольной точке — `TZ-REQ-008`
Конфигурация требуемых статусов по типам объектов для SRR и SDR.
Отчёт: расхождения статусов, незакрытые TBD/TBR, разрывы трассировки, непокрытые
требования. Формируется на произвольную дату по истории версий (срез шага 1).

## 2. Контур потребителей (`core/usr`)

### 2.1. Профили терминалов — `TZ-USR-001`, `TZ-USR-002`
Классы A'/B'/C' по схеме `terminal-profile`. Профиль C' без времени реакции и профиль B'
без политики повторов отклоняются. `knows_ephemeris=false` отклоняется со ссылкой на ADR-005.
Время решения внешней системы принимается как параметр, не вычисляется.

### 2.2. Популяции и подвижность — `TZ-USR-003`
Модели только `static` и `route`; прочее отклоняется со ссылкой на ADR-007.

### 2.3. Сборка карты спроса — `TZ-USR-004`
Три слоя: население → единичные объекты и маршруты → сценарная библиотека.
Карта строится при наличии одного слоя населения.
**Сетка равноплощадная**: вес ячейки пропорционален площади, а не числу ячеек
(эталон: `build_demand_map`, `cell_area_km2`). Веса нормируются в единицу.
Версия карты фиксируется и входит в `input_versions` сценария.

### 2.4. Профили активности — `TZ-USR-005`
Суточный (24) и сезонный (12) множители. Функция выбора худшего сочетания
«час × месяц» (эталон: `worst_case_hour_month`) — она понадобится на шаге 4,
чтобы совместить пик спроса с худшей энергетикой витка.

### 2.5. Библиотека сценариев — `TZ-USR-006`
Шесть референсных сценариев из `docs/model/10-potrebiteli.md`, разворачиваются
в популяции; редактируются без изменения кода.

### 2.6. Метрики и агрегация — `TZ-USR-007`
Метрики по классам раздельно, без усреднения между классами.
Агрегация ячейка → регион → широтный пояс → вариант; сумма весов равна единице
(эталон: `demand_weighted_quality`, `latitude_profile`).

## 3. Отчёты (`core/out`)

### 3.1. Матрицы — `TZ-OUT-004`
Матрица трассировки «цель ↔ требование ↔ элемент ↔ метод» и матрица верификации.
Пустые ячейки — это разрывы, перечисляются отдельно. Устаревшее свидетельство
помечается в матрице.

### 3.2. Отчёт зрелости — `TZ-OUT-003`
Представление `TZ-REQ-008` с группировкой по типам объектов и списком блокирующих причин.

## Известные ловушки

1. **Проекция сетки.** Равноугольная сетка 1°×1° даёт ячейки, площадь которых убывает
   как косинус широты: на 60° она вдвое меньше экваториальной. Если считать вес по числу
   ячеек, высокие широты получают завышенный вес — и вся спрос-взвешенная оценка
   ломается ровно в том месте, ради которого она вводилась. Вес — по площади.
2. **Поверхностное копирование карты.** Ячейки — вложенные структуры; копирование
   внешнего контейнера оставляет их общими, и правка «копии» портит оригинал.
   Эта ошибка была допущена при разработке самого эталона и поймана его же проверками.
3. **Конъюнкция в требовании.** «Система должна принимать и должна передавать» — два
   требования в одном: их нельзя раздельно верифицировать и раздельно базировать.
4. **Устаревшее свидетельство.** Соблазн засчитать результат, который «был верным
   вчера». Правило одно: `stale` → «не проверено», без исключений.
5. **QoS одним числом.** Сервис не имеет единого показателя качества: у A' это
   вероятность доставки за сутки, у C' — вероятность уложиться во время реакции.
   Усреднение между классами лишает показатель смысла.
6. **Отчёт зрелости на «сейчас».** Отчёт обязан строиться на произвольную дату —
   иначе невозможно показать состояние на день обзора. Механика среза уже есть с шага 1.
