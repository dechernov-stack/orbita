# 20. Требования и трассировка

Статус: Draft. Источник: Концепция v0.3, разд. 3, 5.1; БП-PA Прил. 2.
Схемы: `core/need`, `core/service`, `core/requirement`, `core/component`.

Модуль реализует шаги мастера Ш1–Ш4, Ш6 и является ядром ИС: остальные модули поставляют в него свидетельства.

---

### TZ-REQ-001. Реестр нужд и стейкхолдеров (Ш1)

```
REQ:        ИС должна вести реестр нужд с указанием стейкхолдера-источника,
            его роли и приоритета, а также перечня ограничений.
RATIONALE:  Stakeholder Expectation Definition (NASA-HDBK-1009A); вершина
            цифровой нити — без неё трассировка не имеет основания.
TRACE-UP:   КОНЦ-3 (Ш1)
TRACE-DOWN: TZ-REQ-002; TZ-REQ-003
VERIFY:     TEST
ACCEPTANCE:
  - [ ] нужда без стейкхолдера не сохраняется
  - [ ] нужда, не имеющая ни одного сервиса-потомка, выявляется отчётом
  - [ ] приоритеты стейкхолдеров доступны для сортировки в отчётах
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-REQ-002. Каталог сервисов с QoS-профилями (Ш2)

```
REQ:        Сервис должен нести QoS-профиль отдельно по каждому виду
            потребителей (A'/B'/C'), каждый профиль содержит хотя бы один MOE
            с целевым значением. Единый показатель качества на сервис
            в целом не допускается.
RATIONALE:  Р9/ADR-009: один сервис обслуживает классы с несопоставимыми
            критериями качества.
TRACE-UP:   ADR-009; КОНЦ-3 (Ш2); TZ-REQ-001; TZ-USR-007
TRACE-DOWN: TZ-REQ-003; TZ-USR-007
MOP:        доля сервисов с профилем по каждому применимому классу = 100%
VERIFY:     TEST
ACCEPTANCE:
  - [ ] сервис без qos_profiles отклоняется
  - [ ] MOE без целевого значения (target) отклоняется
  - [ ] класс потребителей, присутствующий в карте спроса, но не покрытый профилем сервиса, выявляется отчётом
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-REQ-003. Двунаправленная трассировка и матрицы

```
REQ:        ИС должна поддерживать переход по цепочке
            Нужда → Сервис (×класс) → Требование → Элемент → V&V → Свидетельство
            в обе стороны и формировать матрицу трассировки по Прил. 2 БП-PA.
RATIONALE:  Цифровая нить; предъявляется на SRR.
TRACE-UP:   БП-PA Прил. 2; TZ-COM-002; TZ-REQ-001; TZ-REQ-002
TRACE-DOWN: TZ-OUT-004
VERIFY:     TEST
ACCEPTANCE:
  - [ ] для требования доступны все предки до нужды и все потомки до свидетельства
  - [ ] ссылка требования на сервис без указания consumer_class отклоняется
  - [ ] матрица трассировки формируется без ручного заполнения
  - [ ] требование без источника (traces_up) выявляется отчётом
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-REQ-004. Контроль качества формулировок

```
REQ:        ИС должна проверять формулировки требований по правилам качества:
            наличие субъекта и модального «должна», отсутствие конъюнкций
            («и/или» в нормативной части), отсутствие неизмеримых определений
            («достаточный», «оптимальный»), наличие измеримого показателя
            для категорий performance/reliability.
RATIONALE:  Выходной критерий SRR: требования полны, непротиворечивы,
            реализуемы и проверяемы (БП-PA п. 7.2).
TRACE-UP:   БП-PA п. 7.2
TRACE-DOWN: TZ-AI-002
VERIFY:     TEST
ACCEPTANCE:
  - [ ] нарушения правил перечисляются с указанием фрагмента текста
  - [ ] проверка не блокирует сохранение Draft, но блокирует переход в Baseline
  - [ ] перечень правил конфигурируем без изменения кода
STATUS:     Draft
OWNER:      ведущий системный инженер
```

### TZ-REQ-005. Распределение требований на элементы (flow down, Ш4)

```
REQ:        Системное требование распределяется на один или несколько
            элементов архитектуры. ИС контролирует покрытие: элемент без
            требований и требование без элемента выявляются отчётом.
RATIONALE:  Выходной критерий SDR/MDR: распределение требований на
            функциональные элементы корректно и полно (БП-PA п. 7.3).
TRACE-UP:   БП-PA п. 7.3
TRACE-DOWN: TZ-OUT-004
VERIFY:     TEST
ACCEPTANCE:
  - [ ] нераспределённые системные требования перечисляются отчётом
  - [ ] элементы без назначенных требований перечисляются отчётом
  - [ ] распределение требования на несуществующий элемент отклоняется
STATUS:     Draft
OWNER:      ведущий системный инженер
```

  - [ ] изменение Baseline-требования помечает зависимые требования к пересмотру

### TZ-REQ-007. Матрица верификации и свидетельства (Ш6)

```
REQ:        Каждому требованию назначается метод верификации
            (испытание/анализ/демонстрация/инспекция) и этап. Для требований
            с методом «анализ», проверяемых моделированием, ИС связывает
            требование с результатом сценария и автоматически определяет
            выполнение по сравнению MOP с результатом.
RATIONALE:  V&V Requirements, Planning, Results (NASA-HDBK-1009A);
            результат моделирования — свидетельство верификации.
TRACE-UP:   КОНЦ-3 (Ш6); TZ-FLW-002; TZ-FLW-006
TRACE-DOWN: TZ-FLW-006; TZ-OUT-004
VERIFY:     TEST
ACCEPTANCE:
  - [ ] требование без назначенного метода не переводится в Baseline
  - [ ] связь «требование ↔ результат сценария» устанавливается по MOP
  - [ ] устаревший (stale) результат не засчитывается как свидетельство
  - [ ] статус верификации требования: не проверено / выполнено / не выполнено
STATUS:     Draft
OWNER:      ведущий системный инженер
```
