# 50. Моделирование потребителей

Статус: Draft. Источник: «Моделирование потребителей» v0.2; Концепция v0.3, разд. 5.6.
Схемы: `contracts/terminal-profile`, `contracts/demand-map`.

---

### TZ-USR-001. Профили терминалов трёх классов

```
REQ:        ИС ведёт профили терминалов классов A' (односторонний),
            B' (с подтверждением), C' (оперативного управления) по схеме
            terminal-profile, включая радиопараметры, модель генерации,
            политику надёжности и параметры контура управления.
RATIONALE:  Классы потребителей — источник MOE сервисов и профилей трафика.
TRACE-UP:   КОНЦ-5.6; TZ-MOD-002
TRACE-DOWN: TZ-USR-003; TZ-USR-007
VERIFY:     TEST
ACCEPTANCE:
  - [ ] профиль класса C' без required_reaction_time_s отклоняется
  - [ ] профиль класса B' без политики повторов отклоняется
  - [ ] external_decision_time_s принимается как параметр внешней системы и не вычисляется
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-USR-002. Обязательное знание эфемерид

```
REQ:        Профиль терминала любого класса содержит признак знания эфемерид
            со значением «истина» и допустимый возраст альманаха. Передача
            «вслепую» моделируется только как деградированное состояние
            при устаревшем альманахе.
RATIONALE:  Р5/ADR-005: слепая передача расходует энергию терминала впустую
            и засоряет канал; штатный режим — передача к пролёту.
TRACE-UP:   ADR-005; TZ-COM-008; TZ-KA-006; TZ-MOD-003
TRACE-DOWN: TZ-FLW-008
VERIFY:     TEST
ACCEPTANCE:
  - [ ] профиль с knows_ephemeris=false отклоняется со ссылкой на ADR-005
  - [ ] возраст альманаха сверх допустимого переводит терминал в деградированный режим
  - [ ] в деградированном режиме интенсивность передач умножается на degraded_rate_factor
  - [ ] доля терминалов в деградированном режиме отражается в результатах сценария
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-USR-003. Популяции и подвижность

```
REQ:        Терминалы задаются популяциями (класс, география, численность,
            профиль активности, модель подвижности, прогноз роста).
            Поддерживаются модели «статика» и «маршрут»; роуминг
            регуляторных зон не реализуется.
RATIONALE:  Р7/ADR-007: подвижность первой очереди ограничена; трансграничные
            маршруты остаются, регион считается одним на трек.
TRACE-UP:   ADR-007; TZ-USR-001
TRACE-DOWN: TZ-USR-004
VERIFY:     TEST
ACCEPTANCE:
  - [ ] модель подвижности вне {static, route} отклоняется
  - [ ] маршрут задаётся треком с координатами и скоростью
  - [ ] прогноз роста численности применяется к горизонту оценки ёмкости
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-USR-004. Сборка карты спроса

```
REQ:        Карта спроса собирается тремя слоями: плотность населения на
            равноплощадной сетке (номинал ~100×100 км) с коэффициентом
            «терминалов на жителя»; единичные объекты и маршруты вне
            корреляции с населением; сценарная библиотека. Результат —
            документ demand-map с интенсивностями по классам и весами ячеек.
RATIONALE:  Р8/ADR-008: содержательная карта нужна до получения клиентских
            данных; слой единичных объектов удерживает вес малонаселённых
            стратегических районов.
TRACE-UP:   ADR-008; TZ-USR-003; TZ-USR-006
TRACE-DOWN: TZ-BAL-005; TZ-FLW-003
VERIFY:     TEST
ACCEPTANCE:
  - [ ] карта строится при наличии только слоя населения
  - [ ] добавление единичного объекта изменяет вес ячейки без пересборки остальных
  - [ ] сетка равноплощадная; веса широтных поясов не искажены проекцией
  - [ ] версия карты фиксируется и входит в input_versions сценария
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-USR-005. Профили активности

```
REQ:        Ячейка карты спроса несёт суточный (24 значения) и сезонный
            (12 значений) профили множителей интенсивности.
RATIONALE:  Худший случай — совпадение пика спроса с худшей энергетикой
            витка (зимняя ночь в северных широтах); модель обязана
            показывать эту точку, а не средние значения.
TRACE-UP:   Потребители-3.2; TZ-BAL-004
TRACE-DOWN: TZ-FLW-003
VERIFY:     TEST
ACCEPTANCE:
  - [ ] профили применяются к интенсивности при генерации потоков
  - [ ] сценарий позволяет выбрать худшее сочетание сезона и времени суток
  - [ ] отсутствие профиля трактуется как равномерная активность
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-USR-006. Библиотека референсных сценариев

```
REQ:        ИС содержит редактируемую библиотеку сценариев потребления
            (агромониторинг, метеринг, трубопроводы, трекинг транспорта,
            морские суда, экомониторинг) с типовыми параметрами популяций.
RATIONALE:  Быстрая сборка карты спроса под бизнес-кейсы; сценарии подобраны
            так, чтобы удерживать честный вес и средних широт, и северных
            районов.
TRACE-UP:   Потребители-3.3
TRACE-DOWN: TZ-USR-004
VERIFY:     TEST
ACCEPTANCE:
  - [ ] сценарий разворачивается в популяцию с валидным профилем терминала
  - [ ] библиотека редактируется без изменения кода
  - [ ] состав библиотеки фиксируется версией и входит в состав карты спроса
STATUS:     Draft
OWNER:      аналитик сервисов
```

### TZ-USR-007. Метрики по классам и агрегация

```
REQ:        Модуль определяет метрики качества по классам: A' — вероятность
            доставки за сутки и возраст информации; B' — вероятность доставки
            за N попыток, распределение задержки, среднее число попыток;
            C' — вероятность уложиться во время реакции, готовность контура.
            Метрики агрегируются: ячейка → регион → широтный пояс → вариант.
RATIONALE:  Метрики классов — источник MOE сервисов (Р9) и входы
            спрос-взвешенной оценки.
TRACE-UP:   ADR-009; Потребители-5; TZ-REQ-002; TZ-USR-001
TRACE-DOWN: TZ-BAL-005; TZ-REQ-002
VERIFY:     TEST
ACCEPTANCE:
  - [ ] метрики вычисляются раздельно по классам, без усреднения между ними
  - [ ] агрегация по уровням даёт согласованные значения (сумма весов = 1)
  - [ ] метрика класса связывается с MOE сервиса автоматически
STATUS:     Draft
OWNER:      аналитик сервисов
```
