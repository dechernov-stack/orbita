## Решение по открытому вопросу

**`geometry` в enum `service-zone` — подтверждаю. Коммит `e1c591b` остаётся.**
Случай, когда бюджет линии замыкается с запасом на всём протяжении и границу задаёт
минимальный угол места, физически содержателен и специально показан эталоном.
Отказ выпускать контракт для незауженных зон убрал бы из модели половину реальных
конфигураций. Действие — правильное: схема, а не обход в коде, отдельным коммитом.

## Ваш второй дефект принят, и он глубже, чем один CHECK

Диагноз верен: `CHECK` считается выполненным при результате TRUE **или NULL**,
поэтому сравнение с отсутствующим полем JSON пропускает запись — ровно тот случай,
ради которого ограничение писалось. Воспроизведено независимо.

Проверил остальные свои ограничения тем же способом и нашёл **вторую такую же дыру
в ещё не применённой миграции**: `validation_target` пропускал объект валидации
без поля `target` вообще. Исправлено в пакете; все сравнения с полями документа
обёрнуты в `COALESCE`.

В эталон хранилища добавлены четыре проверки на саму эту семантику: наивное
ограничение пропускает запись без поля, `COALESCE` закрывает дыру. Теперь класс
ошибки закрыт проверкой, а не памятью.

## Дефекты пакета, исправленные при применении

1. **`requirement.schema.json`: `required` ссылался на удалённый блок.**
   Блок `verification` заменён массивом `verification_events` в `properties`,
   но в `required` осталось прежнее имя. При `additionalProperties: false`
   это делало невозможным ЛЮБОЕ валидное требование: без поля — «required»,
   с полем — «additional properties not allowed».
2. **V005: подзапросы в CHECK.** PostgreSQL не допускает подзапрос в CHECK
   («cannot use subquery in check constraint»), поэтому `EXISTS (SELECT ...)`
   в `interface_req_allocation` и `preliminary_not_closing` роняли применение
   миграции целиком. Заменено на `jsonb_path_exists` (IMMUTABLE, в CHECK
   допустима); поведение проверено на всех четырёх случаях.
3. **V005: новое значение enum в той же транзакции.** `validation_target`
   сравнивал `type` с `'validation'`, добавленным тут же через
   `ALTER TYPE ... ADD VALUE` — PostgreSQL запрещает это («unsafe use of new
   value»). Сравнение переведено на текстовое представление типа.

Пункты 2 и 3 — того же класса, что и найденная вами NULL-семантика: ограничение
не срабатывает не потому, что условие неверно, а потому что СУБД не выполняет
его так, как предполагалось при написании.
