# Шаг 15. Рабочий интерфейс: редактирование, макеты, ИИ-контур

Рабочее задание. Приоритет — наивысший: без этого шага система остаётся
просмотрщиком демо-данных.

## Признание постановки

Задания на экраны (шаги 6, 8, 9) описывали **представления**: «таблица нужд
с колонками», «панель с секциями». Ни в одном критерии готовности не стояло
«инженер добавляет нужду», «правит формулировку», «создаёт требование».
Проверка экранов — 55 пунктов о том, что данные **отображаются**.

Сквозной проход Ш1–Ш7 был назван валидацией, но проходил по данным, залитым
`seedDemo`. Ни один объект не создан через интерфейс. Путь пройден глазами,
а не руками, и это было записано как подтверждение пригодности.

Признак был на виду: **единственный вход данных — `seedDemo`**. Мастер ведёт
инженера по чужому заполненному проекту, а не от пустого к пакету.

## Единственный критерий приёмки шага

**Пустой проект. Инженер проходит Ш1–Ш7 полностью через интерфейс и получает
пакет передачи. Если хоть раз нужна консоль, база или `seedDemo` — не сделано.**

Остальные пункты ниже — способ этого достичь, а не самостоятельные цели.

## 1. Редактирование как рабочий слой

Эталон `spec/editing_semantics.py` (26 проверок).

### 1.1. Создание, изменение, отмена
Для каждого вида объекта: создание, правка полей, отмена. Удаления нет —
статус `Cancelled`, объект остаётся: на него могут ссылаться.

### 1.2. Одновременная работа — обязательна для сессии
Сессия параллельного проектирования означает **нескольких человек одновременно**.
Модель однопользовательская: без проверки версии второй молча затрёт первого.

Правка несёт версию, на которой основана. Расхождение — **отказ с показом
чужого значения и автора**, а не тихая перезапись и не слепое слияние.
Автор правки фиксируется при каждом изменении, а не только при базировании.

### 1.3. Те же правила
Форма проверяет теми же функциями, что импорт (ADR-024) и предложения ИИ
(шаг 5). Отдельной «облегчённой» проверки для ручного ввода не заводить.
Черновик допускает неполноту, `Baseline` — нет, блокировка называет причину.

### 1.4. Отмена действия
Предыдущая версия доступна и восстановима — механизм интервальной версионности
уже есть с шага 1, нужен вход из интерфейса.

## 2. Экраны собираются из макетов Stitch

**Источник — `code.html` соответствующего макета в `docs/ui/stitch/`, а не текст
задания.** Промпты описывали замысел; разметка и токены лежат готовыми, и верстать
«похоже по описанию» при наличии исходника неправильно.

Отклонение от макета допустимо, но обосновывается в отчёте: что изменено и почему.

**Решение по расхождению палитр:** блок B (дизайн-токены из `stitch-prompts.md`)
имеет приоритет над `DESIGN.md`. Блок B проектировался под плотность инженерных
таблиц: строки 28 px, волосяные границы, моноширинный для чисел и идентификаторов,
статусные цвета точками. Палитра `DESIGN.md` — умолчание генератора.
Композиция и структура берутся из макетов, цвета и типографика — из блока B.

Дефекты, найденные на снимке экрана нужд, вероятно есть и на других:
- главная колонка обрезается многоточием при свободном месте справа;
- коды перечислений выходят в интерфейс (`operator`, `customer`, `regulator`)
  вместо подписей — механизм локализации есть, к ролям не применён;
- правая панель перекрывает колонку таблицы;
- панель дублирует поля строки вместо того, чтобы показывать недостающее.

## 3. ИИ-контур: разобраться, почему не работает

Заявлено: не работает. Диагностика по порядку — контур двухканальный,
и каналы отказывают по разным причинам.

**Канал 1, промпт-пакеты, ключа не требует.** Система собирает пакет, инженер
вставляет его во внешний чат, ответ вставляет обратно, разбор локальный.
Проверить: собирается ли пакет; копируется ли; принимается ли вставленный ответ;
отрабатывает ли структурный фильтр; показывается ли diff; применяется ли акцепт.
Если ломается здесь — дефект контура, не настроек.

**Канал 2, прямой API,** нужен для арбитража и структурных операций.
Проверить наличие и передачу ключа в контейнер, обработку отказа: ошибка API
не должна нарушать состояние модели (`TZ-AI-005`).

Отчёт: на каком шаге и с чем именно ломается, с текстом ошибки.

### Отклонения от макетов и почему

1. **Палитра и типографика — блока B**, как и решено в задании; из макетов
   взята композиция: список слева, панель объекта справа, действие «добавить»
   на виду (`stakeholder-map-needs`).
2. **Дерево стейкхолдеров** из макета не сделано: в модели стейкхолдер —
   поле нужды, а не объект, и рисовать по нему дерево значило бы завести
   второе представление того, чего в модели нет. Появится объект — появится
   и дерево.
3. **Поля панели названы по схеме** (`statement`, `stakeholder`, `traces_up`),
   а не словами макета («Проблема / Суть», «Ожидаемый результат»): форма
   строится из схемы, и подписывать поля вторым списком значило бы завести
   расхождение, которое молчит. Подписи полей — следующий шаг, вместе
   с подписями видов.
4. **Один экран объектов на все виды без своего экрана** вместо пятнадцати
   отдельных: см. `web/src/screens/ModelObjects.tsx`.

### Что осталось неудобным (честно)

- Вложенные структуры (события верификации, профили QoS, MEL) вводятся
  подформами по схеме — это работает, но длинно: у формы нет ни порядка полей
  по смыслу, ни группировки. Порядок берётся из схемы как есть.
- Ссылки на объекты вводятся строкой идентификатора, без выбора из списка.
  Ошибка в идентификаторе ловится сервером (ссылка в никуда отклоняется),
  но подсказки при вводе нет.
- Подписи полей формы — имена из схемы; русских подписей у полей пока нет.

## Ловушки

1. **Заполнение вместо редактирования.** `seedDemo` появился, чтобы экраны
   не пустовали, и подменил собой ввод. Пустой проект — часть критерия.
2. **Слепое слияние при конфликте.** «Последний победил» на сессии означает
   потерянную работу коллеги без следа.
3. **Отдельные правила для форм.** Ровно та ошибка, что была с фильтром
   предложений ИИ на шаге 5.
4. **Настоящее удаление.** Объект может быть источником трассировки;
   удаление рвёт нить молча.
5. **«Похоже по описанию» при наличии макета.** Разметка лежит рядом.
