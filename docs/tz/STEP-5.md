# Шаг 5. ИИ-контур

Рабочее задание для Claude Code. Основание: архитектура разд. 9 п. 8; Концепция 5.8.
Область: `TZ-AI` (6 требований) плюс структурный фильтр предложений.
Вне области: клиент `web/`.

**Смысл шага.** Три функции, которые определяют полезность инструмента на ранних
фазах: породить требования из сервисов, массово улучшить формулировки, разбить
требование на потомков с распределением на элементы.

**Наше отличие от инструментов, где ИИ предлагает напрямую человеку:** предложение
проходит структурный фильтр **до** показа инженеру. Те же правила, что применяются
к рукописному требованию — оператор условия, единицы, качество формулировки,
описание проверки, согласованность декомпозиции с деревом компонентов, свёртка
бюджета — применяются к сгенерированному. До человека доходит только состоятельное;
остальное возвращается модели на переделку. Инженер тратит внимание на смысл,
а не на вылавливание отсутствующих единиц измерения.

## 0. Долг перед шагом 5

### 0.1. ADR-014 уточнён
Расхождение имён ГПСЧ снято правкой решения, а не кода: требованием является
**свойство** (поток адресуется ключом; разные ключи независимы; отображение
детерминировано и платформонезависимо), а не конкретный алгоритм. Philox, Threefry,
BLAKE2b, SHA-256 — все допустимы. Добавлено обязательство: фактический алгоритм
фиксируется в `module_versions` сценария. Оговорка по производительности с условием
пересмотра — доля времени на генерацию свыше 20% прогона.
Заменить `docs/adr/ADR-014-mc-kernel.md` файлом из комплекта.

## 1. Канал промпт-пакетов (`core/ai`)

### 1.1. Сборка пакета — `TZ-AI-001`
Пакет: идентификатор, вид, контекст (выгрузка из модели), задание, **схема ответа
структурой**. Идентификатор воспроизводим по содержимому: одинаковый контекст
и задание дают тот же идентификатор, изменение задания — другой.
Виды пакетов первой очереди:

| Вид | Вход | Выход |
| --- | --- | --- |
| `needs_to_services` | нужды, ограничения | кандидаты сервисов с MOE |
| `services_to_requirements` | сервис, QoS-профили по классам | системные требования с условиями |
| `requirement_quality` | пакет требований | замечания и переформулировки |
| `requirement_decomposition` | требование, поддерево компонентов | потомки с распределением и видом декомпозиции |
| `verification_approach` | требование, фаза | события верификации с подходом и средством |
| `risk_register` | описание сценария | записи реестра рисков |

Перечень видов конфигурируем без изменения кода. Неизвестный вид отклоняется.

### 1.2. Разбор ответа — `TZ-AI-002`
Разбор **локальный**, без обращения к внешним сервисам. Снимается обрамление
` ```json `. Частично корректный ответ принимается в части валидных объектов;
причина отклонения называется по полю. Неразбираемый ответ не роняет обработку.

### 1.3. Структурный фильтр — новое, ключевое
Каждое предложение прогоняется через уже существующие правила эталонов:

| Источник правила | Что проверяется |
| --- | --- |
| `constraint_semantics` | оператор условия, единица, согласованность формулировки и оператора |
| `verification_semantics` | описан подход, указано средство, есть критерий успеха, не пересказ |
| `traceability_semantics` | распределение внутри области родителя, вид декомпозиции, свёртка бюджета |
| `requirements_semantics` | правила качества формулировки |

Предложение с замечаниями **не показывается инженеру**: оно возвращается в очередь
переделки с перечнем замечаний, пригодным для повторного промпт-пакета.
Отчёт по пакету: сколько предложено, сколько отбраковано и по каким правилам.

**Правила не дублируются.** Фильтр вызывает те же функции, что применяются
к рукописному требованию. Появление отдельной «облегчённой» проверки для
сгенерированных предложений — дефект: именно там и заведётся расхождение.

### 1.4. Арбитраж — `TZ-AI-003`
При загрузке ответов нескольких моделей совпавшие фрагменты выделяются локально;
**в API уходят только расхождения**. Экономия измеряется числом передаваемых
фрагментов. Источник каждого варианта сохраняется.

### 1.5. Акцепт и происхождение — `TZ-AI-004`
До акцепта предложение не участвует в расчётах, выборках и отчётах — правило
уже закреплено ограничением БД (`ai_needs_accept`, V006). Сохраняются:
идентификатор пакета, модель, автор акцепта, признак правки перед акцептом.
Массовый акцепт без просмотра интерфейсом не предусматривается: это обход
управления конфигурацией.

### 1.6. Прямой API-канал — `TZ-AI-005`
Структурные операции малого объёма: декомпозиция на компоненты, проверка
согласованности бюджетов, предложение метода верификации. Результат валидируется
по схеме целевого объекта. Отказ или ошибка API не нарушают состояние модели.

### 1.7. Применение как diff — `TZ-AI-006`
Предложение показывается построчным diff к текущему состоянию: `add`, `change`,
`keep`, `same`. Применяются только выбранные поля; пустой выбор ничего не меняет.
Ручного повторного ввода принятых значений не требуется ни на одном шаге.

## 2. Три функции целиком

### 2.1. Генерация требований из сервисов
`services_to_requirements` → фильтр → diff → акцепт. Порождённое требование несёт
трассировку к паре «сервис × класс потребителя» (Р9) и условие с оператором.

### 2.2. Массовое улучшение формулировок
`requirement_quality` над пакетом требований. **Существенная часть замечаний
детерминирована** — отсутствующий оператор, неизмеримое определение, конъюнкция:
их находят правила, без обращения к модели. К модели уходит только то, что требует
переформулирования. Это и дешевле, и надёжнее.

### 2.3. Декомпозиция требования
`requirement_decomposition` получает требование и **поддерево компонентов**.
Потомки обязаны: распределяться внутри области родителя, нести вид декомпозиции
(`allocated` или `derived`), а для распределённых — сходиться по свёртке бюджета
с остатком резерва. Нарушения отбраковываются фильтром до показа.

## Ловушки

1. **Отдельная «облегчённая» проверка для предложений ИИ.** Соблазн велик: правила
   строгие, модель часто не проходит. Но именно там заведётся расхождение,
   и сгенерированные требования окажутся мягче рукописных.
2. **Массовый акцепт.** «Улучшить тысячу требований» одной кнопкой — это обход
   управления конфигурацией. Baseline меняется процедурой с основанием.
3. **Инфляция требований.** Генерация в секундах даёт реестр, который никто
   не может проверить. Страховка уже стоит: требование без источника — разрыв,
   без плана верификации не базируется. Отчёт по пакету показывает не только
   принятое, но и отброшенное.
4. **Обращение к API там, где хватает правил.** Отсутствующий оператор и неизмеримое
   определение находятся детерминированно. Отправлять это в модель — платить
   за то, что уже умеет делать код.
5. **Схема ответа текстом.** «Верни JSON вот такого вида» в задании вместо структуры
   означает, что разбор будет угадывать. Схема — поле пакета, а не часть текста.
