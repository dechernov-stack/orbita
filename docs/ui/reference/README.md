# Handoff: «Орбита» — многопроектная инженерная система стадии Формулирования

## Overview

«Орбита» ведёт космические проекты через стадию Формулирования по NASA NPR 7120.5 / 7123.1:
Pre-Phase A → Phase A → решение KDP B. В системе много проектов; над каждым работают ведущий
системный инженер, специалист по аппарату, баллистик и экономист. Инженерная работа свободна
(правь, моделируй, сравнивай в любой момент), но проект движется по жёстким контрольным точкам:
внутренний обзор → MCR → KDP A → SRR → SDR/MDR → KDP B.

Система всегда отвечает на три вопроса: **где проект**, **что мешает пройти ближайшую точку**,
**что делать следующим**. Инструмент на весь рабочий день: плотность и спокойствие важнее
эффектности. Язык интерфейса — русский.

## About the Design Files

Файлы в этом пакете — **дизайн-референс, сделанный в HTML**: прототип, показывающий задуманный
вид и поведение, а не продакшн-код для копирования. Задача разработчика — **воспроизвести эти
экраны в целевой кодовой базе** (React, Vue, что принято в проекте), пользуясь её паттернами и
библиотеками. Если среды ещё нет — выбрать подходящий стек и реализовать дизайн в нём.

Прототип написан как один компонент с ветвлением по экрану; в продакшне это, разумеется, роутинг
и отдельные модули. Разметка прототипа использует только inline-стили — это особенность среды
прототипирования, а не рекомендация: переносите значения в токены (`tokens.css`) и классы.

## Fidelity

**High-fidelity.** Цвета, типографика, плотность, размеры каркаса и тексты — финальные;
воспроизводить точно. Данные — правдоподобная вымышленная низкоорбитальная миссия «Ротор-Л»;
обязательны только формы данных (см. «Data shapes»), сами значения система не определяют.

## Каркас (общий для всех экранов внутри проекта)

Горизонтально: **рейка разделов 52 px** (тёмная, `--rail`) · **панель операций 236 px** ·
**рабочая область** (резиновая) · **инспектор 372 px** (только там, где он есть).
Сверху — **шапка 48 px**: имя проекта и фаза; **ближайшая точка с числом незакрытого**
(кликабельна, ведёт на «Готовность к точке» — это главный элемент системы); автор последнего
изменения. На стартовом экране (портфель, создание) шапка без проекта: только система и пользователь,
панель операций скрыта.

Внутри экрана: **шапка экрана 40 px** (`--container`, нижняя граница-волосок) с названием, счётчиками,
фильтрами и главным действием справа; ниже — прокручиваемая рабочая область.

Разделы рейки (сверху вниз): Портфель · Постановка · Требования · Концепция · Модели · Контроль ·
Инструменты. Активный: фон `--rail-active`, левая полоса 2 px `--accent`, подпись белая.

## Плотность и текст — жёсткие правила

- строка таблицы **26 px**, кегль **12,5 px**; при 1440×900 в реестре видно не менее 30 строк;
- формулировка не обрезается, пока справа есть свободное место; заголовки колонок не переносятся;
- числа, идентификаторы, даты, время, единицы — моноширинным (`--font-mono`);
  показатели вида «≤ 30 с», «≥ 0,99» выравниваются вправо;
- единицы подписью («с», «Вт», «бит», «кг»); коды перечислений в интерфейс не выходят:
  не `operator`, а «Оператор сети», не `le`, а «≤»;
- пустое состояние — приглашение к действию с глаголом, не серый прочерк;
  ошибка называет, что случилось и что сделать, без извинений;
- десятичная запятая, неразрывный пробел в разрядах («5 400 кг», «1,74 млрд ₽»);
- у каждого экрана есть наведение (`--container-2`), выбранная строка (`--selection` + левая
  полоса 2 px `--accent`), пустое состояние и ошибка;
- теней нет; углы 6–8 px; все границы — волосок 1 px `--hairline`.

## Screens / Views

22 экрана, все связаны сквозными переходами. Идентификаторы в скобках — ключи экрана в прототипе.

### Раздел «Портфель»

1. **Портфель проектов** (`portfolio`) — стартовый экран. Заголовок 18 px + подпись про стадию;
   справа «Создать проект» (акцентная кнопка) и «Загрузить пачкой» (вторичная). Сетка карточек 2×2,
   зазор 12 px, карточка: имя 15 px, подпись, чип фазы справа; полоса ближайшей точки на
   `--container-2` (название точки, дата моно, число незакрытого — `--error` при >10, иначе
   `--status-approved`); низ — стопка аватаров команды, подпись «N участников», последнее изменение.
   Вся карточка кликабельна → жизненный цикл.
2. **Первая установка** (тот же экран, флаг `firstRun`) — проектов нет: карточка по центру
   объясняет, что за система, и предлагает «Создать первый проект» / «Загрузить данные пачкой».
3. **Создание проекта** (`create`) — имя, фаза (сегмент из двух), таблица контрольных точек
   (набор подставлен по фазе, даты правятся): точка · содержание · дата · ответственный.
   Проект создаётся пустым, без образцов. «Создать проект» → жизненный цикл.
4. **Жизненный цикл** (`lifecycle`) — лента из шести карточек точек (верхняя полоса 3 px цветом
   состояния, статус, дата, шкала прогресса, примечание). Ниже слева карта операций текущей фазы
   (Pre-Phase A: О1–О15, Phase A: О1–О17) в три колонки: код моно, название, маркер состояния
   (выполнена / в работе / не начата). Справа — красный блок возврата после отрицательного
   заключения (куда вернули и что снять, поимённо) и список «Что делать следующим» с числом
   незакрытого; каждая строка ведёт на нужный экран.

### Раздел «Постановка»

5. **Цели миссии** (`goals`) — реестр: идентификатор `MG-0001` · цель · показатель эффективности
   MOE · целевое · текущая оценка · статус.
6. **Нужды стейкхолдеров** (`needs`) — `ND-0001` · стейкхолдер · роль · приоритет (цветом) ·
   формулировка · ограничения · статус.
7. **Сервисы и QoS** (`services`) — `SV-0001` · сервис · три колонки профилей по классам
   потребителей **A′ / B′ / C′** в формате «задержка · готовность · полоса» · статус.

### Раздел «Требования» — эталон плотности

8. **Реестр требований** (`req`) — главный рабочий экран. Шапка: поиск, фильтры, счётчик, действие.
   Таблица с группами по уровню (проект / система / элемент): заголовок группы 26 px на
   `--container-3`; колонки — идентификатор `RQ-0001` · формулировка · показатель (моно, вправо) ·
   статус · верификация · источник (красный, если разрыв). Справа — **инспектор 372 px**:
   - шапка: идентификатор, уровень, статус, формулировка, переключатель четырёх состояний;
   - вкладки: Определение · Трассировка · Распределение · Верификация · История · ИИ;
   - **Определение**: показатель крупно (26 px моно), метод верификации, обоснование, источник;
   - **четыре состояния инспектора** (проп `inspectorState`):
     `baseline` — зелёная рамка «Требование базировано», поле основания и действие
     «Изменить с основанием»; `conflict` — красный блок «показатель пересчитан после базирования»
     (было / стало / что делать); `gap` — на вкладке трассировки красный блок разрыва вниз
     с действиями; `history` — версии v1…v6 (версия, дата, автор, что изменилось, статус) с «Откатить».

9. **Матрицы** (`matrix`) — вкладки «Трассировка» (требование × источник) и «Верификация»
   (требование × событие). Отметка — точка на `--selection`. Строка без единой отметки подсвечена
   `--error-surface`. Справа панель 330 px «Разрывы» со счётчиком и карточками разрывов
   (идентификатор, вид, что не так, владелец, действие) — разрыв показывается списком, а не
   пустой ячейкой.

### Раздел «Концепция»

10. **Альтернативы (AoA)** (`aoa`) — четыре карточки вариантов (выбранный — рамка и фон
    `--selection`) с ключевыми числами; ниже сравнительная таблица по шести критериям
    (значения выбранного варианта на подложке `--selection`, правило «больше/меньше — лучше»);
    внизу — выбранный вариант с обоснованием (зелёная левая полоса 3 px).
11. **Состав системы и WBS** (`wbs`) — дерево с отступом по уровню: идентификатор · элемент ·
    состав · масса · мощность · остаток резерва (красный ниже нормы) · владелец; под таблицей —
    бюджеты массы и энергии со шкалами.
12. **Интерфейсы ICD** (`icd`) — матрица «элемент × элемент», в клетке вид интерфейса
    (питание, команды, данные, радиолиния); диагональ закрыта.

### Раздел «Моделирование»

13. **Входы моделирования** (`siminputs`) — реестр входов (группировка, орбита, аппарат,
    карта спроса, станции, модель атмосферы, профиль потребления, горизонт): значение, владелец,
    дата, состояние «актуален / устарел» (устаревшие помечают результаты).
14. **Баллистика** (`ballistics`) — глобус 320×320 в ортографической проекции: **реальные
    береговые линии и границы** (Natural Earth 110m, файл `src/coastlines.js`), градусная сетка
    20°, трассы аппаратов, зоны обслуживания и наземные станции; легенда справа. Внизу шкала
    времени с полосами пролётов. Справа панель 372 px — расписание пролётов:
    аппарат · цель · начало · конец · длительность (без обрезки).
15. **Карта покрытия** (`coverage`) — сетка ячеек 18×9 (20°), в ячейке среднее окно в минутах;
    легенда трёх порогов, переключатель горизонта (24 ч / 7 сут / 30 сут); провалы видны с первого
    взгляда (`--error-surface`), под сеткой — пояснения по худшему окну и целевой полосе.
16. **Сравнение вариантов** (`compare`) — роза KPI по шести осям (два многоугольника: выбранный
    вариант и альтернатива), таблица под/рядом, устаревший результат помечен красной плашкой
    в шапке с действием «Пересчитать».

### Раздел «Контроль»

17. **Готовность к точке** (`readiness`) — слева зрелость по видам объектов (сделано, %, шкала,
    что мешает); справа «Незакрытое поимённо»: идентификатор · вид · объект · что мешает ·
    владелец, каждая строка ведёт на объект. Действие «Запросить прохождение» открывает диалог:
    либо перечень «не готово», либо переход к **фиксации решения** (положительное / с отступлениями /
    отрицательное + поле основания).
18. **Замечания обзора (RFA/RID)** (`rfa`) — идентификатор · обзор · классификация
    (критическое / замечание / вопрос / рекомендация) · содержание · статус · владелец · срок.
19. **Риски** (`risks`) — реестр (вероятность, ущерб, зона, владелец, меры) и матрица 5×5 справа:
    по вертикали ущерб, по горизонтали вероятность, в клетке число рисков; красная зона требует
    утверждённого плана до KDP B.
20. **Технологии** (`trl`) — технология · текущий TRL · требуемый TRL (красный при недоборе) ·
    план повышения · владелец.
21. **Документы** (`docs`) — комплект фазы: шаблон · точка · состояние · статус · выпущен ·
    пробелы; в шапке цепочка Draft → Preliminary → Approved → Baseline. Справа карточка выпуска:
    разделы с их готовностью, красный блок пробела, действия «Выпустить редакцию» / «Сравнить».

### Раздел «Инструменты»

22. **Предложения ИИ** (`ai`) — пакет предложений списком: объект, поле, было → стало
    (новое значение на подложке `--selection`), обоснование; акцепт выборочно и пачкой;
    принятое помечается зелёным «ИИ · принято». Справа — отчёт фильтра: сколько предложений
    снято до показа и по каким правилам.
23. **Загрузка пачкой** (`importb`) — четыре шага: файл → отчёт проверки до записи
    (строка · идентификатор · поле · правило · решение) → подтверждение → результат.
    Отдельное состояние — отказ всей пачки: что не так и что сделать, красный блок.

## Interactions & Behavior

- **Навигация**: рейка выбирает раздел (и открывает его первый экран), панель операций — конкретный
  экран. Все переходы мгновенные, без анимаций. Шапка проекта: клик по ближайшей точке → «Готовность».
- **Наведение**: строки таблиц и карточки — фон `--container-2`; карточка проекта — граница `--accent`;
  акцентная кнопка — `--accent-hover`.
- **Выбор**: строка реестра требований — `--selection` + левая полоса 2 px `--accent`; инспектор
  показывает выбранное требование.
- **Диалоги** (запрос прохождения точки) — перекрытие `rgba(15,28,44,0.32)`, карточка 560 px по центру.
- **Загрузка пачкой** — шаги переключаются кнопками; до подтверждения в реестр ничего не пишется.
- **Предложения ИИ** — принятие переключает вид карточки (зелёная рамка, метка «ИИ · принято»);
  «Принять пачкой» принимает все, «Снять всё» сбрасывает.
- Анимаций и переходов в системе нет намеренно.

## State Management

Прототип держит: `screen` (ключ экрана), `firstRun` (пустой портфель), `req` (выбранное требование),
`tab` (вкладка инспектора), `ins` (состояние инспектора: baseline / conflict / gap / history),
`mtab` (вкладка матриц), `modal` (null / notready / decision), `acc` (принятые предложения ИИ),
`imp` (шаг загрузки: 1–3, 4 — отказ пачки), `coast` (геометрия береговых линий, подгружается
динамически).

В продакшне это: роут экрана, выбранный объект инспектора, фильтры реестров, состояние диалогов,
и серверные данные по каждому реестру.

## Data shapes (обязательны, значения — нет)

- идентификаторы: `RQ-0001` (требование), `ND-0001` (нужда), `SV-0001` (сервис/аппарат),
  `MG-0001` (цель), `RFA-001`, `RSK-001`, `TRL-001`, `DOC-001`, `IN-0001`, `ICD-007`;
- требования: измеримый показатель в СИ + единица, уровень «проект / система / элемент»,
  статус Draft / Preliminary / Approved / Baseline, метод верификации
  (Анализ / Испытание / Демонстрация / Инспекция), источник, история версий с основанием;
- классы потребителей: `A′ / B′ / C′`;
- контрольные точки: внутренний обзор, MCR, KDP A, SRR, SDR/MDR, KDP B.

## Assets

- `src/coastlines.js` — береговые линии и границы, полученные из Natural Earth 110m
  (world-atlas 2.0.2, public domain), проредённые до ~4 000 точек и записанные как массив
  полилиний `[[широта, долгота], …]`. В продакшне берите геометрию из своего гео-слоя
  (d3-geo + TopoJSON) — глобус не рисуется от руки.
- Шрифты — Google Fonts (Inter, JetBrains Mono). Иконок и растровых изображений в системе нет.
