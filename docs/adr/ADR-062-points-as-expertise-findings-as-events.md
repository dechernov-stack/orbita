# ADR-062. Точки как экспертизы: замечание — событие движка, решение — с ролью, переход фазы — только KDP-A

**Статус:** Принято · 2026-09-09
**Контекст:** `ЗАДАНИЕ-CODE-БОЛЬШОЕ` §Шип D (сцены 15–18), `СЦЕНАРИЙ-PRE-A`
сцены 15–18, `РОМАНОВ-СТАДИИ-0-2` §5–6, `СХЕМЫ-ПОЛЕЙ-V2` (виды `gate`,
`finding`, `decision`), ОНТОЛОГИЯ-PRE-A (Замечание → Сцена).

## Решения

**1. Замечание обзора — событие, не флаг.** `finding` с `returns_to_scene`
читается движком при каждом пересчёте: пока замечание открыто, у сцены
возврата появляется условие выхода `finding_closed:<код>` с текстом
замечания, и прожитая сцена снова `OPEN`; закрыли — условие исчезает,
сцена прожита вновь. Ни поля «переоткрыта», ни ручного статуса: состояние
по-прежнему ВЫЧИСЛЯЕТСЯ из данных (ADR движка). Замечание тем самым
само собой попадает в «Мои задания» роли сцены — они читают условия
сцен. У точки критерий `findings_closed:<точка>`: MCR ждёт закрытия
замечаний внутреннего обзора, KDP-A — RFA/RID обзора MCR.

**2. Пройденность точки — в реестре, не в памяти api.** До шипа D
пройденные точки жили в `MutableSet` внутри api и исчезали с выкатом.
Теперь решение — запись `decision` (кем · когда · исход · помета), точка
получает статус `passed`/`returned` и ссылку на решение; движок читает
пройденность из записей (`GateRecords`). Порт движка остался прежним
(`passedGates`), тесты волны 1 живут без изменений.

**3. Решение принимает роль точки.** У точки шаблона — `role`
(`lead` у внутреннего обзора, `da_review` у MCR и KDP-A); движок
отказывает чужой роли словами с именами («решение по точке «MCR»
принимает DA; ваша роль — инженер (Петрова М.)»). Роли приходят в
маршруты v2 учёткой (`Actor`): обвязка HTTP берёт роль в проекте, а на
стенде руководитель носит и `da_review` — то же правило, что в реестре
прав v1. Запись в v2 без сессии при включённом входе — 401 (раньше
маршруты v2 шли мимо входа вовсе). Исходы решения: `approve` (при
блокирующем — `GateHeldException` → 409 с критерием), `return` (только
при открытых замечаниях), `defer`.

**4. Экспертиза — данными полки, готовность — таблицей зрелости.**
У MCR в шаблоне `expertise` (цель, вопросы валидации, результаты, главный
итог) и **контрольные позиции EXP-0A** с кодом зрелости и ссылкой на наш
артефакт (`our_ref`: `kind:goal`, `document_template:conops`, …).
`MaturityTable` — единственное место, где код превращается в условие:
для документа С → начат, Р/U/Δ → полон к ступени, F/Σ → базирован — и
только документ ДЕРЖИТ точку; для записи реестра любой требующий код →
«записи есть» — помета со состоянием ✓/☐, точку не держит (держать
ворота на «есть хоть одна цель» значило бы подменять критерии сцен
владельца: MCR ждёт сцен 3–8); x и ° — не требуют.
Несопоставленная позиция видна с пометой «не проверяется», а не
спрятана. Это и есть «DMN готовности» задания — таблица решений в коде,
без Flowable DMN: движок и так считает состояние сам (CMMN порождается,
но не исполняется), и второй исполнитель правил дал бы два ответа на
один вопрос.

**5. KDP-A — матрица зрелости Д1–Д9 и переход фазы.** Строки матрицы
(артефакт × три точки, коды) — данные шаблона; проверка к своей точке
той же таблицей. FAD (Д1) и FA (Д9) шаблонов не имеют — строки
информационные, с пометой «придёт шипом C п. 2». Решение `approve` на
точке с `opens_phase` пишет фазу в запись проекта; движок читает фазу из
данных (`Phase A`), шаблон Phase A придёт шипом G — переход случился,
лента Pre-A осталась прожитой.

**6. Легенда кодов зрелости — предположительно.** Расшифровка С · Р ·
F · U · Σ · Δ · x · ° в полке помечена «предположительно»; шаблон несёт
`maturity_note`, экран показывает её при позициях. EXP-0B (экспертиза
концепции миссии, конец стадии 0) в полке не транскрибирована — MCR
сопоставлен с EXP-0A по псевдониму «экспертиза замысла»; вопрос
владельцу в отчёте шипа.

## Последствия

- Новые условия оценщика: `findings_closed:<точка>`, `exists:<вид>`,
  `document_started|complete|baselined:<шаблон>` — у каждого тест на
  отказ (сторож `validate_gate_checks`), все только читают (сторож
  `validate_checks_readonly`).
- `GateView` несёт критерии целиком, экспертизу, замечания, решение,
  матрицу; сериализатор один — `PhaseJson.точка` (сторож
  `validate_one_serializer`; позиция экспертизы и строка матрицы — один
  вид `PositionView`, иначе сторож честно находил два).
- Экран «Точки» (волна 6 по плану) ожил шипом D: список точек, карточка
  вниз — готовность, чек-лист (внутренний обзор — по критериям MCR),
  экспертиза с вопросами и «нет — замечание», матрица, замечания,
  решение. Спрятанных кнопок нет: отказ сервера показывается словами.
- Прогон `walk_scenes.py --points` идёт сценами 15–18 до KDP-A и
  проверяет меру шипа: инженеру — отказ ролью, замечание возвращает
  сцену, после решения DA фаза — Phase A.
