# ADR-071. Служебный вход инструментов стенда

**Статус:** Принято · 2026-09-28
**Контекст:** Стенд 216 опубликован за входом целиком (ADR-065): каждый вход
инструмента (загрузчик полок `load_shelves.py`, прогон `walk_scenes.py`) ждёт
подтверждения владельца в Telegram, а ссылка входа живёт 5 минут
(`AUTHGW_TOKEN_TTL`). Для разовой заливки это терпимо, для повторяющихся
операций — нет (владелец 27.09: «каждый раз ждать с Telegram — не дело»).
Нужен неинтерактивный машинный доступ на **дев-стенд** — как deploy key у CI.

Прямой обход (переиспользовать сохранённую Telegram-сессию владельца, чтобы
ходить «как он») отвергнут: он выдаёт машину за человека, необратим и
неотзываем. Делаем служебный доступ, который владелец **заводит и отзывает сам**.

## Решение

1. **Служебная личность `service:orbita-tools`** («служебный orbita-tools») —
   СВОЯ учётка, не заимствованная у владельца. Схема логина расширена явно
   (V103, как `tg:` в V047): `service:[a-z0-9_-]{1,24}`. В журнале действия
   идут «служебный orbita-tools», не «Чернов Д.».
2. **Вход ключом.** `ORBITA_SERVICE_KEY` в `.env` стенда → `POST
   /auth/service-login` (ключ заголовком `X-Orbita-Service` либо телом
   `{"key":…}`; тело не попадает в access-логи прокси). Ключ совпал — сессия
   служебной личности; сравнение — `MessageDigest.isEqual` (как у HMAC
   сессии). Только режим `telegram`; ключ не задан — маршрута нет (404).
   Логика вынесена в `ServiceLogin.решение` и покрыта тестом.
3. **Права — как у владельца (ADR-066):** служебная личность — владелец
   системы (`systemOwner`), роль `*`→lead и lead в живых проектах, `act-as`
   любой роли. Скоуп владелец выбрал широким (любые проекты стенда, 27.09):
   риск утечки принят осознанно.
4. **Отзыв — одной строкой.** Сессии служебной личности снимаются при КАЖДОМ
   старте (`dropSessionsOf`): убрал/сменил `ORBITA_SERVICE_KEY` в `.env` и
   перезапустил контейнер — ключ мёртв, живые сессии сброшены. Срок сессии — 1
   день (не 30).
5. **Граница.** Прод-переброску (ворота Conductor, Approve в UI) ключ НЕ
   трогает — это другая система, стенд-ключ туда не дотягивается. Сохранённую
   Telegram-сессию владельца инструменты по-прежнему не используют.

## Последствия

- Загрузчик полок и прогон на 216 идут без Telegram, когда в окружении задан
  `ORBITA_SERVICE_KEY` (тот же, что в `.env` сервера); нет ключа — прежний вход
  через бота (`stand_session.py` выбирает путь сам).
- Ключ — секрет: живёт только в `.env` сервера, в git не коммитится.
- Это дев-стенд. На проде маршрут бессмыслен без `telegram`+ключа, а
  прод-ворота остаются за владельцем.
