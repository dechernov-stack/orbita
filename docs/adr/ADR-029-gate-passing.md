# ADR-029. Прохождение контрольной точки и возвраты

**Статус:** принято
**Контекст:** блок B задания «прогон до KDP B». Система знает шесть точек
(`gates.json`) и операции обеих фаз (`operations.json`), умеет считать
зрелость (`/reports/maturity`), но проект по точкам не движется: прохождение
не фиксируется, возвраты §5.1 регламентов не воспроизводятся, состояние
операции никто не считает.

**Решения.**

1. **Точка проходится проверкой, а не кнопкой.** `POST /gates/{gate}/pass`
   не имеет параметра «пройти всё равно». Сервер собирает перечень
   незакрытого; пустой перечень — единственное условие прохождения.
2. **Состав проверки зависит от точки.** Полный отчёт зрелости требует
   и полной верификации — для стадии Формулирования это неправда: верификация
   закрывается в Phase C/D, и точка Pre-Phase A, ждущая закрытых событий
   верификации, не прошлась бы никогда. Прохождение проверяет:
   - статусные разрывы против реестра точек — на всех шести точках;
   - незакрытые TBD/TBR и разрывы трассировки — с SRR и далее
     (базирование требований, §7.1 БП-PA);
   - незакрытые блокирующие замечания обзора (RFA/RID) — на всех точках,
     как только вид появится (блок C); до этого проверка честно отсутствует
     в перечне, а не молчит о найденном.
   Полная верификация остаётся в отчёте зрелости как сведение, но точку
   Формулирования не блокирует.
3. **Прохождение фиксируется решением.** Готовая точка порождает объект
   `decision` (альтернативы Approve/Return/Terminate — состав рассмотрения
   KDP, §7.3/§7.4), `selected: Approve`, основание — от инженера; веха
   проекта получает `held: true` (правка объекта проекта тем же рабочим
   слоем, с автором). Ближайшей становится следующая непройденная веха.
4. **Точки проходятся по порядку вех проекта.** Запрос прохождения не
   ближайшей непройденной точки — отказ: перескочить MCR нельзя (КТ-1 →
   КТ-2 → КТ-3, §4.5 обоих регламентов).
5. **Возврат — состояние проекта.** `POST /gates/{gate}/return` записывает
   в объект проекта поле `return` {точка, операции по §5.1, причина, автор}
   и порождает `decision` с `selected: Return`. Пока возврат не снят
   (`POST /gates/return/resolve`, с автором и основанием), прохождение
   любой точки отклоняется; операции возврата помечаются в реестре операций.
   Допустимые цели возврата — из §5.1 регламентов, зашиты в реестр
   операций, а не в код.
6. **Состояние операции считает сервер** по объектам проекта: у операции
   есть виды выхода (`operations.json`) и требуемый статус к её точке.
   Нет ни одного объекта вида — «не начата»; объекты есть, но не все
   достигли требуемого статуса — «в работе»; все достигли — «выполнена».
   У операций без видов выхода в системе (стоимость, ODA — до блока C)
   состояние — «нечем измерить», видимый пробел, а не прочерк.

**Последствия.**
- Схема проекта получает необязательное поле `return`; веха — `held`
  (существует с шага 17) и `held_at`.
- Эталон — `spec/process_backbone.py`: состояние операции, состав проверки
  по точкам, порядок вех, блокировка возвратом.
- «Сколько точек стало проходимо» — измеримо: перечень незакрытого точки
  пуст или назван поимённо.
