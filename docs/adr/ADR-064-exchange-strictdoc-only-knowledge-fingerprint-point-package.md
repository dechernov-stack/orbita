# ADR-064. Обмен v2: StrictDoc — единственный ReqIF, выгрузка знаний с отпечатком, пакет точки; ТЗ оценивается от нужды

**Статус:** Принято · 2026-09-09
**Контекст:** `ЗАДАНИЕ-CODE-БОЛЬШОЕ` §Шип F; ADR-049 (StrictDoc — канал);
ADR-023 (собственный ReqIF, условие сноса — ответ владельца 03.09 §1: пять
проверок эквивалентности на данных стенда); `ШИП-E-ПРИНЯТ` п. 1 (режим `tor`
на настоящем ТЗ обязан показать дыры против нужд); Ф-10 первой версии
(выгрузка знаний с отпечатком, `core/com KnowledgeExport`).

## Решения

**1. Модуль `core/v2/exchange` — порт `Exchange`, служба StrictDoc — порт
`StrictDocService`.** Ядро раскладывает реестр v2 в грамматику Орбиты поле в
поле (`SdocPayload`: нужды со стороной по связи `owns`, сервисы с нитями
`covers`, требования с показателем `measure` → `mop{name, operator,
value{value, unit}}`, `source` → `SOURCE_DOC/ANCHOR`, нити вверх только на
то, что есть в документе; порядок — по кодам). Всё остальное — `.sdoc`,
ReqIF, разбор — делает служба `ops/strictdoc` по HTTP (`HttpStrictDoc`).
Служба не настроена — отказ словами (`ExchangeUnavailable` → 503 с
`ADR-049`), не пустой файл. Тесты идут с подставной службой: проверяется
то, что делает ядро, а настоящий StrictDoc — `tools/v2/check_exchange.py`
на стенде.

**2. Импорт `.sdoc` — тем же путём, что любой входной документ.** Файл
ложится материалом вида `sdoc`, каждое требование — фактом `obligation` с
якорем блока канона (`UID: …`), план — действиями «завести требование» с
кодом UID (`EntityIntake.accept` теперь берёт код из payload и у
требования, как у узла). В модель канал сам не пишет: требование появится
принятием действия в поле знаний. Так экспорт → импорт → экспорт совпадает
побайтно по блокам требований (тест `ExchangeTest`, живьём —
`check_exchange.py`).

**3. Собственный ReqIF снесён.** Пять проверок `tools/check_reqif_equivalence.py`
на данных стенда (PJ-0001: 248 объектов, 233 связи) дали пять «да» —
запись в `docs/tz/v2/отчёты/ШИП-F-ОТЧЁТ.md`. Удалены `core/out/ReqifExport.kt`,
`ReqifMapping.kt`, их тесты, `spec/reqif_semantics.py`,
`tools/check_reqif_roundtrip.py`, сборка в `ops/exchange` (`/reqif/export` →
410 с адресом нового канала). Осталась сторона РАЗБОРА: `ops/exchange`
`/reqif/parse` (библиотека `reqif`) и `core/out/ReqifImport.kt` — имена
атрибутов обоих словарей (прежний свой и грамматики Орбиты) в поля
черновика, незнакомые — в `foreign_attributes`. Адрес `/export/reqif`
сохранён и отдаёт файл StrictDoc; `/export/reqif/check` удалён — проверять
нечего.

**4. Три провала StrictDoc-канала от 03.09 сняты в адаптере `ops/strictdoc`,
а не в ядре.** (а) MID с буквой впереди — XSD OMG требует от `xsd:ID`
начала с буквы; (б) многострочные поля — XHTML
(`--reqif-multiline-is-xhtml`), однострочные StrictDoc 0.29 пишет через
`unicode_escape` — `_plain_strings` возвращает текст текстом: ReqIF читают
чужие инструменты; (в) `_stable_ids` выводит из MID документа, тега, роли и
ссылок узлов те идентификаторы структуры, что StrictDoc раздаёт заново при
каждом экспорте (шапка, типы, типы связей, связи, узлы иерархии) —
повторная выгрузка неизменённого проекта даёт тот же файл (кроме времени).
Штатный `strictdoc convert reqif → sdoc` в 0.29.0 (последняя на PyPI на
09.09) падает на связи между типами (`SERVICE → NEED`, KeyError ForeignID)
— поэтому обратный путь проверяется тем, чем идёт изделие: разбором
библиотекой (`/import/reqif`), а `strictdoc convert` — пометой в строке
проверки 5.

**5. Выгрузка знаний v2 (`KnowledgeExportV2`) — MD-файлы с отпечатком в
шапке каждого.** Алгоритм отпечатка тот же, что у первой версии
(`KnowledgeFingerprint`: sha256 по отсортированным файлам, имя + тело без
шапки, 16 знаков) — и вынесен в `exchange.api`, чтобы сверять одним числом.
Части: инструкция (правила контура), замысел, ограничения с рамками,
постановка, стейкхолдеры, нормативы полки с пунктами и порогами, глоссарий,
каноны материалов с якорями `sN#M`, **факты по диспозиции — принятые ·
допущенные (с владельцем и точкой) · замеченные, каждый с якорем**;
свободные и отклонённые не идут. `POST /v2/export/knowledge/verify` —
отпечаток внешней службы против нынешнего: устарел — предупреждение, не
отказ (знания на стенде меняются чаще, чем идёт диалог во внешнем контуре).

**6. Пакет точки — один архив** (`GET /v2/points/{key}/package.zip`): JSON
точки как её видит движок (критерии, экспертиза, замечания, решение,
матрица), печать каждого заведённого документа фазы (PDF модулем
документов), `orbita.sgra` + `<проект>.sdoc`, пакет знаний, манифест с
отпечатком и составом. Без службы StrictDoc `.sdoc` не прикладывается — и
манифест говорит об этом словами.

**7. Оценка ТЗ против нужд — в две стороны, с дырой словами** (ответ
владельца 09.09 п. 1). Строка от требования получает `note` (почему partial
или none); блок `needs` — по каждой нужде проекта: `covered · partial ·
uncovered` и `gap` («нет требования на широты выше 70°», а не «покрыто
частично»). Что можно посчитать по данным, считается по данным: нужда без
единой строки — непокрыта, что бы ни сказала модель. Список `gaps` — то,
что видно первым в поле знаний и в плане: частично покрытая нужда — тоже RFA
заказчику с дырой, сирота — RID с причиной. Прогон на настоящем ТЗ до этой
правки показал 59 фактов и 59 строк, но ни одной дыры владельца по имени —
оценка «от требования» их назвать не может по построению.

## Последствия

- Маршруты v2: `GET /v2/export/sdoc[?grammar=1]`, `GET /v2/export/sdoc/reqif`,
  `POST /v2/export/sdoc/baseline`, `POST /v2/import/sdoc`, `GET /v2/export/knowledge[.zip]`,
  `POST /v2/export/knowledge/verify`, `GET /v2/points/{key}/package.zip`.
  Клиент: ссылки `.sdoc`/`ReqIF` в реестре требований, «Выгрузка знаний» в
  поле знаний, «пакет точки (zip)» у раскрытой точки.
- `ci/checks.sh`: блок кругового обмена своего ReqIF снят;
  `check_reqif_equivalence.py` работает только по файлам и остаётся записью
  условия сноса.
- ADR-023 — сторона разбора действует, выгрузка снесена; ADR-049 — StrictDoc
  теперь единственный канал ReqIF.
- Живая проверка на стенде (`tools/v2/check_exchange.py`, повтор
  `tools/v2/check_tor_mode.py`) ждёт выката: сторож места на диске хоста
  отказывает при < 15 ГБ (решение владельца 09.09).
