# ADR-072. Служебная личность не проходит ворота рабочего проекта

**Статус:** Принято · 2026-09-28
**Контекст:** ADR-071 дал служебной личности (`service:orbita-tools`, вход по
`ORBITA_SERVICE_KEY`) права владельца на стенде — она может решать ворота и
довела временный проект до Phase B. Для прогонов это нужно; для рабочих
проектов — нет: ворота проходит человек. Права ключа НЕ сужаем — ограничение
в модели проекта и на сервере ворот.

## Решение

1. **Признак `sandbox` у проекта.** v2-проект — версионируемая JSON-сущность в
   `orbita_kernel.entity` (реляционной таблицы проектов нет), поэтому `sandbox`
   — поле сущности проекта (истина `СХЕМЫ-ПОЛЕЙ-V2.yaml`, `bool`). Задаётся
   ТОЛЬКО при создании и неизменяем.
2. **NOT NULL и неизменяемость — триггером БД** (`V104`+`V105`,
   `guard_project_sandbox` на `orbita_kernel.entity`, как `forbid_baseline_update`
   в V001): отсутствующий признак — на первой версии `false` (fail-closed, NULL
   «не проходит мимо проверки»), на последующей **наследуется** от предыдущей
   версии (V105: правка песочницы документом без `sandbox` не делает её рабочей
   и не падает); смена `sandbox` у новой версии — отказ. Сервер и так делает
   поле create-only (проект не в `правимые`, не в `ПАСПОРТ`); триггер —
   страховка, чтобы рабочий проект нельзя было «перевести в песочницу» и пройти
   ворота. Существующие проекты — `false` (бэкфилл). Триггер идемпотентен
   (`DROP IF EXISTS` + `CREATE`): тестовая БД гоняет миграции повторно.
3. **Служебная личность на воротах рабочего проекта — 403.** Единственная точка
   прохода ворот — `PointRoutes.решение` (единственный вызов `engine.decide`).
   Там `actor.login`: `service:*` + `sandbox=false` → `403`, тело
   `{code: SERVICE_GATE_FORBIDDEN}`, строка в журнал api
   (`SERVICE_GATE_FORBIDDEN project=… gate=… actor=…`), фаза не двигается.
   Песочница → проход обычным путём. Не служебная личность → как раньше.
4. **Проект служебной личности — всегда песочница.** `POST /v2/projects`:
   создатель `service:*` → `sandbox=true`, параметр тела игнорируется (иначе
   ключом можно завести рабочий проект и пройти его ворота). Человек заводит
   рабочий (умолчание `false`), может явно попросить песочницу.
5. **Удаление — только песочницы.** Маршрута удаления проекта в API нет и не
   будет (ADR-071 · комментарий `drop-project.sh`); единственный путь —
   `ops/drop-project.sh` (прямой SQL, служебный ключ до него не дотягивается).
   Скрипт удаляет только `sandbox=true` (в дополнение к коду `PJ-TMP-…`):
   рабочий проект не удаляется даже с таким кодом.
6. **Инструменты.** `walk_scenes.py` заводит временный проект `sandbox=true`
   (служебным ключом сервер ставит сам; в режиме stand — по параметру) и удаляет
   в конце; вывод небуферизован (`sys.stdout.reconfigure(line_buffering=True)`)
   — при падении на длинном шаге шаги уже в логе.
7. **UI.** Метка «Песочница» (янтарный пунктир) — в шапке проекта и карточке
   паспорта; в списке проектов песочница отделена кромкой и меткой на карточке.
8. **Полки не затронуты** — это каталог (`LIB`), не проект.

## Последствия

- Служебный ключ по-прежнему заливает полки и гоняет прогон на песочнице без
  Telegram, но ворота рабочего проекта им пройти нельзя — только человеком под
  своей учёткой (в журнале — его имя, не «служебный orbita-tools»).
- «NOT NULL» здесь — гарантия хранилища (триггер приводит к `false`), а не
  `required` схемы: у вида `project` поле `required:false`, чтобы обновления
  прежних проектов не спотыкались; читается всегда с умолчанием `false`.
- Проверка в ОДНОЙ точке (`PointRoutes.решение`), не по эндпоинтам.
- Аудит на 216 (28.09): решений ворот от `service:*` на переживших проектах —
  ноль (единственный такой проект, временный, уже удалён).
