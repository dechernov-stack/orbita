# ADR-044. Одно дерево носителей: модель аппарата растворена в составе системы

**Статус:** принято (ТЗ-CODE-НОЧЬ 02→03.09.2026, шип 1; источник —
РЕШЕНИЕ-АРХИТЕКТУРА-ОДНО-ДЕРЕВО.md, пункты 1–4 и миграция)
**Контекст:** в системе жили два несвязанных состава. `spacecraft`
(«Модель аппарата», SP-NNNN) нёс характеристики платформы и ПН и был входом
моделирования по `scenario.spacecraft_ref`; `component` + `component_usage`
(PBS) несли дерево определений и вхождений ×N, на узлы которого
распределялись требования. Аппарат, собранный в модели, не был узлом PBS;
требования цеплялись к узлам без характеристик аппарата; трассировке не по
чему было идти; построение (podгруппы planes×per_plane) на КА не ссылалось.

## Решение

### 1. Носитель один — узел дерева состава

- Узел КА — определение `component` с `profile.role = spacecraft` и
  поддеревом: «Платформа» (`role = platform`), «Полезная нагрузка»
  (`role = payload`), подсистемы ведомости масс (`role = subsystem`,
  `profile.subsystem`, `profile.maturity`).
- **Величины — только в `parameters`** узла: имя параметра = ключ анкеты
  Ф-06 (`dry_mass`, `sa_area`, `battery_energy`, `attitude_accuracy`,
  `mass`, `buffer_size`…), единица — справочника. Анкета платформы =
  параметры узла «Платформа»; три пути заполнения Ф-06 работают на узле
  (`DataRequests` ищет носитель анкеты по роли, поле закрыто параметром с
  тем же именем).
- **Структурные не-величины — в `profile`**: пресет, режимы, каналы
  (`links`), политика буфера (`onboard` без объёма), маяк, архитектура ПН,
  политика резервов, крепление панелей, режимы ориентации, двигатель.
- Уровни дерева (`kind`): `segment → element → subsystem → component`;
  `system` и `assembly` — устаревшие значения, читаются в истории, новые
  узлы их не получают.

### 2. Контракт аппарата собирается, не хранится

`CarrierAssembly.assemble(узел КА, определения проекта)` кладёт параметры и
профиль поддерева в форму `contracts/spacecraft`, которую читают расчёты
(`SpacecraftViews`, бюджеты, TPM, маски). Единицы **не пересчитываются
молча**: параметр в чужой единице — претензия сборки, отсутствующий
обязательный — претензия с именем поля. Собранный документ проходит схему
контракта; считать по непрошедшему нельзя (`Carriers.contract` — отказ с
перечнем). Экран «Модель аппарата» — вид узла КА (`GET
/views/spacecraft/CM-NNNN`, `…/assembly` показывает, из каких узлов собрано
и чего не хватает); прежний адрес `SP-NNNN` отвечает, куда модель растворена.

### 3. Моделирование читает узел; подгруппа построения = вхождение КА ×N

- `scenario.carrier_ref → CU-NNNN` (вхождение КА); `spacecraft_ref` из
  живого кода убран (сторож `tools/validate_one_tree.py`). Резолвер входов
  ждёт тип `component_usage`; модель для сценария — вхождение → определение
  → сборка.
- `component_usage.constellation_ref` + `subgroup`: вхождение КА в подгруппу
  построения, `quantity` = число аппаратов подгруппы (walker — одна группа,
  `subgroups[]` — по одной на подгруппу). Ссылка живёт на стороне вхождения:
  построение не переиздаётся, версии входов сценариев не «уезжают».
- `GET /views/composition/tree`: строки вхождений с уровнем и кратностью по
  цепочке родителей, построения группой (подгруппа → вхождение ×N, масса
  группировки = Σ quantity × сухая масса собранного КА — считает сервер),
  узлы КА с претензиями сборки, определения без вхождений.

### 4. Каркас библиотеки — в то же дерево

Фрагмент полки применяется с сохранением `parent` внутри пачки
(идентификаторы переписываются согласованно, `LibraryChannel.apply`), так
что взятые сегменты и элементы ложатся деревом, а не списком. Отдельного
«каркаса PBS» рядом с деревом нет.

### 5. Миграция V038 без потерь (`-- legacy:`)

- Единственный узел `kind = system, segment = 'space'` без профиля
  усыновляется как узел КА новой версией (kind → element, профиль): его
  вхождения и распределённые требования остаются на месте. Иначе узел КА
  создаётся новым под единственным сегментом с `segment = 'space'`, если
  такой один.
- Платформа, подсистемы и ПН — новыми узлами с параметрами и профилем из
  документа SP; вхождения КА — по каждому построению проекта (walker →
  ×total; подгруппы → ×planes·per_plane); вхождение ×1 без построения —
  если его нет.
- Текущие сценарии: `spacecraft_ref → carrier_ref` (вхождение построения
  сценария), ключ версии входа переписан — **новой версией по процедуре
  изменения** (TZ-COM-003, ADR-031): старая версия закрывается с основанием
  `change_ref = 'V038'`, новая наследует статус (базированный сценарий
  остаётся базированным); на месте ничего не правится — сторож базирования
  в БД (`objects_baseline_guard`) это и проверил на стенде. Исторические
  версии не трогаются — констрейнт `scenario_refs_typed` проверяет только
  текущие строки. Сценарий без живой модели — громкий отказ со списком (как
  V0075).
- Объект `spacecraft` — новая версия в статусе Cancelled с `dissolved_into`;
  история читается, новых объектов этого вида сервер не принимает.
- V039 (дополнение): узлам поддерева КА из модели заводятся вхождения под
  вхождением КА, не привязанным к построению (кратность подсистемы — из
  параметра `quantity`, pcs); идемпотентно. Дерево состава, кроме того,
  показывает поддерево ОПРЕДЕЛЕНИЯ без вхождений строками «по определению»
  с унаследованной кратностью — узел, заведённый определением, из состава не
  пропадает; у каждого вхождения КА (×N построения) своё поддерево.

## Последствия

- «Без носителя» закрывается распределением на узел КА; «масса КА ≤ 100 кг»
  живёт на узле, а не на объекте без места в дереве.
- Стенд PJ-0001: ручные дети узла КА без параметров («Полезная нагрузка
  IoT», «Служебная платформа») **слиты** в узлы из модели (CM-0017, CM-0011)
  разовым скриптом `ops/oneoff/2026-09-03-merge-ka-children.sql` с историей
  (Cancelled + `merged_into`, вхождения отменены, интерфейс и технологии
  переведены новой версией по процедуре изменения) — ответ владельца 03.09.
- `slew_rate`: параметр платформы в каноне справочника (рад/с; размерность
  «угловая скорость», ввод и показ °/с); в контракт переводится
  **справочником** (`UnitRegistryIndex.fromCanon`), без справочника —
  претензия сборки. Δv-бюджет — **таблица манёвров** `maneuvers[]` на узле
  КА (`{name, delta_v в m/s, note}`): названия-категории контракта
  (phasing · maintenance · collision_avoidance · deorbit) ложатся в
  `delta_v_budget_ms`, прочие — претензия; свёртка — сумма, показана как
  «вычислено сборкой»; в анкете платформы — [Т]-поле `maneuvers`.
- Энергия АКБ: анкета несёт заряд (А·ч) **и напряжение (В)**; узел без
  `battery_energy` получает `battery_wh = Ah × V` с происхождением
  «вычислено сборкой»; заряд без напряжения — претензия «нет напряжения для
  энергии». Справочник пополнен размерностями «угловая скорость»,
  «напряжение», «ток» (данными сида 07).
