# ADR-060. Поле знаний по замечаниям прохода; критерий обязан уметь отказать

**Статус:** Принято · 2026-09-08
**Контекст:** поставка 08.09 (`docs/tz/v2/поставка-08-09/`): приёмка
`v2-deadline-and-oda` с тремя правилами и замечания прохода по полю знаний.

## Три правила приёмки

**1. У каждого критерия готовности — тест на отказ.** После двух дефектов
одного класса — «проверка, которая молча проходит» (срок искался по коду,
а хранился идентификатором; порог «Б1: … 5 лет» читался как число 1). Сторож
`tools/validate_gate_checks.py` не регистрирует критерий, у которого нет
теста с фикстурой «обязан вернуть не выполнено с причиной»; проверяет по
ПРИЧИНЕ отказа, а не по имени — тесты ходят через маршрут фазы и видят
человеческую формулировку помехи. Дописаны отрицательные тесты всех 31
предметного критерия.

Заодно вскрылось: `maturation_planned` звал ГЕНЕРАТОР созревания и сам
закрывал разрыв, который проверял, — отказать не мог никогда. Ворота теперь
НАБЛЮДАЮТ (`maturationState`), генератор зовётся при заведении технологии.

**2. Пороги — только полями.** `normative_document.clauses[].limit
{key, op, value, unit}`; ОСЗ читает порог у пункта карточки норматива.
Нет карточки или поля — отказ: подставлять умолчание значит вернуть тот же
класс дефекта с другой стороны. «Число перед словом лет» снято: это был
разбор прозы.

**3. Дата вехи технологии — от планового конца пакета созревания.**
`planPackage` ведёт `planned_date` вехи с пометой источника «пакет N»;
ручная дата допустима только пока плана нет и помечается «вручную».

## Замечания прохода — во фронт поля знаний

**Обоснование только по смыслу.** Повод обязателен у `rejected`, при
разрешении `contested` и при смене уже принятого решения; `adopted` и
`noted` с чистого листа — одним кликом. Поле многострочное и появляется
только там, где нужно. Обоснование не должно быть налогом на согласие.

**Загрузка во вкладке.** Текст, файл (читается в браузере) или ссылка
(снимок текста по http(s), до 2 МБ, разметка снята — снимок, а не живая
ссылка: страница завтра другая, а факт с якорем обязан оставаться
проверяемым) + задание → разбор → факты и темы ложатся в поле; разбор
называет своё задание, план ложится на акцепт тут же. Старый экран
загрузки снят — второй панели «Поле знаний» больше нет.

**Ручные темы и факты.** Метка [И], `provenance = manual`, источник —
«инженер, дата» либо материал. Полноправны: диспозиции, связи, промпт.
Правило честности то же: величина без единицы — не факт. Доля знаний ИЗ
ИСТОЧНИКОВ считается без них — `from_manual_facts` отдельной цифрой:
иначе «100 % из знаний» набирается фактами руками под каждую сущность.

## Пойманное живьём в этот раз

* Заголовок `User-Agent` с кириллицей отвергается `HttpClient` до всякого
  запроса — ссылка отказывала. Только ASCII.
* Список фактов и ответ на заведение сериализовались разным кодом: ручной
  факт был `manual` в ответе и не был в списке — отбор «заведены руками»
  показывал пусто. Тот же класс, что два построителя факта, снятые ранее.
* **Стенд:** Postgres семь раз за день уходил в crash-recovery следом за
  «could not send data to client: Broken pipe» (backend `exit code 2`);
  диск и ФС ВМ чистые. У api одно JDBC-соединение без переподключения —
  процесс жив, healthcheck красный, вход отвечает «connection has been
  closed». Лечится перезапуском api; причина обрывов — открытый вопрос.

## Развитие — не сделано, следующим шипом

Грань «где пригодится» с предложением ИИ и матрица применимости
нормативов (норматив × сцена/узел, состояние) — по записке владельца; в
эту поставку не вошли.
