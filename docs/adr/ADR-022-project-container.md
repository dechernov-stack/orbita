# ADR-022. Проект — контейнер объектов и связей

**Статус:** принято
**Контекст:** система хранит объекты одной плоской кучей: `objects` и `links`
не знают, к какому проекту относятся. Пока проект был один (демо «Орбита-IoT»),
это не мешало. Задание «прогон до KDP B» требует портфель проектов: инженер
создаёт пустой проект, ведёт его через контрольные точки, и объекты одного
проекта не видят объектов другого. Вид `project` (`PJ-NNNN`, шаг 17) уже
существует, но он — источник точек и дат, а не контейнер: принадлежность
объекта проекту нигде не записана.

**Решение.**

1. **`project_id` — обязательная колонка** в `objects` и `links`: текстовый
   идентификатор объекта вида `project` (`PJ-NNNN`). Объект проекта принадлежит
   сам себе (`project_id = id`) — «проектов вне проекта» не существует.
2. **Ограничение вводится как `NOT VALID` + `VALIDATE CONSTRAINT`** —
   двухфазно, как принято для больших таблиц: сначала колонка заполняется
   переносом, затем `CHECK (project_id IS NOT NULL)` добавляется `NOT VALID`
   (мгновенно, без пересканирования) и валидируется отдельной командой той же
   миграции. На занятой базе это не держит долгих блокировок; NOT NULL
   остаётся выраженным через валидированный CHECK.
3. **Перенос существующего.** Всё, что лежит в базе к моменту миграции,
   принадлежит проекту «Орбита-IoT (демо)»: миграция создаёт объект
   `PJ-0001` (если объектов нет — не создаёт ничего) и проставляет его
   идентификатор всем строкам без проекта.
4. **Связь не пересекает границу проекта.** Обе стороны связи обязаны
   принадлежать одному проекту; попытка сослаться на объект чужого проекта —
   отказ на границе API с именем нарушенной пары. В базе это закреплено
   тем, что `project_id` связи один, а принадлежность сторон проверяет
   сервер при записи (FK на пары «id проекта × id объекта» потребовал бы
   составного уникального индекса по текущим версиям — избыточно при
   серверной проверке, повторяющей ту же семантику).
5. **API получает проектный контекст.** Чтение и запись объектов и связей
   ведутся в проекте; обращение без проекта — ошибка, а не «все проекты
   сразу». Отчёты, документы, матрицы и экспорт собираются по объектам
   одного проекта.

**Последствия.**
- Демо-профиль (`--profile demo`, ADR-028) наполняет проект `PJ-0001`
  «Орбита-IoT (демо)» — тот же путь данных, что у пользовательских проектов.
- Идентификаторы объектов остаются глобально уникальными (`objects_current`
  по `id`): два проекта не могут держать `RQ-0001` одновременно. Это
  осознанное упрощение — нумерация сквозная через портфель; при переносе
  проекта между стендами идентификаторы сохраняются, конфликт нумерации
  решается на импорте отчётом, а не молчаливым переименованием.
- `ORBITA_GATES`-подобных обходов для «объектов без проекта» нет: пустой
  проект — это проект без объектов, а не объекты без проекта.
