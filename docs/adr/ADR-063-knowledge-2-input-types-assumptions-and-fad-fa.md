# ADR-063. Знания 2: типы входных своим режимом, допущения к точке, FAD/FA из поставки

**Статус:** Принято · 2026-09-09
**Контекст:** `ЗАДАНИЕ-CODE-БОЛЬШОЕ` §Шип E; `ДОКУМЕНТЫ-1-ВХОДНЫЕ` §1–§3
(типология и конвейер); `ИНТЕЛЛЕКТУАЛЬНАЯ-ЗАГРУЗКА` §3–§6; правила поля
знаний в `СХЕМЫ-ПОЛЕЙ-V2` (`intake_rules`, `knowledge_field_rules`,
`input_document_pipeline.stale_rule`); поставка 09.09 `ШАБЛОНЫ-FAD-FA.json`
и ответы `ШИП-D-ПРИНЯТ`.

## Решения

**1. Режим разбора — по типу материала, а не по одному промпту на всё.**
Промпт разбора получает блок режима: ТЗ (`tor`) — каждое требование
фактом `obligation` с действием `requirement` и **оценка против нужд**
проекта (список нужд идёт в промпт, ответ несёт `assessment`); даташит
(`datasheet`) — параметры фактами `quantity` с ключом **анкеты узла**
(`param_key`; анкета — параметры лестницы типового компонента по
`template_ref` узла из задания «обнови параметры ‹узел›»); норматив
(`normative`) — пункты `obligation` с порогом **полем** `limit` и одно
действие `normative_document` на полку. Всё, что считается по данным,
считается по данным (`IntakeModes`): непокрытые нужды — по реестру нужд,
а не по словам модели; параметры в анкету, сверка с рамками Р
(`constraint.bound` против `param_key`: масса 120 кг против Р2 ≤ 100 —
риск в план), недостающие поля анкеты — запрос данных поставщику;
кандидат узла — по заданию «рассмотрим как базовую».

**2. RFA заказчику — замечание обзора.** Непокрытая нужда даёт действие
`request_data` → `finding` вида `rfa` с адресатом «заказчик» и возвратом
в сцену 3; требование ТЗ без нужды — `rid` с возвратом в сцену 8. Так
оценка ТЗ живёт там же, где живут все замечания, и держит внутренний
обзор до ответа.

**3. Новая версия источника — диф канонов блоками.** `putMaterial` с
`supersedes` сравнивает блоки старого и нового канона по якорям; факты
прежней версии в изменённых блоках получают `superseded` и помету
«источник обновлён: SD-n, блок s#», сущности с нитью `derived_from_fact`
— помету `source_updated`. Диспозиции не трогаются (правило поля
знаний): что решил человек, остаётся его решением с пометой, что почва
под ним изменилась.

**4. Конфликт фактов — оба, со ссылкой друг на друга.** После каждого
приёма факты проекта с тем же субъектом и утверждением, но иным
значением, получают `conflicts[]`. ИИ не выбирает; принятый факт с
живым противоречием держит точку (`facts_consistent`), пока спорщик не
отклонён или не заменён.

**5. Допущение — с владельцем, точкой и способом проверки.** Диспозиция
`assumed` без `assumption{owner, confirm_by, validation, impact_if_wrong}`
не ставится (истина схем); помета факта становится П — так допущение
попадает в §10 отчёта. Критерий `assumptions_confirmed:<точка>` держит
точку допущениями, у которых `confirm_by` — она; подтверждение —
диспозиция `adopted` с причиной (`confirmed_by`). Тема с принятыми
фактами обязана разрешиться в сущность (`resolveTopic`, критерий
`topics_resolved`). Три критерия стоят у MCR и KDP-A шаблона фазы, у
каждого тест на отказ.

**6. Снимок ссылки — Chromium по профилю, отказ без рендера.** `UrlSnapshot`
качает HTML; страница-каркас приложения на JS без текста — отказ словами
«пришлите PDF или текст», если служба рендера не поднята; с
`ORBITA_SNAPSHOT_URL` (compose-профиль `snapshot`, browserless/chromium)
страница рендерится, и пустая после рендера тоже отказывает. Образа
DocPilot на стенде нет; профиль не по умолчанию — образ тяжёлый, а диск
стенда 08.09 уронил Docker Desktop на нуле места.

**7. FAD и FA — из поставки генератором.** `tools/v2/gen_document_templates.py`
разворачивает ожидания Прил. 1–2 (`ШАБЛОНЫ-FAD-FA.json`) в наш диалект
живого документа: запрос к реестру там, где сущность есть; `min_statements`
там, где нужен тезис человека (с подсказкой, о чём); честная помета там,
где у нас пока нет вида (сцены Phase A — шип G, записи tailoring).
Лестница ступеней получила `KDP-A`; отбор запросов — `code_prefix`
(пакеты 04.) и `criticality_min` (риски ≥ 12). Строки Д1/Д9 матрицы KDP-A
теперь ссылаются на документы — KDP-A держится ими (код F — базирован).

## Последствия

- Маршруты: `GET /v2/materials`, `POST /v2/materials` с `supersedes` и
  снимком, `POST /v2/facts/{код}/disposition` с `assumption`,
  `POST /v2/topics/{id}/resolve`, `GET /v2/intake/{задание}` с `assessment`.
- Поле знаний: задание по типу, матрица оценки ТЗ, пометы «против …»,
  «источник обновлён», «допущение · владелец · к точке», действие
  «допущение», разрешение темы в сущность, новая версия материала.
- Прогон `walk_scenes.py --knowledge` живой моделью: три материала своим
  режимом, план даташита принят, допущение держит MCR и подтверждается.
- Не сделано: `тз.docx` (МКУСС ПД) и `ПАКЕТ-РАЗБОР-ТЗ` в репозитории нет —
  проверка на учебных выдержках; даташит PDF — текстом (двоичные файлы —
  хвост поля знаний); образ DocPilot для снимка — вопрос владельцу.
