# ADR-061. Стенд: пул с переподключением; критерий только читает; один сериализатор на вид

**Статус:** Принято · 2026-09-08
**Контекст:** `ПРИЁМКА-KNOWLEDGE-REMARKS` (`docs/tz/v2/поставка-08-09/`):
приёмка `v2-knowledge-remarks`, два правила из находок и приказ «стенд —
первым делом»: семь падений Postgres за день прохода, проход невозможен.

## Стенд: одно JDBC-соединение без переподключения — дефект api

Ядро держит один `Connection` и раздаёт его хранилищам (ADR-011). Когда
backend базы умирал (recovery), процесс api жил, healthcheck горел
красным, вход отвечал «This connection has been closed» — до
`docker restart`. Решение — не переписывать хранилища под «соединение на
вызов», а сделать этот один объект живучим:

- `ReconnectingSource` в `core/mod` — HikariCP (`connectionTestQuery`,
  `validationTimeout=3 с`, `maxLifetime=30 мин`, `keepaliveTime=5 мин`,
  пул на два соединения) и **прокси** `Connection`: каждый вызов уходит в
  живое соединение; вне транзакции мёртвое (`isClosed`, `isValid`)
  выбрасывается и берётся свежее. Соединение, ответившее меньше секунды
  назад, не перепроверяется — иначе `isValid` удваивал бы запросы к базе.
- **Внутри транзакции соединение не подменяется**: подмена посреди
  транзакции тихо потеряла бы уже сделанные записи. Мёртвое всплывает
  исключением, `tx` откатывает (откат на мёртвом соединении сам глотается —
  наружу важна причина обрыва, а не «cannot rollback» поверх неё).
- **Повтор в HttpApi**: при SQLState 08xxx / «connection has been closed»
  GET повторяется один раз; запрос с телом повторять нельзя — тело
  прочитано, повторить его значит выдумать, — он получает 503 с
  `retry: true` и словом «повторите», а не 500.
- Api закрывает соединение на SIGTERM (shutdown hook), контейнеру дан
  `stop_grace_period: 20s`: сокет закрывается, а не рвётся на полуслове.
- Тест `ReconnectingSourceTest`: backend убивается `pg_terminate_backend`
  с соседнего соединения — как это делает recovery, — следующий запрос
  проходит; обрыв в транзакции даёт исключение с признаком обрыва;
  `умерло()` отличает обрыв от ошибки запроса.

Диагностика падений — отдельный отчёт
`docs/tz/v2/отчёты/СТЕНД-ПАДЕНИЯ-PG-08-09.md`: десять падений
`exit code 2` / SIGPIPE, OOM исключён фактами, каждое — в секунду выката
или перезапуска на хосте Docker (в том числе выката, у которого сборка не
удалась и api не трогался); умирают свежие backend, не соединение api.
Причина `exit(2)` в backend не
установлена и не выдумана: журнал базы теперь называет клиента
(`%a@%h`, `log_connections`, `ApplicationName=orbita-api`), память задана
явно (`shared_buffers=256MB`, `mem_limit: 1g` — гигиена, не лечение), а на
время прохода владельца хост стенда свободен (`ops/walkthrough.sh on`:
тесты ядра и выкаты отказывают).

## Правило 1: критерий готовности только читает

Находка сторожа отказов (ADR-060): `maturation_planned` звал генератор и
сам закрывал разрыв, который проверял. Правило: проверка не создаёт, не
меняет и не запускает — наблюдает состояние и называет причину. Сторож
`tools/validate_checks_readonly.py`: в `*Checks.kt` и во всём `readiness`
— импорты соседей только через `api`; на портах из конструктора нет
методов записи и генерации (список глаголов портов v2: create/update/
link/unlink/…/maturation/takeWbs/estimate/planPackage/…); неизвестный
метод — тоже отказ, сторож не пропускает неизвестное молча.
Самопроверка ловит подделку с `store.create` и `maturation`.

## Правило 2: один сериализатор на вид

Список фактов и ответ на заведение писались разным кодом — `manual` был
в одном и не был в другом. Сторож `tools/validate_one_serializer.py`
читает data-классы портов v2 и ищет в маршрутах рукописные цепочки
`.put("поле", …)` из ≥ 4 полей; два построителя одного класса в разных
местах — отказ с разницей полей. На первом прогоне нашёл четыре вида
(Fact ×3, EstimateView, RenderedSection, ложный ImpactEdge/SuspectLink —
устранён совпадением усечённых имён `linkId → link`). Построители
собраны в `KindJson` (`факт`, `оценка`, `текст`); маршруты зовут его.

Следующий шаг правила — **DTO видов реестра из схемы YAML генерацией**:
сторож считает оставшиеся рукописные построители по документам реестра
(`.doc.path(` / `тело.path(`) — их 13 — и печатает число, которое должно
идти к нулю.

## Последствия

- Ядро по-прежнему видит один `Connection`; хранилища не тронуты.
- Сторожа в `ci/checks.sh` с самопроверками; правила действуют на новый
  код с этого тега.
- Проход владельца назначается после этого шипа; следующий — шип D.
