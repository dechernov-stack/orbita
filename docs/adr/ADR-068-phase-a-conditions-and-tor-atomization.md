# ADR-068. Условия сцен Phase A — содержание владельца; ТЗ атомизируется по классам

**Статус:** Принято · 2026-09-10 (приёмка шипа G)
**Контекст:** `ШИП-G-ПРИНЯТ` (10.09) и `УСЛОВИЯ-СЦЕН-PHASE-A.json` (PHC-9002):
двенадцать сцен, 44 условия выхода `kind · min · where`, каждое читает
реестр и привязано к мероприятиям Романова и к точке фазы; правило режима
`tor`: «каждое требование, функция и сервис ТЗ — отдельный факт». ADR-067
(шаблон Phase A), ADR-063/064 (поле знаний, режимы входных).

## Решения

**1. Сцены Phase A — из поставки, не из головы.** Генератор
`tools/v2/gen_phase_a_template.py` читает `УСЛОВИЯ-СЦЕН-PHASE-A.json`:
ключи, заголовки, точки (`gate`), коды Романова, `instantiate_per` и условия
выхода — оттуда; роли, вопросы, шаги, связи — наше содержание. Сцены
A1 развёртывание · A2 SEMP · A3 ConOps · A4 аванпроект элемента
(экземпляром) · A5 архитектура · A6 анализы · A7 технологии · A8 риски ·
A9 ОСЗ и SMA · A10 программатика · A11 Project Plan и FA · A12 точки фазы.
Каждая сцена пишет в свою точку: SRR ждёт A1–A3, SDR — A4–A9, KDP-B —
A10–A12 (`scene_done` в критериях точек).

**2. Условие владельца → проверка словаря готовности, ожидание остаётся в
шаблоне.** Таблица ПРОВЕРКИ генератора — по одной проверке на условие, в
порядке поставки (двум условиям — по две); само ожидание (`kind · min ·
where`) лежит в шаблоне полем `reads`, чтобы было видно, что читается. 44
условия → 47 проверок; 21 проверка новая, остальные — словарь Pre-A.
Условие «желательно» (`logical_components_deployed`) видно, но сцену не
держит: движок понимает `blocking: false` у условий выхода.

**3. Новые проверки живут в своих контурах** и только читают:
- требования: `each_segment_has_requirement`, `no_carrierless_requirement:<уровень>`,
  `conditional_requirements_listed` (условные — снимком базовой линии),
  `baseline_taken:<вид>`; `each_system_requirement_derived` требует
  обоснования связи;
- архитектура: `node_functions_min`, `node_stage_closed`, `node_exchange_items_min`
  (по узлу экземпляра), `functions_allocated`, `chains_realized`, `budgets_min`,
  `logical_components_deployed`, `variants_min`, `baseline_concept_with_rejected`,
  `model_runs_verified`;
- программатика: `each_risk_has_owner`, `critical_risks_have_measures`,
  `technology_fallback_named`, `oda_compliant`, `oda_normative_bound`,
  `estimate_method`, `plan_consistent_with_gates`;
- документы: `document_section_started`, `document_version_min`; «начат» —
  по содержанию (строки или тезис), а не по полноте к ступени: документ
  Phase A к MCR не ждут, и считать его пустым из-за этого — ложь;
- точки (`PointChecks`, слой api — ему нужен шаблон фазы): `phase_points_dated`,
  `scene_responsible_min` (ответственные — в окнах плана), `expertise_positions_reviewed`
  (вердикты по позициям EXP-2A/2B, `POST /v2/points/{key}/positions`),
  `maturity_matrix_complete` (Д1–Д10 без дыр: F — базирован, С/Р — начат,
  вид — есть записи).
У каждой проверки — тест на отказ и на проход (`PhaseAConditionsTest`).

**4. Документы под условия.** ICD получает §6 «Протоколы решений (trade
studies)» (Д5 §6); новые шаблоны `sma` (план обеспечения: ОСЗ · надёжность ·
безопасность · EMI/EMC) и `projectplan` (Д10 — ссылками на Д2–Д9, не
копиями). Версия документа = версия записи + число тезисов — «FA обновлён»
измеримо.

**5. Модель верифицируется решением.** `POST /v2/models/{code}/verify`
(`Models.verify`): статус verified · validated только у модели, давшей ответ,
и с основанием — иначе отказ.

**6. ТЗ атомизируется по классам.** Промпт режима `tor` несёт правило: каждое
требование, функция и сервис ТЗ — отдельный факт (сторона, узел состава,
ограничение, веха, норматив — тоже), у факта — `entity_class` (поле вида
`fact`, схема), действия плана — по классу (service → сервис сцены 6,
composition_node → узел сцены 7, stakeholder, constraint, normative_document;
вехи — без действия, даты точек задаёт план). Оценка от требования идёт по
требованиям, функциям И сервисам; сирота называется словами самого факта
(«F-0061 «ТЗ п. 3.2: услуга LEO-PNT» [service] — …») и RID говорит «услуга ТЗ …
без нужды». `check_tor_mode.py` сверяет живой разбор с пакетом по классам
(42 сущности: факты по классу и действия плана) и держит меру 4 из 4.

## Последствия

- Полки на стенде: `PHT-9002` (пересобран), `semp` · `icd` (пересобраны),
  `sma`, `projectplan` — новые; `tools/v2/load_shelves.py`.
- Условиям A4 (функции, элементы обмена), A5 (функции, цепочки, бюджеты,
  логические компоненты) в v2 пока нечем кормить маршрутами — записи
  заводятся только полками и тестами; на стенде эти условия честно держат
  сцены, прогон их печатает.
- Проекты, прошедшие KDP-A на прежнем шаблоне, при следующем чтении ленты
  получают новые сцены A1–A12 (шаблон читается с полки по коду).
