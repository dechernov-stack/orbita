*Версия 0.3 (концепция принята). Связанные документы: Регламент БП-PPA, Регламент БП-PA, «Моделирование потребителей» v0.2, «Моделирование КА» v0.2. Следующий шаг: ТЗ на ИС, затем архитектура.*

## 1. Назначение и границы системы

1.1. Информационная система (далее — ИС) поддерживает ранние фазы жизненного цикла космической системы (Pre-Phase A и Phase A по методологии NASA NPR 7120.5 / 7123.1, в соответствии с регламентами БП-PPA и БП-PA) с фокусом на **выработку требований к элементам космической системы (КС) и формирование пакета для передачи в детальное проектирование**.

1.2. Прикладная область первой очереди — низкоорбитальная связная группировка IoT. Архитектура данных и модулей не привязывается жёстко к этому классу миссий, но оптимизации допустимы.

1.3. Граница на выходе: базированные требования уровня проекта и системы, спецификации сервисов, распределение требований на элементы архитектуры (flow down), методы верификации/валидации, результаты моделирования как обоснование — содержание, эквивалентное пакетам SRR / SDR по регламенту БП-PA. Детальное проектирование (Phase B+) — вне границ ИС; ИС отдаёт в него структурированный экспорт.

## 2. Идеологические основания (цифровой инжиниринг по NASA)

Нормативная база идеологии: NPR 7123.1 (SE Engine), NASA SP-2016-6105 Rev 2, **NASA-HDBK-1009A** (NASA Systems Modeling Handbook, 2025) — интеграция системного моделирования с процессами NPR 7123.1, **NASA-HDBK-1004** (Digital Engineering Acquisition Framework) — определение цифрового инжиниринга и среды DEE.

- **Авторитетный источник данных и моделей (по NASA-HDBK-1004).** Все требования, параметры, модели и результаты расчётов живут в одной связанной модели данных. Документы (Д-артефакты регламентов) — генерируемые представления модели, а не первоисточник.
- **Цифровая нить.** Сквозная двунаправленная трассировка: Стейкхолдер → Нужда (Need) → Сервис → Требование → Элемент архитектуры → Метод V&V → Результат моделирования/верификации. Метамодель связей — по MBSE Grid из NASA-HDBK-1009A; SysML-нотация не обязательна («MBSE-lite»).
- **MOE / MOP / TPM (по NASA-HDBK-1009A и SP-2016-6105).** Показатели качества сервисов — MOE (Measures of Effectiveness); измеримые показатели системных требований — MOP (Measures of Performance); TPM (Technical Performance Measures) — отслеживаемые технические параметры с резервами, автоматически питаемые расчётными модулями (энергобаланс витка, задержки доставки, массовые резервы MEL). TPM с трендами предъявляются на обзорах SRR/SDR.
- **Параметрическая модель (логика Valispace).** Объекты с параметрами; параметры связаны формулами и результатами расчётных модулей; изменение параметра пересчитывает зависимые значения и проверяет требования.
- **Ранний цифровой двойник миссии.** Связка «группировка + аппараты + наземный сегмент + потребители + трафик» — исполняемая модель миссии, на которой требования проверяются до выпуска.
- **Статусная модель и базирование** — по регламентам: Draft → Preliminary → Approved → Baseline; изменение Baseline только через управление изменениями.
- **ИИ как ассистент, не как автор.** ИИ предлагает — инженер утверждает; каждое предложение фиксируется с признаком происхождения (какая LLM, какой пакет) и требует явного акцепта.

Шаги допускают возврат и итерации, но логическая последовательность фиксирована. На каждом переходе работает ИИ-ассистент (механизм — разд. 5.8).

## 4. Ключевые объекты модели данных

Базовая пара — **Система — Компоненты** (рекурсивная декомпозиция). Вокруг неё:

- **Stakeholder / Need** — источники; атрибуты по Прил. 4 БП-PPA;
- **Service** + **MOE** — что КС предоставляет потребителю и с каким качеством (доступность, задержка, ёмкость);
- **Requirement** + **MOP** — уровни: проект / система / элемент; атрибуты по Прил. 2 БП-PA;
- **System / Component** — сегменты (космический, наземный, пользовательский), системы, подсистемы; параметры с единицами, допусками, резервами;
- **Parameter / TPM** — значение + формула/источник (ручной ввод, расчётный модуль); граф зависимостей; TPM — подмножество параметров с целями, резервами и трендом к обзорам;
- **Scenario / Study** — расчётный случай (конфигурация группировки, карта спроса, размещение НС, режим доставки) и результаты;
- **VerificationItem** — требование ↔ метод ↔ свидетельство;
- **Risk, Technology** — реестры по Прил. 6–7 БП-PPA/БП-PA (в первой очереди упрощённо, для полноты gate-пакета).

## 5. Функциональные модули

### 5.1. Модуль требований и трассировки
Ядро: реестры Needs/Services/Requirements, двунаправленная трассировка, матрицы трассировки и верификации, статусная модель, базирование, история изменений, impact-анализ по цифровой нити. Кандидат на переиспользование — StrictDoc / библиотека reqif (разд. 5.10).

### 5.2. Баллистический модуль
Ядро расчётов — **Orekit** (Apache 2.0): пропагация, события видимости, тени/освещённость, манёвры. Надстройка — сценарии группировок (Walker и произвольные), пакетный расчёт вариантов.

Оценка вариантов построения — по двум главным осям: **экономика × качество**, плюс надёжность и среда/регуляторика.

**А. Качество сервиса (спрос-взвешенное).** Вход — **карта спроса**: географическое распределение потребителей по классам (A'/B'/C', разд. 5.6) с их трафиком. Источник карты — трёхслойная схема: плотность населения на сетке ~100×100 км × коэффициент «терминалов на жителя» → единичные объекты и маршруты вне корреляции с населением (СМП, инфраструктура Якутии и т. п.) → сценарная библиотека под реальные бизнес-кейсы. Интегральный показатель — доля спроса, обслуженного с требуемым качеством:
1. класс A' — вероятность доставки сообщения;
2. класс B' — вероятность доставки за ≤ N попыток;
3. класс C' — вероятность уложиться во время реакции T.

«Сервис доступен» = (угол места ≥ рабочего) И (энергетический бюджет линии замыкается) И (есть свободная ёмкость канала). Взвешивание по спросу устраняет паразитное преимущество ССО («идеально у полюсов, где никого нет»). Вспомогательные метрики: кратность покрытия, max/mean gap, revisit — мгновенно / среднесуточно / за период.

**Б. Экономика.**
4. число уникальных пар (наклонение × высота) ≈ число отдельных пусковых кампаний;
5. **срок развёртывания до целевого качества** — явный показатель (разведение по RAAN дифференциальной прецессией дёшево, но медленно; прямое выведение в плоскости дорого, но быстро);
6. число КА всего / в плоскости; прокси-стоимость развёртывания и восполнения.

**В. Надёжность и резерв.**
7. кривая деградации показателя качества при отказе 1, 2, … N аппаратов;
8. стоимость и время восстановления сервиса по стратегиям резерва: орбитальный резерв в плоскости vs наземный резерв с довыведением.

**Г. Энергетика витка (ключевое).**
9. средняя энергия, собираемая за виток (Вт·ч/виток) — **худший и лучший сезон, северное полушарие** (опорные эпохи — солнцестояния + развёртка сезонов теней);
10. доля и длительность теневых участков; для ССО — явный учёт LTAN (терминаторные орбиты почти без теней);
11. допустимый duty cycle полезной нагрузки при заданной платформе.

**Д. Среда и регуляторика.**
12. радиационная обстановка на высоте (ресурсный прокси);
13. соответствие требованиям увода с орбиты (NASA-STD-8719.14 / национальные нормы), время баллистического существования;
14. геометрия связи: доплеровский сдвиг, скорость изменения угла места.

**Визуализация:**
- **роза ветров (лепестковая диаграмма)** нормированных KPI с наложением 3–5 вариантов построения — главный экран сравнения;
- **широтный профиль качества сервиса** с наложенной кривой спроса — диагностика эффекта ССО;
- 3D/2D движение аппаратов и трассы (CesiumJS + OreCzml); наземные станции и зоны;
- тепловые карты доступности сервисов: мгновенная / среднесуточная / за произвольный период; карты разрывов;
- временные диаграммы сеансов и энергобаланса витка.

### 5.3. Модуль моделирования космического аппарата
Ввод параметров платформы и полезной нагрузки. Для связного проекта: частотные планы и мощности, протоколы, антенны (ДН, усиление, наведение), межспутниковая связь, зоны видимости/обслуживания; платформенные параметры для баллистики и энергетики (масса, площадь, СБ, АБ, циклограммы). Архитектура ПН — **regenerative** (обработка на борту); диапазон платформ — **12U–100 кг**; ISL — **только РЧ**. **Режимы доставки данных — три, переключаемые в сценарии:** (а) store-and-forward; (б) ISL внутри плоскости; (в) полная межплоскостная сетка. Задержка в отчётах показывается **по классам потребителей** — необходимость ISL становится выводом модели, а не входным допущением. Детализация — в отдельном документе «Моделирование КА».

### 5.4. Модуль наземного сегмента
Реестр станций приёма и управления; два режима размещения: ручной (карта, координаты, характеристики) и рекомендательный — предложения от задач моделирования (оптимизация покрытия/задержки/стоимости).

### 5.5. Модуль сетевого протокола
Протокол — заменяемая абстракция (адаптер): интерфейс «параметры канала и MAC + модель поведения». Первая реализация — LoRaWAN; вероятный целевой вариант для спутникового канала — LR-FHSS (спутниковая адаптация LoRa, применяется коммерческими операторами спутникового IoT), что подтверждает необходимость абстракции адаптера. Замена протокола = замена адаптера и пересборка (лёгкая модульность). Адаптер используется в моделировании (ёмкость, коллизии) и в описании сервисов. Открытые симуляторы (ns-3-lorawan, FLoRa, ELoRa) — калибровочный референс собственной быстрой модели, не встраиваемый код (GPL; медленны для Монте-Карло).

### 5.6. Модуль потребителей (клиентов)
Три модельных класса терминалов:
- **A' — «тупой датчик»**: односторонняя передача; периодичность/интенсивность, размер пакета, допустимые потери;
- **B' — датчик с подтверждением**: политика повторов, требуемая вероятность доставки;
- **C' — терминал оперативного управления**: двусторонний контур с заданным **временем реакции T** внешней системы на событие (пример: уход с маршрута → команда коррекции за T секунд); ключевой показатель — вероятность уложиться в T.

Все классы **обязаны знать эфемериды**: аппараты регулярно передают широковещательный маяк альманаха/расписания пролётов, терминал передаёт только к пролёту; передача «вслепую» — деградированный режим, а не штатный. Для B' — **эфемеридный backoff**: после N неудачных попыток ожидание следующего аппарата. Потребители задаются популяциями (число, география, профиль активности) — они же образуют **карту спроса** для баллистического модуля (5.2.А). Детализация — в отдельном документе «Моделирование потребителей».

### 5.7. Модуль информационных потоков
- Пуассоновские потоки по классам потребителей (неоднородные по времени и территории; событийный трафик — модулированный Пуассон/MMPP);
- карта потоков: потребители → КА → (ISL) → НС → потребитель данных; узкие места, загрузка, очереди;
- проверка Монте-Карло: распределения задержек, вероятностей доставки, P(реакция ≤ T);
- требование производительности: тысячи прогонов за минуты → собственное лёгкое аналитико-имитационное ядро; события видимости — из предрасчитанной баллистики, канальный уровень — из калиброванного адаптера протокола.

### 5.8. ИИ-ассистент: двухканальный контур
**Канал 1 — промпт-пакеты (человек в контуре, без затрат API на генерацию).**
1. Система на шаге мастера генерирует промпт-пакет: контекст (выгрузка из модели) + задание + жёсткая схема ответа (JSON/YAML c ID пакета);
2. инженер вставляет пакет в Claude и/или другие LLM (пакет один и тот же);
3. ответы вставляются обратно; парсинг по схеме — локально; арбитраж расхождений между несколькими LLM — один дешёвый вызов API;
4. результат — как diff к модели: предложение → правка инженера → принятие → автозагрузка. Происхождение каждой записи фиксируется.

Применение: нужды → сервисы; сервисы → проекты требований; требование → метод V&V; матрица рисков (описание сценария → пакет → ответ → корректировка → утверждённый реестр); контроль качества требований (однозначность, измеримость, проверяемость); анализ полноты и противоречий; генерация текстов Д-документов.

**Канал 2 — прямой API (малые объёмы, строгая структура).** Декомпозиция системы на компоненты и подобные структурные операции: предложение → редакция → загрузка в систему.

Принцип обоих каналов: **исключение ручного перебивания данных** — только «предложение → редактирование → автозагрузка».

### 5.9. Отчёты и экспорт (gate products)
Генерация из модели: спецификация требований (Прил. 2 БП-PA), ConOps-заготовка, описание архитектуры (Прил. 4 БП-PA), матрицы трассировки и верификации, реестр TPM с трендами, отчёты моделирования. Экспорт: ReqIF/CSV; структурный экспорт параметров для САПР детального проектирования.

## 7. Принятые решения и ограничения

1. Модульность — «лёгкая»: без горячего переключения и интеграционных шин; смена протокола/модуля — пересборка;
2. Баллистика — ядро Orekit, сами не разрабатываем;
3. Протокол первой очереди — LoRaWAN; абстракция адаптера обязательна с первой версии;
4. Скорость Монте-Карло — архитектурное требование первого приоритета модуля потоков;
5. Интерфейс Valispace не копируем; заимствуем логику связанных параметров и трассировки;
6. Нормативная база идеологии — документы NASA (NPR 7123.1, SP-2016-6105 Rev 2, NASA-HDBK-1009A, NASA-HDBK-1004); внешние дидактические материалы не используются;
7. Контур ИИ — двухканальный (промпт-пакеты + API для структурных операций); ручное перебивание данных исключается;
8. Формальные методы: Agda — не применяется (стоимость/польза неприемлемы для инженерного контура); допускается точечный эксперимент Alloy/TLA+ на модели трассировки и статусной модели на этапе архитектуры.

### 7.1. Решения по итогам рецензирования модельных документов

| № | Решение | Основание / следствие | Источник |
| --- | --- | --- | --- |
| Р1 | Архитектура ПН — только **regenerative**; bent-pipe не рассматривается | Требуется бортовое понимание протокола (S&F, приоритеты буфера, маяк, ACK); раздельные бюджеты участков. Следствие: протокольная нейтральность борта теряется — смена протокола = модификация бортового ПО | КА, п. 10 |
| Р2 | Диапазон платформ — **12U–100 кг**, вне диапазона конфигурации недопустимы | Согласовано с классом миссии; упрощает прокси-стоимости (попутное выведение) | КА, п. 8 |
| Р3 | ISL — **только РЧ**, оптика вне рамок | Нереалистична в классе 12U–100 кг; из модели уходят точность взаимного наведения и время установления | КА, п. 10 |
| Р4 | Режимы КА по карте спроса — **статические географические маски** + заглушка планировщика | Динамическое планирование — вторая очередь без пересмотра модели | КА, п. 5, 10 |
| Р5 | Терминалы **обязаны знать эфемериды**; КА ведёт широковещательный маяк альманаха | Слепая передача — деградированный режим. Следствия: нисходящая линия нагружена маяком везде, где есть датчики; возраст альманаха связывает качество сервиса с частотой пролётов | Потребители, п. 2.1 |
| Р6 | **Эфемеридный backoff** для класса B' | Смягчает лавину повторов; обменивает надёжность на хвост задержки; связывает качество B' с числом КА в плоскости | Потребители, п. 2.2 |
| Р7 | Подвижность — **«статика + маршруты»**; роуминг регуляторных зон вне MVP | Трансграничные маршруты остаются, регион считается одним на трек | Потребители, п. 8 |
| Р8 | Карта спроса — **трёхслойная**: население (100×100 км) → единичные объекты → сценарная библиотека | Закрывает вопрос источника карты; автоматически штрафует ССО-построения по весу спроса | Потребители, п. 3.1 |
| Р9 | Сервисы несут **QoS-профиль по видам потребителей**; MOP порождаются попарно «сервис × вид» | Гранулярность связи «сервис → требование» | Потребители, п. 1 |
