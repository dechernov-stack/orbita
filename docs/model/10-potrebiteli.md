# МОДЕЛИРОВАНИЕ ПОТРЕБИТЕЛЕЙ (КЛИЕНТОВ)

*Детализация модуля 5.6 Концепции ИС (v0.2). Версия 0.1 — проект для обсуждения.*

---

## 1. Назначение и место в ИС

Модуль описывает **потребителей сервисов КС** (абонентские терминалы IoT) в модельном виде и порождает три ключевых входа для остальной системы:

| Выход модуля | Потребитель | Использование |
| --- | --- | --- |
| Карта спроса | Баллистический модуль (5.2.А) | Спрос-взвешенная оценка качества построений |
| Профили трафика | Модуль потоков (5.7) | Пуассоновские потоки, Монте-Карло |
| Целевые показатели по классам (MOE) | Каталог сервисов (Ш2) — QoS-профили по отдельным видам потребителей; требования (Ш3) | Источник измеримых требований к КС; каждый сервис несёт свой QoS-профиль по видам потребителей (A'/B'/C') |

Принцип: потребитель в ИС — не устройство, а **модельный объект** с минимальным набором параметров, влияющих на связь, трафик и качество сервиса. Все, что не влияет на эти три вещи, в модель не входит.

## 2. Классы терминалов

### 2.0. Общие атрибуты терминала (все классы)

| Атрибут | Содержание | Пример (LoRaWAN) |
| --- | --- | --- |
| ID, класс | Идентификатор; A' / B' / C' | — |
| Протокольный профиль | Ссылка на адаптер протокола (5.5) и его настройки | Класс LoRaWAN A/B/C, диапазон SF |
| Радиопараметры | ЭИИМ; усиление/ДН антенны; чувствительность приёма | ЭИИМ ≤ 14 дБм (EU868) |
| Энергетика | Батарея / harvesting; лимит энергии на сутки; допустимый duty cycle | 1% duty cycle EU868 |
| Регуляторный регион | Частотный план, ограничения мощности и занятости канала | EU868 / US915 / RU864 |
| Размещение | Статичный / подвижный; модель подвижности (п. 3.2) | — |
| Среда | Открытое небо / затенение / indoor (доп. затухание, дБ) | +10…20 дБ indoor |

### 2.1. Класс A' — «тупой датчик» (односторонняя передача)

Передаёт без подтверждения; о судьбе пакета не знает.

| Атрибут | Содержание |
| --- | --- |
| Модель генерации | Периодическая / пуассоновская / событийная; интенсивность (сообщ./сутки) |
| Размер пакета | Байт полезной нагрузки (+ оверхед протокола из адаптера) |
| Допустимые потери | Целевая вероятность доставки (например, ≥ 0,9 за сутки с учётом повторов «вслепую»); считается при передаче по расписанию пролётов — знание эфемерид обязательно (см. ниже) |
| Политика повторов вслепую | Число слепых повторов одного сообщения (без ACK) |
| Свежесть данных | Допустимый возраст информации (Age of Information) у потребителя данных |

Ключевое модельное решение (по итогам рецензирования): терминалы класса A' **обязаны знать эфемериды** — передача «вслепую» вне зоны видимости КА не допускается как штатный режим (пустые передачи убивают энергетику терминала и засоряют канал). Следствие на стороне КС: **аппараты регулярно сбрасывают эфемериды/альманах широковещательным маяком** по абонентской нисходящей линии. Односторонность класса A' сохраняется в части данных: приём — только маяк, без ACK. Дополнительные атрибуты терминала: допустимый возраст альманаха; периодичность приёма маяка; поведение при устаревшем альманахе (деградация в слепой режим с пониженной интенсивностью — учитывается в модели как отказовое состояние, а не как штатное).

### 2.2. Класс B' — датчик с подтверждением

| Атрибут | Содержание |
| --- | --- |
| Модель генерации, размер пакета | Как у A' |
| Политика подтверждений | ACK на каждое сообщение / на пачку; окно ожидания ACK |
| Политика повторов | Максимум попыток N; стратегия backoff (случайная задержка, смена SF/канала); **эфемеридный backoff**: после N неудачных попыток на текущем КА — прекращение попыток и ожидание следующего аппарата по известному расписанию пролётов |
| Целевая надёжность | P(доставка за ≤ N попыток) — например ≥ 0,99 |
| Допустимая задержка доставки | От генерации до подтверждённой доставки (минуты — часы) |
| Буферизация | Глубина буфера при недоступности сервиса; политика вытеснения |

Важно для модели потоков: повторы — это **обратная связь нагрузки** (offered load > carried load): при деградации канала трафик B' растёт лавинообразно. Монте-Карло обязан это воспроизводить — это типовой механизм коллапса ёмкости.

### 2.3. Класс C' — терминал оперативного управления

Двусторонний контур: событие на объекте → решение внешней системы → команда на объект.

| Атрибут | Содержание |
| --- | --- |
| Модель событий | Интенсивность нештатных событий; кластеризация (события коррелированы — шторм, авария сети) |
| Время реакции T_треб | Требуемое время «событие → команда исполнена», сек/мин |
| Время решения внешней системы t_реш | **Параметр внешней системы (вводится пользователем)** — ИС его не моделирует, но учитывает в бюджете |
| Требование к нисходящему каналу | Размер команды; подтверждение исполнения |
| Готовность | Доля времени, когда контур управления доступен |
| Приоритет | Вытеснение трафика A'/B' при передаче C' (да/нет) |

**Бюджет времени реакции** (декомпозиция — считается ИС по компонентам):

T = t_обнаружения (на объекте) + t_ожидания восходящего канала (ближайший КА в видимости или пролёт) + t_транзита вверх (S&F / ISL → НС) + **t_реш (внешняя система)** + t_ожидания нисходящего канала + t_транзита вниз + t_доставки команды + t_исполнения.

Итоговый показатель: **P(T ≤ T_треб)** — распределение T строится Монте-Карло по геометрии группировки, режиму доставки (5.3) и очередям (5.7). Именно этот показатель решает вопрос «нужен ли ISL».

Пример (из постановки): зафиксирован уход объекта с маршрута → требуется команда коррекции за T_треб. При store-and-forward t_ожидания может составлять десятки минут — контур C' не закрывается; с ISL — закрывается. Модель обязана показывать это число, а не мнение.

## 3. Популяции и карта спроса

### 3.1. Популяция

Потребители задаются не поштучно, а **популяциями**:

| Атрибут | Содержание |
| --- | --- |
| Класс терминала | Ссылка на профиль (п. 2) |
| География | Полигон / сетка / набор точек / маршруты |
| Численность и плотность | Количество терминалов; распределение по территории |
| Профиль активности | Суточный и сезонный профиль генерации (множитель к интенсивности) |
| Модель подвижности | Статика / маршруты (треки транспорта, судов) / случайное блуждание в области; роуминг регуляторных зон — за рамками первой очереди (решение п. 8) |
| Рост | Прогноз численности по годам (для оценки ёмкости на горизонте) |

**Нулевое приближение популяций** (по итогам рецензирования): для старта спрос строится от плотности населения — численность людей в ячейке ~100×100 км × сценарный коэффициент «терминалов на жителя». Это грубо, но сразу даёт содержательную карту спроса для первых trade studies, а открытые данные населения на сетке общедоступны. Поверх населённой основы добавляются **единичные объекты и маршруты**, не коррелирующие с населением, — Северный морской путь, промышленные и инфраструктурные объекты Якутии и подобные: их вклад в суммарный трафик мал и общей картины не искажает, но именно они удерживают ненулевой вес стратегических малонаселённых районов в оценке качества построения.

### 3.2. Карта спроса

Агрегат всех популяций на дискретной сетке (равноплощадная сетка; кандидат — H3 или широтно-скорректированная равноугольная; первое приближение — ячейка ~100×100 км):

- на ячейку: ожидаемая интенсивность сообщений по классам (вверх/вниз), численность терминалов, вес ячейки;
- карта — **вход баллистического модуля**: интеграл качества считается по ячейкам с весами спроса;
- карта — **вход модуля потоков**: интенсивности ячеек порождают пуассоновские потоки;
- временные срезы: карта × суточный/сезонный профиль (спрос ночью ≠ днём — важно вместе с энергетикой витка).

### 3.3. Источник карты для первой очереди — библиотека сценариев

Предустановленные референсные сценарии (редактируемые), из которых собирается карта:

| Сценарий | Класс | География | Характерные параметры |
| --- | --- | --- | --- |
| Агромониторинг | A' | Сельхозрайоны 30–55° с.ш. | 1–4 сообщ./сутки, 20–50 байт, статика |
| Учёт ресурсов (метеринг) | A'/B' | Населённые районы | 1–24 сообщ./сутки, indoor-затухание |
| Мониторинг трубопроводов | B' | Линейные объекты, в т.ч. > 55° с.ш. | Высокая надёжность, события редкие |
| Трекинг транспорта/контейнеров | B'/C' | Маршруты (авто, ж/д, море) | Подвижность, роуминг регуляторных зон |
| Морские суда / рыболовство | C' | Акватории | Контур управления, T_треб — минуты |
| Экомониторинг / дикая природа | A' | Малонаселённые области | Энергодефицит, harvesting |

Смысл библиотеки: «идеальный сервис у полюсов» автоматически получит близкий к нулю вес — спрос сосредоточен в средних широтах и на маршрутах; при этом трубопроводы и морские сценарии удержат честный вес северных широт.

## 4. Модель трафика (интерфейс к модулю потоков)

1. Базовый поток терминала — пуассоновский с интенсивностью из профиля; суперпозиция по ячейке — пуассоновский поток ячейки (это и делает Монте-Карло быстрым);
2. Событийный трафик (C', частично B') — модулированный Пуассон (MMPP): фоновая интенсивность × всплески по событийной модели; **корреляция событий** внутри ячейки/региона задаётся явно (шторм будит тысячи датчиков одновременно — худший случай для ёмкости и для контура C');
3. Повторы B' — генерируются моделью, не входят в исходную интенсивность (offered vs carried load);
4. Канальный уровень (коллизии, SF, duty cycle, capture) — из адаптера протокола (5.5), калиброванного по референсным симуляторам.

## 5. Метрики по классам (MOE модуля)

| Класс | Основная метрика | Дополнительные |
| --- | --- | --- |
| A' | P(доставка за сутки) | Возраст информации (медиана/квантиль); энергия на доставленное сообщение |
| B' | P(доставка ≤ N попыток) | Распределение задержки; среднее число попыток; энергия на доставленное сообщение |
| C' | P(T ≤ T_треб) | Готовность контура; худший разрыв доступности; распределение T по компонентам бюджета |

Агрегация: спрос-взвешенное качество по ячейке → региону → широтному поясу → интеграл варианта построения (вход розы ветров и Парето-фронта из 5.2).

## 6. Потребители в мастере и контуре ИИ

- **Ш1 → Ш2:** классы потребителей и целевые MOE выводятся из нужд (промпт-пакет: описание нужд → предлагаемые популяции с параметрами по схеме JSON → правка инженера → загрузка);
- **Ш3:** MOE классов порождают системные требования (пример: «P(T ≤ 120 с) ≥ 0,95 для класса C' в акватории X» → требования к ISL/НС);
- **Ш5:** популяции подключаются к сценариям; карта спроса пересчитывается автоматически при правке популяций;
- промпт-пакет «сценарная библиотека»: описание бизнес-кейса заказчика → черновик популяции со всеми атрибутами п. 3.1.

## 7. Интерфейсы модуля

| Направление | Контрагент | Данные |
| --- | --- | --- |
| → | Баллистический модуль | Карта спроса (ячейки, веса, временные срезы) |
| → | Модуль потоков | Интенсивности по ячейкам и классам; событийные модели; политики повторов |
| → | Требования (Ш3) | Целевые MOE классов |

| ← | Модуль КА | Параметры широковещательного маяка эфемерид (периодичность, покрытие) |

## 8. Решения и открытые вопросы

**Решено (рецензирование):** модели подвижности первой очереди — «статика + маршруты», этого достаточно; роуминг регуляторных зон (пересечение терминалом EU868 → RU864) — за рамками MVP.

Открытые вопросы:

1. Приоритезация C' над A'/B' в канале: моделируем в первой очереди или фиксируем как допущение;
2. Формат сетки карты спроса (H3 vs равноплощадная широтная) — решить вместе с производительностью Монте-Карло;
3. Широковещательный маяк эфемерид: формат (полный альманах группировки vs упрощённое расписание пролётов), периодичность сброса, допустимый возраст альманаха до перехода терминала в деградированный режим — согласовать нагрузку на нисходящую линию с документом «Моделирование КА». **Референс — Lacuna Space (штатная практика):** спутники широковещательно передают времена пролётов, терминал просыпается только к пролёту (система LoneWhisper, узловое ПО LWiN, физуровень LR-FHSS); их патентный подход (US 10,877,158) — терминалу передаётся компактная динамическая модель орбиты, по которой он сам генерирует синтетические элементы и считает пролёты стандартным пропагатором (SGP4) на длинном горизонте. Следствие для нашей модели: маяк может нести не расписание, а модель орбиты — тогда частота маяка снижается, допустимый возраст альманаха растёт, а цена — вычисления на терминале;
4. Состав референсной библиотеки сценариев — подтвердить/дополнить перечень п. 3.3 под реальные бизнес-кейсы проекта.
